Справочники: ответы сайта и Mobile API, реестры кодов ошибок, словарь полей | **Самый надёжный.** Основан на регламентах wiki, сверен с кодом, обкатан на задачах 1126–2343 с выводами QA |

## 3. Уникальное содержание, которое можно потерять

### 3.1. `backend-task` — сохранить полностью

- §2: проверка цепочки МП → Gate → монолит, таблица выбора, что дорабатывать, правило «дорабатывается только новый гейт».
- §3: правила блоков:
  - «Логика» — AS-IS, внутренние переменные, «новая логика внутри существующей», ограничения;
  - «Маппинг API → БД»;
  - «Совместимость с МП» с классификатором изменений;
  - «Тестирование», «Открытые вопросы».
- §4, п. 6–10: зависимость от настроек админки, маппинг, прозрачный Gate, текст ошибки для МП, старые версии МП.
- §5: связь с бандлом требований и именование файлов.
- Чек-листы Mobile API и Gate.
- Уроки QA в примерах («Что всплыло на тесте»). Это источник правил §4, без них непонятно, откуда правила взялись.

### 3.2. Справочники `backend-task/references` — сохранить целиком

- Реестр кодов Mobile API с HTTP-статусами и реестр предметных кодов возврата, включая коды без статуса в маппинге (они дают 500).
- Разбор спорных случаев: 403 или 404 для чужого ресурса, массовое обновление «0 записей = 200».
- Заголовки МП (`x-platform`, `x-version`, `x-session-token`) и конверт `success` / `result`.
- Словарь полей.

### 3.3. `web-endpoint` — уникальное

- Анализ восьми групп новых эндпоинтов и найденные отклонения:
  - ошибки корзины с HTTP 200;
  - гео-методы без общего конверта;
  - в `change-payment-method` нет проверки владельца заказа;
  - в swagger у гео-методов параметры отмечены обязательными, хотя в коде у них есть значения по умолчанию.
- Правила пути, метода (включая «201 в монолите не используется»), авторизации, капчи и ограничения частоты.
- Правила заполнения полей swagger (§3.2) и порядок доописания существующих методов с таблицей «на согласование» (§3.3).
- Пример swagger и шаблон задачи на новый метод.

### 3.4. `openapi-spec` — уникальное и применимое к любому сервису

- Схемы именуются в PascalCase, пути — в kebab-case.
- `summary` короче 50 символов.
- Обязательные элементы операции.
- Примеры хороших и плохих описаний («❌ Получает данные» / «✅ Возвращает список с пагинацией»).
- Проверка соответствия ERD и Use Case.
- Инструменты: Spectral, Swagger Editor.

## 5. Не станет ли документация беднее

Беднее она станет только при трёх ошибках, и их можно избежать:

1. **Если заменить правила в `backend-task` ссылками без уроков QA.** Пропадёт контекст «почему так». Правило должно жить в `openapi-spec`, а `backend-task` — давать ссылку и напоминать, на какой задаче это всплыло (`1126: enum без поведения при невалидном значении → 500`).
2. **Если заменить общий `openapi-spec` правилами сайта.** Пропадут принципы для ESB и Go-гейта, а там swagger генерируется из кода:
   - в `mobile-monorepo-go` — swagger 2.0, генерируется из аннотаций `swag`;
   - в ESB — из декораторов `@nestjs/swagger`.
3. **Если перенести `web-endpoint` как стандарт.** Несогласованные предложения превратятся в обязательные правила. Нужна явная пометка статуса у каждого правила (раздел 6).

**Пробел, которого сейчас нет ни в одном скилле:** правила swagger для `docs/openapi/mobile.yml` (Mobile API монолита, тоже версии 3.1.0). При объединении его стоит отметить как отдельный раздел.

## 6. Противоречия: AS-IS и TO-BE

Предлагаемые статусы правил в объединённом документе:

| Статус | Значение |
|---|---|
| **Согласовано** | Регламент wiki или памятка аналитика |
| **Предложение** | Нужно согласовать |
| **AS-IS-исключение** | Так работает сейчас, в новых методах не повторяем |

### 6.1. 400 или 422

Решение пока не принимаем — ниже контекст использования.

| Где | Что на практике (AS-IS) | Источник |
|---|---|---|
| Сайт, сервис ответа: `Auth`, корзина / подписка | **422** + `20279` + `errors[]` для ошибок полей | `FrontendApiBaseController`, `ResponseErrorCode::getStatusCode()` |
| Вебхуки 1С и доставки; отзывы офлайн (`modules/feedback`, `mobilev2/Feedback`) | **422** | `OneC/WebhooksController`, `Delivery/WebhooksController`, `FeedbackOfflineController` |
| Сайт: предметные коды гео, формы возврата, доставки, `40000` | **400** | `getStatusCode()` |
| Сайт: `return-details`, `return-method-list` | **200** с `code: 40000` в теле | ответ в контроллере |
| Сайт: часть ошибок корзины | **200** | `getStatusCode()`: `CART_IS_EMPTY` и другие |
| Mobile API монолита | **400** (`1015`), в коде комментарий `TODO: Как будто должно возвращать 422 статус` | `Mobile/BaseController` |

Что сказано в документах (TO-BE):

- `api-errors_memo.md` (согласовано): «400 — универсальный статус валидации в проекте, 422 — тема для ретро»;
- `web-endpoint` (предложение): 422 для полей, 400 для сломанного запроса.

**Итог.** Явного противоречия с реализацией нет, на практике действуют два режима:

- 422 — в новых контроллерах сайта и вебхуках;
- 400 — в Mobile API и старых методах сайта.

Решить нужно одно: распространять ли 422 на новые методы сайта и Mobile API. До решения в документ попадают оба режима с указанием, где какой.

### 6.2. Версия OpenAPI

| Проект | Факт (AS-IS) |
|---|---|
| Монолит, `frontend.yml` и `mobile.yml` | Заявлена 3.1.0, но местами синтаксис 3.0 (`nullable: true`, `required` внутри свойства) |
| Go-гейт `mobile-monorepo-go` | Swagger 2.0, генерируется из аннотаций в коде (`docs/mobile_api/swagger.yaml`) |
| ESB | Генерируется из декораторов NestJS |
| `openapi-spec` (TO-BE, общий) | 3.0.3 как минимальная структура |

Общие правила `openapi-spec` (описание, пример, обязательность, именование, примеры хороших и плохих описаний) применимы ко всем трём проектам. Различается синтаксис, и в Go и ESB swagger описывается аннотациями в коде, а не правкой YAML.

**Предложение:**

- общие принципы оставить для всех сервисов;
- для каждого проекта вынести особенности: версию, где описывается swagger (YAML или код), как задаётся nullable.

### 6.4. Другие противоречия

| Противоречие | Тип | Как разрешить |
|---|---|---|
| `openapi-spec`: POST → 201, DELETE → 204; в монолите 201 нигде не используется, удаление отдаёт 200 | Общий TO-BE против AS-IS проекта | 201 / 204 — общий принцип, для монолита указать 200 |
| `openapi-spec`: код ошибки — число; на сайте `code` — строка, в Mobile `error_code` — число | Общий TO-BE против AS-IS | Описывать по ответу конкретного проекта |
| `openapi-spec`: пагинация через `page`; в проекте `limit` / `offset` | Общий TO-BE против AS-IS | Для проекта — `limit` / `offset` |
| `api-errors_memo` §3.2 рекомендует 404 для чужого ресурса, а образец в §4 той же памятки даёт 403 для `notifications/read` | Противоречие внутри согласованного документа | В §4 описано текущее поведение (AS-IS). Отметить это и уточнить у автора памятки |
| `/api/v1` для нового раздела | Предложение `web-endpoint`, в реализации смешано | Согласовать с бэком |
| Список — `data.items` | Согласовано (регламент), AS-IS-исключение — уведомления | Сохранить как стандарт с исключением |
| Неполные таблицы тегов | TO-BE, обе неполные | Объединить |

## 7. Варианты структуры

### Вариант А (предварительно выбран): две папки с чёткими ролями

- **`openapi-spec` — как правильно описать API.** Все правила контракта (путь, метод, ответ, ошибки, имена полей) и правила оформления swagger.
- **`backend-task` — что написать в задаче.** Структура задачи, шаблоны и примеры задач. Правила контракта задача не пересказывает, а ссылается на раздел `openapi-spec`.
- **`web-endpoint` расформировывается**, содержимое раскладывается по двум папкам выше.
- **`mobile-endpoint`** — так же: правила контракта и swagger (`mobile.yml`, аннотации гейта) → `openapi-spec`, шаблоны задач `[B][Mobile API]` и `[B][Mobile API][Gate]` → `backend-task/templates`.

```
openapi-spec/
├── SKILL.md            как писать контракт и swagger: общие принципы, особенности проектов, доописание, чек-лист
├── references/
│   ├── web.md          ответ сайта (request-response_web.md + web-endpoint §1–2)
│   ├── mobile-api.md   ответ Mobile API (request-response_mobile-api.md)
│   ├── errors.md       коды и HTTP-статусы (api-errors_memo.md + web-endpoint 2.6)
│   └── field-glossary.md
└── examples/
    └── web-new-endpoint.yml   (web-endpoint/swagger-example.yml)

backend-task/
├── SKILL.md            структура задачи: теги, декомпозиция, цепочка МП → Gate, блоки, чек-лист задачи
├── templates/
│   ├── full.md               (template.md)
│   ├── simple.md             (template-simple.md)
│   └── new-web-endpoint.md   (web-endpoint/template.md)
└── examples/           ECOMDEV-*.md без изменений
```

### Вариант Б: три папки, у каждого типа задачи своя

# Часть 2. Полный сравнительный анализ (28.10.2026)

Ниже анализ всех скиллов про эндпоинты: `backend-task` со справочниками, шаблонами и примерами, `openapi-spec`, `web-endpoint` и `mobile-endpoint`. Сверил их между собой, с `AGENTS.md`, базой знаний `knowledge\` и настройками агентов.

Анализ выявил три вещи, которые меняют рекомендацию:

1. **`web-endpoint` и `mobile-endpoint` не подключены к агенту.** Их нет ни в `opencode.json` (там запрещено всё, кроме перечисленных скиллов), ни в таблице скиллов роли в `.claude/agents/system-analyst.md` и `.opencode/agents/system-analyst.md`. Сейчас агент системного аналитика их не вызывает. `backend-task` и `openapi-spec` подключены.
2. **У `openapi-spec` по `AGENTS.md` есть вторая обязанность, о которой сам скилл ничего не говорит:**
   - разбор действующих API в `knowledge/<репозиторий>/api/{web,mobile}/`;
   - разбор API отдельного процесса в `as-is/api/`;
   - целевые контракты `requirements/*_openapi.yaml`.

   Формат таких разборов нигде не описан. Например, `order-view_web.md` с разделами «Название метода», «Используемые методы», «Диаграмма» оформлен без правил.
3. **Для описания текущего поведения системы (AS-IS) уже есть отведённое место — база знаний.** Это `knowledge/12storeez-master-web/architecture/05-api.md` (маршрутизация, авторизация, обёртки ответа, валидация, покрытие swagger в CI) и `knowledge/mobile-monorepo-go/`. Анализ в разделах 1 `web-endpoint` и `mobile-endpoint` частично повторяет её. В самой базе есть неточность: ответ Mobile API с ошибкой показан без `success: false`.

- **Факты AS-IS живут в базе знаний.** В скиллах остаются только исключения, которые меняют применение правила (например, «новый метод в контроллере с ответом в контроллере делается как соседние»).

`openapi-spec` (общий стандарт и swagger) + `web-endpoint` + `mobile-endpoint` (стандарты каналов) + `backend-task`. Минусы:
- нужно регистрировать два скилла;
- правила ошибок общие для двух каналов (предметные коды едины), и их придётся либо дублировать, либо разносить ссылками между скиллами;
- шаблоны задач окажутся в трёх папках.
