### Новый эндпоинт мобильного приложения: контракт и swagger

**Назначение.** Скилл задаёт стандарт контракта **нового** эндпоинта МП на двух уровнях — гейт `mobile-monorepo-go`
(`mobile.12stz.*`) и монолит `12storeez-master-web` (`/mobile/...`) — и правила swagger для обоих. Формат задачи в Трекере,
логика, маппинг и проверка цепочки МП → гейт → монолит описываются по `skill/tracker-task` (§2 — цепочка, §3 — блоки,
«Совместимость с МП»); этот скилл их не повторяет, а уточняет контракт и добавляет блок «Swagger».
Парный скилл для сайта — [web-endpoint](../web-endpoint/SKILL.md).

**Статусы правил:** **Согласовано** — регламент wiki или памятка; **AS-IS** — так работает сейчас; **Предложение** — нужно согласовать.

#### 1. Анализ: новые эндпоинты МП

Сверено с кодом `12storeez-master-web` и `mobile-monorepo-go` 28.10.2026.

- **Монолит:** коммиты в `src/Modules/Mobile`, `src/Modules/MobileV2` и маршруты `config/url.php` с 01.2026. Историю `docs/openapi/mobile.yml` не восстановить — файл пересобран целиком 16.09.2026 (ECOMDEV-329).
- **Гейт:** коммиты `mobile-monorepo-go` с 04.2026 с новыми маршрутами в `cmd/mobile_api/mobile_api.go`.
- **Глубина:** «код» — прочитан контроллер / сервис гейта; «swagger» — только спецификация.

##### 1.1. Что делает каждый уровень (AS-IS)

| Что | Гейт (`mobile-monorepo-go`) | Монолит (`/mobile/...`) |
|---|---|---|
| Пути | `/api/v1/...`, `/api/v2/...` | `/mobile/...`, `/mobile/v1/...`, `/mobile/v2/...` — смешаны |
| Авторизация | JWT `Authorization: Bearer` для всех методов, кроме групп `/auth` и `/errors` | Сессия `x-session-token` + ключ `x-access-token`; обязательность — правило `isAuthRequired` у метода |
| Передача запроса в монолит | `ProxyToSite`: `session_token` из JWT → `x-session-token`; `x-access-token` из конфига; пробрасывает `x-platform`, `x-version`, `Cookie`, тело. Query — **только если `isCrutch = false`** | — |
| Обязательные заголовки | `X-Platform`, `X-Version`; без них 400 `{"error": {"message": "missing X-Platform header"}}` | `x-platform`, `x-version`; язык — `X-Language` |
| Проверка запроса | В прокси — только разбор path / body; ECOMDEV-2034 убрал проверку JSON-тела для `/api/v2/cart` | `requestRules` в `beforeAction`: `isAuthRequired`, `fieldRules` (тип, длина, диапазон, своя функция), `methods`, `headers`; валидаторы через исключение |
| Успех | Прокси — ответ монолита как есть; свои методы — `{"success": true, "result": ...}` | `{"success": true, "result": ..., "total": ...}` |
| Ошибка | Три формата: прокси — ответ монолита + `"isErrorFromPHP": true` при статусе ≠ 200; свои ошибки — `{"error": {"message", "details"}}`; `FailureResponse` — `{"success": false, "result": {"error_code", "error_text"}}` | `{"success": false, "result": {"error_code", "error_text", "error_data"}}`; HTTP — по `error_code` в `getError()` |
| Ошибки полей | — | `1015`, HTTP **400**, `error_text: "Ошибка валидации данных"`, `error_data[]` с `target` / `code` / `message`; в коде `TODO: Как будто должно возвращать 422 статус` |

- HTTP по коду: 404 — `1009`, `1013`; 500 — `1016`, `1026`; 401 — `1001`, `1002`, `1007`; 405 — `1000`; 406 — `1012`, `1014`, `1018`, `1020`, `1021`; 403 — `1017`, `1023`; остальные — 400.
- Для кодов `1001`, `1002`, `1011`, `1017`, `4001`, `4002`, `1026`, `1027` текст подменяется фиксированным — текст, переданный методом, до клиента не дойдёт.
- `ApiBaseController` (новый чекаут, ECOMDEV-772 / 987) — копия `BaseController` с тем же маппингом.

#### 2. Правила контракта

##### 2.1. Пара путей и версия

1. **Согласовано.** У метода МП всегда пара: `Gate: <МЕТОД> /api/v1/...` → `Site: <МЕТОД> /mobile/...` (`tracker-task` §2, шаг 3).
2. **Предложение.** Путь гейта повторяет ресурс монолита: `/mobile/orders/{order_id}/<подресурс>` → `/api/v1/orders/{order_id}/<подресурс>`. Одна группа маршрутов гейта — один ресурс.
3. **Предложение.** Новый метод монолита — `/mobile/<ресурс>` без версии. Ресурс — существительное во множественном числе, kebab-case; path-параметр — snake_case с суффиксом `_id`.
4. **AS-IS / Согласовано.** Версия `v2` появляется, только когда меняется контракт существующего метода и старые версии МП должны продолжить работать на `v1` (`PUT /mobile/v2/cart`). Решение — в блоке «Совместимость с МП» задачи.
5. Действие, которое не ложится на CRUD, — глагол kebab-case последним сегментом (`/subscription/check`).

##### 2.2. HTTP-метод

| Действие | Метод | Тело | Успех |
|---|---|---|---|
| Получить список / объект | `GET` | нет, фильтры — плоские query | 200 |
| Создать | `POST` (AS-IS встречается `PUT`: `user-address`, `v2/cart`) | JSON | 200, `result` — созданный объект |
| Частично изменить | `PATCH` | JSON | 200 |
| Удалить | `DELETE` | нет | 200, `result` — `[]` |
| Действие | `POST` | JSON | 200 |

Новый метод — по таблице; `PUT` для создания в новых методах не используется (**Предложение**). Метод ограничивается правилом `methods` в `requestRules` или `VerbFilter`; чужой метод → `1000` / 405.

##### 2.3. Авторизация и доступ

1. **AS-IS.** Гейт: все методы под JWT, кроме групп `/auth` и `/errors`. Открытый метод гейта ставится в эти группы или явно до `jwtMiddleware` — указать в задаче на гейт.
2. **AS-IS.** Монолит: закрытый метод — `isAuthRequired = true`; без сессии → `1002` / 401. Повторно проверять пользователя в методе и отдавать `1015` не нужно.
3. **Согласовано.** Ресурс ищется по id **и** текущему пользователю.
4. **Предложение.** Ресурс не найден или чужой → код «не найдено» с HTTP 404 (сейчас `1019` / 400 у возврата). Код согласовать — `1009` по смыслу «Недоступно».
5. Открытый метод с SMS / email / перебором — ограничение частоты. **AS-IS:** в гейте отключено — лимиты указывать в задаче и отмечать открытым вопросом.

##### 2.4. Заголовки

| Заголовок | Кто передаёт | В задаче |
|---|---|---|
| `Authorization: Bearer <JWT>` | МП → гейт | не описывается (общий) |
| `X-Platform` (`ios` / `android`), `X-Version` | МП → гейт → монолит; обязательны | не описывается (общий) |
| `x-session-token`, `x-access-token` | гейт → монолит | не описывается (общий) |
| `X-Language`, `Cookie`, `X-Device-Id` | МП → гейт → монолит | только если метод их использует |

В задаче — только заголовки, специфичные для метода.

##### 2.5. Запрос

1. Имена — snake_case по [словарю полей](../tracker-task/references/field-glossary.md); поле метода, который есть и на сайте, называется так же, как на сайте.
2. Query — плоские параметры. Пагинация — `limit` (по умолчанию 50, максимум 1000) / `offset` (максимум 100000) — `BaseController`.
3. Для каждого поля тела: тип, обязательность, формат, enum (все значения), nullable и когда `null`, предобработка.
4. **Предложение.** Если метод есть на сайте — проверки полей **одинаковые**, различается только формат ошибки (1.4).
5. **Согласовано.** Новый обязательный параметр в существующем методе — опасное изменение: значение по умолчанию для старых версий МП (`method_return = courier`) или `v2` (2.1, «Совместимость с МП»).

##### 2.6. Ответ

1. **Согласовано.** `{"success": true, "result": ..., "total": ...}` ([request-response_mobile-api.md](../tracker-task/references/request-response_mobile-api.md)).
2. `result` — объект; список — `result.items`, количество — `total`. **AS-IS:** встречается `result` — массив (`return-method-list`, бронирования); в новом методе — `result.items`.
3. Поля ответа: полный путь, тип, nullable и когда `null`, все значения enum; пример = таблица.
4. Значения для показа пользователю бэк отдаёт готовыми; тексты — с учётом `X-Language`.
5. Поля для одного метода на сайте и в МП — по таблице соответствия в `request-response_mobile-api.md`.

##### 2.7. Ошибки

| HTTP | `error_code` | `error_data[]` | Когда |
|---|---|---|---|
| 400 | `1015` | да: `target`, `code` (предметный код `ResponseErrorCode`, строка), `message` | Не пройдена проверка полей (AS-IS; 422 — открытый вопрос, `api-errors_memo.md` §3.1) |
| 401 | `1002` | нет | Нет / истекла сессия |
| 404 | согласовать (2.3) | нет | Ресурс не найден или чужой |
| 403 | `1017` | нет | Нет прав (если не маскируется под 404) |
| 405 | `1000` | нет | Не тот HTTP-метод |
| 406 | `1018`, `1020`, `1021`, … | по ситуации | Бизнес-ошибки корзины (AS-IS) |
| 500 | `1016` / `1026` | нет | Непредвиденная ошибка; в задаче не описывается |

1. **Согласовано.** Детальная структура (`error_data[]`) — для форм ввода, плоская — для остальных ([api-errors_memo.md](../tracker-task/references/api-errors_memo.md) §2).
2. Предметные коды полей общие с сайтом — новый код заводится один раз в `ResponseErrorCode` и используется в обоих каналах.
3. Для кодов с фиксированным текстом (1.1) свой текст ошибки не задаётся.
4. **Согласовано.** В задаче согласовать с МП, из какого поля строится текст для пользователя — `error_text` или `error_data[].message` (`tracker-task` §4, п. 9).
5. Новый `error_code` верхнего уровня не вводится без необходимости — список в `BaseController` общий для всех методов.

##### 2.8. Гейт

1. **Согласовано.** Прокси прозрачен: ответ гейта = ответ прямого запроса в монолит при тех же query, теле и заголовках (`tracker-task` §4, п. 8).
2. **Предложение.** Прокси передаёт query всегда (`isCrutch = false`). Если query не нужен — указать это в задаче на гейт явно.
3. **AS-IS.** При статусе ≠ 200 гейт добавляет к ответу монолита `"isErrorFromPHP": true` — учитывать в примерах ошибок гейта.
4. **Предложение.** Свои ошибки гейта (заголовки, разбор тела) — в формате монолита `{"success": false, "result": {"error_code", "error_text"}}` (`FailureResponse`), а не `{"error": {...}}`.
5. Логика в гейте — только по решению из `tracker-task` §2 (переезд из `core`); тогда она описывается в задаче на гейт полностью.
6. В задаче на гейт: путь гейта, путь монолита, группа маршрутов, нужен ли JWT, передаются ли query, ключ пути в конфиге (`cfg.Site.<...>Path`) — по образцу ECOMDEV-1241.

##### 2.9. Чего нет в задаче

Классы контроллеров, правила `requestRules` в коде, функции гейта (`ProxyToSite`, `isCrutch`), имена DTO — решение разработчика.
Задача фиксирует контракт: пара путей, метод, доступ, поля, ошибки, тексты, совместимость.

#### 3. Правила swagger

**Цель:** по открытому методу понятно, что передаётся, зачем, в каком формате и обязательно ли это — на обоих уровнях.
Swagger обновляется в задаче на тот уровень, где появился метод: `mobile.yml` — в задаче `[B][Mobile API]`, гейт — в задаче `[B][Mobile API][Gate]`.

##### 3.1. Монолит — `docs/openapi/mobile.yml` (OpenAPI 3.1.0)

1. **Пути — без `/mobile`:** `servers` уже заканчиваются на `/mobile`. Новый метод `/mobile/favourite-stores` описывается как `/favourite-stores`. **AS-IS:** в файле встречаются оба варианта — существующие пути не трогать, расхождение — в список на согласование (3.4).
2. **Версия 3.1:** nullable — `type: [string, "null"]`; `required` — списком у объекта; коды ответов в кавычках.
3. **Общие элементы:**
   - параметры `$ref: "#/components/parameters/x-version"`, `$ref: "#/components/parameters/x-platform"` — в каждом методе;
   - `security: - MobileApiKey: [ ]` + `SessionToken: [ ]` (не `Bearer` — он у гейта);
   - ошибки — `MobileErrorBadRequestVersionOneResponse` (400), `MobileErrorNotAuthVersionOneResponse` (401).
4. **AS-IS-ошибка общей схемы:** `MobileErrorVersionOneResponseSchema` описывает `error_code` / `error_text` / `error_data` на верхнем уровне, а в ответе они внутри `result` рядом с `success: false`. Для нового метода пример ошибки показывает фактическую структуру; исправление общей схемы — открытый вопрос (не менять без согласования).
5. **Тег** — из списка `tags` файла; `operationId` — camelCase, уникален в файле (в `mobile.yml` и `frontend.yml` бывают одинаковые — это допустимо, файлы разные).
6. **Без имён классов** в `description` (AS-IS: `"...ReservationOrderTransformer"`) — поля описываются схемой.

##### 3.2. Гейт — аннотации `swag` (swagger 2.0)

Swagger гейта генерируется из комментариев к функции сервиса и тегов DTO; файлы `docs/mobile_api/*` руками не правятся.

1. **Операция:** `@Summary`, `@Description` — первой строкой `Proxy to <МЕТОД> /mobile/...` (для прокси), второй — что делает метод **на русском**; `@Tags` — ресурс; `@Security Bearer` (кроме открытых методов); `@Router <путь> [<метод>]`.
2. **Заголовки** — в каждом методе: `X-Platform` (`Enums(android, ios)`), `X-Version` (`example(1.16.1)`); `Cookie` — только если монолит его использует, без выдуманного примера.
3. **Параметры** `@Param <имя> <path|query|header|body> <тип> <обязательность> "<описание>"` + `example(...)`, `Enums(...)`, `default(...)`, `minimum(...)` / `maximum(...)`.
4. **Ответы:** `@Success 200` и `@Failure` на **каждый** HTTP-статус, который может вернуть монолит или гейт (400, 401, 404, 500), а не только 500.
5. **DTO:** у каждого поля — тег `json`, `example:"..."`; обязательность — `binding:"required"` / `validate:"required"`; описание — комментарием к полю (попадает в `description`); enum — `enums:"a,b"`; nullable — указатель (`*string`) + `x-nullable` (`extensions:"x-nullable"`).
6. Имя DTO — `<Ресурс><Действие>Request` / `...Response` (как `CartSubscriptionCheckRequest`).

##### 3.3. Заполнение параметров и полей

Для **каждого** параметра запроса и **каждого** поля ответа, включая вложенные, на обоих уровнях:

| Атрибут | `mobile.yml` | Гейт (`swag`) | Как заполнять |
|---|---|---|---|
| `description` | `description` | текст в `@Param` / комментарий к полю DTO | На русском: смысл и назначение, не имя поля; для необязательного — поведение без него; для nullable — когда `null`; единицы измерения |
| `type` | `type` | тип в `@Param` / тип поля Go | `string` / `integer` / `number` / `boolean` / `array` / `object` |
| `format` | `format` | `format(...)` / тег `format:"..."` | Только если применимо: `date`, `date-time`, `uuid`, `email`, `int64` |
| `required` | `required` у параметра / список у объекта | `true` / `false` в `@Param`; `binding:"required"` | Для ответа — поле приходит всегда |
| `example` | `example` | `example(...)` / тег `example:"..."` | Реалистичное значение, без ПДн и токенов |
| `enum` | `enum` + расшифровка в `description` | `Enums(...)` / `enums:"..."` + расшифровка в описании | Все значения: `<значение> — <смысл>; …` |

Ограничения (`minimum`, `maximum`, `maxLength`, `pattern`, `default`) — если они есть в коде (`fieldRules`) или в задаче.

##### 3.4. Доописание существующих методов

Порядок тот же, что для сайта — [web-endpoint](../web-endpoint/SKILL.md) §3.3: изучить текущие описания и соглашения; сохранить
структуру и стиль; не дублировать и не трогать корректное; не менять контракт; не придумывать; несоответствия и неизвестное —
в таблицу на согласование (`Метод | Параметр / поле | Что в swagger | Что в коде / что неизвестно | Предложение | Кому`).
Для гейта доописание — правка аннотаций и DTO, а не сгенерированного YAML.
