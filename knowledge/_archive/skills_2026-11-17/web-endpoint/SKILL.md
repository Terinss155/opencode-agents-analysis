| Что | Где | Почему плохо |

| У параметров нет `description` или оно повторяет имя (`description: locale`, `description: limit`) | `/api/v1/delivery/geo/*`, `/api/cart/*` (`mode`) | Непонятно, что передавать и зачем |

| `in: form` у параметров тела | `POST /api/cart/user-info` | В OpenAPI 3 такого места нет; тело описывается через `requestBody` |
| `required: true` внутри `properties`, нет `requestBody.required` | `PATCH /api/cart/items`, `SaveOrderReturnDetailsRequest` | Обязательность не читается инструментами |
| Ответ 200 без схемы | `GET /api/user/me` | Непонятно, что возвращается |
| `Authorization` — параметром заголовка при `security: [ ]` | `GET /api/user/me`, `/api/auth/refresh`, `/api/auth/logout` | Авторизация описывается через `security` |

| Хорошо: `required` списком, `description` с правилами и кодами ошибок, пример ошибки | `POST /cart/subscription/check` | Образец |

**Что общее и берётся в стандарт** (эндпоинты 1–3, 6):

- конверт `status` / `message` / `data`; у ошибки — `status` / `message` / `code` / `errors[]`;
- HTTP-статус ошибки соответствует коду (`ResponseErrorCode::getStatusCode()`); заголовки `X-Response-*` проставляются автоматически;
- ошибки ввода — 422 с кодом `20279` и `errors[]`, где у каждой ошибки `target` (поле) и предметный код;
- один HTTP-метод на действие, чужой метод отклоняется;
- тексты `message` — через переводы `translations/<раздел>/…+intl-icu.{ru,en}.yaml`;
- в swagger: `tags`, `summary`, `operationId`, `security`, `requestBody` со списком `required`, ответы через `$ref` на общие схемы (`BaseSuccessResponse`, `BaseErrorResponse`, `ValidationErrorResponse`), пример ошибки с кодами.

**Что не повторяем** (расхождения между эндпоинтами):

| Расхождение | Где | Как в стандарте |
|---|---|---|
| Путь без `/api` | `/cart/subscription/check` | Всегда `/api/...` (раздел 2.1) |
| Версия в пути у одних, нет у других | `/api/v1/notifications` vs `/api/auth/...`, `/api/orders/...` | Новый раздел — `/api/v1/<раздел>`; метод в существующем разделе продолжает его путь |
| camelCase в теле | `orderId` в `read-all` | Только snake_case |
| Обязательное поле не передано → 400 без `errors[]` | `notifications/read` (`uuid`) | Поле тела → 422 / `20279` + `errors[]` с `target`; 400 / `40000` — только сломанный запрос (раздел 2.6) |
| Чужой ресурс → 403 | `notifications/read` | 404 / `40004` — не раскрываем существование чужих записей |
| Ошибка с HTTP 200 / тело исключения Yii | `return-details`, `change-payment-method`, ошибки корзины в `/api/cart/*` | Только сервис ответа: HTTP-статус по коду, единый конверт |
| Ответ без конверта `status` / `data` | `/api/v1/delivery/geo/*`, `pickup/*` | Конверт сервиса ответа и для методов-прокси |
| Лишнее поле `success` рядом со `status` | `return-details`, `/api/cart/*` | Только `status` |
| Нет проверки владельца ресурса | `change-payment-method` | Ресурс ищется по id и текущему пользователю |
| Список целиком в `data`, `total` на верхнем уровне | `GET /api/v1/notifications` | Список — `data.items`; пагинация — объект `pagination` (раздел 2.5) |
| Path-параметр `orderId` в swagger при `order_id` в маршруте; camelCase в пути | `components/parameters/orderId`; `{countryIso}`, `{providerId}`, `{geoId}` | Имя в swagger = имя в маршруте; в новых путях — snake_case |
| `required: true` внутри `properties`, `nullable: true` при `openapi: 3.1.0` | `SaveOrderReturnDetailsRequest`, `Notification` | Список `required` у объекта; `type: [string, "null"]` (раздел 3) |

Эндпоинты 4, 5, 7, 8 остаются как есть: новый метод **в их контроллерах** делается тем же способом, что и соседние
([request-response_web.md](../tracker-task/references/request-response_web.md)). Стандарт ниже — для нового контроллера или раздела.

#### 2. Правила контракта

##### 2.1. Путь

1. Префикс — `/api/`. Новый раздел API — `/api/v1/<раздел>` (как `/api/v1/notifications`, `/api/v1/delivery/...`). Новый метод в существующем разделе продолжает его путь (`/api/orders/{order_id}/...`).
2. Ресурс — существительное во множественном числе, kebab-case: `/api/v1/notifications`, `/api/v1/users/me/addresses`.
3. Вложенность — по владельцу: `/api/v1/orders/{order_id}/<подресурс>`. Текущий пользователь — `users/me`, id пользователя в путь не передаётся.
4. Path-параметр — snake_case с суффиксом `_id`, целое: `{order_id}`, `{address_id}`.
5. Действие, которое не ложится на CRUD, — глагол kebab-case последним сегментом: `/read`, `/read-all`, `/check`. Сначала проверить, нельзя ли выразить CRUD-ом.

##### 2.2. HTTP-метод

| Действие | Метод | Тело | Успех |
|---|---|---|---|
| Получить список / объект | `GET` | нет, фильтры — плоские query-параметры | 200 |
| Создать | `POST` | JSON | 200, созданный объект в `data` |
| Частично изменить | `PATCH` | JSON, только изменяемые поля | 200, объект в `data` |
| Удалить | `DELETE` | нет | 200, `data` — пустой массив `[]` (так сервис ответа отдаёт пустые данные) |
| Действие (`/read`, `/check`) | `POST` | JSON | 200 |

Одно действие — один метод. Сайт отвечает 200 и на создание: 201 в монолите не используется.

##### 2.3. Авторизация и доступ

1. Для каждого метода указывается: закрытый (нужна авторизация) или открытый.
2. Закрытый метод без авторизации → 401 / `40001`.
3. Ресурс пользователя ищется по id **и** текущему пользователю. Не найден или чужой → 404 / `40004`.
4. Открытый метод с отправкой SMS / email или перебором (вход, проверка кода) — капча и ограничение частоты: 400 капча не пройдена, 424 сервис капчи недоступен, 429 слишком частые запросы (как `/api/auth/*`). Лимиты (сколько попыток за какое время) указываются в задаче.

##### 2.4. Запрос

1. Имена — snake_case, по [словарю полей](../tracker-task/references/field-glossary.md).
2. Query — только плоские параметры; пагинация — `limit` / `offset` с допустимыми значениями и значениями по умолчанию.
3. Тело — JSON. Для каждого поля: тип, обязательность, формат (длина, регулярное правило, диапазон, enum — все значения), nullable и когда `null`.
4. Предобработка указывается явно: обрезка пробелов по краям (`email` в `cart/subscription/check`), удаление пробелов и дефисов из номеров.
5. Заголовки `X-Request-*` не описываются; блок «Заголовки» — только для специфичных для метода (`Authorization` у `refresh`).

##### 2.5. Ответ

1. Конверт успеха — `status: "success"`, `message`, `data` ([request-response_web.md](../tracker-task/references/request-response_web.md)).
2. `message` — текст для пользователя или пустая строка. Если текст есть — ru и en в задаче, ключ перевода выбирает разработчик.
3. `data` — объект. Список — `data.items`; при пагинации рядом объект `pagination: {limit, offset, total}`.
4. Поля ответа: полный путь, тип, nullable и когда `null`, все значения enum; пример совпадает с таблицей.
5. Значения для показа пользователю (признаки, суммы, даты, тексты) бэк отдаёт готовыми.

##### 2.6. Ошибки

| HTTP | Код (`code`) | `errors[]` | Когда |
|---|---|---|---|
| 422 | `20279` | да: `target` — поле, `code` — предметный код, `message` | Не пройдена проверка полей запроса (пусто, формат, enum) |
| 400 | `40000` | нет | Запрос не разобран: невалидный JSON, тип не тот (строка вместо числа), значение технического параметра вне справочника |
| 401 | `40001` | нет | Закрытый метод без авторизации |
| 404 | `40004` | нет | Ресурс не найден или принадлежит другому пользователю |
| 400 / 403 / 409 | предметный код | по ситуации | Бизнес-запрет действия (нельзя удалить адрес по умолчанию) — свой код и HTTP-статус |
| 500 | `50000` | нет | Непредвиденная ошибка; в задаче и swagger не описывается |

1. Для каждой проверки поля — предметный код: номер из свободного диапазона `ResponseErrorCode`, текст ru / en, HTTP-статус и требование добавить код в `getStatusCode()` ([api-errors_memo.md](../tracker-task/references/api-errors_memo.md), раздел 1.2). Образец — `20450` / `20451` в `cart/subscription/check`.
2. Если ошибок полей несколько — возвращаются все сразу, по одной записи на поле и правило.
3. Невалидное значение, `null` и отсутствие поля не приводят к 500.
4. Массовое действие по фильтру, под который ничего не попало, — не ошибка: 200 ([api-errors_memo.md](../tracker-task/references/api-errors_memo.md), раздел 3.3).

##### 2.7. Чего нет в задаче

Класс контроллера, маршрут в `config/url.php` или `UrlRule` модуля, имена валидаторов и сервисов — решение разработчика.
Задача фиксирует контракт: путь, метод, доступ, поля, ошибки, тексты.

#### 3. Правила swagger

Фрагмент добавляется в `12storeez-master-web/docs/openapi/frontend.yml` разработчиком в той же задаче. Аналитик прикладывает
фрагмент к задаче (блок «Swagger» шаблона), образец — [swagger-example.yml](./swagger-example.yml).

**Цель:** swagger самодостаточен — по открытому методу понятно, что передаётся, зачем, в каком формате и обязательно ли это, без чтения кода и задачи.

##### 3.1. Общие правила

1. **Версия.** Файл объявлен как `openapi: 3.1.0`: nullable — `type: [string, "null"]`, а не `nullable: true`; `required` — списком у объекта, не у свойства.
2. **Место.** Путь — в блоке `paths` рядом с путями того же тега; схемы — в `components/schemas`, ответы — в `components/responses`, общий path-параметр — в `components/parameters`.
3. **Тег** — из существующего списка `tags` (`Order`, `Cart`, `User`, `Notification`…). Новый тег — только с `description`.
4. **Операция:** `tags`, `summary` (одна фраза по-русски), `description` (поведение, значения по умолчанию, предобработка — если есть что сказать), `operationId` (camelCase, глагол + ресурс, уникален в файле: `getUserAddresses`, `createUserAddress`), `security`.
5. **`security`:** закрытый метод — `- Bearer: []`; открытый — `[]`.
6. **Параметры:** имя совпадает с маршрутом (`order_id`), `in` — только `path` / `query` / `header`; заполнение — по разделу 3.2.
7. **`requestBody`:** `required: true`, схема в `components/schemas` с именем `<Операция>Request`, список `required`; поля — по разделу 3.2.
8. **Ответы:** коды в кавычках (`"200"`). Успех — `$ref` на `components/responses/<Операция>Response` с заголовками `X-Response-Id`, `X-Response-Version`, `X-Language` и схемой через `allOf` от `BaseSuccessResponse`.
9. **Ошибки:** каждая — `description` с условием и `$ref` на `ValidationErrorResponse` (422) или `BaseErrorResponse` (остальные) + `example` с реальными `code` и `target`. 500 не описывается.
10. **Без кода и секретов:** без имён классов в `description`, без реальных токенов и персональных данных в `example`.
11. **Проверка:** фрагмент проходит `docker run --rm -v $PWD:/spec redocly/cli lint frontend.yml` без новых ошибок; HTML пересобирается командой из `docs/openapi/readme.md`.

##### 3.2. Заполнение параметров запроса и полей ответа

Для **каждого** параметра запроса (`path`, `query`, `header`, поле тела) и **каждого** поля ответа, включая вложенные объекты и элементы массивов:

| Атрибут | Когда | Как заполнять |
|---|---|---|
| `description` | всегда | На русском: что означает поле и для чего используется. Не повторяет имя (`description: locale` — нельзя). Для необязательного параметра — что происходит без него (значение по умолчанию). Для nullable — когда приходит `null`. Единицы измерения (секунды, рубли, копейки). Связь с другим методом, если значение берётся оттуда (`ID адреса — data.items[].id из списка адресов`) |
| `type` | всегда | `string` / `integer` / `number` / `boolean` / `array` / `object`; nullable — `[<тип>, "null"]`; у `array` — `items` с типом элемента |
| `format` | только если применимо | `date` (`YYYY-MM-DD`), `date-time` (ISO 8601 со смещением), `uuid`, `email`, `uri`, `int64`, `float`. Для строк без стандартного формата — `pattern` или правило в `description`, не выдуманный `format` |
| `required` | всегда | Параметр — `required: true / false`. Поле тела и ответа — список `required` у объекта. Для ответа `required` = поле приходит всегда (в том числе со значением `null`) |
| `example` | всегда | Реалистичное значение в формате поля; без реальных персональных данных и токенов. У параметра — на уровне параметра, у поля — в свойстве |
| `enum` | если значения ограничены списком | Все значения в `enum`; расшифровка каждого — в `description` в виде `<значение> — <смысл>; …`. Отдельные атрибуты (`x-enum-descriptions`) не вводятся — в файле их нет |

Ограничения (`minimum`, `maximum`, `maxLength`, `pattern`, `default`) указываются, если они есть в коде или в постановке задачи.

##### 3.3. Доописание существующих методов

Применяется, когда задача — дополнить swagger уже работающих методов (а не описать новый).

1. **Сначала изучить** текущие описания метода и соседних методов того же тега, общие схемы в `components` и соглашения файла.
2. **Сохранить структуру и стиль** файла: тот же порядок ключей, те же общие схемы и `$ref`, тот же язык описаний.
3. **Не дублировать** уже описанное и **не трогать корректные** определения: добавляются только недостающие атрибуты из раздела 3.2.
4. **Не менять контракт:** имена полей, типы, обязательность, пути, коды ответов и бизнес-логика остаются как в коде, даже если они нарушают раздел 2.
5. **Не придумывать:** `format`, обязательность, значения `enum`, ограничения и смысл поля берутся только из кода, переводов, данных БД или задачи.
6. **Несоответствия и неизвестное — на согласование.** Если swagger противоречит коду (`required: true` у параметра с значением по умолчанию) или смысл / формат / список значений не удалось установить, swagger в этом месте не меняется, а пункт выносится в отдельный список:

   | Метод | Параметр / поле | Что в swagger | Что в коде / что неизвестно | Предложение | Кому |
   |---|---|---|---|---|---|
   | `GET /api/v1/delivery/geo/countries/{countryIso}/cities` | `limit` | `required: true` | необязательный, по умолчанию `0` | `required: false`, описать поведение при `0` | бэк |

7. **SRS не дополняется** отдельными таблицами параметров и лишними атрибутами: контракт живёт в swagger, SRS ссылается на метод.
