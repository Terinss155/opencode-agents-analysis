Обзор

Четыре звена цепочки

У приложения два своих хоста. Оба шлюза почти ничего не решают сами: большую часть запросов они проксируют в монолит, остальное отправляют по gRPC в сервисы ESB. Внешние системы (1С, RetailCRM, Mindbox, платёжные провайдеры) видит только монолит, и чаще всего через очередь.

Конец цепочки

Что монолит делает дальше, по доменам

Каталог и поиск синхронно

  1. Листинг: кеш Redis, затем Elasticsearch; если Elastic выключен или помечен сломанным, то MySQL
  2. Поиск advanced-search: Diginetica, при ошибке — свой движок
  3. Рекомендации: Mindbox через BFB MS, при сбое — запасные выборки из MySQL
  4. Наличие в магазинах: остатки в MySQL

Корзина и чекаут синхронно+ очередь

  1. Корзина в MySQL, сервис выбирает CartServiceFactory
  2. Скидки и бонусы: расчёт Mindbox через BFB MS, с кешем
  3. PUT v2/cart публикует mindbox.mobile-cart.send.v1.command
  4. Варианты доставки, ПВЗ, интервалы, гео: BFB MS и кеш Redis

Создание заказа и резерва транзакцияoutbox

  1. OrderService::createOrder: заказ и позиции в MySQL, commit
  2. События AfterSaveEvent: 10 у POST v1/orders (CreateOrderServiceMobile), 5 у старого PUT orders — буфер остатков, блокировка сертификатов, переиндексация, срок резерва
  3. Outbox → to.onec.order.create, to.rcrm.order.create, mindbox.order.create
  4. Письмо менеджеру по SMTP

Платежи созданиестатусы

  1. YooKassa: SDK напрямую, вебхуки в modules/yandex/controllers/PayController.php
  2. Подели, Сплит, Yandex Pay, СБП: billing MS через BFB; Долями — отдельный хост AGGREGATE_BILLING_MS_URL
  3. Commit, cancel, refund: outbox → to.<система>.payment.v1.command
  4. Чек предоплаты YooKassa — API чеков YooKassa; остальные чеки: outbox order_receipts_to_send_outbox → ATOL (через BFB при USE_RECEIPT_MS)

Возвраты синхронноoutbox

  1. Способы возврата: конфигурация в Redis (ReturnDetailsConfigService)
  2. Детали возврата: MySQL + outbox в RetailCRM
  3. Статус возврата из 1С приходит через inbox

Сертификаты, лояльность, вход синхронно

  1. Сертификаты: Giftcards MS; коды подтверждения — Mindbox через BFB
  2. Бонусы и история: шлюз mobile берёт из Mindbox по gRPC
  3. SMS-коды входа и смены телефона: Mindbox по gRPC из шлюза core
  4. Мобильная сессия: MySQL монолита

Высокий

Outbox заказа пишется после commit iOS затронут

Строки outbox для 1С, RetailCRM и Mindbox создаются вне транзакции: после commit и после событий AfterSaveEvent. Если событие упадёт с исключением, заказ останется в БД, но во внешние системы не уйдёт. Касается POST v1/orders, PUT orders и POST v1/reservation.

12storeez-master-web/src/Modules/Order/Services/OrderService.php:182 → :201 → :209
Высокий

Один JWT-ключ на два шлюза iOS затронут

Токен выдаёт только esb: ключ HS256 — константа в коде. Go проверяет тот же токен по JWT_SECRET из Vault. Значения обязаны совпадать: если сменить ключ в одном месте, все вызовы на mobile получат 401. Сам ключ при этом хранится в репозитории.

esb-monorepo/libs/core/src/lib/constants.ts:7-9 · mobile-monorepo-go/cmd/mobile_api/mobile_api.go:468-493
Средний

Два чекаута одновременно iOS затронут

Старый чекаут (CreateOrderManager, OrderManager) ходит в core: cart/*, cart/delivery2, PUT orders. Новый (Managers/Checkout/*) ходит в mobile: v1/cart/*, POST v1/orders. Оба сходятся в одном OrderService::createOrder, поэтому любое изменение заказа нужно проверять в обоих.

TwelveStoreez/Classes/Business/Managers/CreateOrderManager.swift · Managers/Checkout/CheckoutCreateOrderManager.swift
Средний

Маршруты esb без проверки авторизации iOS затронут

cart/delivery и cart/delivery2* работают без guard. metadata/about, metadata/stores* и geo/countries/phone-details идут сразу в gRPC: подпись JWT у них проверяет только перехватчик Sentry.

esb-monorepo/libs/cart/controllers/src/lib/delivery*/ · libs/sentry/src/sentry.interceptor.ts:76
Средний

Платёжный /info знает не все системы iOS не затронут

Правило монолита пропускает только dolyame|yookassa|podeli|split, а для pay и yandex-sbp маршрута нет. Долями в новом пути v2/payments — заглушка с исключением. iOS проверяет статус только для Подели, а Долями получает через core (orders/dolyame-id).

12storeez-master-web/src/Modules/Mobile/Rules/UrlRule.php:147-154 · SplitPaymentManager.swift:43
Низкий

Работает по совпадению: резерв и последние запросы iOS затронут

В Go роут /reservation/:id зарегистрирован раньше /instructions и /expiration, поэтому оба запроса обрабатывает GetReservationItem. Выручает то, что он строит тот же адрес в монолите. То же в esb: products/v2/last-search-term перехватывает /:model_id. Если поменять формат адреса, эти вызовы сломаются.

mobile-monorepo-go/cmd/mobile_api/mobile_api.go:287-290 · esb-monorepo/libs/products/controllers/src/lib/v2/v2.controller.ts:106, :192
Низкий

Ошибки в неиспользуемых iOS ручках Go iOS не затронут

POST v1/giftcards/send-code идёт в mobile/v2/giftcards/send-email-code, а такого действия в монолите нет, ответ 404. LoginByPhoneRequestCode передаёт в Mindbox платформу в поле Version. Swagger Go не описывает metadata/contacts и about. Возможно, это касается Android.

mobile-monorepo-go/.deploy/helm/values.yaml · internal/app/service/auth.go:380
Низкий

Расхождения базы знаний с кодом iOS не затронут

В 08-integrations.md сказано, что Долями и Подели вызываются напрямую, а в коде оба идут через billing MS. В карте esb §5.4 написано, что срок JWT не проверяется, а на деле exp проверяется. Карты esb и Go сверены на коммит раньше текущего HEAD.

Ручки Go-шлюза, которые iOS не вызывает

Возможно, их вызывает Android, иначе это мёртвый код. Проверить по логам шлюза.

  • Весь /api/v1/auth/*: iOS входит через core
  • metadata/contacts, metadata/about
  • profile/bind-phone
  • geo/cities/:ip, …/normalize, get-by-phone
  • delivery/types
  • PUT v1/cart, cart/reset-exclude-positions
  • POST cart/delivery-list, cart/subscription/check, cart/ping
  • giftcards/send-code, весь /api/v2/giftcards/*
  • products/:id/accompaniments
  • version/check: в iOS endpoint описан, но не вызывается
