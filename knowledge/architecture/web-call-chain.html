Обзор

Путь запроса браузера

Браузер ходит в монолит напрямую: ни BFF, ни отдельного SSR-сервиса нет. PHP рендерит HTML и кладёт данные первого экрана в window._site, затем Vue-бандл догружает остальное AJAX-запросами на тот же домен. Пользователя монолит узнаёт по cookie, JWT сайт не использует.

Сайт и приложение

Где каналы сходятся и где расходятся

Входные контроллеры у сайта свои, а бизнес-логика в основном общая. Поэтому изменение в корзине, заказе или оплате обычно затрагивает оба канала, даже если задача пришла только про один.

Конец цепочки

Что монолит делает дальше для сайта

Каталог и поиск синхронно

  1. Листинг: Elasticsearch, если включён и не помечен сломанным, иначе MySQL
  2. Карточка: Redis (cachedProductsService)
  3. Поиск и подсказки: Diginetica, при ошибке свой поиск
  4. Рекомендации: Mindbox через BFB по cookie mindboxDeviceUUID

Корзина синхронно

  1. Сервис корзины из CartServiceFactory, MySQL
  2. Скидки и бонусы: расчёт Mindbox через BFB с кешем
  3. При каждом изменении — sendCartList прямо в api.mindbox.ru
  4. Сертификат в корзине: Giftcards MS

Доставка и гео синхронно

  1. Варианты доставки: MySQL (delivery_tk, delivery_city) + кеш
  2. ПВЗ, гео, интервалы: BFB MS + кеш Redis
  3. Boxberry: статичный /export_boxberry.json из консольной выгрузки

Создание заказа транзакцияoutbox

  1. Блокировка корзины, бонусы Mindbox, блокировка сертификатов
  2. OrderService::createOrder: MySQL, commit, 5 событий
  3. Outbox → 1С, RetailCRM, Mindbox через RabbitMQ
  4. Синхронно: подписка, GA, письмо менеджеру, Roistat

Платежи созданиестатусы

  1. YooKassa: SDK напрямую; вебхук /yandex/pay/proceed полностью синхронный, чек предоплаты — через API YooKassa
  2. Сплит, Pay, СБП, Подели: BFB_MS_HOST/aggregate-billing
  3. Долями: отдельный хост AGGREGATE_BILLING_MS_URL, вебхук TinkoffController
  4. Commit, cancel, refund — outbox; чеки — outbox → ATOL

ЛК, возвраты, отзывы синхронноoutbox

  1. Заказы: MySQL; офлайн-чеки — gRPC Orders
  2. Отмена и возврат: OrderService::updateOrder → outbox
  3. Способы возврата: Redis-конфигурация, как у приложения
  4. Отзыв о заказе: gRPC Feedbacks, затем Mindbox REST
Находки

Что стоит проверить

Метка «проверено» — место открыто и перечитано вручную после агента. Остальное собрано агентами по коду без ручной сверки.

Критично

Смена способа оплаты чужого заказа без входа проверено

Веб-версия PATCH /api/orders/{id}/change-payment-method и GET /api/payment-types?order_id= не требует входа и не проверяет владельца: заказ ищется просто по номеру. Номера заказов идут подряд, поэтому можно перебором читать суммы чужих заказов и менять их способ оплаты. В мобильной версии того же контроллера есть и вход, и проверка владельца (findOneByIdAndUserId).

Высокий

Кеш страниц может отдать чужие персональные данные проверено

Контент, блог и поддержка кешируются целиком вместе с window._site.user: имя, email, телефон. Ключ кеша различает только «вошёл или нет» и GET-параметры. Первый вошедший пользователь попадает в кеш, следующие вошедшие до часа видят его данные в исходнике страницы.

Высокий

Сбой после commit: заказ есть, клиент видит ошибку проверено

Outbox пишется после commit. Если событие или outbox падает, сайт ловит исключение, отвечает orderFailed, снимает блокировку с корзины и сертификатов. Заказ при этом уже в БД и не уходит в 1С, RetailCRM и Mindbox, а повторное нажатие создаёт дубль.

Высокий

Зашитый в код ключ к странице «Заказ оформлен» проверено

Кроме хэша заказа actionSuccess принимает постоянную строку из кода. С ней открывается страница успеха любого заказа по номеру. Значение здесь не приводится.

Средний

Отмена заказа из ЛК без серверной проверки проверено

Веб-ЛК отменяет любой свой заказ: проверки «можно ли отменить» нет ни в контроллере, ни в OrderCancelService. Кнопку скрывает только интерфейс. В приложении такая проверка есть.

Средний

CSRF выключен, есть меняющие данные GET-запросы проверено

Проверка CSRF и подпись cookie выключены глобально, а cookie входа доступна из JS. При этом корзину меняют GET-запросы /cart/add-item/…, reset-exclude-positions, send-cart-list: их может вызвать любая сторонняя страница.

Средний

Хранилище PHP-сессий не настроено

Компонент session не задан, в php.ini нет save_handler. Если сессии лежат в файлах пода, при трёх репликах без привязки к поду пользователь будет терять сессию. Проверить настройки базового образа php8.2-monolith.
