## 0. Назначение и как пользоваться отчётом

Это протокол решений по нормализации раздела 7 «Бизнес-требования» текущего
[`brd.md`](./brd.md) (v8). Задача — не переписать BRD, а разложить содержимое `BR-1`…`BR-41`
по типам требований (Business Requirement / Business Rule / Functional Requirement /
Non-functional Requirement / Integration-Technical Requirement / Constraint / Assumption /
Open Question / Scope) **внутри существующего шаблона документа**, проверить атомарность и
найти внутренние дубли/противоречия.

**Не входит в этот прогон**: синхронизация с User Story, Use Case, AC, трассировкой. Ссылки
на `US-*` в исходных текстах `BR-*` ниже приводятся дословно, но не проверяются и не
исправляются.

**Источники**: основной — текущий [`brd.md`](./brd.md) v8 (все разделы 1–12 прочитаны
целиком). Справочный — оригинальный `drafts/BRD_Возвраты_2_0.docx` (v2.0 от 29.07.2026),
использован там, где текущая формулировка недостаточна для классификации сама по себе (см.
раздел 7 карточек ниже; таких случаев 5 из 41). Дополнительно использован уже существующий в
бандле [`gap-analysis.md`](./gap-analysis.md) v1 — он содержит построчную сверку `brd.md` с
оригинальным BRD и с ADR; там, где его находки пересекаются с этим аудитом (в первую очередь
`BR-17`/`BR-18`), они процитированы, а не выведены заново.

Каждая карточка ниже самодостаточна: содержит полный исходный текст `BR-*`, разбор по
смыслам, классификацию, рекомендацию и готовый предлагаемый текст. Открывать `brd.md`
параллельно не требуется.

### Легенда типов требований (коротко; полные определения — в постановке задачи этого аудита)

| Тип | Отвечает на вопрос |
|---|---|
| **Business Requirement (BR)** | Какая бизнес-возможность нужна? |
| **Business Rule (RULE)** | По какому правилу работает процесс? |
| **Functional Requirement (FR)** | Что конкретно должна делать система? |
| **Non-functional Requirement (NFR)** | С каким измеримым качеством должна работать система? |
| **Integration/Technical Requirement (INT)** | Что требуется от обмена данными между системами? |
| **Constraint (CONSTR)** | Какая внешняя/организационная/правовая граница уже задана? |
| **Assumption / Open Question / Scope** | Существующие разделы BRD — трогаем только по ссылке |

### Легенда решений владельца (поле `Решение владельца` в каждой карточке)

`ОСТАВИТЬ` · `РАЗДЕЛИТЬ` · `ПЕРЕНЕСТИ` · `РАЗДЕЛИТЬ И ПЕРЕНЕСТИ` · `ДОРАБОТАТЬ` · `НУЖНО ОБСУДИТЬ` · `ОТКЛОНИТЬ`.
Пустое поле = изменения по карточке не выполняются. Значения соответствуют разделу 18/29
постановки задачи; повторно объяснять их в чате не потребуется — следующий агент будет
применять `brd.md`-изменения строго по этому полю.

### Временные ID

Разделённые фрагменты получают временные ID вида `BR-12-A`, `RULE-12-A`, `FR-12-A`,
`NFR-12-A`, `INT-12-A`, `CONSTR-12-A`. Окончательная нумерация — отдельным этапом после
согласования.

## 4. Предложение по минимальному изменению структуры

Общий шаблон `brd.md` сохраняется полностью: порядок и названия разделов 1–12 не меняются.
Внутри раздела **7. Бизнес-требования** предлагается ввести подразделы (структура,
приведённая как пример в самой постановке задачи, подходит без изменений):

```text
7. Требования
7.1 Бизнес-требования            (BR-*)
7.2 Бизнес-правила                (RULE-*)
7.3 Функциональные требования     (FR-*)
7.4 Нефункциональные требования   (NFR-*)
7.5 Интеграционные / технические требования (INT-*)
```

Правила размещения:

- Заголовок раздела 7 меняется с «Бизнес-требования» на «Требования» (родовое название),
  таблица `BR-*` становится подразделом 7.1 без изменения состава колонок (`ID | Требование |
  Источник | Приоритет`).

Смысл правила не в том, что после создания заявки никакие её данные вообще не могут изменяться.

Основное ограничение относится к самостоятельному редактированию созданного возврата клиентом через ЛК / мобильное приложение:

- клиент не может открыть созданную заявку и самостоятельно изменить ранее выбранные данные возврата;
- если клиент хочет изменить состав возврата, способ возврата, точку передачи или другие данные, которые он самостоятельно выбирал при оформлении, необходимо отменить текущую заявку и создать новую, если повторное оформление ещё доступно;

При этом существуют отдельные сценарии, в которых данные уже созданного возврата могут изменяться без отмены заявки:

- клиент может обратиться в «Дружбу» по вопросам уже созданного возврата; возможность изменения отдельных данных определяется соответствующим сценарием возврата.;
- дата или временной интервал могут быть изменены по договорённости клиента с транспортной компанией;
- после получения / фиксации согласованных изменений они становятся актуальными данными существующего возврата, повторное оформление заявки не требуется.

Поэтому формулировка:

> «любое изменение (...) выполняется через отмену текущей заявки и создание новой»

некорректна без уточнения границ правила.

Необходимо разделить:
1. запрет самостоятельного редактирования созданной заявки клиентом через ЛК / мобильное приложение;
2. правило отмены и создания новой заявки для изменения данных, самостоятельно выбранных клиентом при оформлении;
3. исключения для изменения условий через «Дружбу» или транспортную компанию без создания новой заявки.

Фразу «самостоятельный перенос даты и времени курьера не предусмотрен» также необходимо понимать именно как отсутствие самостоятельного изменения через ЛК / мобильное приложение, а не как полный запрет изменения даты уже созданного курьерского возврата.

### СБП

В оригинальном BRD зафиксировано: Возврат по номеру телефона автоматически в течение 1–3 дней.

При этом более поздним комментарием к разделу подтверждено:

Поэтому слово `автоматически` в строке СБП необходимо перепроверить с учётом этого более позднего уточнения.

- возврат по СБП — по номеру телефона;
- ожидаемый срок — 1–3 дня.

- возврат — на банковские реквизиты клиента;
- ожидаемый срок — 3–5 дней.

### Бонусы

В оригинальном BRD указано: Пересчитываются / платежи 1–3 дня.

Дополнительно в комментарии к исходному BRD зафиксировано требование:

> «Нужно чтобы автоматически возвращались бонусы, много проблем так как скидки в разных местах».

Под автоматическим восстановлением бонусов в данном случае понимается возврат именно того количества бонусов, которое было использовано при оплате возвращаемой единицы товара.

Например, если при покупке конкретной единицы товара на неё было распределено `500` бонусов, то при возврате этой единицы клиенту должны быть восстановлены эти `500` бонусов.

При частичном возврате заказа бонусы восстанавливаются только по тем единицам товара, которые входят в данный возврат. Бонусы, относящиеся к товарам, которые клиент не возвращает, не восстанавливаются.

То есть правило следует сформулировать не как абстрактное:

> «бонусы восстанавливаются пропорционально позициям»,

а как более точное:

> Использованные бонусы восстанавливаются автоматически в размере, который был применён к возвращаемым единицам товара при исходной покупке.

Если в возврат включена только часть товаров заказа, восстанавливаются только бонусы, относящиеся к этим возвращаемым единицам.

Комментарий владельца:
>Требуется доработать формулировку `BR-19`, чтобы не смешивать разные документы, существующие в процессе возврата.

В оригинальном BRD в разделе `5.4. Проблемы клиента (по клиентской CJM AS-IS)` зафиксирована проблема:

> «Не выдают документ о возврате» — «Клиенту не выдают чек/накладную о возврате».

При этом в целевом процессе отдельно существует электронное заявление на возврат.

Электронное заявление:
- формируется при оформлении заявки на возврат;
- доступно клиенту в созданном возврате;
- может быть скачано клиентом и при необходимости распечатано;
- подтверждает данные и состав оформленной заявки на возврат.

При этом электронное заявление не является подтверждением фактической передачи изделия, поскольку оно формируется до момента сдачи товара.

Следовательно, необходимо разделять:

1. Электронное заявление на возврат — документ, сформированный при создании заявки.

2. Подтверждение фактической передачи / приёма изделия в возврат — подтверждение, которое клиент получает после того, как изделие действительно передано через выбранный канал возврата.

`BR-19` по смыслу исходной болевой точки должен относиться ко второму случаю.

Предлагаемый смысл Business Requirement:

> После фактической передачи изделия в возврат клиенту должно быть доступно подтверждение его приёма / передачи.

Конкретная форма такого подтверждения пока не определена и должна быть уточнена отдельно по каналам возврата (`OQ-8`):
- квитанция;
- чек / слип;
- документ транспортной компании;
- электронное подтверждение;
- иной подтверждающий документ.

Не использовать формулировку `документ, подтверждающий возврат изделия` без уточнения, поскольку она может быть ошибочно понята как электронное заявление или как чек о возврате денежных средств.

Также не считать электронное заявление таким подтверждением автоматически: оно подтверждает оформление заявки, но не факт физической сдачи изделия.
