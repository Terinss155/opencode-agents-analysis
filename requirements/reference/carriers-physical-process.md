# Справочник: физический процесс возврата у транспортных компаний

**Статус:** Справочный материал, не входит в основной конвейер BRD → US → UC → трассировка.
**Владение:** физический процесс передачи, приёмки и перемещения возврата — вне ответственности
BA/SA по сайту, МП, монолиту и интеграциям (см. `as-is/00-overview.md`, раздел «Границы»:
«Физическая передача возврата, приёмка, экспертиза» и «Формирование ТТН/трек-номеров, статусы
транспортных компаний» явно вынесены вне границ AS-IS).

**Зачем этот файл нужен именно здесь.** Хотя сам процесс не в нашей зоне, факты о нём —
когда транспортная компания формирует штрихкод/QR и в какой момент её статус впервые
отражает физическую передачу товара — прямо определяют, что может (и не может) знать
монолит через интеграцию с ТК. Эти факты нужны для проектирования статусной модели и
для оценки открытых вопросов `OQ-9`, `OQ-10`, `OQ-11`, `OQ-39`, `OQ-40`, `OQ-41`
(см. [brd.md](../brd.md), §9), но не являются самим бизнес-требованием — поэтому вынесены
из BRD сюда, а не описаны как ещё один открытый вопрос.

**Источник:** `drafts/Физические сценарии возвратов_3.html` (внутренний документ владельца
логистического процесса, «Физ.сценарии КЛ.В.xlsx» + уточнения, обновлено 02.09.2026).
Документ описывает **текущий ручной процесс** (выгрузка заказов в ТК вручную) — во всех
разделах есть предупреждение «при интеграции состав может измениться». Считать AS-IS
транспортных компаний, не подтверждённым для целевой интеграции.

## Сводка по каналам

| Канал | Когда формируется ШК/QR для клиента | Кто физически наносит ШК | Первый статус, видимый ПОСЛЕ физической передачи товара |
|---|---|---|---|
| **СДЭК курьер** (забор у клиента) | Формируется при выгрузке заказа в ТК, но **клиенту не выдаётся** — курьер идентифицирует заказ по своей системе, не по коду у клиента | Сотрудник РЦ (транзитный склад) — не курьер, не клиент | `в пути` — только когда груз **сдан курьером на РЦ**, не в момент забора у клиента |
| **СДЭК ПВЗ** (сдача в пункт) | Номер накладной уходит клиенту на почту из CRM после выгрузки в ТК и загрузки трек-номеров в 1С | Сотрудник ПВЗ — при приёме у клиента | `в Пути` — сразу при приёме на ПВЗ (близко к реальному времени) |
| **5Post постомат/касса** (сдача в магазине) | ШК **не существует до сдачи** — до этого у клиента только код + QR из СМС | Постомат / кассир — в момент сдачи | `Готов к изъятию из пункта выдачи` — сразу при сдаче (близко к реальному времени) |
| **Далли Сервис курьер** (забор у клиента) | ШК не формируется при заборе вообще — появляется только на складе Далли; на участке «клиент → склад» заказ идёт по внутренней задаче курьера в приложении | Склад Далли — не курьер, не клиент | `Доставлен предварительно` / `Доставлен` — тоже только по прибытии на склад Далли, не в момент забора |

## Значимые для интеграции факты

1. **Для курьерских каналов (СДЭК курьер, Далли) в системах ТК нет события «курьер принял у
   клиента».** Самый ранний статус, который в принципе может увидеть монолит, привязан к
   прибытию груза на РЦ/склад партнёра курьерской службы — то есть уже после того, как курьер
   физически покинул клиента. Разрыв во времени между реальной передачей и первым видимым
   статусом не равен нулю и не оценён количественно в источнике.
   → Прямое основание для `OQ-39`: технического события «курьер принял у клиента» с нулевым
   лагом не существует в описанном процессе; вопрос не «какое событие выбрать», а «какой лаг
   до РЦ/склада партнёра приемлем для блокировки отмены на сайте/в МП».
2. **Статус `Доставлен` у Далли — не финальная точка.** Означает «курьер сдал посылку на склад
   Далли», а не «возврат поступил к нам на склад». При маппинге статусной модели (`OQ-1`) не
   путать с приёмкой на складе интернет-магазина.
3. **Наличие/отсутствие клиентского идентификатора по каналу подтверждает уже принятое `BR-9`**:
   курьерские каналы (СДЭК курьер, Далли) не входят в перечень `BR-9` (QR-код / QR+PIN /
   штрих-код+накладная) — и этот документ объясняет почему физически: опознание идёт по заявке
   в системе ТК или в приложении курьера, а не по коду, предъявляемому клиентом.
4. **Раздел «Выгрузка заказа в ТК» с предупреждением про интеграцию повторяется во всех
   четырёх каналах** — весь описанный процесс (кто и когда клеит ШК, в какой момент отправляется
   трек-номер) сегодня зависит от ручной выгрузки сотрудником. Это ограничивает применимость
   документа к целевой интеграции (`OQ-10`, `OQ-11`) — он описывает, как это работает **сейчас**,
   а не то, как будет работать после интеграции 1С/склада с ТК напрямую.

## Связанные открытые вопросы (не дублируются, только ссылка)

- `OQ-9` — что содержит QR/PIN и когда наносится ШК: этот файл даёт справочный ответ по
  ручному процессу, окончательный ответ для интеграции остаётся открытым.
- `OQ-10`, `OQ-11` — момент и участник интеграции «1С ↔ ТК»: см. п. 4 выше.
- `OQ-39` — событие и допустимый лаг при физической передаче курьеру: см. п. 1 выше — ключевой
  вход для решения этого вопроса.
- `OQ-40`, `OQ-41` — сдача в другой точке СДЭК/5Post по тому же коду: этим документом не
  покрывается (описывает только основной сценарий одной точки).
