# Шаг 04 (mobile, TO-BE). Автоподстановка города, способа возврата и точки / адреса

**Канал:** Мобильное приложение
**Статус:** DRAFT · **Дата:** 29.09.2026
**AS-IS:** [as-is/mobile/04-select-city.md](../../as-is/mobile/04-select-city.md), [as-is/mobile/05-select-return-method.md](../../as-is/mobile/05-select-return-method.md)
**Связанный TO-BE:** [01-load-order-card.md](01-load-order-card.md) — открытие карточки заказа
**Результат шага:** форма возврата открыта с предзаполненными городом, способом возврата и (если проверки прошли) пунктом выдачи или адресом курьера. В базе ничего не меняется.

> Параметры в угловых скобках (`<...>`) — рабочие наименования новых полей, таблиц и параметров, не утверждённые окончательно.
> Описан только мобильный канал. Сайт описывается отдельно.

## Обозначения

Стрелка всегда читается **слева направо: откуда → куда**. Тип источника указан в квадратных скобках:

| Метка | Что означает |
|---|---|
| `[БД]` | значение из таблицы базы данных; путь через несколько таблиц записан по шагам |
| `[JSON <метод>]` | поле из ответа указанного метода |
| `[path]` | параметр в пути запроса (`/.../{param}/...`) |
| `[query]` | параметр запроса после `?` |
| `[UI]` | что видит клиент |

Пример: `[JSON карточка] return.order_delivery.city_geo_id → [path] geo_id` — значение поля `city_geo_id` из ответа карточки заказа подставляется в параметр пути `geo_id`.

## 1. Сценарий взаимодействия (что видит клиент)

1. Клиент открывает карточку заказа. Система заранее получает все данные заказа, нужные для возврата (блок `return.order_delivery`, раздел 3.1).
2. Клиент нажимает «Оформить возврат».
3. Клиент выбирает товары и указывает причины.
4. Клиент нажимает «Продолжить».
5. Система выполняет проверки автоподстановки (раздел 2): город → способ возврата → точка / адрес.
6. Система показывает форму возврата:
   - проверки успешны — город, способ возврата и пункт выдачи (или адрес курьера) уже заполнены;
   - пункт выдачи не принимает возвраты — способ выбран, поле пункта пустое, показано действие «Выберите пункт»;
   - город не определён — показан призыв «Укажите город, в котором хотите сделать возврат» и открыта шторка выбора города;
   - для города нет способов возврата — показано сообщение об отсутствии способов и кнопка «Написать нам».
7. Клиент подтверждает предзаполненные данные или выбирает город / способ / пункт самостоятельно.

## 2. Логика системы

Логика разделена на три блока, выполняемых последовательно после нажатия «Продолжить»:

- **Блок А.** Предвыбор города.
- **Блок Б.** Предвыбор способа возврата с проверкой его доступности в городе.
- **Блок В.** Проверка и подстановка пункта выдачи (ПВЗ) или адреса курьера.

Исходные данные всех блоков — блок `return.order_delivery` из ответа карточки заказа `GET /mobile/orders/{id}` (состав и источники — раздел 3.1).

### Блок А. Предвыбор города

**А.1. Проверка наличия идентификатора города в заказе**

- **Условие:** в ответе карточки заполнено `[JSON карточка] return.order_delivery.city_geo_id`.
- **Результат:**
  - заполнено → шаг А.2;
  - пусто (`null`) → шаг А.3.

**А.2. Получение актуальных данных города по идентификатору**

Метод: `GET /api/v1/geo/countries/{country_iso_code}/cities/{geo_id}/details` (шлюз → геосервис).

Параметры запроса:
- `[JSON карточка] return.order_delivery.country_iso → [path] country_iso_code`
- `[JSON карточка] return.order_delivery.city_geo_id → [path] geo_id`

- **Условие:** ответ `success = true`, объект `data` заполнен.
- **Результат:**
  - город найден → данные города (город, регион, страна, идентификаторы) сохраняются в форме возврата для блока Б; источник полей — раздел 3.2. Шаг А.3 пропускается, переход к блоку Б;
  - `success = false`, пустой `data`, ошибка или таймаут → шаг А.3.

**А.3. Поиск города по названию (запасной вариант)**

Метод: `GET /api/v1/geo/countries/{country_iso_code}/cities?search={search}` — тот же метод, что используется на экране ручного выбора города.

Параметры запроса:
- `[JSON карточка] return.order_delivery.country_iso → [path] country_iso_code`
- `[JSON карточка] return.order_delivery.city → [query] search`

- **Условие:** в списке найденных городов ровно один город, у которого одновременно:
  1. название города совпадает с `[JSON карточка] return.order_delivery.city` (без учёта регистра и типа населённого пункта: «г», «г.», «город»);
  2. название региона совпадает с `[JSON карточка] return.order_delivery.region` (проверяется, если регион в заказе заполнен).
- **Результат:**
  - найден ровно один город → его данные сохраняются в форме возврата так же, как в А.2 (раздел 3.2), переход к блоку Б;
  - найдено ноль или больше одного города, в заказе не заполнены страна или город, ошибка сервиса → **город не определён**:
    - `[UI]` экран «Укажите город, в котором хотите сделать возврат» + автоматически открытая шторка выбора города;
    - при закрытии шторки без выбора остаётся кнопка «Выбрать город»;
    - блоки Б и В выполняются после ручного выбора города.

**А.4. Признак «город заказа»**

- **Условие:** идентификатор города, выбранного в форме возврата, совпадает с `[JSON карточка] return.order_delivery.city_geo_id`.
- **Результат:**
  - совпадает → `<is_order_city> = true` (внутренний признак формы);
  - не совпадает (клиент выбрал другой город вручную) → `<is_order_city> = false`.

  При автоподстановке (А.2 / А.3) город всегда совпадает с городом заказа. Признак пересчитывается при каждой смене города клиентом и используется в блоках Б и В: **если город отличается от города заказа, ни способ заказа, ни пункт выдачи, ни адрес не подставляются — способ выбирается по приоритету.**

### Блок Б. Предвыбор способа возврата с проверкой доступности

**Б.1. Запрос способов возврата для города**

Метод: `GET /mobile/orders/{order_id}/return-method-list?countryIso=&city=&cityId=&region=&regionId=`

Параметры запроса (из данных города, сохранённых в блоке А):
- `[JSON геосервис, детали города] data.country.isoCode → [query] countryIso`
- `[JSON геосервис, детали города] data.city.title → [query] city`
- `[JSON геосервис, детали города] data.city.id → [query] cityId`
- `[JSON геосервис, детали города] data.region.title → [query] region`
- `[JSON геосервис, детали города] data.region.id → [query] regionId`
- `[JSON карточка] id → [path] order_id`

> При поиске по названию (А.3) те же поля берутся из выбранного элемента списка городов.

**Б.2. Что делает система внутри метода**

1. **Проверка заказа** (AS-IS, без изменений):
   - **Условие:** `[path] order_id → [БД] cms_orders.id`; `cms_orders.user_id` = авторизованный пользователь; `cms_orders.lamoda_id` не заполнен.
   - **Результат:** заказ не найден → ошибка «Заказ не найден», способы не возвращаются.

2. **Поиск служб возврата, работающих в городе:**
   - **Условие:** система ищет строки `[БД] <cms_return_tk_city>`, у которых `<cms_return_tk_city>.geo_id` равен `[query] cityId` **или** `[query] regionId` (способ может быть заведён на город или на весь регион), и `<cms_return_tk_city>._state` = активна.
   - **Результат:** список служб возврата города (`<cms_return_tk_city>.return_tk_id`).

3. **Переход от службы к способу возврата:**
   - **Условие:** по каждой найденной службе:
     `[БД] <cms_return_tk_city>.return_tk_id → <cms_return_tk>.id` (служба активна: `<cms_return_tk>.is_enabled` = 1)
     `→ <cms_return_tk>.return_method_id → cms_return_method.id` (способ активен в приложении: `cms_return_method.is_enabled_mobile` = 1).
   - **Результат:** список способов возврата, доступных в городе, с данными службы (`<cms_return_tk>.slug` — провайдер для логистики).

4. **Сортировка по приоритету:**
   - **Условие:** способы упорядочиваются по `[БД] cms_return_method._order` по возрастанию.
   - **Результат:** первый элемент списка — способ с наивысшим приоритетом.

5. **Даты по каждому способу** (`available_dates_return`) — рассчитываются как в AS-IS; правила дат (в т.ч. буфер курьера) описываются отдельно.

6. **Если способов нет:**
   - **Результат:** метод возвращает пустой список. Подстановка курьера по умолчанию (AS-IS) не выполняется.

Состав ответа — раздел 3.3, пример — раздел 4.2.

**Б.3. Обработка пустого списка**

- **Условие:** `[JSON return-method-list] result` пустой.
- **Результат:** `[UI]` сообщение об отсутствии доступных способов возврата + кнопка «Написать нам»; поле города остаётся доступным для нажатия. Блок В не выполняется.

**Б.4. Сверка со способом получения заказа**

- **Условие:** одновременно:
  1. `<is_order_city> = true` (А.4);
  2. `[JSON карточка] return.order_delivery.return_method` заполнен;
  3. в `[JSON return-method-list] result[]` есть элемент, у которого `method` равен `[JSON карточка] return.order_delivery.return_method`.
- **Результат:**
  - все условия выполнены → предвыбирается этот способ (способ заказа), переход к блоку В;
  - хотя бы одно не выполнено → предвыбирается `[JSON return-method-list] result[0]` (первый по приоритету); пункт выдачи и адрес **не** подставляются, блок В не выполняется.

### Блок В. Проверка и подстановка пункта выдачи или адреса

Выполняется, только если в Б.4 предвыбран способ заказа.

**В.1. Определение ветки**

- **Условие:** `[JSON return-method-list] result[].method_type` выбранного способа.
- **Результат:**
  - `pvz` → шаг В.2 (пункт выдачи);
  - `courier` → шаг В.4 (адрес курьера).

**В.2. Проверка пункта выдачи в логистике**

- **Условие:** в карточке заполнен `[JSON карточка] return.order_delivery.pvz` (у заказа был пункт выдачи).

Метод: `GET /api/v1/pickup/provider/{provider}/points/{point}` (шлюз → логистика `/api/v1/winner/pickup/{provider}/points/{point}`).

Параметры запроса:
- `[JSON карточка] return.order_delivery.pvz.provider → [path] provider`
- `[JSON карточка] return.order_delivery.pvz.id → [path] point`

> Используется провайдер **заказа**, а не службы возврата: пункт был выбран в службе доставки заказа, поэтому проверяется у неё.

- **Результат:**
  - `success = true` и `<признак приёма возвратов>` = да → шаг В.3;
  - `success = false`, признак = нет, ошибка или таймаут → **пункт не подставляется**: `[UI]` способ выбран, поле пункта пустое, действие «Выберите пункт» («Выберите магазин» — для магазина).

**В.3. Подстановка пункта выдачи**

- **Результат:** в форме возврата заполняется блок пункта:
  - `[JSON логистика, детали пункта] data.id → [UI] идентификатор выбранного пункта`
  - `[JSON логистика, детали пункта] data.title → [UI] название пункта`
  - `[JSON логистика, детали пункта] data.address → [UI] адрес пункта`
  - `[JSON логистика, детали пункта] data.work_time → [UI] режим работы`

**В.4. Проверка адреса курьера в геосервисе**

- **Условие:** в карточке заполнен `[JSON карточка] return.order_delivery.address`.

Метод: нормализация адреса в геосервисе по тексту (`.../geo/countries/{country_iso_code}/addresses/normalize?query=`; путь на мобильном шлюзе — уточнить).

Параметры запроса:
- `[JSON карточка] return.order_delivery.country_iso → [path] country_iso_code`
- `[JSON карточка] return.order_delivery.address.full_address → [query] query`

> Идентификатор адреса в геосервисе в заказе не хранится, поэтому проверка возможна только по тексту адреса.

- **Результат:**
  - геосервис вернул адрес → поля адреса курьера (улица, дом, квартира, индекс) предзаполняются из ответа геосервиса; если геосервис не вернул индекс — из `[JSON карточка] return.order_delivery.address.postal`;
  - геосервис не вернул адрес → поля адреса курьера остаются пустыми, способ «Курьер» остаётся выбранным.

### Повторная автоподстановка при действиях клиента

| Действие клиента | Условие | Результат |
|---|---|---|
| Сменил город на другой | `<is_order_city> = false` | Способ сбрасывается; выбирается `result[0]` нового города; пункт и адрес не подставляются |
| Вернул город заказа | `<is_order_city> = true` | Повторяются Б.4 и блок В: подставляются способ, пункт / адрес заказа (если доступны) |
| Сменил способ и вернулся к способу заказа | `<is_order_city> = true` | Повторяется блок В для способа заказа |

| `result[].description` | `cms_return_method.description` | AS-IS |

| `result[].active_mobile` | `cms_return_method.is_enabled_mobile` | AS-IS |
| `result[].available_dates_return` | расчёт дат (AS-IS) | AS-IS |
| `result[].<provider>` | `<cms_return_tk>.slug` найденной для города службы | **TO-BE**, нужен для ручного выбора пункта (запрос списка пунктов у логистики) |
| порядок элементов `result[]` | `cms_return_method._order` по возрастанию | **TO-BE** |

## 5. Изменения модели данных

| Объект | Изменение | Совместимость |
|---|---|---|
| `cms_return_method._order` | Новое поле: порядок (приоритет) способа | Значение по умолчанию обязательно; поле нужно вывести в админке способов возврата, иначе порядок нельзя будет менять |
| `<cms_return_tk>` | Новая таблица: служба возврата (кто выполняет). Поля: `id`, `return_method_id` → `cms_return_method.id`, `slug` (провайдер для логистики), `title`, `<rcrm_tk_id>` (служба в RetailCRM), `is_enabled` | Аналог `cms_delivery_tk` для доставки |
| `<cms_return_tk_city>` | Новая таблица: город × служба возврата. Поля: `id`, `return_tk_id` → `<cms_return_tk>.id`, `geo_id` (идентификатор города / региона геосервиса), `country`, `region`, `city`, `_state` | Аналог `cms_delivery_city`. С `cms_delivery_city` внешним ключом не связана — общее только значение `geo_id`. **До включения новой логики таблицу нужно заполнить текущими данными**, иначе у всех городов пропадут способы возврата |
| `<cms_return_method_delivery_type>` | Новый справочник: тип службы доставки заказа → способ возврата. Поля: `delivery_type` → `cms_delivery_types.internal_id`, `return_method_id` → `cms_return_method.id` | Не затрагивает таблицы доставки |
| Метод `return-method-list` | Пустой список вместо подстановки курьера; фильтр по признаку активности в приложении; сортировка по `_order`; новое поле `provider` | Метод общий с сайтом. Пустой список должен корректно отображаться и на сайте, и в старых версиях приложения; при необходимости новое поведение включается по версии приложения |

Таблицы `cms_delivery_city`, `cms_delivery_tk` и `cms_order_return_positions` (возвраты из 1С) не изменяются.

## 6. Ограничения

- Фактический путь, который вызывает iOS-приложение для списка способов, отличается от пути в монолите — см. [AS-IS 05](../../as-is/mobile/05-select-return-method.md). Требует подтверждения у бэкенд-команды.
- Метод проверки пункта выдачи для мобильного канала проходит через шлюз; признак «пункт принимает возвраты» в ответе логистики появится после доработки сервиса логистики.
- Заказы Lamoda в сценарий не попадают (отсекаются при открытии карточки заказа).
