# Шаг 03 (web). Выбор причины возврата

**Канал:** Сайт · **Экран:** попап оформления возврата, экран «Причина возврата»
**Статус:** DRAFT · **Дата:** 07.09.2026
**Результат шага:** на клиенте по каждой выбранной позиции указаны группа причины и причина (её код). В базу ничего не пишется — фиксируется до нажатия «Подтвердить возврат».

---

## 1. Пользовательский сценарий

### 1.1 Откуда пользователь приходит

С экрана выбора изделий (шаг [02](02-select-return-items.md)), кнопка «Указать причину возврата».

### 1.2 Что система отображает

Экран показывается **по одной выбранной позиции за раз**:

- Заголовок «Причина возврата» и подзаголовок «Изделие N из M» (порядковый номер текущей позиции среди выбранных).
- Карточка текущего изделия (фото, цена, название, артикул, цвет, размер).
- Выпадающий список **групп причин** (плейсхолдер «Выберите причину»).
- После выбора группы — список **причин** этой группы, каждая с чекбоксом (можно выбрать одну).
- Кнопка внизу — «Продолжить».

### 1.3 Какие данные доступны

Все активные группы и причины из справочника — одинаковый список для любой позиции. Привязки причин к категории или бренду товара нет.

### 1.4 Действия пользователя

- Выбрать группу. При этом ранее выбранная причина сбрасывается.
- Выбрать причину (сохраняется её код).
- «Продолжить»:
  - если остались ещё не заполненные выбранные позиции — показывается следующее изделие (тот же экран);
  - если это последняя позиция — переход к экрану «Оформление возврата» (шаги [04](04-select-city.md) и далее).
- «Назад» в шапке: если это не первое изделие — вернуться к предыдущему; иначе — назад на экран изделий.

### 1.5 Ограничения

- Кнопка «Продолжить» неактивна, пока для **текущей** позиции не выбрана причина.
- Список причин не показывается, пока не выбрана группа.
- Иерархия — два уровня: **группа причин → причина**. Это те же два уровня, что в целевом сценарии названы «причина → подпричина»: AS-IS «группа причин» ≈ TO-BE «причина», AS-IS «причина» ≈ TO-BE «подпричина». Оба уровня приходят в одном ответе на шаге 01 (причины вложены в группы); в БД лежат в разных таблицах: 1-й уровень — `cms_return_reasons_groups`, 2-й — `cms_return_reasons` (связь `cms_return_reasons.group_id = cms_return_reasons_groups.id`).

### 1.6 Что происходит после действия

По каждой выбранной позиции в памяти попапа сохраняются группа и код причины. На шаге 08 в запрос создания возврата по каждой позиции уйдёт пара «идентификатор позиции + код причины».

### 1.7 Ошибочные сценарии

- Сменил группу — ранее выбранная причина обнуляется, кнопка «Продолжить» гаснет.
- Обмена с сервером на этом шаге нет — сетевых ошибок нет.
- Устаревший эндпоинт `POST /user/cabinet/return-item/ajax/check-reason` (проверка/создание возврата по одной позиции) текущим попапом не вызывается.

## 2. Системная реализация

### 2.0 Диаграмма последовательности

```mermaid
sequenceDiagram
    actor U as Пользователь
    participant W as Сайт (попап)

    Note over W: справочник причин уже получен на шаге 01
    loop по каждой выбранной позиции
        W-->>U: карточка изделия + список групп причин
        U->>W: выбрать группу
        W->>W: position.reasonGroupId = groupId; reasonId = null
        U->>W: выбрать причину
        W->>W: position.reasonId = cms_return_reasons.code
        U->>W: «Продолжить»
    end
    W-->>U: экран «Оформление возврата» (шаг 04)
```

Backend и БД на этом шаге не участвуют.

### 2.1 Источники данных

| Данные | Где хранится | Поля |
|---|---|---|
| Группы причин | `cms_return_reasons_groups` (`active = 1`, сортировка по полю `order`) | `id`, `title` |
| Причины | `cms_return_reasons` (`active = 1`, `group_id`, сортировка по полю `_order`) | `code`, `title` |

Оба справочника уже переданы на сайт на шаге 01. В подпись причины идёт поле `title`.

### 2.2 Как система собирает данные

На этом шаге сервер не участвует — оба уровня справочника (группы и причины) уже пришли одним ответом на шаге 01. Отдельного запроса за вторым уровнем нет (в `UC-RET-02` на этом месте стоит нераскрытая пометка «API: уточняется»).

### 2.3 Обмен по API

Нет.

### 2.4 Что использует сайт

| Поле | Использование |
|---|---|
| `id` группы | признак выбранной группы у позиции; ключ выбора в выпадающем списке |
| `title` группы | подпись группы |
| `code` причины | сохраняется у позиции; именно это значение уйдёт в запрос создания возврата |
| `title` причины | подпись причины |

### 2.5 Что передаётся на следующий шаг

Внутри попапа: код причины по каждой позиции — дальше в запрос `POST /orders/refund/save-reason` (шаг 08). Идентификатор группы в запросы не передаётся, он нужен только интерфейсу.

### 2.6 Что сохраняется или меняется

Ничего (только локальное состояние формы).

### 2.7 Неуточнённые места

- Матрицы «какие причины доступны для какой категории» в AS-IS нет — список плоский и общий.
- Проверка того, что выбранный код причины существует и активен, выполняется только на шаге создания возврата, не здесь.

## 3. Отличия от TO-BE

| TO-BE (`UC-RET-02`) | AS-IS (web) |
|---|---|
| Два уровня выбора названы «причина → подпричина»; на получении второго уровня стоит пометка «API: уточняется» | Те же два уровня, названы «группа причин → причина»; оба уровня приходят одним ответом на шаге 01, хранятся в `cms_return_reasons_groups` и `cms_return_reasons` |
| Открытый вопрос: какие причины/подпричины доступны для какой категории товара | Привязки к категории нет — один и тот же плоский справочник для любой позиции |
| Система связывает с товаром **и причину, и подпричину** | На позицию сохраняется только один код — второго уровня (`cms_return_reasons.code`); первый уровень (группа) в запрос и в БД не попадает |
