# Use Case: Оформление возврата товара

## 1. Назначение

Документ декомпозирует верхнеуровневую историю `US-100` на последовательные пользовательские сценарии оформления заявки: от выбора товаров до подтверждения возврата.

## 2. Источники и границы

**Источники:**

- `product-return_user-story.md`;
- `../drafts/obshie-biznes-pravila-oformleniya-vozvrata.md`;
- `../drafts/vozvrat-kurerom-biznes-process-to-be.md`;
- `../drafts/vozvrat-cherez-5post-biznes-process-to-be.md`;
- `../drafts/vozvrat-cherez-sdek-pvz-biznes-process-to-be.md`;
- уточнения заказчика от 07.09.2026 о предзаполнении города, способа, адресов/пунктов и канале «Почта России».

**В границах:** оформление авторизованным пользователем возврата из карточки заказа до создания заявки.

**Вне границ:** физическая передача товара, отслеживание, экспертиза, перечисление денежных средств, отмена и изменение уже созданной заявки.

## 3. Общая информация

| Поле | Значение |
|---|---|
| Основной актор | Авторизованный пользователь, совершивший покупку |
| Система | Сайт или мобильное приложение |
| Триггер | Пользователь выбирает действие «Оформить возврат» в доступном для возврата заказе |
| Предусловия | Заказ принадлежит пользователю; срок создания заявки не истёк; есть товар с доступным количеством |
| Результат | Создана заявка с выбранными товарами, причинами, городом, способом и канальными данными |
| Связанная история | `US-100` |

## 4. Сквозной основной сценарий

| Шаг | Use Case | Действие пользователя | Результат системы |
|---:|---|---|---|
| 1 | `UC-RET-01` | Выбирает товары и количество | Состав возврата сформирован |
| 2 | `UC-RET-02` | Выбирает причину и подпричину для каждого товара | Причины заполнены для всего состава |
| 3 | `UC-RET-03` | Подтверждает предложенный город или выбирает другой | Определены город и доступные способы |
| 4 | `UC-RET-04` | Выбирает способ возврата | Открывается соответствующая канальная форма |
| 4.1–4.5 | Канальная ветка | Заполняет или подтверждает данные способа | Канальные данные готовы к подтверждению |
| 5 | `UC-RET-05` | Проверяет сводку и подтверждает оформление | Заявка на возврат создана |

Переход между экранами последовательный. Пользователь не может перейти к причинам, пока не выбрал товары; не может перейти к оформлению, пока не указал причину и подпричину для каждого товара; не может подтвердить возврат, пока не заполнил обязательные данные экрана оформления. Банковские реквизиты входят в обязательные данные только тогда, когда система определила необходимость их заполнения.

## 5. UC-RET-01 — Выбор товаров и количества

**Цель:** определить состав возврата.

### Основной сценарий

1. Система показывает товары заказа и доступное к возврату количество каждого товара.
2. Пользователь выбирает один или несколько товаров.
3. Пользователь указывает количество по каждому выбранному товару.
4. Пользователь может выбрать все товары, имеющие доступное количество.
5. Система сохраняет выбранный состав и разрешает переход к причинам.

### Альтернативы и проверки

- Если доступное количество товара равно нулю, система не позволяет выбрать этот товар.
- Если пользователь указывает количество больше доступного, система не принимает значение и показывает максимально доступное количество.
- Если не выбран ни один товар, переход к следующему шагу недоступен.
- При действии «Выбрать все» система выбирает только товары с доступным количеством и устанавливает для них доступное количество.

**Постусловие:** выбран минимум один товар и допустимое количество каждого товара.

---

## 6. UC-RET-02 — Выбор причины и подпричины

**Цель:** получить причину возврата отдельно для каждого выбранного товара.

### Основной сценарий

1. Система последовательно показывает выбранные товары.
2. Для каждого товара пользователь выбирает причину возврата.
3. Система показывает подпричины, относящиеся к выбранной причине.
4. Пользователь выбирает подпричину.
5. После заполнения данных по всем товарам система разрешает переход к оформлению.

### Альтернативы и проверки

- При изменении причины ранее выбранная подпричина очищается, если она не относится к новой причине.
- Если причина или подпричина не указана хотя бы для одного товара, переход к следующему шагу недоступен.
- Ограничения причин для невозвратных категорий применяются по `BR-COM-14`; причина «Брак» должна оставаться доступной.

**Постусловие:** для каждого товара зафиксированы причина и подпричина.

## 7. UC-RET-03 — Определение и выбор города

**Цель:** определить город, относительно которого формируется список способов возврата.

### Основной сценарий: город определён

1. Система предзаполняет город данными из заказа.
2. Пользователь подтверждает город либо выбирает действие изменения.
3. Система определяет доступные способы возврата для выбранного города и данных заказа.

### Альтернативный сценарий: город не определён

1. Система открывает экран выбора города.
2. Пользователь может:
   - ввести наименование города и выбрать результат поиска;
   - выбрать город из списка;
   - выбрать или изменить страну, если страна не определена либо определена неверно.
3. После выбора города система обновляет список доступных способов возврата.

### Альтернативный сценарий: изменение предзаполненного города

1. Пользователь открывает экран выбора города.
2. Пользователь выбирает другой город теми же способами: поиск или список.
3. Система очищает адрес или пункт возврата, относящийся к предыдущему городу.
4. Система повторно определяет доступные способы.

### Проверки

- Без выбранного города переход к выбору способа недоступен.
- Если для города нет способов возврата, система сообщает о недоступности и предлагает выбрать другой город; пустой список не отображается.

**Постусловие:** выбран город, для него получен непустой список доступных способов.

---

## 8. UC-RET-04 — Выбор способа возврата

**Цель:** выбрать доступный канал и заполнить его обязательные данные.

### Общие правила

1. Система показывает только способы, доступные для выбранного города и данных заказа.
2. Если способ получения заказа присутствует среди доступных способов возврата, система предвыбирает соответствующий способ:
   - Курьер → Курьер;
   - 5Post → 5Post;
   - СДЭК → СДЭК;
   - самовывоз из магазина → Магазин.
3. Предвыбор не ограничивает пользователя: до создания заявки он может выбрать другой доступный способ.
4. Адрес или пункт из заказа предзаполняется только при одновременном выполнении условий:
   - выбранный способ соответствует способу получения заказа;
   - выбранный город совпадает с городом адреса или пункта заказа;
   - адрес или пункт остаётся доступным для возврата.
5. Если пользователь выбрал другой город, адрес или пункт из заказа не предзаполняется.
6. При смене способа данные предыдущего способа не используются для создания заявки.

### Альтернатива: способ получения недоступен для возврата

Если соответствующий покупке способ отсутствует среди доступных, система не выполняет предвыбор и ожидает выбора пользователя.

## 9. UC-RET-04.1 — Возврат курьером

**Предусловие:** способ «Курьер» доступен для выбранного города.

### Основной сценарий

1. Система предзаполняет адрес из заказа, если заказ был получен курьером в выбранном городе.
2. Пользователь подтверждает адрес или изменяет его.
3. Если выбран другой город либо адрес заказа отсутствует, пользователь вводит новый адрес.
4. Система показывает доступные даты и интервалы приезда курьера.
5. Пользователь выбирает дату и интервал.

### Проверки

- Адрес должен относиться к выбранному городу.
- Без заполнения обязательных полей адреса, доступной даты и интервала подтверждение возврата недоступно.
- Если интервалы отсутствуют, система сообщает об этом и предлагает выбрать другой доступный способ.

**Канальные данные:** адрес забора, дата, временной интервал.

---

## 10. UC-RET-04.2 — Возврат через 5Post

**Предусловие:** 5Post доступен для выбранного города и данных заказа.

### Основной сценарий

1. Если заказ был получен через 5Post в выбранном городе и исходный пункт доступен для возврата, система предзаполняет постамат или кассу из заказа.
2. Пользователь подтверждает пункт либо выбирает другой доступный пункт на карте или в списке.
3. Если выбран другой город, пункт не предзаполняется; пользователь выбирает его самостоятельно.
4. Система показывает:
   - крайний срок передачи «Вернуть до [Дата]»;
   - выбранные товары и количество;
   - итоговую сумму к возврату;
   - баллы к возврату.

### Проверки

- Без выбранного доступного пункта подтверждение возврата недоступно.
- Пользователь может изменить пункт до создания заявки.
- Конкретная продолжительность срока передачи и правило расчёта даты остаются открытыми (`5POST-OQ-11`).

**Канальные данные:** идентификатор и адрес пункта 5Post.

---

## 11. UC-RET-04.3 — Возврат через СДЭК

**Предусловие:** СДЭК доступен для выбранного города и данных заказа.

### Основной сценарий

1. Если заказ был получен через СДЭК в выбранном городе и исходная точка доступна для возврата, система предзаполняет ПВЗ или офис из заказа.
2. Пользователь подтверждает точку либо выбирает другую доступную точку на карте или в списке.
3. Если выбран другой город, точка не предзаполняется; пользователь выбирает её самостоятельно.
4. Система показывает:
   - крайний срок передачи «Вернуть до [Дата]»;
   - выбранные товары и количество;
   - итоговую сумму к возврату;
   - баллы к возврату.

### Проверки

- Без выбранной доступной точки подтверждение возврата недоступно.
- Пользователь может изменить точку до создания заявки.
- Конкретная продолжительность срока передачи и правило расчёта даты остаются открытыми (`CDEK-OQ-07`).

**Канальные данные:** идентификатор, тип и адрес точки СДЭК.

## 12. UC-RET-04.4 — Возврат в магазин

**Предусловие:** способ «Магазин» доступен для выбранного города и данных заказа.

### Основной сценарий

1. Если заказ был получен самовывозом из магазина в выбранном городе и исходный магазин доступен для возврата, система предзаполняет его.
2. Пользователь подтверждает магазин либо выбирает другой доступный магазин.
3. Если выбран другой город, магазин не предзаполняется; пользователь выбирает его самостоятельно.
4. Система показывает:
   - крайний срок передачи «Вернуть до [Дата]»;
   - выбранные товары и количество;
   - итоговую сумму к возврату;
   - баллы к возврату.

### Проверки

- Без выбранного доступного магазина подтверждение возврата недоступно.
- Пользователь может изменить магазин до создания заявки.
- Канальный бизнес-процесс магазина и правило расчёта даты требуют согласования (`COM-OQ-24`).

**Канальные данные:** идентификатор и адрес магазина.

## 13. UC-RET-04.5 — Возврат через Почту России

**Предусловие:** выбран город Калининград.

### Основной сценарий

1. Система показывает способ «Почта России» только для Калининграда.
2. Пользователь выбирает способ «Почта России».
3. Система не предзаполняет и не требует выбирать конкретное отделение.
4. Система сообщает, что пользователь может самостоятельно передать возврат в любое подходящее отделение Почты России.
5. Система показывает:
   - крайний срок передачи «Вернуть до [Дата]»;
   - выбранные товары и количество;
   - итоговую сумму к возврату;
   - баллы к возврату.

### Проверки

- Для города, отличного от Калининграда, способ не отображается.
- Вызов курьера в рамках этого способа недоступен.
- Операционный процесс, срок передачи и способ подтверждения сдачи требуют согласования.

**Канальные данные:** способ «Почта России»; конкретный адрес отделения в заявке не фиксируется.

## 14. UC-RET-05 — Проверка и создание заявки

**Цель:** проверить данные и создать возврат.

### Основной сценарий

1. Система показывает сводку:
   - товары и количество;
   - причины и подпричины;
   - выбранный город;
   - способ возврата и его канальные данные;
   - крайнюю дату передачи, если она применяется;
   - итоговую сумму к возврату;
   - баллы к возврату.
2. Пользователь проверяет данные и подтверждает оформление.
3. Система повторно проверяет срок создания заявки, доступное количество товаров, доступность способа и выбранной точки/интервала.
4. Если проверки пройдены, система создаёт заявку на возврат.
5. Система показывает подтверждение и данные созданного возврата.

### Альтернативные сценарии

- Действие подтверждения недоступно, пока не выбраны город, способ возврата и обязательные данные выбранного способа.
- Если банковские реквизиты требуются по способу оплаты, действие подтверждения недоступно до заполнения их обязательных полей.
- Если банковские реквизиты не требуются, их отсутствие не блокирует подтверждение.
- Если товар, количество, способ, пункт либо интервал стали недоступны, система не создаёт заявку и предлагает актуализировать выбор.
- При ошибке создания система не показывает возврат как созданный и предлагает повторить подтверждение; правило сохранения введённых данных зависит от технической реализации.

**Постусловие:** создана одна заявка с зафиксированными данными либо пользователь получил проверяемую причину отказа в создании.
