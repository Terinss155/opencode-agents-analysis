# Use Case: Оформление возврата товара

## 1. Назначение и границы

Документ описывает варианты использования для оформления возврата авторизованным пользователем на сайте или в мобильном приложении: от выбора товаров до создания заявки и первого просмотра клиентских идентификаторов СДЭК или 5Post.

**Вне границ:** физическая передача возврата, изменение или отмена созданной заявки, автоотмена, транспортировка, экспертиза и перечисление денежных средств. Эти процессы требуют связанных Use Case жизненного цикла возврата.

## UC-RET-01. Выбрать товары для возврата

| Поле | Содержание |
|---|---|
| **Область действия** | Сайт и мобильное приложение, оформление возврата из карточки заказа |
| **Уровень** | Подпроцесс |
| **Цель** | Выбрать один, несколько или все доступные товары и указать возвращаемое количество |
| **Основное действующее лицо** | Авторизованный пользователь |
| **Участники** | Отсутствуют |
| **Предусловие** | Карточка принадлежащего пользователю заказа открыта; данные заказа загружены; заказ содержит хотя бы один товар с доступным для возврата количеством |
| **Гарантии успеха / Результат** | Минимум один товар и его допустимое количество зафиксированы во временном клиентском состоянии формы; данные в БД не сохранены; переход к причинам доступен |
| **Триггер** | Пользователь нажимает «Оформить возврат» в карточке заказа |

### Описание

1. Пользователь нажимает «Оформить возврат».
2. Система открывает экран выбора товаров, используя данные заказа, ранее загруженные для отображения карточки заказа. Дополнительный запрос для получения товаров не выполняется.
3. Система определяет по загруженным данным товары, доступные для возврата, и доступное количество каждого товара.
4. Система отображает товары, доступные для возврата, и элементы управления их количеством.
5. Пользователь выбирает товар.
6. Пользователь нажимает «+» для увеличения возвращаемого количества выбранного товара.
7. Система увеличивает возвращаемое количество товара на одну единицу, если текущее количество меньше доступного для возврата количества.
8. Когда возвращаемое количество достигает доступного количества, система делает кнопку «+» неактивной и не допускает дальнейшего увеличения.
9. Система фиксирует выбранный товар и его количество во временном клиентском состоянии формы оформления возврата. Заявка на возврат не создаётся, данные в БД не сохраняются.
10. Система предоставляет действие перехода к причинам.

### Расширения

**5.1. Пользователь выбирает все товары**

5.1.1. Пользователь выбирает действие «Выбрать все».
5.1.2. Система выбирает все товары с доступным для возврата количеством.
5.1.3. Пользователь при необходимости изменяет количество каждого товара с помощью элементов управления количеством.
5.1.4. Система применяет к каждому товару ограничение, указанное в шагах 7–8.
5.1.5. Система фиксирует выбранные товары и их количество во временном клиентском состоянии формы.
5.1.6. Сценарий продолжается с шага 10.

**5.2. Пользователь выбирает дополнительный товар**

5.2.1. Пользователь выбирает следующий товар.
5.2.2. Сценарий продолжается с шага 6.

**10.1. Не выбран ни один товар**

10.1.1. Система не предоставляет действие перехода к экрану причин.
10.1.2. Пользователь выбирает минимум один товар.
10.1.3. Сценарий продолжается с шага 6.

## UC-RET-02. Указать причины возврата

| Поле | Содержание |
|---|---|
| **Область действия** | Сайт и мобильное приложение, экран причин возврата |
| **Уровень** | Подпроцесс |
| **Цель** | Указать причину и подпричину для каждого товара, выбранного для возврата |
| **Основное действующее лицо** | Авторизованный пользователь |
| **Участники** | Отсутствуют |
| **Предусловие** | В `UC-RET-01` во временном клиентском состоянии формы зафиксирован минимум один товар с допустимым количеством |
| **Гарантии успеха / Результат** | Для каждого товара сохранены причина и подпричина; переход к оформлению доступен |
| **Триггер** | Пользователь нажимает «Продолжить» после выбора товаров |

### Описание

1. Пользователь нажимает «Продолжить» на экране выбора товаров.
2. Система получает доступные причины возврата.
   API: уточняется.
3. Система отображает первый выбранный товар и доступные причины.
4. Пользователь выбирает причину.
5. Система получает подпричины для выбранной причины.
   API: уточняется.
6. Система отображает доступные подпричины.
7. Пользователь выбирает подпричину.
8. Система связывает выбранные причину и подпричину с товаром в форме оформления.
9. Система проверяет наличие причины и подпричины у каждого товара.
10. Система фиксирует причины и подпричины для всех выбранных товаров в черновике оформления.
11. Система предоставляет действие перехода к оформлению возврата.

### Расширения

**5.1. Подпричины не получены**

5.1.1. Система не позволяет завершить заполнение причины для товара.
5.1.2. Система сообщает, что список подпричин недоступен.
5.1.3. Система предоставляет возможность повторить получение данных.
5.1.4. Пользователь повторяет получение подпричин.
5.1.5. Сценарий продолжается с шага 5.

**8.1. Для возврата выбран ещё один товар**

8.1.1. Система отображает следующий товар.
8.1.2. Сценарий продолжается с шага 4.

**9.1. Причина или подпричина отсутствует**

9.1.1. Система не предоставляет действие перехода к оформлению возврата.
9.1.2. Система указывает товар с незаполненными данными.
9.1.3. Пользователь заполняет причину и подпричину.
9.1.4. Сценарий продолжается с шага 9.

**10.1. Причины и подпричины не сохранены**

10.1.1. Система сообщает, что данные не сохранены.
10.1.2. Система предоставляет возможность повторить подтверждение причин.
10.1.3. Пользователь повторно подтверждает заполненные причины.
10.1.4. Сценарий продолжается с шага 9.

- Допускается ли возврат товара из невозвратной категории по причине «Брак» и какие причины следует показывать в этом случае?

|---|---|

| **Уровень** | Подпроцесс |
| **Цель** | Подтвердить город из заказа или выбрать другой город для определения доступных способов возврата |
| **Основное действующее лицо** | Авторизованный пользователь |
| **Участники** | Отсутствуют |
| **Предусловие** | Для каждого выбранного товара сохранены причина и подпричина |

### Описание

1. Пользователь нажимает «Продолжить» на экране причин.
2. Система получает город из данных заказа.
   API: уточняется.
3. Система отображает предзаполненный город.
4. Пользователь подтверждает город.
5. Система сохраняет выбранный город в черновике оформления.

2.1.3. Пользователь выбирает или изменяет страну.
2.1.4. Пользователь вводит наименование города либо открывает список городов.
2.1.5. Система отображает найденные или доступные города.
2.1.6. Пользователь выбирает город.
2.1.7. Система сохраняет город в черновике оформления.
2.1.8. Сценарий продолжается с шага 6.

**4.1. Пользователь изменяет предзаполненный город**

4.1.1. Пользователь выбирает действие изменения города.
4.1.2. Система открывает экран выбора города.
4.1.3. Пользователь выбирает другой город.
4.1.4. Система сохраняет новый город.
4.1.5. Система очищает адрес или пункт, относящийся к предыдущему городу.
4.1.6. Сценарий продолжается с шага 6.

**5.1. Город не сохранён**

5.1.1. Система сообщает, что город не сохранён.
5.1.2. Система предоставляет возможность повторить сохранение.
5.1.3. Пользователь повторно подтверждает город.
5.1.4. Сценарий продолжается с шага 5.

**7.1. Не удалось определить доступные способы**

7.1.1. Система сообщает, что способы временно недоступны.
7.1.2. Система предоставляет возможность повторить получение данных.
7.1.3. Пользователь повторяет действие.
7.1.4. Сценарий продолжается с шага 7.

## UC-RET-04. Выбрать способ возврата

| Поле | Содержание |
|---|---|
| **Область действия** | Сайт и мобильное приложение, экран оформления возврата |
| **Уровень** | Подпроцесс |
| **Цель** | Выбрать один из способов возврата, доступных для города и места покупки |
| **Основное действующее лицо** | Авторизованный пользователь |
| **Участники** | Отсутствуют |
| **Предусловие** | Город сохранён; система сформировала непустой список доступных способов |
| **Гарантии успеха / Результат** | Способ сохранён в черновике; открыта форма данных выбранного способа |
| **Триггер** | Пользователь переходит к выбору способа после сохранения города |

### Описание

1. Пользователь переходит к выбору способа возврата.
2. Система отображает список доступных способов возврата.
3. Система предвыбирает способ, соответствующий способу получения заказа, если он доступен.
4. Пользователь подтверждает предвыбранный способ.
5. Система проверяет доступность способа для города и данных заказа.
   API: уточняется.
6. Система сохраняет выбранный способ в черновике оформления.
7. Система запускает соответствующий канальный Use Case.

Шаг выбора в канальном Use Case детализирует действие шага 4 и не является повторным выбором пользователя.

### Бизнес-правила доступности

| Место покупки | Базовый набор каналов возврата |
|---|---|
| Розничный магазин (офлайн) | Только розничный магазин |
| Аутлет | Только аутлет |
| «Цветной» | Только «Цветной» |
| Онлайн-магазин | Розничный магазин, Курьер, 5Post (касса и постамат), СДЭК (ПВЗ и офис), Почта России |

Базовый набор фильтруется по выбранному городу и данным заказа. Почта России доступна только для Калининграда.

Если способ получения заказа входит в итоговый список, система предвыбирает соответствующий способ: Курьер → Курьер, 5Post → 5Post, СДЭК → СДЭК, самовывоз из магазина → Магазин.

### Расширения

**3.1. Способ получения заказа недоступен для возврата**

3.1.1. Система не предвыбирает недоступный способ.
3.1.2. Пользователь выбирает способ из доступного списка.
3.1.3. Сценарий продолжается с шага 5.

**4.1. Пользователь выбирает другой способ**

4.1.1. Пользователь выбирает другой доступный способ.
4.1.2. Система очищает данные предыдущего способа из черновика.
4.1.3. Сценарий продолжается с шага 5.

**5.1. Способ стал недоступен**

5.1.1. Система не сохраняет способ.
5.1.2. Система обновляет список доступных способов.
5.1.3. Система предлагает пользователю повторить выбор.
5.1.4. Пользователь выбирает способ.
5.1.5. Сценарий продолжается с шага 5.

**6.1. Способ не сохранён**

6.1.1. Система сообщает, что способ не сохранён.
6.1.2. Система предоставляет возможность повторить сохранение.
6.1.3. Пользователь повторно подтверждает способ.
6.1.4. Сценарий продолжается с шага 5.

### Открытые вопросы

## UC-RET-04.1. Указать адрес и время возврата курьером

| Поле | Содержание |
|---|---|
| **Область действия** | Сайт и мобильное приложение, оформление курьерского возврата |
| **Уровень** | Подпроцесс |
| **Цель** | Указать адрес, дату и интервал приезда курьера |
| **Основное действующее лицо** | Авторизованный пользователь |
| **Участники** | Курьерская служба |
| **Предусловие** | Товар приобретён онлайн; способ «Курьер» доступен в выбранном городе |
| **Гарантии успеха / Результат** | Адрес, дата и интервал сохранены в черновике; пользователь возвращён на экран оформления |
| **Триггер** | Пользователь выбирает способ «Курьер» |

### Описание

1. Пользователь выбирает способ «Курьер».
2. Система проверяет, совпадает ли город заказа с выбранным городом возврата.
3. Система предзаполняет адрес заказа, если заказ был получен курьером в том же городе.
4. Система отображает форму адреса.
5. Пользователь подтверждает адрес.
6. Система проверяет заполнение обязательных полей адреса.
7. Система получает доступные даты и интервалы.
   API: уточняется.
8. Система отображает доступные даты и интервалы.
9. Пользователь выбирает дату.
10. Пользователь выбирает интервал.
11. Система повторно проверяет доступность выбранного интервала.
12. Система сохраняет адрес, дату и интервал в черновике оформления.
13. Система возвращает пользователя на экран оформления.

### Расширения

**3.1. Адрес не предзаполняется**

3.1.1. Система оставляет форму адреса незаполненной, если город изменён, заказ получен другим способом или адрес отсутствует.
3.1.2. Пользователь вводит новый адрес.
3.1.3. Сценарий продолжается с шага 6.

**5.1. Пользователь изменяет предзаполненный адрес**

5.1.1. Пользователь выбирает действие изменения адреса.
5.1.2. Пользователь вводит новый адрес в выбранном городе.
5.1.3. Сценарий продолжается с шага 6.

**6.1. Обязательные поля адреса не заполнены**

6.1.1. Система не получает даты и интервалы.
6.1.2. Система указывает незаполненные поля.
6.1.3. Пользователь заполняет обязательные поля.
6.1.4. Сценарий продолжается с шага 6.

**7.1. Даты или интервалы отсутствуют**

7.1.1. Система сообщает об отсутствии доступных вариантов.
7.1.2. Система предоставляет действие возврата к выбору способа.

## UC-RET-06. Просмотреть клиентские идентификаторы возврата
