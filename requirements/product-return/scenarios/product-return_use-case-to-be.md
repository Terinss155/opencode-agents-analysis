# Use Case — Оформление возврата товара (TO-BE)

**Статус:** DRAFT
**Область:** сайт и мобильное приложение, оформление возврата авторизованным пользователем.
**Границы:** от входа в форму возврата из карточки заказа до создания заявки (`UC-RET-01…05`).
**Вне границ:** приёмка, экспертиза, возврат денег и баллов, транспортировка — отдельные Use Case. Изменение / отмена / автоотмена созданной заявки — отдельные Use Case (US-108…US-110). **Просмотр карточки созданного возврата и клиентских идентификаторов** — это экран восприятия, описан отдельно как спецификация экрана: `screens/product-return_screen-spec.md` (`SCR-RET-01`).

## User Story

> **Как** пользователь, совершивший покупку,
> **Я хочу** оформить возврат одного, нескольких или всех доступных товаров из заказа удобным доступным способом,
> **Чтобы** вернуть неподошедшие товары и получить за них денежные средства и использованные баллы в соответствии с условиями возврата.

## Условные обозначения

- **TO-BE** — целевое поведение.
- **Открытый вопрос** — решение бизнеса ещё не принято; без ответа шаг нельзя описать однозначно.
- **Не хватает** (в блоках «Параметры экрана») — параметр нужен целевому сценарию, а текущими ответами API он не отдаётся **и** в БД в готовом виде его нет.
- Эндпоинты в шагах — **текущие (AS-IS)**, приведены как источник параметров; для TO-BE подлежат подтверждению и расширению.
- Блок «Параметры экрана» — 4 колонки: имя параметра в ответе **мобильного приложения**, имя в ответе **сайта**, **поле в БД** (`таблица.столбец`, либо «вычисляется» / «внешний гео-сервис»), **описание**. В колонках имён параметров каждая ячейка: `имя параметра` — `запрос, в ответе которого он приходит`.
- Строки вида «в БД есть, в API не отдаётся» показывают данные, которые для целевого сценария можно взять из **существующих** колонок — нужно лишь добавить их в ответ метода.

- **Мобильное приложение:** почти все данные для всего процесса приходят **одним** запросом карточки заказа `GET /mobile/orders/{order_id}` (позиции, суммы, баллы, признак реквизитов, получатель). Отдельно — справочник причин (`GET /mobile/v2/orders/return-reasons`).

## UC-RET-01. Выбрать товары для возврата

| Поле | Содержание |
|---|---|
| **Область действия** | Сайт и мобильное приложение, оформление возврата из карточки заказа |
| **Цель** | Выбрать один, несколько или все доступные товары и указать возвращаемое количество |
| **Основное действующее лицо** | Авторизованный пользователь |
| **Участники** | Отсутствуют |
| **Предусловие** | Карточка принадлежащего пользователю заказа открыта; данные заказа загружены; заказ содержит хотя бы один товар, доступный для возврата (срок возврата не истёк; товар не возвращён ранее, не является подарком) |
| **Гарантии успеха / Результат** | Минимум один товар и его возвращаемое количество зафиксированы в форме оформления возврата; данные в БД не сохранены; доступен переход к причинам |
| **Триггер** | Пользователь нажимает «Оформить возврат» в карточке заказа |

### Описание

1. Пользователь нажимает «Оформить возврат».
2. Система открывает экран выбора товаров.
   - **Мобильное приложение** использует данные карточки заказа, уже загруженные для её отображения; дополнительный запрос за товарами не выполняется.
   - **Сайт** получает состав товаров, доступных для возврата, и признак необходимости банковских реквизитов.
     `GET /orders/refund/get-positions`
3. Система определяет товары, доступные для возврата, и доступное для возврата количество каждого товара.
4. Система рассчитывает и отображает срок возврата: «Можно вернуть изделие до `<дата>`», где `<дата>` = дата доставки заказа клиенту плюс срок подачи заявления (14 дней — обычный клиент, 30 дней — F&F).
5. Система отображает товары, доступные для возврата, и элементы управления возвращаемым количеством.
6. Пользователь выбирает товар.
7. Пользователь увеличивает возвращаемое количество выбранного товара.
8. Система увеличивает возвращаемое количество на одну единицу, если текущее возвращаемое количество меньше доступного для возврата количества.
9. Когда возвращаемое количество достигает доступного, система делает увеличение недоступным.
10. Система фиксирует выбранный товар и его возвращаемое количество в форме оформления возврата. *Заявка не создаётся, данные в БД не сохраняются.*
11. Пользователь выбирает следующий товар, если требуется.
12. Система предоставляет действие перехода к причинам.

### Расширения

**12.1. Не выбран ни один товар**

12.1.1. Система не предоставляет действие перехода к причинам.
12.1.2. Пользователь выбирает минимум один товар.
12.1.3. Сценарий продолжается с шага 7.

### Открытые вопросы

- Как рассчитывается «доступное для возврата количество» по позиции при частично возвращённых ранее единицах?
- Как система определяет, что клиент относится к F&F (для срока 30 дней вместо 14)?
- Дата «Можно вернуть до …» считается от `cms_orders.end_date` (дата выполнения заказа, подтверждена 1С). Это поле клиенту **не отдаётся** — нужен расчётный параметр в ответе метода. Объект `expiration_date` (`start` = `created_at`, `end` = `delivery_date`) к сроку возврата **не относится**.
- Допускается ли возврат товара из невозвратной категории по причине «Брак»?

## UC-RET-02. Указать причины возврата

| Поле | Содержание |
|---|---|
| **Область действия** | Сайт и мобильное приложение, экран причин возврата |
| **Цель** | Указать причину и подпричину для каждого выбранного товара |
| **Основное действующее лицо** | Авторизованный пользователь |
| **Участники** | Отсутствуют |
| **Предусловие** | В `UC-RET-01` зафиксирован минимум один товар с возвращаемым количеством |
| **Гарантии успеха / Результат** | Для каждого выбранного товара сохранены причина и подпричина; доступен переход к оформлению возврата |
| **Триггер** | Пользователь нажимает «Продолжить» после выбора товаров |

### Описание

1. Пользователь нажимает «Продолжить» на экране выбора товаров.
2. Система получает доступные причины и подпричины возврата.
   - Сайт: справочник уже получен вместе с товарами в `UC-RET-01`.
   - Мобильное приложение: система получает справочник причин.
     GET /mobile/v2/orders/return-reasons
3. Система отображает первый выбранный товар и доступные причины.
4. Пользователь выбирает причину.
5. Система отображает подпричины выбранной причины.
6. Пользователь выбирает подпричину.
7. Система связывает выбранные причину и подпричину с товаром в форме оформления.
8. Система проверяет наличие причины и подпричины у каждого выбранного товара.
9. Система фиксирует причины и подпричины для всех выбранных товаров в форме. Данные в БД не сохраняются.
10. Система предоставляет действие перехода к оформлению возврата.

### Расширения

**5.1. Подпричины недоступны**

5.1.1. Система не позволяет завершить заполнение причины для товара.
5.1.2. Система сообщает, что список подпричин недоступен, и предоставляет повтор.
5.1.3. Пользователь повторяет получение подпричин.
5.1.4. Сценарий продолжается с шага 5.

**7.1. Для возврата выбран ещё один товар**

7.1.1. Система отображает следующий выбранный товар.
7.1.2. Сценарий продолжается с шага 4.

**8.1. Причина или подпричина отсутствует у товара**

8.1.1. Система не предоставляет действие перехода к оформлению возврата.
8.1.2. Система указывает товар с незаполненными данными.
8.1.3. Пользователь заполняет причину и подпричину.
8.1.4. Сценарий продолжается с шага 8.

### Открытые вопросы

- Требуется подтвердить окончательную матрицу доступности причин и подпричин по категориям товаров.
- В текущей реализации иерархия ровно «группа причин → причина» (два уровня): справочник плоский, одинаковый для всех позиций, привязки к категории нет. Соответствует ли это целевой модели «причина → подпричина»?
- Должны ли на позицию сохраняться оба уровня (причина и подпричина) или только нижний уровень?
- Какое сообщение и действие показывать, если у товара нет ни одной доступной причины?

### Параметры экрана

## UC-RET-04. Выбрать способ возврата

| Поле | Содержание |
|---|---|
| **Область действия** | Сайт и мобильное приложение, экран оформления возврата |
| **Цель** | Выбрать один из способов возврата, доступных для города и места покупки |
| **Основное действующее лицо** | Авторизованный пользователь |
| **Участники** | Отсутствуют |
| **Предусловие** | Город сохранён; система сформировала непустой список доступных способов |
| **Гарантии успеха / Результат** | Способ сохранён в форме; открыта канальная форма выбранного способа |
| **Триггер** | Пользователь переходит к выбору способа после сохранения города |

### Описание

1. Пользователь переходит к выбору способа возврата.
2. Система отображает список доступных способов возврата с описаниями и доступными датами.
3. Система предвыбирает способ, соответствующий способу получения заказа, если он доступен.
4. Пользователь подтверждает предвыбранный способ.
5. Система проверяет доступность способа для города и данных заказа.
6. Система сохраняет выбранный способ в форме оформления.
7. Система запускает канальный Use Case (`UC-RET-04.1…04.5`).

### Бизнес-правила доступности

| Место покупки | Базовый набор способов возврата |
|---|---|
| Розничный магазин (офлайн) | Только розничный магазин |
| Аутлет | Только аутлет |
| «Цветной» | Только «Цветной» |
| Онлайн-магазин | Розничный магазин, Курьер, 5Post (касса и постамат), СДЭК (ПВЗ и офис), Почта России |

Базовый набор фильтруется по выбранному городу. Почта России доступна только для Калининграда. Если способ получения заказа входит в итоговый список, система его предвыбирает.

### Бизнес-правила выбора даты передачи

| Способ возврата | Выбор даты при оформлении | Срок передачи товара клиентом |
|---|---|---|
| Курьер | Пользователь выбирает **дату и интервал** приезда курьера (`UC-RET-04.1`) | Действует выбранная дата и интервал |
| СДЭК ПВЗ | Дата **не выбирается** | Отдельный срок после создания заявки (норматив СДЭК — уточняется, «5 дней или меньше») |
| 5Post | Дата **не выбирается** | Отдельный срок после создания заявки (норматив 5Post — уточняется) |
| Розничный магазин / аутлет / «Цветной» | Дата **не выбирается** | **14 дней** после создания заявки |
| Почта России (Калининград) | Дата **не выбирается** | **14 дней** после создания заявки |

Для способов без выбора даты система после создания заявки устанавливает конечный срок передачи «Сдать возврат до `<дата>`», явно показывает его клиенту вместе с предупреждением об автоотмене и по его истечении автоматически отменяет заявку (`UC-RET-05`).

### Расширения

**3.1. Способ получения заказа недоступен для возврата**

3.1.1. Система не предвыбирает недоступный способ.
3.1.2. Пользователь выбирает способ из доступного списка.
3.1.3. Сценарий продолжается с шага 5.

**4.1. Пользователь выбирает другой способ**

4.1.1. Пользователь выбирает другой доступный способ.
4.1.2. Система очищает канальные данные предыдущего способа.
4.1.3. Сценарий продолжается с шага 5.

**5.1. Способ стал недоступен**

5.1.1. Система не сохраняет способ.
5.1.2. Система обновляет список доступных способов и предлагает повторить выбор.
5.1.3. Пользователь выбирает способ.
5.1.4. Сценарий продолжается с шага 5.

## UC-RET-04.1. Указать адрес и время возврата курьером

| Поле | Содержание |
|---|---|
| **Область действия** | Сайт и мобильное приложение, оформление курьерского возврата |
| **Цель** | Указать адрес, дату и интервал приезда курьера |
| **Основное действующее лицо** | Авторизованный пользователь |
| **Участники** | Курьерская служба |
| **Предусловие** | Товар приобретён онлайн; способ «Курьер» доступен в выбранном городе |
| **Гарантии успеха / Результат** | Адрес, дата и интервал сохранены в форме; пользователь возвращён на экран оформления |
| **Триггер** | Пользователь выбирает способ «Курьер» |

### Описание

1. Пользователь выбирает способ «Курьер».
2. Система предзаполняет адрес заказа, если заказ получен курьером в том же городе.
3. Система отображает форму адреса.
4. Пользователь подтверждает или изменяет адрес.
   - При вводе улицы и дома система получает адресные подсказки.
     GET /api/v1/delivery/geo/countries/{countryIso}/addresses (сайт)
     GET /api/v1/geo/countries/{country_iso_code}/addresses (мобильное приложение)
   - По выбранному дому система получает почтовый индекс.
     GET /api/v1/delivery/geo/countries/{countryIso}/addresses/{geo_id}/details (сайт)
5. Система проверяет заполнение обязательных полей адреса.
6. Система отображает доступные даты и интервалы приезда курьера. Количество доступных дней **одинаковое** для всех клиентов и не зависит от того, в какой день срока подачи заявления оформляется возврат.
7. Пользователь выбирает дату.
8. Пользователь выбирает интервал.
9. Система повторно проверяет доступность выбранного интервала.
10. Система сохраняет адрес, дату и интервал в форме оформления.
11. Система возвращает пользователя на экран оформления.

### Расширения

**2.1. Адрес не предзаполняется**

2.1.1. Система оставляет форму адреса незаполненной, если город изменён, заказ получен другим способом или адрес отсутствует.
2.1.2. Пользователь вводит адрес.
2.1.3. Сценарий продолжается с шага 5.

**5.1. Обязательные поля адреса не заполнены**

5.1.1. Система не показывает даты и интервалы.
5.1.2. Система указывает незаполненные поля.
5.1.3. Пользователь заполняет поля.
5.1.4. Сценарий продолжается с шага 5.

## UC-RET-04.6. Указать банковские реквизиты

| Поле | Содержание |
|---|---|
| **Область действия** | Сайт и мобильное приложение, оформление возврата денежных средств |
| **Цель** | Указать реквизиты для возврата денег за заказ, оплаченный курьеру при получении (наличными или картой) |
| **Основное действующее лицо** | Авторизованный пользователь |
| **Участники** | Отсутствуют |
| **Предусловие** | Способ оплаты заказа — «наличными курьеру» (`CASH_COURIER`) или «картой курьеру» (`CASHLESS_COURIER`); товары, причины, город, способ и обязательные канальные данные заполнены |
| **Гарантии успеха / Результат** | Обязательные реквизиты сохранены и показаны на экране оформления |
| **Триггер** | Пользователь выбирает действие заполнения банковских реквизитов |

### Описание

1. Пользователь выбирает действие заполнения банковских реквизитов.
2. Система открывает форму банковских реквизитов.
3. Пользователь вводит фамилию, имя и **отчество** держателя счёта, БИК банка получателя, номер лицевого счёта физического лица. **Отчество обязательно** (нужно для идентификации получателя платежа банком).
4. Пользователь нажимает «Продолжить».
5. Система проверяет заполнение и формат обязательных полей.
6. Система определяет тип лицевого счёта по началу его номера:
   - счёт начинается с `40817810…` (обычный лицевой счёт) — номер банковской карты или договора **не требуется**;
   - счёт начинается с `30232810…` (кредитный счёт) — система **требует** номер банковской карты **или** номер договора, иначе банк отклонит платёж.
7. Система сохраняет реквизиты.
   - Сайт: реквизиты сохраняются отдельным запросом.
     POST /user/cabinet/return-item/ajax/check-bank-details
   - Мобильное приложение: реквизиты передаются в теле запроса создания возврата (`UC-RET-05`).
8. Система возвращает пользователя на экран оформления и отображает сохранённые реквизиты.

### Расширения

**2.1. Пользователь отказывается от заполнения**

2.1.1. Пользователь закрывает форму без сохранения.
2.1.2. Система не предоставляет подтверждение возврата до заполнения реквизитов.
2.1.3. Сценарий завершается.

**5.1. Обязательное поле не заполнено или не проходит формат**

5.1.1. Система не сохраняет реквизиты и указывает поле.
5.1.2. Пользователь исправляет поле.
5.1.3. Сценарий продолжается с шага 4.

**6.1. Кредитный лицевой счёт (`30232810…`), номер карты и договора не заполнены**

6.1.1. Система не сохраняет реквизиты.
6.1.2. Система указывает, что нужно заполнить номер банковской карты или номер договора.
6.1.3. Пользователь заполняет одно из полей.
6.1.4. Сценарий продолжается с шага 7.

### Ограничения

**Два типа курьерской доставки — разное поведение по реквизитам:**

| Тип доставки заказа | Оплата | Примерка / частичный выкуп | Реквизиты при возврате |
|---|---|---|---|
| Курьер обычный (`DeliveryTk::TYPE_COURIER`) | **Только онлайн** | Нет | **Форма не показывается.** Возврат исходным способом оплаты + текст-подсказка про «Дружбу» |
| Курьер с примеркой (`DeliveryTk::TYPE_COURIER_FITTING`) | Курьеру при получении: наличными (`CASH_COURIER`) или картой (`CASHLESS_COURIER`) | Да | **Форма показывается** — способ расчёта при получении системе неизвестен |

- **Единый признак:** форма реквизитов открывается тогда и только тогда, когда `cms_orders.payment_method ∈ {CASH_COURIER (3), CASHLESS_COURIER (5)}` (`OrderHelper::isCourierPayment()`). Тип доставки «с примеркой» коррелирует, но каноничный триггер — способ оплаты.
- **При любом другом способе оплаты** (онлайн, BNPL и пр.) клиент **не может** ввести или изменить реквизиты; деньги возвращаются исходным способом. На экране оформления в блоке «Банковские реквизиты» система показывает поясняющий текст: деньги вернутся тем же способом, которым была оплата; если нужен перевод по другим реквизитам — обратиться в поддержку «Дружба».
- Система **не запрашивает** CVV/CVC и паспортные данные.
- До создания заявки пользователь может изменить введённые реквизиты; после создания — изменение только через поддержку или отмена и оформление заново (`RET-BR-05`).

### Открытые вопросы

- **Разночтение AS-IS между платформами:** веб показывает форму для **всех** не-онлайн способов (`need_bank_details = !in_array(payment_method, ALL_ONLINE_PAYMENT_METHODS)`), мобилка — только для оплаты курьеру (`is_bank_data_required = isCourierPayment()`, типы `3`, `5`). По уточнению заказчика верно поведение **мобилки**: веб-логику сузить до `isCourierPayment()`.
- Точная формулировка текста-подсказки про «Дружбу» и место его показа (блок «Банковские реквизиты» / отдельная плашка).
- Как обрабатывается лицевой счёт, начинающийся **не** с `30232810…` и **не** с `40817810…`?
- **ИНН банка** и **название банка** в подтверждённый набор Марии не вошли (только ФИО + БИК + счёт + карта/договор). Оставляем ли эти поля в форме, или определяем банк по БИК автоматически?
- Проверки формата и контрольных значений (ФИО, БИК, счёт, карта, договор). В текущей реализации — только длина (БИК 9, ИНН банка 10), наличие цифр; без контрольных сумм.
- В мобильном приложении номер карты в БД подменяется номером счёта — подтвердить целевое поведение.
- Электронное заявление: если введённые реквизиты входят в бланк заявления и изменяются — нужен зафиксированный пример шаблона; изменения только через поддержку либо отмена + новая заявка.

## UC-RET-05. Подтвердить и создать возврат

| Поле | Содержание |
|---|---|
| **Область действия** | Сайт и мобильное приложение, подтверждение возврата |
| **Цель** | Проверить итоговые данные и создать заявку на возврат |
| **Основное действующее лицо** | Авторизованный пользователь |
| **Участники** | Курьерская служба / 5Post / СДЭК / розничный магазин / Почта России — в зависимости от выбранного способа |
| **Предусловие** | Товары, количества, причины, подпричины, город, способ, обязательные канальные данные и реквизиты (при необходимости) сохранены в форме |
| **Гарантии успеха / Результат** | Создана одна заявка с номером и начальным статусом; для способов без выбора даты установлен конечный срок передачи; сформировано электронное заявление; пользователь видит данные созданного возврата |
| **Триггер** | Пользователь нажимает «Продолжить» / «Подтвердить возврат» после заполнения данных оформления |

### Описание

1. Пользователь нажимает «Подтвердить возврат» на экране оформления.
2. Система проверяет заполнение обязательных данных.
3. Система отображает сводку: товары, количество, причины и подпричины, город, способ, канальные данные, итоговую сумму и баллы к возврату, способ возврата денег.
4. Пользователь проверяет сводку и подтверждает создание возврата.
5. Система повторно проверяет: не истёк ли срок подачи заявления (14 дней — обычный клиент, 30 дней — F&F, от даты доставки заказа); доступное количество товаров; доступность способа и выбранной точки / интервала.
6. Система сохраняет данные возврата в заказ.
   POST /api/orders/{order_id}/return-details (сайт)
   POST /mobile/orders/{order_id}/return-details (мобильное приложение)
7. Система создаёт заявку на возврат.
   POST /orders/refund/save-reason (сайт)
   POST /mobile/orders/return-positions (мобильное приложение)
8. Система присваивает заявке номер и устанавливает начальный статус.
9. Система определяет срок передачи товара:
   - **Курьер** — действует выбранная пользователем дата и интервал; отдельный конечный срок не устанавливается.
   - **СДЭК ПВЗ / 5Post / розничный магазин / Почта России** — система устанавливает конечный срок передачи «Сдать / отправить возврат до `<дата>`» (магазин и Почта России — 14 дней от создания заявки; 5Post и СДЭК ПВЗ — по нормативу транспортной компании) и правило автоотмены заявки при его нарушении.
10. Система формирует электронное заявление на возврат и предоставляет действие «Скачать заявление». Заявление не хранится — формируется по запросу из данных базы.
11. Система отображает карточку созданного возврата: номер, статус, товары, итоговую сумму и баллы, конечный срок передачи (для способов без выбора даты) с предупреждением об автоотмене, блок «Возврат средств», действие «Скачать заявление».

### Расширения

**2.1. Обязательные данные не заполнены**

2.1.1. Система не открывает сводку и указывает незаполненные данные.
2.1.2. Пользователь заполняет данные в соответствующем Use Case.
2.1.3. Сценарий продолжается с шага 1.

**4.1. Пользователь отказывается от подтверждения**

4.1.1. Система не создаёт заявку и открывает экран оформления.
4.1.2. Сценарий завершается.

**5.1. Срок создания заявки истёк**

5.1.1. Система не создаёт заявку и сообщает об истечении срока.
5.1.2. Система возвращает пользователя в карточку заказа.
5.1.3. Сценарий завершается.

**5.2. Доступное количество, способ или точка / интервал изменились**

5.2.1. Система не создаёт заявку и сообщает об изменении доступности.
5.2.2. Система возвращает пользователя к соответствующему шагу.
5.2.3. Сценарий завершается.

**7.1. Заявка не создана**

7.1.1. Система не показывает возврат как созданный и сообщает об ошибке.
7.1.2. Система оставляет пользователя на экране подтверждения и предоставляет повтор.
7.1.3. Пользователь повторно подтверждает создание возврата.
7.1.4. Сценарий продолжается с шага 5.

**Постусловия — автоотмена (обрабатывается отдельным процессом).**

- **Способы без выбора даты.** За 24 часа до окончания конечного срока передачи система уведомляет клиента о последнем дне. Если товар не передан / не отправлен до конца срока — на следующий день заявка автоматически отменяется. Дополнительного времени нет.
- **Курьер.** Если товар не передан курьеру в выбранную дату — заявка аннулируется. Пока общий срок подачи заявления (14 / 30 дней) не истёк, клиент оформляет **новую** заявку. Если срок истёк — возможность возврата исчерпана (решается через поддержку).
- Особый случай ПВЗ: если срок передачи (норматив ТК, короче общего) вышел, а общий срок подачи заявления ещё открыт — после автоотмены клиент может оформить заявку заново.
- При автоотмене электронное заявление сохраняется и получает статус аннулированного; при повторном оформлении формируется новое заявление, предыдущее сохраняется отдельно.
- **Изменение заявки после создания.** Самостоятельно клиент созданную заявку **не редактирует** — изменения вносятся только через поддержку либо отмена заявки и оформление новой.

### Бизнес-правила сроков (подтверждено)

| Срок | Значение | Отсчёт от |
|---|---|---|
| Подача заявления на возврат | 14 дней (обычный клиент) / 30 дней (F&F) | Дата доставки заказа клиенту (`cms_orders.end_date`) |
| Передача — розничный магазин, Почта России (Калининград) | 14 дней | Создание заявки |
| Передача — 5Post | Норматив 5Post (цифра не подтверждена) | Создание заявки |
| Передача — СДЭК ПВЗ | Норматив СДЭК, «5 дней или меньше» (цифра не подтверждена) | Создание заявки |
| Передача — курьер | Выбранная пользователем дата и интервал | — |
| Уведомление о последнем дне передачи | За 24 часа до конца срока | — |

Клиенту даётся одинаковое количество дней на передачу независимо от того, в какой день срока подачи заявления он оформил возврат.

### Открытые вопросы

- Конкретные сроки передачи для 5Post и СДЭК ПВЗ (норматив ТК) — цифры не названы.

- Отдельной сущности возврата и номера заявки нет — статус фиксируется в заказе (`cms_orders.status`). Подтвердить целевую модель заявки и статусную модель.

## Просмотр созданного возврата — вынесен в спецификацию экрана

Бывшие `UC-RET-06` (клиентские идентификаторы СДЭК / 5Post) и `UC-RET-07` (карточка созданного возврата) описывали **экран восприятия**: система не меняет состояние, линейного сценария нет. Переоформлены как **спецификация экрана** — `screens/product-return_screen-spec.md`, `SCR-RET-01. Карточка созданного возврата` (идентификаторы — в разделе «Правила отображения», блок 3).

Здесь остаётся только **смежное правило события «клиент передал товар»** (подтверждено, детали — в канальных процессах):

> Триггер «клиент выполнил свою часть» по каналам: курьер — товар принят курьером; СДЭК ПВЗ — принят в ПВЗ; 5Post — принят в постамате / ПВЗ; розничный магазин — принят сотрудником магазина; Почта России (Калининград) — приём отправления Почтой России (если технически отслеживается). Опираться на статусы транспортных компаний. Утрата / повреждение при доставке до склада — разбор аномалий на складе, решение через поддержку.

## Подтверждено (ответы Марии / Кати, 09.2026)

| Тема | Решение |
|---|---|
| Срок подачи заявления | 14 дней (обычный клиент) / 30 дней (F&F), от даты доставки заказа (`cms_orders.end_date`) |
| Выбор даты передачи | Курьер — выбирает дату и интервал; СДЭК ПВЗ, 5Post, магазин, Почта России — дату не выбирают |
| Срок передачи для способов без даты | Магазин и Почта России — 14 дней от создания заявки; 5Post и СДЭК ПВЗ — норматив ТК; доп. времени нет |
| Показ срока и автоотмена | Срок «Сдать / отправить до <дата>» показываем явно + предупреждение об автоотмене; уведомление за 24 ч; отмена на следующий день |
| Количество дней на передачу | Одинаковое для всех, независимо от дня оформления заявки (убирает AS-IS «+3 дня») |
| Пропуск даты курьером | Заявка аннулируется; при открытом общем сроке — оформляется новая заявка |
| Банковские реквизиты | Форма — **только при оплате курьеру** (`payment_method ∈ {CASH_COURIER, CASHLESS_COURIER}`, доставка «курьер с примеркой»); обычный курьер = только онлайн-оплата → форма не показывается. При отсутствии формы реквизиты не вводятся, деньги возвращаются исходным способом + текст-подсказка про «Дружбу». Обязательно: фамилия, имя, **отчество**, БИК, лицевой счёт; карта **или** договор — только для кредитного счёта (`30232810…`); для `40817810…` — не нужны; CVV/паспорт не запрашиваем |
| Электронное заявление | Клиент может скачать из МП / сайта; мы не храним, формируем из базы; Калининграду прикладывать не нужно; версии сохраняются |
| Изменение заявки после создания | Только через поддержку или отмена + новая заявка |
| Событие «клиент передал товар» | По статусам ТК: принят курьером / в ПВЗ / в постамате / сотрудником магазина / приём Почтой России |
