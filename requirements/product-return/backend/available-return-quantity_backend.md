# Backend Logic: Расчёт доступного количества для возврата

**Документ:** Описание логики расчёта параметра `available_return_quantity` и его добавления в ответы API просмотра заказа.
**Домен:** E-commerce / Fashion-ритейл.
**Статус:** Требуется реализация.
**Связанные артефакты:** `product-return-eligibility_backend.md` (шаг 4 «Расчёт доступного количества», раздел 8 «Выходные данные»); TBD-03, TBD-08, TBD-09, TBD-10 (см. раздел 10).

---

## 1. Цель

Добавить в ответы API просмотра заказа (Web и Mobile) вычисляемый параметр `available_return_quantity`, показывающий клиенту количество единиц позиции заказа, доступных для оформления возврата на момент запроса.

Параметр **не хранится** в базе данных и **рассчитывается бэкенд-логикой** в момент формирования ответа.

### Предусловие: только для позиций, прошедших первичную проверку

Расчёт `available_return_quantity` **дополняет**, а не заменяет существующую логику определения возвратных позиций (`product-return-eligibility_backend.md`, шаг 3 / `OrderHelper::canPositionBeReturned()`).

Расчёт выполняется **только для позиций, прошедших первичное отсечение AS-IS:**
- заказ в статусе «выполнен» или «возвращён»;
- срок не истёк (`end_date + days_can_be_returned > now`);
- статус позиции = `STATUS_ADDED` (не отменена, не невыкуплена, не возвращена ранее);
- позиция не является подарком.

Для позиции, **не прошедшей** первичное отсечение, `available_return_quantity` не рассчитывается:
- **Веб:** позиция отсутствует в `positions[]`.
- **Мобильное приложение:** позиция остаётся в `items[]` (весь состав заказа показывается всегда), возвращается `available_return_quantity = 0` и `can_be_returned = false`.

**Инвариант:** `available_return_quantity = 0` ⇒ на вебе позиции нет в списке; в МП `can_be_returned = false`.

## 2. Текущее состояние (AS-IS)

| Платформа | Эндпоинт | Что возвращается | Что отсутствует |
|-----------|----------|------------------|-----------------|
| Веб | `GET /orders/refund/get-positions?id={orderId}` | Список позиций с исходным `quantity` | Поле `available_return_quantity` |
| Mobile | `GET /api/orders/{orderId}` | `items[].count` (исходное количество), `items[].can_be_returned` (boolean) | Поле `available_return_quantity` |

На данный момент клиент не получает информации о том, сколько единиц товара фактически доступно для возврата. Кнопка «Оформить возврат» отображается, но без указания доступного количества.

**Что AS-IS уже делает (и остаётся без изменений):**
- `OrderHelper::canPositionBeReturned()` — единый для веб и МП метод первичного отсечения: статус заказа, срок, статус позиции = `STATUS_ADDED`, не подарок.
- Веб дополнительно фильтрует список позиций в `OrderPositionRepository::findAllForRefundByOrderId()` (`status = STATUS_ADDED AND price_before_discount > PRESENT_MAX_PRICE`).
- `OrderHelper::canBeReturned()` скрывает кнопку «Оформить возврат», когда ни одна позиция не прошла первичное отсечение.

Новый расчёт `available_return_quantity` встраивается **после** этих проверок и работает только с их результатом.

## 3. Новые данные

### 3.1. Параметр ответа

| Параметр | Тип | Описание |
|----------|-----|----------|
| `available_return_quantity` | integer | Количество единиц позиции, доступных для возврата на момент запроса. Рассчитывается бэкенд-логикой. Не хранится в БД. |

### 3.2. Изменения в ответах API

**Веб** (`GET /orders/refund/get-positions?id={orderId}`):

В каждую позицию массива `positions[]` добавляется поле `available_return_quantity`.

**Mobile** (`GET /api/orders/{orderId}`):

В каждый элемент массива `items[]` добавляется поле `available_return_quantity`.

## 4. Источники данных для расчёта

| Источник | Таблица | Поля | Назначение | Статус |
|----------|---------|------|-----------|--------|
| Позиция заказа | `cms_order_positions` | `id`, `order_id`, `barcode`, `quantity`, `status` | Идентификация позиции, штрихкод, исходное количество, статус | Подтверждено |
| Реализация | `cms_order_position_realizations` | `position_id`, `barcode`, `quantity` | Фактически выкупленное количество | Кандидат (TBD-09) |
| Завершённый возврат | `cms_order_return_positions` (данные 1С) **или** `cms_order_position_refunds` (данные чеков) | `order_id`, `position_id`, `barcode`, `quantity` | Количество, уже завершённое возвратом | Кандидат, авторитетный источник и правило дедупликации — TBD-10 |
| Занято действующей заявкой | **источник не подтверждён** | количество по позиции в незавершённой клиентской заявке + перечень блокирующих статусов | Исключение единиц, уже заявленных к возврату | TBD-03 |

> **Примечание 1:** поле `cms_order_positions.quantity` содержит исходное заказанное количество и **не изменяется** при частичном невыкупе. При невыкупе позиция целиком переводится в статус `SOLDOUT_SHOP (15)`. Фактически выкупленное количество определяется из таблицы `cms_order_position_realizations`.
>
> **Примечание 2:** таблицы `cms_order_return_positions` (id, order_id, position_id, return_quid, barcode, quantity) и `cms_order_position_refunds` **не содержат поля статуса клиентской заявки** — они фиксируют уже зарегистрированный/оплаченный возврат. Отдельной таблицы `cms_returns` со статусами `CREATED`/`PROCESSING`/`COMPLETED` в AS-IS **не существует** (см. TBD-03). До закрытия TBD-03 шаг 3 алгоритма не реализуем; шаги 1, 2, 4 реализуемы после закрытия TBD-09 и TBD-10.
>
> **Примечание 3 (нижняя граница):** на уровне целой позиции повторный возврат в AS-IS уже исключён — при регистрации возврата позиция уходит из статуса `STATUS_ADDED` и не попадает в шаг 3 `product-return-eligibility_backend.md`. Расчёт `available_return_quantity` уточняет это до уровня отдельных единиц.

## 5. Алгоритм расчёта

### Шаг 0. Предусловие (вход)

На вход подаются **только позиции, прошедшие первичное отсечение** (`product-return-eligibility_backend.md`, шаг 3). Позиции, не прошедшие отсечение, в расчёт не поступают: на вебе они отсутствуют в списке, в МП получают `available_return_quantity = 0`.

### Шаг 1. Определить выкупленное количество

Для указанного заказа и штрихкода позиции система определяет суммарное количество из таблицы `cms_order_position_realizations` (TBD-09).

### Шаг 2. Определить завершённые возвраты

Для указанного заказа и штрихкода система определяет суммарное количество, уже завершённое возвратом, из авторитетного источника (`cms_order_return_positions` или `cms_order_position_refunds` — TBD-10).

### Шаг 3. Определить количество, занятое действующими заявками

Для указанного заказа и штрихкода система определяет суммарное количество по позиции в незавершённых клиентских заявках на возврат.

> **TBD-03:** физический источник этого количества и перечень блокирующих статусов в AS-IS не подтверждены. До закрытия TBD-03 шаг 3 даёт `0` (не уменьшает доступное количество), а защита от гонок выполняется повторной проверкой при создании заявки (раздел 9).

### Шаг 4. Рассчитать доступное количество

Формула:

```
available_return_quantity = выкупленное количество − количество в завершённых возвратах − количество в активных заявках
```

### Шаг 5. Ограничения

- Если `available_return_quantity` равно нулю, позиция недоступна для новой заявки на возврат.
- Если `available_return_quantity` больше нуля, клиент может выбрать значение от 1 до `available_return_quantity` включительно.

## 6. Пример расчёта

Заказ содержит 3 единицы товара с штрихкодом `123456`.

| Показатель | Значение | Источник |
|------------|----------|----------|
| Исходное заказанное количество | 3 | `cms_order_positions.quantity` |
| Фактически выкуплено | 2 | `cms_order_position_realizations.quantity` (TBD-09) |
| Завершённые возвраты | 0 | авторитетный источник завершённого возврата (TBD-10) |
| Занято действующей заявкой | 1 | источник не подтверждён (TBD-03) |
| **available_return_quantity** | **1** | 2 − 0 − 1 |

## 7. Пример ответа API

### Веб

```json
{
  "can_return": true,
  "positions": [
    {
      "id": 101,
      "article": "ART-001",
      "title": "Платье летнее",
      "quantity": 3,
      "available_return_quantity": 1,
      "is_present": false
    }
  ],
  "return_deadline": "2026-09-22",
  "days_remaining": 10
}
```

### Mobile

Позиция остаётся в `items[]` всегда; поле добавляется рядом с существующими `count` и `can_be_returned`.

```json
{
  "orderId": 100500,
  "items": [
    {
      "id": 101,
      "barcode": 123456,
      "name": "Платье летнее",
      "count": 3,
      "can_be_returned": true,
      "available_return_quantity": 1
    },
    {
      "id": 102,
      "barcode": 123457,
      "name": "Юбка (возвращена ранее)",
      "count": 1,
      "can_be_returned": false,
      "available_return_quantity": 0
    }
  ]
}
```

## 8. Бизнес-валидации

| Проверка | Условие | Ошибка |
|----------|---------|--------|
| Есть хотя бы одна позиция с положительным доступным количеством | `available_return_quantity > 0` для минимум одной позиции | `NO_AVAILABLE_ITEMS` |
| Запрашиваемое количество не превышает доступное | `запрошенное_количество ≤ available_return_quantity` | `QUANTITY_EXCEEDS_AVAILABLE` |

---

## 9. Конкурентный сценарий

При одновременном создании заявок суммарное количество в активных заявках не должно превысить выкупленное. Перед фиксацией заявки система повторно рассчитывает `available_return_quantity` по формуле из шага 4 и проверяет, что запрашиваемое количество не превышает актуальное доступное.
