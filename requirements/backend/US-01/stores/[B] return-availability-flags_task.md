# ECOMDEV-2359: [B] Добавить признак приёма возвратов

## Цель

Добавить признак «Принимает возвраты» магазинам и покрытию служб доставки по городам, чтобы методы оформления возврата показывали клиенту только магазины и службы, которые принимают возвраты в выбранном городе. Признак настраивается в админке.

## Описание реализации

Что требуется изменить:

1. Создать поле `cms_catalog_stock.for_returns` — раздел 1.
2. Создать поле `cms_delivery_city.for_returns` — раздел 1.
3. Вывести оба признака в формы редактирования в админке — раздел 2.

Вне этой задачи:
* новые таблицы возврата (`cms_returns`, `cms_return_positions`, `cms_return_statuses` и др.) — задача на модель данных;
* отбор магазинов по `cms_catalog_stock.for_returns` — задачи на метод списка магазинов для возврата (`[B][Mobile API]`, `[B][Web]`)

---

#### 1. Создать новые данные БД

Оба поля создаются по аналогии с существующим `cms_catalog_stock.for_reservation`.

| Таблица | Поле | Тип | NULL | По умолчанию | Комментарий |
|---|---|---|---|---|---|
| `cms_catalog_stock` | `for_returns` | `tinyint(1)` | Нет | `0` | Магазин принимает возвраты |
| `cms_delivery_city` | `for_returns` | `tinyint(1)` | Нет | `0` | Служба принимает возвраты в этом городе |

У обоих полей по умолчанию `0`: магазин и служба в городе принимают возвраты только после явного включения.

{red}(Начальные значения: какие магазины и какие службы в каких городах отмечаются при выкатке — миграцией по списку или вручную в админке.)

#### 2. Вывести признаки в админку

| Раздел админки | Поле формы | Тип | Значение для новой записи | Сохраняется в |
|---|---|---|---|---|
| Магазины и склады — форма редактирования магазина | «Принимает возвраты» | Чекбокс | Не отмечен | `cms_catalog_stock.for_returns` |
| Покрытие служб доставки — форма записи города службы | «Принимает возвраты» | Чекбокс | Не отмечен | `cms_delivery_city.for_returns` |

> **AS-IS:** далее применяется существующая логика синхронизации покрытия служб доставки по вебхуку логистики `POST /api/v1/delivery/webhooks/city-carriers-coverage`. Она не изменяется в рамках данной задачи и должна соответствовать текущей реализации. Приведённые в задаче условия могут быть описаны укрупнённо; если фактическая AS-IS-логика отличается, необходимо сохранить текущую реализацию при условии, что она не противоречит новой логике.

1. Сейчас вебхук передаёт город (`city_geo_id`) и список служб, которые в нём работают, и меняет только активность `cms_delivery_city._state` существующих записей. Признака приёма возвратов в вебхуке нет.
2. В рамках задачи вебхук не должен менять `cms_delivery_city.for_returns`.

{red}(Может ли логистика передавать признак приёма возвратов по службе в городе — например, если ПВЗ службы перестали принимать возвраты или начали. Если да — `cms_delivery_city.for_returns` заполняется из вебхука, а ручная настройка в админке либо не нужна, либо перезаписывается синхронизацией; правило — после ответа логистики.)

### Ошибки

Новых методов API нет — раздел не заполняется.

## Тестирование

**Предусловия**
- Миграция применена.

**Критерии приёмки**
- В `cms_catalog_stock` есть поле `for_returns` (`tinyint(1)`, NOT NULL, по умолчанию `0`); у существующих записей значение `0`.
- В `cms_delivery_city` есть поле `for_returns` (`tinyint(1)`, NOT NULL, по умолчанию `0`); у существующих записей значение `0`.
- Чекбокс «Принимает возвраты» сохраняется и отображается в форме редактирования магазина и в форме покрытия службы доставки.
- После вебхука `city-carriers-coverage` значение `cms_delivery_city.for_returns` не меняется {red}(пересмотреть после ответа на вопрос 2).
- Откат миграции удаляет оба поля.
