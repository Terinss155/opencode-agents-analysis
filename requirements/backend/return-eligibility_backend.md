# Backend Logic: Определение возможности начала возврата

## BL-RET-ELIG-01. Определить, может ли клиент начать возврат

**Системная цель:** На основании пользователя, заказа, срока и позиций определить, можно ли начать возврат, и вернуть по каждой доступной позиции готовое значение `available_return_quantity`.

**Источники требований:**
- `../user-story/user-story.md` — US-101, `COM-ALT-01`, `COM-ALT-02`;
- `../use-case/use-case.md` — `UC-RET-01`, шаги 2–3;
- Бизнес-правила: `BR-COM-01`, `BR-COM-02`, `BR-12`, `BR-COM-24`.

**Не входит в эту цель:** причины возврата, город, способы возврата, банковские реквизиты, создание заявки, интеграции с перевозчиками, жизненный цикл возврата, переделка веб-карточки заказа (TBD-07), **а также алгоритм расчёта `available_return_quantity` — он описан в `available-return-quantity_backend.md` и в данном документе не дублируется**.

---

## 1. Общий обзор

**Назначение:** Предоставить клиенту информацию о возможности возврата и доступном количестве товаров до начала оформления.

**Высокоуровневая логика (по шагам сценария):**
1. **Шаг 1.** Проверить авторизацию и принадлежность заказа. *(AS-IS — реализовано)*
2. **Шаг 2.** Проверить срок создания заявки. *(AS-IS — реализовано)*
3. **Шаг 3.** Получить позиции заказа, доступные для возврата (первичное отсечение). *(AS-IS — реализовано)*
4. **Шаг 4.** Получить `available_return_quantity` по каждой позиции, прошедшей шаг 3 (расчёт делегирован `available-return-quantity_backend.md`). *(TO-BE — добавляется этой задачей)*
5. **Шаг 5.** Сформировать результат для клиента (в ответ добавляется `available_return_quantity`). *(AS-IS + новое поле)*

### AS-IS → TO-BE

| | Что уже реализовано (AS-IS) | Где в коде |
|---|---|---|
| **Первичное отсечение** | Заказ в статусе «выполнен» или «возвращён»; срок `end_date + days_can_be_returned > now`; позиция в статусе `STATUS_ADDED` (не отменена, не невыкуплена, **не возвращена ранее**); позиция не подарок | `OrderHelper::canPositionBeReturned()` — единый метод для веб и МП; веб дополнительно фильтрует список в `OrderPositionRepository::findAllForRefundByOrderId()` (`status = STATUS_ADDED AND price_before_discount > PRESENT_MAX_PRICE`) |
| **«Нет товаров для возврата»** | Кнопка «Оформить возврат» скрыта, когда `canBeReturned()` = `false` (нет ни одной позиции, прошедшей первичное отсечение) | `OrderHelper::canBeReturned()` |

| | Что добавляет эта задача (TO-BE) | Примечание |
|---|---|---|
| **Расчёт `available_return_quantity`** | По каждой позиции, прошедшей первичное отсечение, вычисляется доступное к возврату количество (выкуплено − завершено возвратом − занято действующими заявками) | Алгоритм — в `available-return-quantity_backend.md`. Для позиций, **отсечённых на шаге 3, расчёт не выполняется** |
| **Учёт частичной заявки** | Если часть единиц позиции занята незавершённой заявкой — эти единицы вычитаются из `available_return_quantity` | В AS-IS отдельной сущности действующей заявки с количеством нет; на уровне целой позиции повторный возврат уже блокируется сменой статуса. Уровень количества — TBD-03 (в `available-return-quantity_backend.md`) |

> **Принцип:** новая логика **не заменяет** первичное отсечение AS-IS, а работает после него. Если позиция отсечена по первичной причине (срок, статус заказа, статус позиции, подарок, ранее возвращена) — `available_return_quantity` для неё не рассчитывается.

**Границы:**
- Вход: авторизованный пользователь, ID заказа.
- Выход: список позиций с доступным количеством или причина недоступности.
- Состояние: только чтение; данные БД не изменяются.

**Место выполнения проверки (по платформам):**

| Платформа | Когда выполняется | Эндпоинт | Что было до проверки |
|-----------|-------------------|----------|----------------------|
| Веб | В момент клика «Оформить возврат» | `GET /orders/refund/get-positions?id={orderId}` (AJAX) | При открытии карточки заказа выполняется только грубая проверка (статус + срок) → флаг `show_refund_button` |
| Мобильное приложение | При открытии карточки заказа | `GET /api/orders/{orderId}` (внутренний путь `GET /mobile/orders/{orderId}`) | Отдельный запрос не выполняется; ответ карточки уже содержит `items[].can_be_returned` и `messages[]` |

> Логика проверки (BL-RET-ELIG-01) — **единая для обеих платформ**. Различается только точка её выполнения.
> Перенос полной проверки на веб-карточку заказа (по образцу мобилки) — вне рамок задачи возврата, зафиксировано как TBD-07.

### 3.2. Модель хранения количества (кратко)

- Несколько одинаковых единиц одного размера/SKU обычно хранятся одной строкой `cms_order_positions` с `quantity = N` и единым `status` на всё количество.
- При невыкупе позиция целиком переводится в статус невыкупа; отдельного поля выкупленного количества в `cms_order_positions` нет.
- Клиентские Web- и Mobile-сценарии AS-IS не принимают количество при оформлении возврата и применяют изменение к позиции целиком.
- Фактически доступное к возврату количество (`available_return_quantity`) не хранится в БД и рассчитывается логикой `available-return-quantity_backend.md` (разделы 4–5).

## 4. Валидации

### 4.1. Структурные валидации

| # | Проверка | Условие | Код ошибки |
|---|----------|---------|------------|
| V-01 | `orderId` предоставлен и имеет допустимый формат | Положительное целое число | `ORDER_ID_REQUIRED` |
| V-02 | Пользователь авторизован | `userId` предоставлен, сессия активна | `UNAUTHORIZED` |

### 4.2. Бизнес-валидации

| # | Проверка | Условие | Код ошибки | Источник |
|---|----------|---------|------------|----------|
| V-03 | Заказ принадлежит указанному пользователю | `cms_orders.user_id` совпадает с `userId` | `ORDER_NOT_FOUND` | `BR-COM-01` |
| V-04 | Статус заказа допускает возврат | `cms_orders.status` в допустимом наборе (выполнен или возвращён) | `ORDER_NOT_RETURNABLE` | `BR-COM-01` |
| V-05 | Заказ не привязан к Lamoda | `cms_orders.lamoda_id` пустой | `ORDER_NOT_RETURNABLE` | Подтверждено для Web AS-IS; Mobile требует подтверждения |
| V-06 | Срок создания заявки не истёк | `cms_orders.end_date + days_can_be_returned` больше текущей даты; в MVP `days_can_be_returned = 14` | `RETURN_PERIOD_EXPIRED` | `BR-12`, `BR-COM-28` |
| V-07 | В заказе есть хотя бы одна позиция, доступная для возврата | Существует позиция, прошедшая первичное отсечение (шаг 3, AS-IS), **и** с `available_return_quantity > 0` (шаг 4) | `NO_AVAILABLE_ITEMS` | `BR-COM-01`, `COM-ALT-02` |
| V-08 | Позиция имеет допустимый статус *(AS-IS)* | Статус позиции = `STATUS_ADDED` | `ITEM_NOT_AVAILABLE` | `BR-COM-02` |
| V-09 | Позиция не является подарком *(AS-IS)* | `cms_order_positions.is_present` = false (веб: `price_before_discount > PRESENT_MAX_PRICE`) | `GIFT_NOT_RETURNABLE` | AS-IS ограничение |
| V-11 | Запрашиваемое количество не превышает доступное *(TO-BE)* | Запрашиваемое количество ≤ `available_return_quantity` | `QUANTITY_EXCEEDS_AVAILABLE` | `BR-COM-02` |

> V-08 и V-09 — это существующее первичное отсечение AS-IS (шаг 3). V-07 объединяет AS-IS-условие (позиция прошла отсечение) и новое (`available_return_quantity > 0`).
> Значение `available_return_quantity` (включая учёт количества в других действующих заявках) поступает из логики `available-return-quantity_backend.md`. Проверки V-07 и V-11 используют это значение как готовый вход и не выполняют собственного расчёта.

## 5. Основная логика

> Шаги 1–5 описывают **единую логику проверки** для обеих платформ. Точка выполнения зависит от платформы (см. раздел 1):
> - **Веб:** все шаги выполняются в момент клика «Оформить возврат».
> - **Мобильное приложение:** все шаги выполняются при открытии карточки заказа; результат включается в ответ просмотра заказа.
>
> **Порядок обязателен.** Первичные отсекающие проверки (шаги 1–3) выполняются раньше расчёта количества (шаг 4). `available_return_quantity` рассчитывается **только** для позиций, прошедших шаг 3; для отсечённых позиций расчёт не запускается. Шаги 1–3 — это существующая логика AS-IS (`OrderHelper::canPositionBeReturned()`), шаг 4 — новый.
>
> **Представление недоступной позиции по платформам:**
> - **Веб:** позиция, не прошедшая шаг 3, **отсутствует** в `positions[]` (список уже отфильтрован в `findAllForRefundByOrderId()`).
> - **Мобильное приложение:** позиция остаётся в `items[]` (карточка показывает весь состав заказа), но с `can_be_returned = false`; после добавления поля — с `available_return_quantity = 0`. **Из `items[]` позиция не удаляется никогда.**

### 5.1. Шаг 1. Проверка заказа и авторизации *(AS-IS — реализовано)*

**Входные параметры:** `orderId`, `userId`

**Поля БД:** `cms_orders.id`, `cms_orders.user_id`, `cms_orders.status`, `cms_orders.lamoda_id`

**Бизнес-правило:** `BR-COM-01` — до подтверждения возврата система проверяет принадлежность и статус заказа, применимый срок и доступность изделия.

**Логика:**
- Система находит заказ по `orderId` и проверяет принадлежность `user_id`.
- Система проверяет, что статус заказа допускает возврат.
- Система проверяет, что заказ не привязан к Lamoda.
- Если любое из условий не выполняется — система прерывает процесс и возвращает соответствующую ошибку.

**Результат при выполнении:** Заказ найден, принадлежит пользователю, статус допускает возврат. Переход к шагу 2.

**Результат при нарушении:** Ошибка `ORDER_NOT_FOUND` или `ORDER_NOT_RETURNABLE`.

---

### 5.2. Шаг 2. Проверка срока создания заявки *(AS-IS — реализовано)*

**Входные параметры:** `orderId`

**Поля БД:** `cms_orders.end_date`, параметр `days_can_be_returned`.

**Бизнес-правило:** `BR-12` — в MVP клиент оформляет заявку в течение 14 дней с момента фактического получения товара независимо от сегмента. 30-дневный срок F&F отложен до интеграции с авторитетным источником признака F&F (`C-6`). `BR-COM-28` — истечение срока создания новой заявки не отменяет уже созданную заявку.

**Логика:**
- Система получает значение `days_can_be_returned = 14` из параметров системы.
- Система вычисляет предельно допустимую дату: `orders.end_date + days_can_be_returned`.
- Система сравнивает текущую дату с предельно допустимой датой.

**Результат при выполнении:** Срок не истёк, переход к шагу 3.

**Результат при нарушении:** Ошибка `RETURN_PERIOD_EXPIRED`. Кнопка «Оформить возврат» недоступна. Уже созданная заявка остаётся активной.

**TBD-01:** Точный источник даты фактического получения товара — `orders.end_date` или отдельное поле.

---

### 5.3. Шаг 3. Первичное отсечение позиций, доступных для возврата *(AS-IS — реализовано)*

**Входные параметры:** `orderId`

**Поля БД:** `cms_order_positions.order_id`, `cms_order_positions.status`, `cms_order_positions.price_before_discount`, `cms_order_positions.is_present`, `cms_order_positions.model_id`, `cms_order_positions.item_id`, `cms_order_positions.barcode`, `cms_order_positions.quantity`

**Бизнес-правило:** `BR-COM-02` — клиент может выбрать одно или несколько доступных изделий из заказа.

**Логика (AS-IS, `OrderHelper::canPositionBeReturned()`):** позиция проходит первичное отсечение, если одновременно:
- заказ в статусе «выполнен» или «возвращён» (шаг 1) и срок не истёк (шаг 2);
- статус позиции = `STATUS_ADDED` — этим одновременно отсекаются: отменённые, невыкупленные (`SOLDOUT_SHOP`) и **уже возвращённые ранее** позиции (при возврате позиция уходит из `STATUS_ADDED`);
- позиция не является подарком (`is_present = false`; на вебе эквивалентно `price_before_discount > PRESENT_MAX_PRICE`).

**Отдельная действующая заявка на возврат:** на уровне целой позиции повторный возврат уже исключён сменой статуса. Отдельной проверки «по позиции есть незавершённая заявка» в AS-IS нет — учёт занятого заявкой количества выполняется на шаге 4 (TBD-03).

**Представление результата:**
- **Веб:** в `positions[]` попадают только прошедшие отсечение позиции.
- **Мобильное приложение:** в `items[]` остаются все позиции заказа; не прошедшие отсечение помечаются `can_be_returned = false`.

**Результат при выполнении:** Список позиций, прошедших первичное отсечение. Переход к шагу 4.

**Результат при нарушении:** Если не прошла ни одна позиция — ошибка `NO_AVAILABLE_ITEMS` (веб) / отсутствие сообщения `can_be_returned` и кнопки (МП). Это существующее поведение AS-IS.

### 5.4. Шаг 4. Расчёт доступного количества по каждой позиции *(TO-BE — добавляется этой задачей)*

**Входные параметры:** `orderId`, **только** позиции, прошедшие первичное отсечение на шаге 3

**Бизнес-правило:** `BR-COM-02` — выбираемое количество не может превышать доступный остаток. `BR-COM-24` — наличие действующей заявки на другое изделие того же заказа не препятствует оформлению нового возврата.

**Логика:**
- Расчёт запускается **только для позиций из шага 3.** Для позиций, отсечённых на шаге 3, `available_return_quantity` не вычисляется (веб — позиции нет в ответе; МП — `available_return_quantity = 0`).
- Для каждой такой позиции система получает значение `available_return_quantity`, рассчитанное логикой `available-return-quantity_backend.md`.
- Алгоритм расчёта, источники данных (выкупленное количество, завершённые возвраты, занятое действующими заявками количество), формула и связанные TBD описаны в `available-return-quantity_backend.md` (разделы 4–5, 9) и в данном документе **не дублируются**.

**Инвариант согласованности с AS-IS-флагом:**
- Веб: позиция с `available_return_quantity = 0` **не попадает** в `positions[]`.
- Мобильное приложение: если `available_return_quantity = 0`, то `can_be_returned` обязан быть `false`; позиция остаётся в `items[]`.

**Результат при выполнении:** Для каждой позиции, доступной к возврату, известно `available_return_quantity > 0`; клиент может выбрать значение от 1 до `available_return_quantity` включительно. Если ни у одной позиции нет положительного количества — `NO_AVAILABLE_ITEMS`. Переход к формированию результата на шаге 5.

**Результат при нарушении:** Ошибка `QUANTITY_EXCEEDS_AVAILABLE` при последующем выборе количества больше доступного.

---

### 5.5. Шаг 5. Формирование результата

**Входные параметры:** результаты шагов 1–4

**Поля БД:** все поля, использованные на предыдущих шагах

**Логика:**
- Система формирует ответ, содержащий:
  - Признак возможности возврата (`can_return`).
  - Список позиций с доступным количеством (`available_return_quantity`).
  - Предельно допустимую дату возврата.
  - Оставшееся количество дней.
- Если какая-либо проверка не пройдена — система формирует ответ с причиной недоступности.

**Результат при выполнении:** Успешный ответ с данными о доступности возврата.

**Результат при нарушении:** Ответ с кодом ошибки и описанием причины.

**TBD-05:** Формат даты в ответе (ISO 8601 / Unix timestamp).

## 6. Интеграции

## 7. Исключительные ситуации

### 7.1. Заказ не найден или не принадлежит пользователю

- **Код:** `ORDER_NOT_FOUND`
- **HTTP:** 404
- **Действие:** Не показывать кнопку «Оформить возврат» или возвращать пустой список.
- **Логирование:** Информационное — клиент обратился к несуществующему заказу.

### 7.2. Срок создания заявки истёк

- **Код:** `RETURN_PERIOD_EXPIRED`
- **HTTP:** 409
- **Действие:** Скрыть кнопку «Оформить возврат». Если заявка уже создана — она остаётся активной.
- **Логирование:** Информационное — истёк срок возврата.

### 7.3. Нет доступных позиций для возврата

- **Код:** `NO_AVAILABLE_ITEMS`
- **HTTP:** 409
- **Действие:** Сообщить клиенту, что нет товаров, доступных для возврата. Поведение AS-IS (кнопка «Оформить возврат» скрыта, когда `canBeReturned()` = `false`).
- **Причины:** все позиции не прошли первичное отсечение (срок, статус заказа, статус позиции, подарок, ранее возвращены) **или** у всех прошедших `available_return_quantity = 0`.
- **Логирование:** Информационное.

### 7.4. Позиция недоступна (неверный статус, подарок)

- **Код:** `ITEM_NOT_AVAILABLE` или `GIFT_NOT_RETURNABLE`
- **HTTP:** 409
- **Действие:**
  - **Веб:** позиция отсутствует в `positions[]`.
  - **Мобильное приложение:** позиция остаётся в `items[]` с `can_be_returned = false` и `available_return_quantity = 0` — из состава заказа не удаляется.
- **Логирование:** Информационное — позиция исключена из доступных для возврата по первичному ограничению (AS-IS).

### 7.5. Запрашиваемое количество превышает доступный остаток

- **Код:** `QUANTITY_EXCEEDS_AVAILABLE`
- **HTTP:** 409
- **Действие:** Вернуть актуальное `available_return_quantity` для позиции (пересчёт — на стороне `available-return-quantity_backend.md`).
- **Логирование:** Предупреждение — клиент попытался выбрать количество больше доступного.

## 8. Выходные данные

### 8.1. Успешный ответ

Система возвращает список позиций, доступных для возврата, с указанием допустимого количества для каждой.

> **Формат ответа по платформам:**
> - **Веб:** `GET /orders/refund/get-positions?id={orderId}` должен дополнить каждую позицию полем `available_return_quantity`.
> - **Мобильное приложение:** `GET /api/orders/{orderId}` должен дополнить каждый элемент `items[]` полем `available_return_quantity`.

| Поле ответа | Тип | Описание |
|-------------|-----|----------|
| `can_return` | boolean | Признак возможности начала возврата |
| `positions` | array | Список доступных позиций |
| `positions[].id` | integer | Идентификатор позиции |
| `positions[].article` | string | Артикул товара |
| `positions[].title` | string | Название товара |
| `positions[].available_return_quantity` | integer | Доступное количество для возврата (Web); значение из `available-return-quantity_backend.md` |
| `items[].available_return_quantity` | integer | Доступное количество для возврата (Mobile); значение из `available-return-quantity_backend.md` |
| `positions[].is_present` | boolean | Признак подарка |
| `return_deadline` | datetime | Предельно допустимая дата создания заявки |
| `days_remaining` | integer | Оставшееся количество дней до истечения срока |

### 8.2. Ответ с ошибкой

| Поле ответа | Тип | Описание |
|-------------|-----|----------|
| `can_return` | boolean | Всегда `false` |
| `error_code` | string | Код ошибки (`ORDER_NOT_FOUND`, `RETURN_PERIOD_EXPIRED`, `NO_AVAILABLE_ITEMS`, и т.д.) |
| `message` | string | Описание ошибки для пользователя |

## 10. Транзакционность и конкурентный доступ

- **Режим:** Только чтение. Транзакции не требуются.
- **Конкурентный доступ:** Перед созданием заявки система должна повторно рассчитать `available_return_quantity` — механизм описан в `available-return-quantity_backend.md`, раздел 9.
- **Идемпотентность:** Запрос идемпотентен — повторный вызов с теми же параметрами возвращает тот же результат.
