# Шаг 08 (web). Подтверждение и создание возврата

**Канал:** Сайт · **Экран:** «Оформление возврата», кнопка «Подтвердить возврат»
**Статус:** DRAFT · **Дата:** 07.09.2026
**Результат шага:** реквизиты возврата записаны в `cms_orders`; возвращаемые позиции переведены в статус `9`; заказ переведён в статус `31`; отправлены обновления в RetailCRM, Mindbox и (для lamoda-заказов) Lamoda. Показан экран «Заявка уже у нас».

---

## 1. Пользовательский сценарий

### 1.1 Откуда пользователь приходит

Экран «Оформление возврата» с заполненными городом, способом, данными способа и (если требуется) банковскими реквизитами.

### 1.2 Что система отображает

- Отдельного экрана «сводка / проверка» в web-версии AS-IS **нет**. Пользователь остаётся на экране оформления; роль сводки играют его блоки (город, способ, адрес/дата, реквизиты).
- Кнопка внизу — «Подтвердить возврат». Активна, когда заполнены обязательные данные способа и (при необходимости) реквизиты.

### 1.3 Действие пользователя

Нажатие «Подтвердить возврат» запускает подряд:

1. запрос **сохранения реквизитов возврата** — `POST /api/orders/{order_id}/return-details`;
2. запрос **создания возврата** — `POST /orders/refund/save-reason`;
3. показ окна успеха.

### 1.4 Что происходит после действия

1. **Сохранение реквизитов возврата.** Записывает город/способ/дату (и для курьера адрес и индекс) в заказ и сразу отправляет заказ в RetailCRM.
2. **Создание возврата.** Меняет статусы позиций и заказа, записывает банковские реквизиты в заказ, отправляет заказ в RetailCRM, Mindbox и (если заказ lamoda) Lamoda.
3. **Окно успеха:** заголовок «Заявка уже у нас», текст «Работаем над ней. Если найти курьера на выбранную дату не получится, свяжемся с вами в течение часа.». По закрытию — затемнение экрана и перезагрузка страницы карточки заказа.

### 1.5 Ограничения и важные особенности

- Два запроса идут **последовательно и не атомарно** (`TECH-GAP-02`).
- Если первый запрос (реквизиты возврата) завершился ошибкой — второй не выполняется; на форме подсвечиваются ошибочные поля, при ошибке даты — окно «Выберите другой день».
- Если второй запрос (создание возврата) завершился ошибкой — эта ошибка **проглатывается**: показывается уведомление с текстом ошибки, но окно успеха всё равно открывается. При этом реквизиты возврата уже сохранены и заказ уже ушёл в RetailCRM, а статусы возврата не изменены.

### 1.6 Ошибочные сценарии

| Ситуация | Поведение |
|---|---|
| Способ не выбран или не из набора `courier` / `sdek-pvz` / `5post` | ответ с ошибкой по полю `method_return` |
| Дата не из доступных / неверный формат / пустая при непустом списке | ошибка по полю `date_return`, в данных ответа — пересчитанный список дат |
| Курьер: индекс не 6 цифр / пустой адрес / пустой город | ошибки по полям `index_return` / `address_return` / `city_return` |
| ПВЗ: у заказа не заполнена дата завершения (`end_date`) | ошибка «заказ не завершён» по полю `date_return` |
| Создание возврата: причина не входит в активные | ответ «Ошибка валидации данных» |
| Создание возврата: не переданы реквизиты при не-онлайн оплате | ошибка по полю `user_refund` |
| Сбой внутри транзакции создания возврата | откат, запись в лог, сообщение «Возникла ошибка, попробуйте еще раз» |

## 2. Системная реализация

### 2.0 Диаграмма последовательности

```mermaid
sequenceDiagram
    actor U as Пользователь
    participant W as Сайт (попап)
    participant B as Backend
    participant DB as БД
    participant RCRM as RetailCRM
    participant EXT as Mindbox / Lamoda

    U->>W: «Подтвердить возврат»

    W->>B: POST /api/orders/{order_id}/return-details
    B->>DB: SELECT cms_orders (order_id, user_id)
    B->>B: валидация способа / даты / индекса / города / адреса
    Note over B: для ПВЗ index_return и address_return обнуляются
    B->>DB: UPDATE cms_orders SET return_city, return_date,<br/>return_delivery_tk, return_postal, return_address
    B->>RCRM: обновить заказ (очередь)
    B-->>W: { success: true }

    W->>B: POST /orders/refund/save-reason
    B->>DB: SELECT cms_order_positions (по id) + cms_users_refund
    B->>B: валидация причин (in cms_return_reasons active),<br/>принадлежность заказа, need_bank_details
    B->>DB: BEGIN
    B->>DB: UPDATE cms_order_positions SET status=9, reason=<code>
    B->>DB: UPDATE cms_orders SET status=31<br/>(+ user_refund JSON, если оплата не онлайн)
    B->>DB: COMMIT
    B->>RCRM: обновить заказ (очередь)
    B->>EXT: Mindbox: обновить заказ; Lamoda: смена статусов (для lamoda-заказов)
    B-->>W: { success: true }

    W-->>U: попап «Заявка уже у нас» → window.location.reload()
```

> Если `save-reason` завершается ошибкой, она проглатывается фронтом: показывается уведомление, но окно успеха всё равно открывается (`return-details` при этом уже сохранён).

### 2.1 Источники данных

| Что нужно | Где хранится | Значения / поля |
|---|---|---|
| Заказ | `cms_orders` | по `order_id` и `user_id` |
| Позиции возврата | `cms_order_positions` | по `id` из запроса создания возврата |
| Проверка причины | `cms_return_reasons` (`active = 1`) | список кодов активных причин |
| Банковские реквизиты | `cms_users_refund` | по `user_id` |
| Соответствие «способ → транспортная компания» | `courier` → `13`, `sdek-pvz` → `567`, `5post` → `55` | пишется в `cms_orders.return_delivery_tk` |
| Статус заказа при возврате | `31` — внутреннее название «Возврат из ЛК», клиентское «Заявка на возврат принята», код `vozv-lk` (справочник `cms_order_statuses`) | `cms_orders.status` |
| Статус возвращённой позиции | `9` («Возврат (если был отгружен)») | `cms_order_positions.status` |

### 2.2 Как система собирает данные

#### 2.2.1 Запрос сохранения реквизитов возврата — `POST /api/orders/{order_id}/return-details`

1. Находит заказ по `order_id` и `user_id`; если нет — 404.
2. Разбирает тело запроса: способ (`method_return`), город (`city_return`), индекс (`index_return`), адрес (`address_return`), дата (`date_return`).
3. **Проверяет:**
   - способ не пустой и входит в набор `courier` / `sdek-pvz` / `5post`;
   - **курьер:** дата входит в список доступных дат; индекс — ровно 6 цифр; город — не пустой, не длиннее 255; адрес — не пустой, не длиннее 1024;
   - **ПВЗ:** у заказа заполнена дата завершения (`cms_orders.end_date`); дата входит в список доступных дат; город не пустой.
   При ошибках — ответ с полем `data` (текущие значения + пересчитанный список доступных дат) и списком ошибок.
4. Для ПВЗ **обнуляет** индекс и адрес (даже если бы их прислали).
5. **Записывает в `cms_orders`:**
   | Значение | Поле |
   |---|---|
   | город | `return_city` |
   | дата | `return_date` |
   | код транспортной компании по способу (`13` / `567` / `55`) | `return_delivery_tk` |
   | индекс (если не пустой) | `return_postal` |
   | адрес (если не пустой) | `return_address` |
   | время изменения; `last_change_source = 'user'`; номер версии заказа | служебные поля |
   Заказ сохраняется без повторной валидации модели.
6. **Отправляет заказ в RetailCRM** (в очередь на отправку) — уже здесь, до смены статуса.
7. Ответ: `{ "success": true, "message": "..." }`.

#### 2.2.2 Запрос создания возврата — `POST /orders/refund/save-reason`

1. Разбирает тело: массив пар «`id` позиции + код причины». Проверяет, что в каждой паре оба значения заполнены и `id` — число.
2. Берёт запись реквизитов пользователя из `cms_users_refund`.
3. **По каждой позиции проверяет:**
   - позиция существует;
   - заказ позиции принадлежит текущему пользователю;
   - код причины заполнен и входит в список кодов активных причин (`cms_return_reasons` с `active = 1`);
   - если тип оплаты заказа **не** входит в список всех онлайн-методов — запись реквизитов (`cms_users_refund`) обязана существовать.
4. **В транзакции, по каждой позиции:**
   - если запись реквизитов есть и оплата не онлайн — кладёт JSON реквизитов в `cms_orders.user_refund`;
   - сохраняет заказ;
   - **переводит позицию в возврат:** `cms_order_positions.status = 9`, `cms_order_positions.reason = код причины`;
   - **пересчитывает статус заказа:** если в заказе есть хотя бы одна позиция в статусе возврата (`5` или `9`) — `cms_orders.status = 31`;
   - если заказ lamoda и статус изменился — ставит задачу на отправку статусов в Lamoda;
   - вызывает устаревший сервис смены статуса.
5. **После транзакции**, по каждому затронутому заказу — ставит задачи на отправку заказа в RetailCRM и Mindbox.
6. При любом сбое в транзакции — откат, запись в лог, ошибка «Возникла ошибка, попробуйте еще раз».
7. Ответ: `{ "success": true }`.

### 2.3 Обмен по API

**Запрос 1**

```http
POST /api/orders/{order_id}/return-details
Content-Type: application/json

// Курьер:
{ "method_return": "courier", "address_return": "ул. Тверская, д. 1, кв. 5",
  "city_return": "Москва", "date_return": "2026-09-10", "index_return": "125009" }

// ПВЗ (5post / sdek-pvz):
{ "method_return": "5post", "city_return": "Москва", "date_return": "2026-09-09" }
```

**Ответ 1**

```json
{ "success": true, "message": "Данные возврата сохранены" }
```

При ошибке валидации:

```json
{
  "status": "error", "success": false, "code": "INVALID_REQUEST",
  "data": {
    "method_return": "courier", "city_return": "Москва",
    "index_return": "12", "address_return": "…", "date_return": "2026-09-10",
    "available_dates_return": ["2026-09-11", "2026-09-12"]
  },
  "errors": [ { "target": "index_return", "message": "Неверный формат индекса" } ]
}
```

**Запрос 2**

```http
POST /orders/refund/save-reason
Content-Type: application/json

{ "positions": [ { "id": 123456, "reasonCode": "300" }, { "id": 123457, "reasonCode": "305" } ] }
```

**Ответ 2**

```json
{ "data": [], "errorCode": null, "errors": [], "message": "success", "success": true }
```

Существующие карточки: [`api/web/orders/post-return-details.md`](../../reference/api/web/orders/post-return-details.md), [`api/web/orders/post-save-reason.md`](../../reference/api/web/orders/post-save-reason.md).

### 2.4 Что использует сайт

| Данные | Использование |
|---|---|
| ответ первого запроса `success` | продолжить ко второму запросу |
| ошибки первого запроса | подсветить поля; при ошибке даты — окно «Выберите другой день» и список доступных дат из ответа |
| текст ошибки второго запроса | показать уведомление (успех второго запроса перед показом окна успеха отдельно не проверяется) |
| закрытие окна успеха | перезагрузка страницы карточки заказа |

### 2.5 Что передаётся на следующий шаг

Это терминальный шаг оформления. После перезагрузки карточка заказа отдаётся уже в статусе `31`. Блок «клиентские идентификаторы» СДЭК / 5Post (штрихкод, накладная, QR, PIN) в web-версии AS-IS не формируется.

### 2.6 Что сохраняется или меняется

| Сущность | Изменение | На каком запросе |
|---|---|---|
| `cms_orders` | `return_city`, `return_date`, `return_delivery_tk`, `return_postal`*, `return_address`*, время изменения, `last_change_source = 'user'`, версия | реквизиты возврата |
| `cms_orders` | `user_refund` (JSON) — если оплата не онлайн и есть запись в `cms_users_refund` | создание возврата |
| `cms_orders` | `status = 31` (`vozv-lk`) | создание возврата |
| `cms_order_positions` | `status = 9`, `reason = <код причины>` по каждой возвращаемой позиции | создание возврата |
| RetailCRM | обновление заказа (очередь) — **дважды**: на первом и на втором запросе | оба запроса |
| Mindbox | обновление заказа (очередь) | создание возврата |
| Lamoda | смена статуса позиций — только для lamoda-заказов | создание возврата |

`* return_postal` / `return_address` для ПВЗ не пишутся (обнуляются сервером).
Поля `cms_orders.return_money`, `return_store`, `return_interval`, `return_reason` (верхнего уровня), `return_status_wms`, `return_order_num` — **не заполняются**.

### 2.7 Неуточнённые места

- Атомарность двух запросов не гарантирована (`TECH-GAP-02`): при сбое создания возврата реквизиты в заказе и отправка в RetailCRM остаются, а статусы возврата — нет.
- Отдельной сущности возврата и номера заявки нет (`TECH-GAP-03`); «номер возврата» = номер заказа.
- Автоматическое создание курьерского задания / накладной / трек-номера в коде оформления **не подтверждено** (`TECH-GAP-04`); вероятно, это делает RetailCRM по обновлённому заказу (**допущение**).
- Транспорт отправки в RetailCRM / Mindbox / Lamoda из очередей в этом описании не разбирается (`TECH-GAP-01`).
- **Отправка статуса в 1С.** В прослеженном коде создания возврата на сайте явного вызова 1С нет (в очередь ставятся только RetailCRM и Mindbox; для мобильного канала 1С добавлена явно). При этом по материалам проекта успешная загрузка статуса `vozv-lk` в 1С в web-сценарии **наблюдалась**. Путь до 1С (через устаревший сервис смены статуса или отдельный обработчик события) по коду не прослежен.
- Несогласованность наборов методов оплаты: признак «нужны реквизиты» и проверка при создании возврата используют список **всех** онлайн-методов, а запись реквизитов в заказ — список онлайн-методов **без рассрочек**. Для рассрочек: реквизиты не требуются, но при их наличии всё равно записываются в заказ.
- Уведомление клиенту о создании заявки в этом коде не отправляется (только окно успеха в интерфейсе).

## 3. Отличия от TO-BE

| TO-BE (`UC-RET-05`) | AS-IS (web) |
|---|---|
| Отдельный экран сводки: товары, количества, причины, город, способ, канальные данные, итоговая сумма и баллы, способ возврата денег | Отдельного экрана сводки нет; сумма и баллы к возврату не рассчитываются и не показываются |
| Одно действие создаёт **одну заявку** с номером и начальным статусом | Два последовательных запроса; «заявка» = заказ в статусе `31`, отдельного номера нет |
| Повторные проверки при подтверждении: срок создания, доступное количество, доступность способа, доступность точки/интервала | Повторно проверяются только способ, город, дата, индекс/адрес; срок и количество на этом шаге не перепроверяются |
| Запуск отдельного срока передачи возврата по каналу | Не реализовано |
| Возврат пользователя к нужному шагу при истёкшем сроке / изменившемся количестве / недоступном способе | Только ошибки полей формы; ошибка создания возврата проглатывается сайтом |
| Показ карточки созданного возврата с блоком «Возврат средств» | Перезагрузка страницы; карточка перерисовывается по статусу `31` |
