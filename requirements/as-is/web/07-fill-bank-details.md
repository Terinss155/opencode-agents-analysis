# Шаг 07 (web). Заполнение банковских реквизитов

**Канал:** Сайт · **Экран:** «Оформление возврата», блок «Банковские реквизиты» → отдельный попап
**Статус:** DRAFT · **Дата:** 07.09.2026
**Условие шага:** признак `need_bank_details = true` (оплата заказа была не онлайн).
**Результат шага:** реквизиты сохранены в таблице `cms_users_refund` (одна запись на пользователя) и продублированы в состояние формы. Заказ не затрагивается.

---

## 1. Пользовательский сценарий

### 1.1 Откуда пользователь приходит

Тот же экран «Оформление возврата». Блок «Банковские реквизиты» показывается, только если на шаге 01 пришёл `need_bank_details = true`.

### 1.2 Что система отображает

- Строка-кнопка: «Укажите банковские реквизиты», либо (если уже заполнено) ФИО, банк и счёт.
- По нажатию открывается попап с полями:

| Поле | Проверка | Обязательно |
|---|---|---|
| Фамилия получателя | не пусто | да |
| Имя получателя | не пусто | да |
| Отчество получателя | не пусто | да |
| БИК банка | 9 цифр | да |
| Название банка | не пусто | да |
| ИНН банка | 10 цифр | да |
| Номер лицевого счёта получателя | по маске | да |
| Номер банковской карты физлица | по маске | да |

### 1.3 Действия пользователя

1. Заполняет все 8 полей. Кнопка «Продолжить» активна, только когда все поля заполнены и по длине маски.
2. Нажимает «Продолжить» — реквизиты уходят запросом `POST /user/cabinet/return-item/ajax/check-bank-details`.
3. При успехе попап закрывается, реквизиты переносятся в основной экран, строка-кнопка показывает заполненные данные.
4. При ошибке проверки поля подсвечиваются, попап остаётся открытым.

### 1.4 Ограничения

- До заполнения реквизитов кнопка «Подтвердить возврат» на основном экране неактивна.
- **Номер карты на сайте обязателен всегда**, независимо от типа счёта.
- Ранее сохранённые реквизиты в форму не подгружаются — она открывается пустой.

### 1.5 Что происходит после действия

- В таблице `cms_users_refund` создаётся или обновляется запись пользователя.
- Реквизиты попадают в память попапа.
- Заказ (`cms_orders`) на этом шаге **не меняется**. Реквизиты попадут в поле `cms_orders.user_refund` (в виде JSON) только на шаге [08](08-confirm-and-create-return.md), при создании возврата.

### 1.6 Ошибочные сценарии

- Пользователь закрыл попап без сохранения — реквизиты не заполнены, подтверждение возврата недоступно.
- Ошибка сохранения — показывается сообщение об ошибке, попап открыт.

## 2. Системная реализация

### 2.0 Диаграмма последовательности

```mermaid
sequenceDiagram
    actor U as Пользователь
    participant W as Сайт (попап)
    participant B as Backend
    participant DB as БД

    Note over W: блок показан, если need_bank_details = true (шаг 01)
    U->>W: тап «Укажите банковские реквизиты»
    W-->>U: попап с 8 полями (ФИО, БИК, ИНН, банк, счёт, карта)
    U->>W: заполнил поля, «Продолжить»
    W->>B: POST /user/cabinet/return-item/ajax/check-bank-details<br/>(UserRefund[...])
    B->>B: валидация (длина БИК 9, ИНН 10, есть цифры, без URL/тегов)
    alt валидно
        B->>DB: INSERT/UPDATE cms_users_refund (по user_id)
        B-->>W: { success: true }
        W-->>U: попап закрыт; реквизиты показаны; «Подтвердить возврат» разблокирована
    else ошибка
        B-->>W: { success: false, errors: {...} }
        W-->>U: подсветка полей, попап открыт
    end
```

### 2.1 Источники данных

| Данные | Таблица | Поля |
|---|---|---|
| Реквизиты пользователя | `cms_users_refund` | `user_id`, `surname`, `name`, `patronymic`, `bank_name`, `bank_inn`, `bank_bic`, `user_account`, `user_card_number` |
| Признак `need_bank_details` | вычислен на шаге 01 по типу оплаты заказа | — |

### 2.2 Как система собирает данные

По запросу `POST /user/cabinet/return-item/ajax/check-bank-details` система:

1. Берёт присланные значения полей, привязывает их к текущему пользователю (`user_id`).
2. Проверяет:
   - все поля обязательны;
   - название банка, ИНН банка, ФИО — строки не длиннее 255 символов;
   - БИК — ровно 9 символов;
   - ИНН банка — ровно 10 символов;
   - номер счёта и номер карты — должны содержать цифры/дефис;
   - в названии банка и ФИО запрещены ссылки и теги.
   При провале — ответ с ошибками по полям.
3. Если у пользователя уже есть запись в `cms_users_refund` — обновляет её присланными значениями; иначе создаёт новую.
4. Сохраняет. Успех — ответ `{ "success": true }`; ошибка сохранения — сообщение об ошибке.

> Есть также эндпоинт `POST /orders/refund/save-bank-data`, делающий то же самое, но текущим попапом он **не используется**.

### 2.3 Обмен по API

**Запрос**

```http
POST /user/cabinet/return-item/ajax/check-bank-details
Content-Type: application/x-www-form-urlencoded

UserRefund[bank_name]=...&UserRefund[bank_inn]=...&UserRefund[bank_bic]=...
&UserRefund[name]=...&UserRefund[patronymic]=...&UserRefund[surname]=...
&UserRefund[user_account]=...&UserRefund[user_card_number]=...
```

**Ответ — успех**

```json
{ "success": true }
```

**Ответ — ошибка валидации**

```json
{
  "success": false,
  "message": "Ошибка валидации данных",
  "errors": { "bank_bic": ["Значение «БИК банка» должно содержать 9 символов."] }
}
```

Существующая карточка: [`api/web/user/post-check-bank-details.md`](../../reference/api/web/user/post-check-bank-details.md).

### 2.4 Что использует сайт

| Данные | Использование |
|---|---|
| ответ `success` | закрыть попап, перенести реквизиты в основной экран, разблокировать «Подтвердить возврат» |
| `errors` | подсветка полей |
| реквизиты в основном попапе | отображение в строке-кнопке; проверка полноты |

Сами значения реквизитов в запросы шага 08 сайт **не передаёт** — сервер на шаге 08 берёт их из таблицы `cms_users_refund` по `user_id`.

### 2.5 Что передаётся на следующий шаг

Явно — ничего. Связь со следующим шагом только через базу: на шаге 08 сервер подтягивает запись из `cms_users_refund` по `user_id` и, если оплата не онлайн, кладёт её JSON в `cms_orders.user_refund`.

### 2.6 Что сохраняется или меняется

| Что | Где | Когда |
|---|---|---|
| Запись реквизитов | `cms_users_refund` (одна на пользователя, создание или обновление) | на этом шаге |
| `cms_orders.user_refund` (JSON) | заказ | на шаге 08 |

Смен статусов, событий, интеграций на этом шаге нет.

### 2.7 Неуточнённые места

- Проверки контрольных сумм БИК/ИНН/счёта/карты на сервере **нет** — только длина и наличие цифр (`TECH-GAP-07`).
- Логика «тип лицевого счёта (`30232810...` / `40817810...`) определяет, нужны ли карта/договор» (из целевого сценария) в коде **не реализована**.
- Поля «номер договора» в AS-IS нет.
- В мобильном канале номер карты фактически подменяется номером счёта (см. `mobile/`).

## 3. Отличия от TO-BE

| TO-BE (`UC-RET-04.6`, `RET-BR-09`) | AS-IS (web) |
|---|---|
| Реквизиты запрашиваются только для оплаты курьеру | Запрашиваются при любой не-онлайн оплате |
| Поля: ФИО, БИК, номер лицевого счёта; карта/договор — только для счёта `30232810...` | Поля: ФИО, БИК, ИНН банка, название банка, лицевой счёт, **номер карты (всегда обязателен)**; договора нет |
| Система определяет тип лицевого счёта и по нему решает про карту/договор | Логики типа счёта нет |
| Проверки формата и контрольных значений | Только длина полей и «есть цифра» |
| «Реквизиты предыдущих возвратов не переиспользуются» | Наоборот: в `cms_users_refund` одна запись на пользователя, переиспользуется и перезаписывается |
