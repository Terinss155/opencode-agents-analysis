### SRS по шаблону

**Назначение.** Краткая инструкция по заполнению SRS. Основной референс — [template.md](./template.md): структура, формулировки разделов и пример заполнения берутся оттуда. Скилл не добавляет разделов сверх шаблона. SRS фиксирует пользовательский сценарий, поведение системы, API, взаимодействие компонентов и задачи — без дублирования BRD.

#### 1. Разделы

| Раздел | Когда |
|---|---|
| Полезные материалы | **Всегда.** Только реально существующие и релевантные материалы; в «Название» — тип материала (`Макеты`, `User Flow`, `BRD / ТЗ`, `Epic`, `API-документация`, `ADR / решения`, `Другие материалы`). |
| Основные принципы | Только если есть общие правила, относящиеся сразу к нескольким User Story. |
| Функциональные требования | Только если ФТ действительно зафиксированы в этом SRS. Из BRD ради заполнения не переносить. |
| Разделение MVP / Post-MVP | Только если такое разделение зафиксировано; иначе блок удалить. |
| User Story | Основная часть документа. User Story группируются по функциональным областям и оформляются строго по структуре `template.md`. |

#### 2. Группировка User Story

- `## <Функциональная область>` — группа связанных историй (Корзина, Оформление заказа…). Это не название US и не обязательно экран.
- Под ней — `### US <N>. <Название User Story>` для каждой истории, затем формулировка «Как <роль>, я хочу <действие>, чтобы <ценность>».
- Заголовок области не повторяется перед каждой историей; новый `##` — только при переходе к другой группе.

#### 3. Блоки одной User Story (по порядку)

1. **Дизайн** — ссылка на Figma, только если есть макеты.
2. **Сценарий**
   - **Предусловия** — только если они есть.
   - **Основная последовательность «<Название User Story>»** — таблица `Шаг | Исполнитель | Описание`. В `Исполнитель` указывается фактический участник шага: обычно `Пользователь` или `Система`, при необходимости — другой реально участвующий актор или компонент.
   - **Опционально** — альтернативные и ошибочные ветки. Оформлять по образцу из `template.md`, не вводя новый формат от себя.
3. **Взаимодействие компонентов** — см. п. 5.
4. **Задачи** — всегда, см. п. 6.

#### 4. API в сценарии

- Смысловое действие + фактический `HTTP-метод endpoint` в скобках: `Система получает список бронирований (GET /api/v1/reservation).`
- Не писать условные обозначения вида `GET /Получить данные`, если endpoint известен.
- Endpoint не определён — `TBD`, не выдумывать.

#### 5. Взаимодействие компонентов

- Добавлять только если в User Story действительно взаимодействуют несколько систем / компонентов.
- Использовать `mermaid sequenceDiagram` с `autonumber` по образцу из `template.md`.
- Для конкретной User Story использовать только подходящий вариант взаимодействия — например, мобильное приложение или сайт. Не создавать оба варианта, если один из них не относится к сценарию.
- Указывать только фактически участвующие компоненты, реальные методы и endpoint'ы; неизвестные значения обозначать `TBD`.

#### 6. Таблица «Задачи»

- Присутствует в каждой US всегда: `| Название | Ссылка |`.
- Только реально заведённые задачи этой US. Нет задач — таблица пустая.
- Не создавать фиктивные строки по компонентам (`Backend`, `API Gateway`, `Mobile`, `Web`…).
- Нет названия задачи — в «Название» указывать её ID (как в примере шаблона).

#### 7. Что не создавать без данных

На уровне SRS целиком не создавать без фактических данных: `Основные принципы`, `Функциональные требования`, `MVP / Post-MVP`.

На уровне конкретной User Story не создавать без фактических данных: `Дизайн`, `Предусловия`, `Опционально`, `Взаимодействие компонентов`.

`Полезные материалы` присутствуют всегда, но без фиктивных строк.

`Задачи` присутствуют в каждой User Story всегда. Если задачи ещё не заведены, таблица остаётся пустой.

#### 8. Чек-лист

- [ ] «Полезные материалы» есть и содержат только реальные источники.
- [ ] US сгруппированы по функциональным областям; заголовки `US <N>. <Название>`.
- [ ] В шагах с API указан `метод endpoint` в скобках или `TBD`.
- [ ] Sequence-диаграмма есть только там, где участвует несколько компонентов, и без лишних участников.
- [ ] Таблица «Задачи» есть в каждой US, без фиктивных строк.
- [ ] Неиспользуемые необязательные разделы удалены; ничего не продублировано из BRD.
