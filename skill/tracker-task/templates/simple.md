## Теги заголовка

Формат заголовка — `SKILL.md` §1: `<теги> <Раздел/процесс>. <Что сделать>`, раздел отделяется точкой. Для бага — тот же формат, заголовок называет, что исправить; `[Баг]` не ставится (исключение — очередь, где так принято).

Примеры:

- `[B] Возврат. Одинаковые правила запроса и проверки банковских реквизитов на сайте и в мобильном приложении`
- `[B][Mobile API] Возврат из мобильного приложения. Сохранять номер карты вместо номера лицевого счёта`
- `[F] Возврат. Проверка банковских реквизитов по общим правилам`
- `[iOS] Возврат. Проверка банковских реквизитов по общим правилам`

## Состав разделов

### Вариант А. Доработка

| Раздел / блок | Обязательность | Когда писать |
|---|---|---|
| Заголовок `<теги> <Раздел/процесс>. <Что сделать>` | обязательно | всегда |
| Цель — одна фраза в инфинитиве (`SKILL.md` §7 п. 1) | обязательно | всегда |
| Проблема — 1–2 предложения в начале «Описания реализации» | необязательно | если без неё непонятна доработка |
| Список «Нужно» | необязательно | если изменений несколько; один пункт на каждый раздел «Описания реализации» |
| Описание реализации → `### N. <название>` | обязательно | один раздел на каждое изменение (правило, проверка формата и т.д.) |
| — правило бизнес-языком | обязательно | если меняется правило / условие |
| — таблица мест «Платформа / Эндпоинт / Что меняется / Что сейчас» | обязательно | всегда, если изменение затрагивает больше одного места |
| — таблица мест «Платформа / Эндпоинт / Что делает» | необязательно | вместо предыдущей, если поведение «сейчас» описывать не нужно (например, правила формата пишутся с нуля) |
| — таблица полей «Поле / Правило» | необязательно | если описываются правила проверки полей |
| — блок «признак для интерфейса / проверка при отправке» | необязательно | если одни эндпоинты отдают клиенту признак, а другие проверяют то же правило при отправке |
| — блок «эндпоинт меняется автоматически» | необязательно | если есть эндпоинт, который получит изменение через общие данные без доработки |
| — блок «вызов через гейт / прокси» | необязательно | если в задаче есть эндпоинты МП |
| — блок «общую проверку не меняем» | необязательно | если правило нельзя менять в общем месте, потому что оно используется в других сценариях |
| — блок «связь с другим разделом» | необязательно | если выполнение одного раздела зависит от результата другого |
| — блок «ошибки / формат ответа» | необязательно | если меняются проверки, которые возвращают ошибки |
| Критерии приёмки: подраздел на каждый раздел реализации | обязательно | всегда; нумерация сквозная |
| — критерий «что не должно измениться» | обязательно | всегда, если есть блок «общую проверку не меняем» или затронуты соседние сценарии |
| — критерий «совместимость с текущими клиентами» | необязательно | если меняются ответы или ошибки эндпоинтов, которые уже используют сайт / МП |

### Вариант Б. Баг

Структура — по задачам С. Щербатых DEVIOS-2584 и ECOMDEV-1890 (стиль — `SKILL.md` §7). Используется для любого канала — `[B]`, `[F]`, `[iOS]`, `[Android]`.
Блоки с пометкой «(BE)» взяты не из её задач, а из нашей задачи `BE_баг_номер_карты_возврат.md`.
Граница с каркасом Г «Корректировка» (`mobile-app.md`): причина известна и требование однозначно → Г; причину надо найти (2584) → этот вариант.

| Раздел / блок | Обязательность | Когда писать |
|---|---|---|
| Заголовок `<теги> <Раздел>. <Что исправить>` («[F] Чекаут. Обрабатывать адрес как ручной при пустом house/postalCode» — 1890) | обязательно | всегда; `[Баг]` не ставится, исключение — очередь, где так принято |
| Первопричина: ссылка | необязательно | если баг найден в другой задаче, инциденте или обращении |
| Цель (BE) | необязательно | если без неё из заголовка непонятен результат |
| Описание проблемы: что происходит — при каком условии, что приходит в ответе API, что видит пользователь | обязательно | всегда; прозой или шагами |
| — шаги воспроизведения, фактический и ожидаемый результат (BE) | необязательно | если проблему нельзя описать одним условием |
| — контекст | необязательно | если без предыстории непонятно, откуда данные |
| — где ошибки нет | необязательно | если на другой платформе / в другом сценарии работает правильно |
| — ранее исправлялось | необязательно | если баг уже чинили: в какой задаче, почему не сработало, запись во вложении (2584) |
| — почему так происходит | необязательно | если причина установлена; обязательно, если без неё исправление можно сделать не в том месте или баг выглядит как ожидаемое поведение |
| — проблема | необязательно | после «Почему так происходит»: конкретный сбойный случай; здесь же — «это не баг <чего>, а ожидаемое следствие …» (2584, 1890) |
| — почему нельзя исправить полностью на <стороне> | необязательно | если исправление частичное или разнесено по нескольким задачам (бэк и клиенты) |
| Необходимо: что исправить | обязательно | всегда; если причина не найдена — что исследовать («Проверить, не относится ли …» — 2584) |
| — куда должно доходить значение (BE) | необязательно | если данные уходят дальше: админка, 1С, RetailCRM и т.д. |
| — работа с историческими данными (BE) | необязательно | если баг уже испортил сохранённые данные |
| Ожидаемое поведение | необязательно | если оно не очевидно из «Необходимо» |
| Критерии приёмки (в «Тестировании», cut): основной результат | обязательно | всегда; конкретное проверяемое условие и ожидаемый результат, а не общая фраза; точные входные значения (страна, город, статус заказа, значение поля) — когда без них нельзя однозначно определить ожидаемый результат |
| — по каждой системе, куда уходят данные | необязательно | если есть пункт «куда должно доходить значение» |
| — что не должно измениться | обязательно | всегда |
| — результат по историческим данным | необязательно | если есть пункт «работа с историческими данными» |
