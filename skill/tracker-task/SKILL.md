**Назначение.** Скилл описывает формат одной задачи разработчику в Яндекс Трекере: что и в каком порядке написать, чтобы разработчик сделал без уточнений.

#### 1. Заголовок задачи и декомпозиция

Формат для всех типов задач, включая баги: `<теги> <Раздел/экран>. <Что сделать>` — раздел отделяется точкой, не двоеточием.
Пример: `[B][Web] Форма возврата. Метод для получения способов возврата`.
Баг — тот же формат, заголовок называет, что исправить: `[F] Чекаут. Обрабатывать адрес как ручной при пустом house/postalCode` (1890). `[Баг]` после тегов не ставится; исключение — очередь, где так принято.

| Теги | Значение |
|---|---|
| `[B]` | Задача на бэк без привязки к одному каналу (или сразу несколько каналов — тогда все эндпоинты перечислены в «Цели») |
| `[B][Web]` | Доработка для сайта (эндпоинты `/api/...` монолита) |
| `[B][Mobile API]` | Доработка для МП на стороне монолита (эндпоинты `/mobile/...`) |
| `[B][Mobile API][Gate]` | Для МП нужен эндпоинт и на Gate (`/api/v1/...`, сервис `mobile-monorepo-go`) |
| `[B][Admin]` | Настройки и поля в админке |
| `[B][<сервис>]` | Задача в другом сервисе: `[B][Monolith-bfb]`, `[B][orders-srv-go]` |
| `[F]` | Фронт сайта |
| `[iOS]` / `[Android]` | Мобильное приложение |

Шаблон задаёт состав разделов, а не обязательный объём: блок, условие которого не выполнено, удаляется. Стиль изложения во всех шаблонах — §7.

- Новый метод для обоих каналов → **три задачи**: `[B][Web]`, `[B][Mobile API]`, `[B][Mobile API][Gate]` (1239 / 1240 / 1241).
- Для МП состав задач (только гейт / гейт + доработка downstream / гейт + новый downstream) определяется проверкой цепочки по разделу 2.
- Небольшая доработка существующего метода во всех каналах → одна задача `[B]` со списком эндпоинтов по каналам (1126).
- Задача на Gate — по шаблону [templates/gate-proxy.md](./templates/gate-proxy.md): пара `Gate: ...` / `Site: ...`, ссылка на задачу `[B][Mobile API]`, критерии приёмки. Контракт не повторяется.
- Настройки админки — **отдельной задачей** `[B][Admin]`, если основная задача большая (1860 + 1887) или настройки нужны раньше логики; иначе — разделом «Админка» в задаче на логику (1731). Решает аналитик.
- Передача данных во внешние системы (RetailCRM, 1С) — **отдельная задача** по шаблону [templates/integration.md](./templates/integration.md); в задаче на эндпоинт — только ссылка на неё в «Связях».

#### 2. Цепочка вызова МП → Gateway → backend

Перед описанием доработки эндпоинта для МП всегда проверяется **вся цепочка вызова**: МП → Gateway → downstream (backend-эндпоинт монолита `/mobile/...` или другого сервиса). Что дорабатывать, решается только после проверки текущего downstream и того, где выполняется бизнес-логика.

**Хосты.** Идёт переезд со старого гейта на новый; дорабатывается **только новый гейт**.

| Хост | Что это |
|---|---|
| `core.12stz.*` | Старый гейт — не дорабатываем |
| `mobile.12stz.*` | Новый гейт (`mobile-monorepo-go`, swagger `mobile.12stz.dev/swagger`) — дорабатываем и создаём здесь |
| `mobiledev.12stz.tech/mobile/...` | Прямой вызов монолита (`/mobile/...`), встречается в примерах тестирования 1240 / 1241 |

**Шаг 1. Проверить цепочку:**
1. Какой путь вызывает МП и на каком гейте он опубликован — по swagger нового гейта и по запросам приложения.
2. В какой downstream-эндпоинт гейт проксирует запрос.
3. Где выполняется бизнес-логика: в гейте (`core` или новом) или в downstream.
4. Хватает ли текущему downstream данных и логики для новых требований.

**Шаг 2. Выбрать, что дорабатывать:**

| Ситуация после проверки | Что ставится задачами |
|---|---|
| Новый гейт может использовать существующий downstream без изменений | Только эндпоинт на гейте `[B][Mobile API][Gate]` (создать или доработать) |
| Существующему downstream не хватает данных или логики | Два уровня: эндпоинт на гейте `[B][Mobile API][Gate]` **и** доработка существующего downstream `[B][Mobile API]` |
| Нужной backend-операции нет | Два уровня: эндпоинт на гейте `[B][Mobile API][Gate]` **и** новый downstream-эндпоинт `[B][Mobile API]` |
| Логика сейчас выполняется в старом `core` | Дополнительно решить, куда она переезжает: в новый гейт или в backend. Решение и причина — в строке `Endpoint` (часть Gate) и в «Вне этой задачи» |

Нельзя автоматически считать, что уход с `core` означает только новый эндпоинт на гейте или, наоборот, обязательно два эндпоинта.

**Шаг 3. Записать результат.** В строке `Endpoint` в начале «Описания реализации» задачи `[B][Mobile API]` (не в «Цели» — решение 16.11.2026) — **всегда пара путей**, даже если гейт в этой задаче не дорабатывается: МП вызывает гейт, гейт — метод монолита, и пути у них разные (`Gate: GET /api/orders/{id}` → `Site: GET /mobile/orders/{id}`). Строка Site — метод, который дорабатывается; строка Gate — через какой гейт (`core.12stz.*` / `mobile.12stz.*`) приходит запрос и есть ли задача на гейт. Sequence-диаграмма вызовов нужна, только если цепочка нетривиальна (логика в гейте, несколько downstream). Работы на других уровнях — строкой «Вне этой задачи» и в связях Трекера. Чего не удалось проверить (например, только ли проксирует `core`) — в «Открытые вопросы». Сам разбор (где логика, почему выбран вариант) в задачу не переписывается.

#### 3. Правила заполнения блоков

Правила ниже — для задач на метод бэка: [change-existing.md](./templates/change-existing.md), [new-web.md](./templates/new-web.md), [new-mobile.md](./templates/new-mobile.md) (переработаны 17.11.2026 по решениям `knowledge/_archive/skills_2026-11-17/Анализ_скиллов_эндпоинты.md`, часть 3, §4). Остальные типы — правила в своих шаблонах `templates/`, стиль — §7.
Блоки — в порядке шаблона; блок с пометкой «если» удаляется, когда условие не выполнено; разделы ради шаблона не добавляются.
**Порядок блоков = порядок работы разработчика:** новые данные БД → параметры → логика. Разделы работ нумеруются (`#### 1.`, `#### 2.`, `#### 3.`) и соответствуют пунктам списка «Необходимо».
Доработка существующего метода: описываются **только изменения**; существующая логика не пересказывается, а помечается **AS-IS** (см. «Логика»).
Контракт — по `skill/openapi-spec` (сценарий 2.1 — новый метод, 2.2 — изменение существующего).

**Формат Трекера.** Задача заводится в Яндекс Трекере (YFM): таблицы — markdown или `#| ... |#`; крупные таблицы, примеры ответа, flowchart и шаги логики сворачиваются в `{% cut "..." %}`; неподтверждённое помечается на месте `{red}(...)`. Файл в `requirements/backend/` — копия задачи из Трекера.

**Связи и трассировка.** Связи (QA, iOS / Android, гейт, задача на модель данных) ставятся штатными связями Трекера; трассировка к `BR` / `US` / `UC` ведётся в матрице трассируемости (`skill/traceability-matrix`). В тексте задачи — только то, что влияет на работу разработчика: зависимость выкатки и «будет реализован в рамках задачи KEY» отдельной строкой (§7, п. 18).

##### «Цель»
Одна фраза по §7, п. 1; для крупной задачи — одно предложение со всем объёмом. Путь метода в «Цель» не пишется.

##### Начало «Описания реализации»
- **Назначение** (новый метод) — где и когда вызывается, что делает и чего не делает (§7, п. 2).
- **Строка `Endpoint`** — `<МЕТОД> <путь>`; для Mobile API — пара Site / Gate в той же строке (раздел 2, шаг 3); задача `[B]` на несколько каналов — строка на каждый канал.
- **«Контекст»** (доработка) — как метод работает сейчас; текущий ответ — в cut; «Ограничения, текущий метод не позволяет: 1… 2…» (1214).
- **Аналог** — если то же уже описано для другого канала: ссылка на задачу-аналог и только отличия (§7, п. 9).
- **Список работ «Необходимо»** — если работ больше двух; каждая работа одной строкой: доработать метод; создать параметр / поле / таблицу; добавить поля в запрос или ответ (имена полей перечислить); изменить логику / расчёт поля. Подробности в список не переносятся. В `logic-admin.md` список называется «Что нужно сделать» (1860) или «Необходимо» (1731) — как в образцах.
- **«Вне этой задачи: …»** — если по цепочке МП → Gateway → backend (раздел 2) нужны работы на другом уровне.

##### «Создать новые данные БД»
Новый параметр админки (`cms_parameters`), поле или таблица — **первым разделом**: это первая работа разработчика (миграция). Для параметра — таблица `alias | title | description | value | value_type` (форма — `templates/logic-admin.md`, раздел «Админка»); для поля или новой таблицы — `Поле | Тип | Обяз-ть | Описание` и под ней правила заполнения: когда создаётся запись, кто и когда заполняет поле (1339). «По аналогии с существующим `<...>`» — если есть образец.

##### «Параметры»
- **Входные:** таблица `Параметр | Место | Тип данных | Обязательность | Описание`. Не меняются — одна строка «Входные параметры не меняются»; нет — «Отсутствуют». Заголовки — только специфичные для метода.
- **Изменённые поля** (доработка): таблица `Параметр | Было | Стало` — для существующих полей, у которых меняется смысл или правило расчёта, включая элементы `messages[]` и тексты.
- **Новые поля ответа:** таблица `Поле | Тип данных | Источник | Описание` (решение части 3, §4 п. 6). Полные пути (`items[].available_return_quantity`, `order_delivery.pvz.id`); вложенный объект — отдельной таблицей. Требования к описанию поля (nullable, enum, когда `null`) — `openapi-spec` SKILL.md §3 п. 8. Простое правило значения — прямо в описании поля; в описании допустимо коротко указать назначение («для проверки в геосервисе»).
- **Ответ аналогичен существующему методу** — одной строкой «Ответ аналогичен методу `<…>`» + только отличия (1339).
- **Пример ответа** совпадает с таблицей; поля AS-IS допустимы для контекста с пометкой «поля AS-IS без изменений сокращены»; новые поля — `//новый параметр`. Если ответ различается по веткам — пример на каждую ветку.
- **Взаимоисключающие объекты** (`address` / `pvz` / `store`) — по `openapi-spec` SKILL.md §3 п. 9. Если в монолите уже есть такое ветвление — сослаться на него (`getFullAddressCompiled()`, §7 п. 21).
- **Сценарии использования** (доработка, если новые параметры комбинируются или меняют выдачу) — «пример запроса → Метод должен вернуть …» (1214, 1508).
- Имена — по [словарю полей](../openapi-spec/references/field-glossary.md); для Web и Mobile — по колонке «Web» в [mobile.md](../openapi-spec/references/mobile.md).

##### «Логика»
Изменение логики описывается **в той же задаче**, где добавляются новые параметры.

- **Эндпоинт** — путь Site, в котором выполняется логика (строка `Endpoint`).
- **Порядок шагов** — порядок выполнения; получение данных и расчёты стоят **до** проверок, которые от них зависят. Первый шаг закрытого метода — проверка доступа; последний шаг нового метода — «Сформировать и вернуть соответствующий ответ». Строка «Проверки выполняются последовательно — от первого пункта к последнему» — если порядок неочевиден (решение части 3, §4 п. 3).
- **Шаг** — по §7 п. 3–6: с глагола; условие и реакция в одном предложении; источник `<таблица>.<поле>`; результат — в поле ответа или внутреннюю переменную. Ветка «иначе» — где она есть, не механически.
- **Внутренние переменные** — `<name>` (`<days_limit>`, `<return_deadline>`), если значение используется в нескольких шагах. В ответ и БД не попадают; имя отражает смысл.
- **Ошибка — в шаге проверки** + cut «Пример ошибки, если …» (решение части 3, §4 п. 5); отдельная таблица — раздел «Ошибки» ниже.
- **Существующая логика** не пересказывается. В задаче — одна строка: «Далее — существующая логика <чего>, не меняется» (решение части 3, §4 п. 4). Смысл этой строки (действует для разработчика и QA без повторения в задаче):
  > **AS-IS:** далее применяется существующая логика <чего>. Она не изменяется в рамках данной задачи и должна соответствовать текущей реализации. Приведённые в задаче условия могут быть описаны укрупнённо; если фактическая AS-IS-логика отличается, необходимо сохранить текущую реализацию при условии, что она не противоречит новой логике.

  Если без перечня непонятно место новой логики — под строкой укрупнённый перечень AS-IS-условий, **сверенный с кодом** монолита.
- **Логика расчёта** — нетривиальный расчёт: формула в `code` с пояснением величин + cut «Примеры расчёта» по каждому случаю (1321).
- **Повторный вызов** метода создания — что происходит: ошибка или существующая запись без дубля (1271).
- **Новая логика внутри существующей.** Если новая проверка заменяет часть AS-IS-проверки — явно: что из AS-IS остаётся, что исключено и чем заменено. Пример (2343): срок 14 дней внутри `canPositionBeReturned()` отсекал клиентов F&F раньше проверки 30 дней — проверка срока вынесена до первичной проверки позиций и из неё исключена.
- **Значения в каждой ветке.** Для каждого нового и изменённого поля ответа — значение во всех ветках, где расчёт не выполняется (`can_be_returned = false`, `available_return_quantity = 0`, `request_until_date = null`).
- **Ограничение** — известное влияние AS-IS-логики или другого решения на новый расчёт, которое в задаче не прорабатывается: цитатой «Ограничение: …».
- **Соединения таблиц** не расписываются условиями SQL — разработчик возьмёт их из модели данных. Пишется только неочевидное: ключ сопоставления (`order_position_id`, а не штрихкод) и чей статус фильтруется (заявки, а не позиции возврата).
- **Неизменённый расчёт**, который остаётся в ответе рядом с изменённым, — одной строкой «логика не меняется».
- **Flowchart** — по желанию, в `{% cut %}`. Текст шагов — канон; схема совпадает с ним узел в узел.
- **Только то, что нужно сделать.** Пояснения «зачем» (для чего поле на следующих шагах, как работают соседние сервисы) в шаги не пишутся. Исключение — одна фраза-предостережение, если без неё разработчик возьмёт неверный источник («не `cms_orders.store_code`»).
- **Состав полей — по макетам** (`projects/<проект>/sources/mockups/`, `projects/<проект>/requirements/screen-spec/`). Поведение AS-IS — справка, не ориентир.

##### Колонка «Источник» (вместо прежнего раздела «Маппинг API → БД»)
Решение части 3, §4 п. 6: источник поля — колонкой в таблице выходных параметров, отдельная таблица маппинга не пишется.
- Поле из БД — `<таблица>.<поле>`; через связь — с условием связи: `cms_delivery_tk.slug` (по `cms_orders.delivery_method = cms_delivery_tk.id`). Соединения таблиц условиями SQL не расписываются (см. «Логика»).
- Вычисляемое поле — «Расчётный — см. раздел <N>» или короткая формула через поля-источники.
- Источник «аналогично методу / модели `<…>`» — допустим, если поле берётся так же, как в существующем методе (1214, 1215).
- Новые входные параметры, которые **сохраняются**, — отдельная таблица «Запрос → БД» (в cut).
- Имена и типы колонок сверяются с ERD (`projects/<проект>/requirements/diagrams/erd/`), `architecture-docs/monolith/database.puml` и кодом монолита; неизвестный тип — в «Открытые вопросы».
- Внешние системы в источники не входят — отдельная задача (раздел 1).

##### «Ошибки»
Правила выбора структуры, кодов и HTTP-статусов — [openapi-spec/references/errors.md](../openapi-spec/references/errors.md); конверт ошибки канала — [web.md](../openapi-spec/references/web.md) / [mobile.md](../openapi-spec/references/mobile.md).
- Состав ошибок не меняется — одна строка «Состав ошибок не меняется»; недоступность бизнес-действия (возврат недоступен) ошибкой не является.
- **Для одного метода ошибки пишутся в шагах логики** + cut «Пример ошибки, если …» (решение части 3, §4 п. 5).
- **Таблица ошибок** — только если ошибок много или задача сразу на два канала; формат — [errors.md](../openapi-spec/references/errors.md), раздел 4. Один код на группу ошибок, по которому ветвится клиент, — и тот же код в связанных методах (1271, 1339).
- **Новый предметный код** — номер из свободного диапазона `ResponseErrorCode`, ключ перевода, HTTP-статус и требование добавить код в `getStatusCode()` ([errors.md](../openapi-spec/references/errors.md), раздел 1.3).
- **Web** — способ сборки ответа (сервис ответа или ответ в контроллере, как у соседних методов): от него зависит HTTP-статус ошибки ([web.md](../openapi-spec/references/web.md), раздел 1).

##### «Совместимость с МП»
Общие правила обратной совместимости и версионирования — `AGENTS.md` → «Правила системного анализа при разработке нового функционала», п. 4–5; ниже — их применение к Mobile API монолита.

Обязателен при доработке **существующего** метода Mobile API. Старые версии приложения продолжают вызывать изменённый метод,
а механизма ветвления по версии в монолите нет: `x-version` пишется только в лог ошибок (`Mobile\Controllers\BaseController`).
Отсечь старые версии можно только принудительным обновлением — `version_ios_required` / `version_android_required` в `AppVersionsConfig` (админка).

Каждое изменение классифицируется:

| Изменение | Тип | Что увидит старая версия |
|---|---|---|
| Новый необязательный параметр запроса | безопасное | — |
| Новое поле в ответе | безопасное* | *если приложение игнорирует неизвестные поля |
| Новый эндпоинт | безопасное | — |
| Новый обязательный параметр / параметр стал обязательным | **опасное** | Не шлёт его → ошибка валидации |
| Поле ответа удалено / переименовано | **опасное** | Падение или пустое место на экране |
| Сменился тип / формат поля | **опасное** | Ошибка разбора ответа |
| Поле ответа может стать `null` | **опасное** | Падение, если ожидается значение |
| Новое значение enum в ответе | **опасное*** | *если приложение не обрабатывает неизвестные значения |
| Сменились коды ошибок, конверт, поведение по умолчанию | **опасное** | Неверный текст ошибки или ветка экрана |

В задаче (решение части 3, §4 п. 8: все изменения безопасные — одна фраза «Все изменения обратно совместимы для текущих версий МП: <какие>»; таблица — только при опасных изменениях):
1. Каждое опасное изменение — строкой таблицы блока с типом по классификатору.
2. Решение для каждого опасного изменения: сделать безопасным (новое поле рядом, старое не удалять) / новый эндпоинт / поднять обязательную версию (решение продукта) / ветвление по `x-version` (отдельная доработка — механизма нет).
3. Минимальная версия МП, поддерживающая изменение, — из задач iOS / Android в «Связях».
4. Критерий приёмки: метод проверен на последней версии приложения из стора и на новой сборке.
5. Порядок выкатки: бэк раньше приложения и работает с обеими версиями.

Пока команда МП не подтвердила, отметки `*` в классификаторе — в «Открытые вопросы» задачи:
игнорирует ли приложение неизвестные поля ответа; как обрабатывает неизвестное значение enum; кто принимает решение о поднятии обязательной версии.

##### «Тестирование»
- **Предусловия** — статус заказа, сроки (`cms_orders.end_date`), включённые настройки в админке, стенд (на dev нет обменов с RetailCRM → `end_date IS NULL`).
- **Критерии приёмки** — в cut «Критерии приёмки»; проверяемые: что сохраняется и где, какие ошибки на какие входы, изменения в swagger / Gate. Шаблонные критерии («Разработан новый метод согласно описанию») — только вместе с проверяемыми (§7 п. 17).
- **Доработка — обязательный критерий обратной совместимости:** «Если новые параметры не переданы, метод возвращает данные в текущем формате и логике» (1214).
- Блок не пишется, если тест-документацию ведёт отдельная задача QA (связь в Трекере).

##### «Открытые вопросы»
Всё, что не подтверждено кодом, ERD, макетами или командой: неизвестный тип колонки, неподтверждённое поведение клиента, нерешённое бизнес-правило. В тексте — пометка `{red}(...)` на месте, где решение влияет на логику; в конце — сводка вопросов с адресатом, чтобы было видно, что блокирует реализацию.

#### 4. Общие правила (выведены из замечаний QA по примерам)

Правила API — невалидные значения без 500, одно имя на один смысл, enum = значения системы, пример = таблица, поведение по умолчанию, без секретов, расчёт на бэкенде — перенесены 17.11.2026 в `skill/openapi-spec` SKILL.md §3 (прежние п. 1–5, 11, 12) и применяются к каждой задаче на метод. Здесь — правила задачи:

6. **Зависимость от настроек и данных.** От каких настроек админки (`cms_return_method`, флаги по каналу) и полей БД (`cms_orders.end_date`) зависит результат и что отдаётся, если настройка выключена / поле пустое (1126, 1239).
7. **Куда пишется и откуда берётся** — колонка «Источник» и «Запрос → БД»; передача во внешние системы — отдельная задача (в 1126 была совмещена — так больше не делаем).
8. **Проксирующий Gate прозрачен.** Если гейт только проксирует, его ответ = ответ прямого запроса в downstream при тех же query-параметрах, теле и заголовках (1241). Если в гейте выполняется логика — она описывается в задаче на гейт (раздел 2).
9. **Текст ошибки для клиента.** Согласовать с МП, из какого поля строится сообщение (`error_text` или `error_data[].message`) (1126).
10. **Старые версии МП не ломаются** — блок «Совместимость с МП».

Нумерация п. 6–10 сохранена: на неё ссылаются примеры и анализ.

**Правила**

1. **Цель** — одна фраза в инфинитиве о результате реализации: «Создать новый метод для проверки пользователя на фрод перед созданием бронирования» (1289). В задачах фронта, МП и интеграций допустимо «…, чтобы <результат для пользователя>» (DEVIOS-2543); бизнес-обоснование — в «Контекст». Несколько методов — цель списком методов (TNT-2515). Существительным («Доработка метода…») цель не пишется.
2. **Назначение и границы.** Для метода — где и когда вызывается, что делает и **чего не делает**: «должен возвращать только результат проверки доступности бронирования» (1289). Для клиента — когда метод **не** вызывается: «Если не авторизован, метод не вызывать» (2191).
3. **Шаг логики начинается с глагола**: Проверить / Получить / Найти / Отфильтровать / Сохранить / Вызвать / Отобразить / Сформировать и вернуть. Один шаг — одно действие системы. Последний шаг нового метода — «Сформировать и вернуть соответствующий ответ» (1339). Первый шаг закрытого метода — проверка доступа. Исключения:
   - **экран** (фронт, МП) — пункт начинается с элемента, триггера или глагола действия. Элемент — заголовком пункта, поведение — вложенным списком: «Кнопка "Отправить"», под ней «1. По умолчанию неактивна, при нажатии на кнопку, когда оценка не выбрана…» (DEVIOS-1850). Триггер — «При нажатии на кнопку "Подтвердить бронь" вызывать метод `POST /reservation`» (2300);
   - **цепочка интеграции** — сервис заголовком пункта, его действия списком под ним в настоящем времени: под «monolith-bfb:» — «передает `email` в grpc метод mindbox-srv-go» (2043).
4. **Условие и реакция — в одном предложении**: «Проверить авторизацию пользователя, если не авторизован, вернуть ошибку авторизации» (1289). Вложенность 1 → 1.1 → 1.1.1 — только для уточнения шага.
5. **Перечень состояний — списком со стрелкой**: «`is_subscribed = false` -> чекбокс показываем неотмеченным, в том числе если статус получить не удалось» (DEVIOS-2618). Случай «ответ не получен / ошибка» — в том же списке.
6. **У каждого значения есть источник** в `code`: `таблица.поле`, статусы `internal_id`, поле ответа другого метода, параметр `cms_parameters`. Источник неизвестен — не выдумывать: `{red}(…)` и «Открытые вопросы».
7. **Определения вводятся решением**: «Активными считаем заказы в незавершенных статусах `cms_order_statuses.internal_id NOT IN (…)`» (1289); «Передавать `isSubscribed = false` не будем» (1962, 2043).
8. **Обоснование — одной фразой** через «так как» / «иначе» или в «Контексте» / `{% note info "Для информации" %}`. В шаги не смешивается: шаги — что сделать, контекст — почему.
9. **Повтор — отсылкой**: «аналогично текущей реализации», «по правилам п. 2», «ориентироваться на реализацию в МП». **Аналог метода** (тот же метод для другого канала, доработка «как в МП») — ссылка на задачу-аналог и **только отличия**: путь, формат ответа, ошибки, отличающиеся поля, что уже сделано в задаче-аналоге (таблицы, параметры, коды). Логику аналога не копировать: в копиях 2182 и 2222 разошлись типы и тексты.
10. **Свобода реализации оговаривается**: «(название на усмотрение разработки)», «Вариант на усмотрение разработки:», «Способ реализации определяется с разработкой».
11. **Нефункциональное — числом и последствием**: «Установить timeout на ожидание ответа от monolith-bfb 2 секунды (значение может быть изменено на усмотрение разработки)» (1962); ошибка вызова не блокирует основной процесс (создание заказа).
12. **Доработка метода — поведение без новых параметров**: «Если новые параметры не переданы, метод должен работать по текущей логике без изменений, структура ответа не меняется» (1214). Ограничения текущего метода — списком «текущий метод не позволяет: 1… 2…».
13. **Тексты для пользователя — дословно в кавычках**, с указанием, приходят ли они с бэка или задаются на клиенте. Подписи элементов (заголовки, кнопки, поля) называются дословно, чтобы на них можно было сослаться: Кнопка "Применить промокод" (DEVIOS-2543). Не пересказывается оформление макета (вёрстка, цвета, отступы) — «по макету».
14. **Таблица — только для однотипных перечислений**: параметры, поля, маппинг, комбинации флагов, тексты ошибок (если задача про них). Правила и последовательности — текстом или списком.
15. **Схемы — только для нетривиальной цепочки**, в cut; текст шагов — канон.
16. **Примеры**: длинный JSON ответа, большое тело, XML — в `{% cut %}`; короткое тело (несколько полей) и фрагмент proto — без cut. Пример реальный или реалистичный; новые поля — `//новый параметр`; неизвестный код ошибки — `XXXXX`; секреты и идентификаторы окружения — плейсхолдерами `{Секретный ключ}`, `{Идентификатор точки интеграции}`. **Скриншоты**: к шагу — рядом с ним, без cut; иллюстрации контекста (1771) и скриншоты отдельных состояний (DEVIOS-2122) — в cut.
17. **Пометки**: `{red}(…)` — только блокер, открытый вопрос, upd («НЕ КАТИТЬ БЕЗ KEY», «upd 19.08») и неутверждённое название метода — `{red}(черновой вариант)` перед путём (1966, 2007); выкатка без блокера — обычной строкой. Отменённое требование — `~~…~~` со ссылкой на новую задачу, а не удаление; так же — старый роут или путь. Критерии приёмки — в cut, проверяемые «условие — результат», сгруппированы по сценарию, состоянию или каналу. Шаблонные критерии («Разработан согласно документации») — только вместе с проверяемыми.
18. **Зависимости и выкатка — отдельной строкой**: «Выкатывать после KEY и совместно с фронтом» (2253); «будет реализован в рамках задачи KEY».
19. **Объём по задаче.** Мелкая доработка — без разделов шаблона: «Цель», что изменить в 1–2 предложения, при необходимости значения параметра и пример JSON с `//новый параметр` (1215, 1633). Gate — около 10 строк (2065). Разделы ради шаблона не добавляются.
20. **Не делать**: дублировать одну логику в нескольких разделах; пересказывать оформление макета; оставлять пустые разделы; смешивать требования с допущениями и собственными предположениями.
21. **Имена кода.** В бэк-задачах класс или метод кода можно назвать как указатель «где взять / аналогично чему» (1399, 1215, 2066; `canPositionBeReturned()` в §3), без фрагментов кода и номеров строк. В задачах фронта и МП имена классов, архитектура и код не пишутся.
22. **Граница задачи — явно**: что не меняется («Для сайта логика категорий не меняется» — 2066), что не входит («Тогл … не добавляем, так как …» — DEVIOS-2122), что уже есть («(уже реализовано)» — DEVIOS-2002), кто обрабатывает дальше («Дальнейшую обработку … выполняет Monolith» — 2043). К «что не меняется» — критерий приёмки на регрессию.
23. **Временное решение MVP — одной фразой**: «Сейчас …, в пост мвп …» (1339).
24. **Обоснование в скобках внутри шага** — только если без него разработчик выберет не ту реализацию; остальное — в «Контекст».
