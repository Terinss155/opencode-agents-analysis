### Формирование BRS (Business Requirements Specification)

#### 1. Назначение

BRS — компактный документ на **одну доработку/фичу**: собирает в одном файле пользовательскую
потребность, проблематику, функциональные и нефункциональные требования, критерии приёмки.

BRS — **альтернативный «всё-в-одном» формат**. В бандле требований `requirements/`
по умолчанию используется связка **BRD (`skill/brd`) + User Story (`skill/user-story`) +
Use Case (`skill/use-case`)**; BRS применяется, когда бандл избыточен — небольшая изолированная
доработка, для которой заводить полный бандл нецелесообразно.

Канонический источник пользовательского сценария — раздел «User Story» этого документа
(формат — `skill/user-story`). Как уровни требований складываются вместе — `AGENTS.md` →
«Иерархия артефактов требований».

Файл: `{фича}_brs.md`.

#### 2. Структура документа

```markdown
| Ссылка на задачу         |     |

### История изменений документа

| Версия документа | Дата | Автор | Описание                        |

## 1. Глоссарий

по-разному разными командами.

| НПП | Термин/сокращение | Определение |
| --- | ----------------- | ----------- |

## 2. User Story

Я хочу/могу: <выполнить действие или получить результат>
Чтобы: <получить ценность>

### 2.1. Проблематика и цели

**AS-IS**
- Проблематика: проблемы, с которыми сталкивается пользователь на текущем пути к ценности.
- Пользовательский путь AS-IS: как пользователь получает ценность сейчас.

**TO-BE**
- Цель: какие цели несёт доработка.
- Пользовательский путь TO-BE: как ценность будет достигаться после доработки.

### 2.2. Реализация у конкурентов

Решения конкурентов, ссылки, изображения; плюсы/минусы; считаем ли референсом.

## 3. Функциональные требования

Основной сценарий и альтернативные сценарии.

### 3.1. Acceptance Criteria

Всё, что считаете важным, в свободной форме.
```

#### 3. Правила заполнения

- **Код Acceptance Criteria** — буквенно-числовой уникальный код для трассировки. Формат:
  `AC-<код Story>-<порядковый номер критерия>`, где «код Story» — идентификатор истории, в
  рамках которой ведётся проработка, а «порядковый номер» — номер строки в таблице AC этого
  документа.
- **Описание сценария AC** — сценарно-ориентированный подход на ключевых словах Gherkin:
  - `Given` — предварительные условия или начальный контекст;
  - `When` — событие или триггер;
  - `Then` — ожидаемый результат;
  - `And` — объединение двух высказываний;
  - `But` — в значении «И НЕ», для высказывания, которое должно быть ложным.
- **User Story** — по INVEST (`skill/user-story`): формулировка «Как… Я хочу… Чтобы…»,
  ценность выражена явно.
- **Проблематика AS-IS** — с наблюдаемым проявлением; «неудобно»/«долго» без факта или числа
  не принимаются.
- **Нефункциональные требования** — измеримые, с единицами измерения и условиями проверки;
  формулировки «быстро», «надёжно» без числа запрещены.
- Разделы 1, 2, 3 (включая 3.1) — обязательны. Раздел 4 включается по наличию требований;
  пустой подраздел не выдумывается.
- Факты не выдумывать: нет вводных — открытый вопрос, а не правдоподобное предположение.

#### 4. Пример (фрагмент)

```markdown
# BRS: Автоподстановка города доставки по последнему заказу

## 2. User Story

Как: зарегистрированный покупатель
Я хочу/могу: чтобы город доставки подставлялся из моего последнего заказа
Чтобы: не выбирать город заново при каждом оформлении

### 2.1. Проблематика и цели

**AS-IS**
- Проблематика: город доставки каждый раз выбирается вручную из списка (~1500 городов);
  на мобильных это 3 экрана и ~20 секунд, доля отказов на шаге выбора города — 8%.
- Путь AS-IS: открыл оформление → «Выбрать город» → поиск по списку → подтверждение.

**TO-BE**
- Цель: сократить шаг выбора города до подтверждения; снизить отказы на шаге до ≤ 3%.
- Путь TO-BE: открыл оформление → город из последнего заказа уже подставлен → при
  необходимости меняет вручную.

## 3.1. Acceptance Criteria

| Код | Acceptance Criteria | Сценарий |
|---|---|---|
| AC-1023-1 | Город из последнего заказа подставлен автоматически | Given у покупателя есть завершённый заказ с городом «Казань»<br>When покупатель открывает оформление нового заказа<br>Then в поле города отображается «Казань» |
| AC-1023-2 | Возможность сменить подставленный город | Given город подставлен автоматически<br>When покупатель нажимает «Изменить город» и выбирает «Уфа»<br>Then поле города меняется на «Уфа», подстановка не возвращается |
| AC-1023-3 | Нет истории заказов | Given у покупателя нет ни одного завершённого заказа<br>When покупатель открывает оформление<br>Then поле города пустое, показан выбор города вручную |
```

#### 5. Чек-лист качества

- [ ] Заполнен блок Information и история изменений (версия, статус)
- [ ] Глоссарий содержит только бизнес-термины, реально встречающиеся в документе
- [ ] User Story сформулирована по «Как… Я хочу… Чтобы…», ценность конкретна
- [ ] Проблематика AS-IS подкреплена наблюдаемым проявлением или числом
- [ ] Цель TO-BE измерима
- [ ] Каждый функциональный сценарий покрыт критериями приёмки в Gherkin
- [ ] У каждого AC уникальный код `AC-<код Story>-<n>`
- [ ] Нефункциональные требования измеримы, с единицами и условиями проверки
- [ ] Нет технических деталей реализации (алгоритмы, схемы БД, конкретные API) — это уровень системного аналитика
- [ ] Неизвестные данные зафиксированы открытыми вопросами, а не додуманы
