# [B] Форма возврата. Добавить выбор ПВЗ в качестве метода возврата

> Эталонный пример задачи типа **«доработка существующего метода» сразу по всем каналам** (Web + Mobile API + Gate в одной задаче).
> Источник: Яндекс Трекер, `ECOMDEV-1126` (экспорт 30.09.2026). Статус: тестирование завершено успешно.
> Описание перенесено без изменения смысла; комментарии сведены в блок «Что всплыло на тесте».

## Цель

Внести изменения в методы сохранения деталей возврата для сайта и МП — добавить сохранение выбранного метода возврата.

**Web**
- `POST /api/orders/{order_id}/return-details`

**Mobile API** — [Swagger](https://mobile.12stz.dev/swagger/index.html#/Delivery/post_api_v1_delivery__order_id__return_details)
- Site: `POST /mobile/orders/{order_id}/return-details`
- Gate: `POST /api/v1/delivery/{order_id}/return-details`

## Описание реализации

В теле запроса передавать дополнительное поле `method_return` c одним из значений: `courier` / `sdek-pvz` / `5post`.

```jsonc
{
  "method_return": "5post",
  "address_return": "?string", // необязательное для методов ПВЗ, в них не валидируется и не сохраняется
  "city_return": "string",
  "date_return": "string",
  "index_return": "?string"    // необязательное для методов ПВЗ, в них не валидируется и не сохраняется
}
```

## Тестирование

**Критерии приёмки**

- Метод сохраняет в заказе метод возврата в поле `return_delivery_tk` (значение соответствует полю `slug_tk` из таблицы `cms_delivery_tk`) и передаёт это значение в RetailCRM.
- Дата возврата, если выбран способ с ПВЗ, валидируется [в соответствии с критериями](https://tracker.yandex.ru/ECOMDEV-723) (раздел «Правила выбора даты»).
- Внесены изменения в swagger.
- Внесены изменения в Gate.
- Исправлен формат ошибок для МП, чтобы соответствовал [контракту](https://wiki.yandex.ru/teams/web-development/arxitektura/standarty/request-response/requestresponse-mobile-api/).

Пример error response (МП):

```json
{
  "result": {
    "error_code": 1015,
    "error_data": [
      {
        "code": "20110",
        "message": "Некорректная дата возврата",
        "target": "date_return"
      }
    ],
    "error_text": "Некорректный запрос"
  },
  "success": false
}
```

## Что всплыло на тесте (уроки для постановки)

| # | Что произошло | Чего не хватило в постановке |
|---|---|---|
| 1 | `POST /api/orders/{order_id}/return-details` с `method_return` вне enum (`invalid_method`) или `null` → **HTTP 500** (`UnexpectedValueException` / `TypeError`). Ожидалось: 200, `status: error`, ошибка валидации поля («Поле Метод возврата заполнено некорректно» / «Необходимо выбрать Способ возврата»). | Явное поведение для значения вне enum и для `null` / отсутствующего поля + текст ошибки. |
| 2 | Mobile API с валидными данными → **400** «Выбор даты недоступен». Причина — способы возврата выключены для МП в `cms_return_method`, при выключенном методе диапазон дат пустой. | Предусловие по настройке в админке (`cms_return_method`, флаги активности по каналу) и что отдавать, если метод выключен. |
| 3 | МП строит текст сообщения из `error_text`, а бэк отдаёт общий «Некорректный запрос» и массив `error_data` (ошибок может быть несколько). Решено разбирать `error_data` на стороне МП. | Согласовать с МП, из какого поля клиент берёт текст ошибки, до старта разработки. |
| 4 | Фронт сайта шёл отдельной веткой — после фикса бэка изменения пришлось доливать в ветку фронта. | Связь с задачей фронта в «Связях». |
| 5 | Передача `return_delivery_tk` в RetailCRM поставлена в той же задаче, что и доработка эндпоинта. | Передача во внешние системы — отдельная задача со ссылкой в «Связях» (правило скилла). |
