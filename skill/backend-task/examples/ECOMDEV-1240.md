# [B][Mobile API] Форма возврата. Метод для получения способов возврата

> Эталонный пример задачи типа **«новый эндпоинт на сайте для мобильного приложения»** (`[B][Mobile API]`).
> Источник: Яндекс Трекер, `ECOMDEV-1240`. Статус: протестировано (монолит и гейт).
> Парная задача для сайта — [ECOMDEV-1239](./ECOMDEV-1239.md), прокси на Gate — [ECOMDEV-1241](./ECOMDEV-1241.md).
> Отличие от Web-версии — путь `/mobile/...` и конверт ответа мобильного контракта (`success` / `result` / `total`).

**Связи**
- Связана: ECOMDEV-1342 — [QA] Подготовка тестовой документации по ECOMDEV-1240

## Цель

Добавить метод `GET /mobile/orders/{order_id}/return-method-list`, чтобы получать список способов возврата для выбранного заказа.

## Описание реализации

### 1. Характеристики метода

- Архитектура: REST
- Протокол взаимодействия: HTTPS
- Формат выходных данных: JSON

### 2. Входные параметры

Пока не валидируются и не используются, будут добавлены в рамках [ECOMDEV-1290](https://tracker.yandex.ru/ECOMDEV-1290).

| Параметр | Тип данных | Обязательность | Описание |
|---|---|---|---|
| `country_iso` (query) | string | Нет | ISO-код страны |
| `region` (query) | string | Нет | Регион |
| `region_id` (query) | string | Нет | Идентификатор региона в сервисе логистики |
| `city` (query) | string | Нет | Город |
| `city_id` (query) | string | Нет | Идентификатор города в сервисе логистики |
| `city_fias` (query) | string | Нет | Идентификатор города в системе ФИАС |

### 3. Выходные параметры

| Параметр | Тип данных | Описание |
|---|---|---|
| `success` | bool | В случае успешного ответа `true`, в случае ошибки `false` |
| `result` | obj[] | Массив объектов |
| `result[i]` | obj | Объект с данными способа возврата |
| `result[i].method` | string | `courier` / `sdek-pvz` / `5post` |
| `result[i].method_type` | string | `courier` / `pvz` |
| `result[i].title` | string | Название для вывода текстом |
| `result[i].description` | ?string | Описание (если нет — клиент ничего не выводит) |
| `result[i].active` | bool | Включен ли на сайте |
| `result[i].active_mobile` | bool | Включен ли на МП |
| `result[i].available_dates_return` | string[] | Массив дат в формате `YYYY-MM-DD` |

## Тестирование

**Критерии приёмки**

- Добавлен метод `GET /mobile/orders/{order_id}/return-method-list`, его ответ соответствует [данным в админке](https://admin.12storeez.com/cms/return/return-details) и учитывает сроки возврата для выбранного заказа.

## Что всплыло на тесте (уроки для постановки)

| # | Что произошло | Чего не хватило в постановке |
|---|---|---|
| 1 | МП попросило отдавать описание способа с бэка (необязательное поле; нет — ничего не выводится). | Согласовать с МП, какие тексты приходят с бэка, а какие зашиты в клиенте. |
| 2 | МП спросило, почему нет гео-параметров на входе, если метод выбирается после выбора населённого пункта. Ответ: привязки к гео не было, все методы доступны везде; фильтрация по гео вынесена в ECOMDEV-1290. | Явно указать, зависит ли результат от гео, и если нет — почему и где это будет сделано. |
| 3 | В исходном примере ответа стояли `cdek` / `five_post` / `pickup`. МП попросило значения как в чекауте и Pickup Points API: `sdek-pvz` / `5post`, `method_type: pvz` (`pickup` в чекауте = самовывоз из магазина). | Enum сверять с уже существующими значениями в системе; пример = таблица. |
| 4 | Без query-параметров (после ECOMDEV-1290) приходил только `sdek-pvz`. Ожидалось: зашитый дефолт `courier` (по Москве). | Поведение при отсутствии необязательных параметров (дефолт). |
