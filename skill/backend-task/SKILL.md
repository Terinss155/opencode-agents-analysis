### Постановка задачи на бэк (трекер)

**Назначение.** Скилл описывает формат одной задачи бэк-разработчику в Яндекс Трекере (очередь `ECOMDEV`):
доработка существующего метода или создание нового эндпоинта. Это **не** спецификация логики фичи
(для неё — `skill/backend-logic`) и **не** полный контракт API (для него — `skill/openapi-spec`):
задача ссылается на эти артефакты по ID, а не копирует их.

#### 1. Заголовок задачи и декомпозиция

Формат: `<теги> <Раздел/экран>. <Что сделать>`
Пример: `[B][Web] Форма возврата. Метод для получения способов возврата`.

| Теги | Значение |
|---|---|
| `[B]` | Задача на бэк без привязки к одному каналу (или сразу несколько каналов — тогда все эндпоинты перечислены в «Цели») |
| `[B][Web]` | Доработка для сайта (эндпоинты `/api/...` монолита) |
| `[B][Mobile API]` | Доработка для МП на стороне монолита (эндпоинты `/mobile/...`) |
| `[B][Mobile API][Gate]` | Для МП нужен эндпоинт и на Gate (`/api/v1/...`, сервис `mobile-monorepo-go`) |

- Новый метод для обоих каналов → **три задачи**: `[B][Web]`, `[B][Mobile API]`, `[B][Mobile API][Gate]` (1239 / 1240 / 1241).
- Для МП состав задач (только гейт / гейт + доработка downstream / гейт + новый downstream) определяется проверкой цепочки по разделу 2.
- Небольшая доработка существующего метода во всех каналах → одна задача `[B]` со списком эндпоинтов по каналам (1126).
- Задача на Gate оформляется по образцу 1241: пара `Gate: ... → Site: ...`, ссылка на задачу `[B][Mobile API]`, критерии приёмки. Контракт не повторяется.
- Передача данных во внешние системы (RetailCRM, 1С) — **отдельная задача**; в задаче на эндпоинт — только ссылка на неё в «Связях».

#### 2. Цепочка вызова МП → Gateway → backend

Перед описанием доработки эндпоинта для МП всегда проверяется **вся цепочка вызова**: МП → Gateway → downstream (backend-эндпоинт монолита `/mobile/...` или другого сервиса). Что дорабатывать, решается только после проверки текущего downstream и того, где выполняется бизнес-логика.

**Хосты.** Идёт переезд со старого гейта на новый; дорабатывается **только новый гейт**.

| Хост | Что это |
|---|---|
| `core.12stz.*` | Старый гейт — не дорабатываем |
| `mobile.12stz.*` | Новый гейт (`mobile-monorepo-go`, swagger `mobile.12stz.dev/swagger`) — дорабатываем и создаём здесь |
| `mobiledev.12stz.tech/mobile/...` | Прямой вызов монолита (`/mobile/...`), встречается в примерах тестирования 1240 / 1241 |

**Шаг 1. Проверить цепочку:**
1. Какой путь вызывает МП и на каком гейте он опубликован — по swagger нового гейта и по запросам приложения.
2. В какой downstream-эндпоинт гейт проксирует запрос.
3. Где выполняется бизнес-логика: в гейте (`core` или новом) или в downstream.
4. Хватает ли текущему downstream данных и логики для новых требований.

**Шаг 2. Выбрать, что дорабатывать:**

| Ситуация после проверки | Что ставится задачами |
|---|---|
| Новый гейт может использовать существующий downstream без изменений | Только эндпоинт на гейте `[B][Mobile API][Gate]` (создать или доработать) |
| Существующему downstream не хватает данных или логики | Два уровня: эндпоинт на гейте `[B][Mobile API][Gate]` **и** доработка существующего downstream `[B][Mobile API]` |
| Нужной backend-операции нет | Два уровня: эндпоинт на гейте `[B][Mobile API][Gate]` **и** новый downstream-эндпоинт `[B][Mobile API]` |
| Логика сейчас выполняется в старом `core` | Дополнительно решить, куда она переезжает: в новый гейт или в backend. Решение и причина — строкой Gate в «Цели» и в «Вне этой задачи» |

Нельзя автоматически считать, что уход с `core` означает только новый эндпоинт на гейте или, наоборот, обязательно два эндпоинта.

**Шаг 3. Записать результат.** В «Цели» задачи `[B][Mobile API]` — **всегда пара путей**, даже если гейт в этой задаче не дорабатывается: МП вызывает гейт, гейт — метод монолита, и пути у них разные (`Gate: GET /api/orders/{id}` → `Site: GET /mobile/orders/{id}`). Строка Site — метод, который дорабатывается; строка Gate — через какой гейт (`core.12stz.*` / `mobile.12stz.*`) приходит запрос и есть ли задача на гейт. Sequence-диаграмма вызовов нужна, только если цепочка нетривиальна (логика в гейте, несколько downstream). Работы на других уровнях — строкой «Вне этой задачи» и в связях Трекера. Чего не удалось проверить (например, только ли проксирует `core`) — в «Открытые вопросы». Сам разбор (где логика, почему выбран вариант) в задачу не переписывается.

#### 3. Правила заполнения блоков

Задача пишется по [шаблону](./template.md): блоки в его порядке; блок с пометкой «если» удаляется, когда условие не выполнено.
**Порядок блоков = порядок работы разработчика:** новые данные БД → входные и выходные параметры → логика → маппинг. Разделы работ нумеруются (`#### 1.`, `#### 2.`, `#### 3.`) и соответствуют пунктам «Что требуется изменить».
Доработка существующего метода: описываются **только изменения**; существующая логика не пересказывается, а помечается **AS-IS** (см. «Логика»).
Задача на Gate по шаблону не пишется — образец [ECOMDEV-1241](./examples/ECOMDEV-1241.md).

**Формат Трекера.** Задача заводится в Яндекс Трекере (YFM): таблицы — markdown или `#| ... |#`; крупные таблицы, примеры ответа, flowchart и шаги логики сворачиваются в `{% cut "..." %}`; неподтверждённое помечается на месте `{red}(...)`. Файл в `requirements/backend/` — копия задачи из Трекера.

**Связи и трассировка** в текст задачи не пишутся: связи (QA, iOS / Android, гейт, задача на модель данных) ставятся штатными связями Трекера; трассировка к `BR` / `US` / `UC` ведётся в матрице трассируемости (`skill/traceability-matrix`).

##### «Цель»
Одно-два предложения: что и зачем. Под ними — эндпоинты по каналам; для Mobile API всегда пара Site / Gate (раздел 2, шаг 3).

##### Начало «Описания реализации»
Список **«Что требуется изменить»** — каждая работа одной строкой: доработать метод; создать параметр / поле / таблицу; добавить поля в запрос или ответ (имена полей перечислить); изменить логику / расчёт поля. Подробности в список не переносятся. Если по цепочке МП → Gateway → backend (раздел 2) нужны работы на другом уровне — под списком строка «Вне этой задачи: …».

##### «Создать новые данные БД»
Новый параметр админки (`cms_parameters`), поле или таблица — **первым разделом**: это первая работа разработчика (миграция). Таблица атрибутов: для параметра — `alias`, `value`, `title`, `description`; для поля — тип, nullable, default. «По аналогии с существующим `<...>`» — если есть образец.

##### «Входные и выходные параметры»
- **Входные:** таблица `Параметр | Место | Тип данных | Обязательность | Описание`. Не меняются — одна строка «Входные параметры не меняются». Заголовки — только специфичные для метода.
- **Изменённые поля** (доработка): таблица `Параметр | Было | Стало` — для существующих полей, у которых меняется смысл или правило расчёта, включая элементы `messages[]` и тексты.
- **Новые поля ответа:** таблица `Поле | Тип данных | Описание`, полные пути (`items[].available_return_quantity`, `order_delivery.pvz.id`); вложенный объект — отдельной таблицей. Nullable — `string \| null`; enum — все значения через ` / `; для `null` — когда он возвращается. В описании поля допустимо коротко указать назначение («для проверки в геосервисе»).
- **Пример успешного ответа** совпадает с таблицей; поля AS-IS допустимы для контекста с пометкой «поля AS-IS без изменений сокращены». Если ответ различается по веткам — пример на каждую ветку.
- **Взаимоисключающие объекты** (`address` / `pvz` / `store`): под таблицей — когда формируется объект, какой признак выбирает ветку (`<таблица>.<поле>`), проверки по порядку, что равно `null`. Признак сверяется с данными: если поле заполнено не только в нужной ветке (как `cms_delivery_tk.store_code` у служб «Отгрузка»), ветка выбирается по типу. Если в монолите уже есть такое ветвление — сослаться на него (`getFullAddressCompiled()`).
- Имена — по [словарю полей](./references/field-glossary.md). Для Web и Mobile — по таблице соответствия из [request-response_mobile-api.md](./references/request-response_mobile-api.md).

##### «Логика»
Изменение логики описывается **в той же задаче**, где добавляются новые параметры.

- **Эндпоинт** — путь Site, в котором выполняется логика.
- **Первая строка шагов:** «Проверки выполняются последовательно — от первого пункта к последнему». Получение данных и расчёты стоят **до** проверок, которые от них зависят.
- **Шаг** — условие → действие → источник `<таблица>.<поле>` → результат (во внутреннюю переменную или в поле ответа). У каждого шага есть ветка «иначе»: что дальше не выполняется.
- **Внутренние переменные** — `<name>` (`<days_limit>`, `<return_deadline>`). В ответ и БД не попадают; имя отражает смысл.
- **Существующая логика** не пересказывается. Перед ней — пометка:
  > **AS-IS:** далее применяется существующая логика <чего>. Она не изменяется в рамках данной задачи и должна соответствовать текущей реализации. Приведённые в задаче условия могут быть описаны укрупнённо; если фактическая AS-IS-логика отличается, необходимо сохранить текущую реализацию при условии, что она не противоречит новой логике.

  Под пометкой — укрупнённый перечень AS-IS-условий, **сверенный с кодом** монолита.
- **Новая логика внутри существующей.** Если новая проверка заменяет часть AS-IS-проверки — явно: что из AS-IS остаётся, что исключено и чем заменено. Пример (2343): срок 14 дней внутри `canPositionBeReturned()` отсекал клиентов F&F раньше проверки 30 дней — проверка срока вынесена до первичной проверки позиций и из неё исключена.
- **Значения в каждой ветке.** Для каждого нового и изменённого поля ответа — значение во всех ветках, где расчёт не выполняется (`can_be_returned = false`, `available_return_quantity = 0`, `request_until_date = null`).
- **Ограничение** — известное влияние AS-IS-логики или другого решения на новый расчёт, которое в задаче не прорабатывается: цитатой «Ограничение: …».
- **Соединения таблиц** не расписываются условиями SQL — разработчик возьмёт их из модели данных. Пишется только неочевидное: ключ сопоставления (`order_position_id`, а не штрихкод) и чей статус фильтруется (заявки, а не позиции возврата).
- **Неизменённый расчёт**, который остаётся в ответе рядом с изменённым, — одной строкой «логика не меняется».
- **Flowchart** — по желанию, в `{% cut %}`. Текст шагов — канон; схема совпадает с ним узел в узел.
- **Только то, что нужно сделать.** Пояснения «зачем» (для чего поле на следующих шагах, как работают соседние сервисы) в шаги не пишутся. Исключение — одна фраза-предостережение, если без неё разработчик возьмёт неверный источник («не `cms_orders.store_code`»).
- **Состав полей — по макетам** (`projects/<проект>/sources/mockups/`, `projects/<проект>/requirements/screen-spec/`). Поведение AS-IS — справка, не ориентир.

##### «Маппинг API → БД»
Последний раздел, справочник для разработчика: таблица `API | Тип данных | БД | Тип данных`.
- Поле из БД — `<таблица>.<поле>` с типом колонки; через связь — с условием связи: `cms_delivery_tk.slug` (по `cms_orders.delivery_method = cms_delivery_tk.id`).
- Вычисляемое поле — «Динамический расчёт: <формула через поля-источники>», тип БД — `—`.
- Новые входные параметры — отдельная таблица «Запрос → БД».
- Имена и типы колонок сверяются с ERD (`projects/<проект>/requirements/diagrams/erd/`) и кодом монолита; неизвестный тип — в «Открытые вопросы».
- Внешние системы в маппинг не входят — отдельная задача (раздел 1).

##### «Ошибки»
Состав ошибок не меняется — одна строка «Состав ошибок не меняется»; недоступность бизнес-действия (возврат недоступен) ошибкой не является. Иначе:
1. **Структура ошибки**: детальная — пользователь вводит данные в форму (`return-details`); плоская — ввода нет (`return-method-list`). Подробно — [api-errors_memo.md](./references/api-errors_memo.md), раздел 2.
2. **Таблица ошибок** — коды и HTTP-статусы по реестрам [api-errors_memo.md](./references/api-errors_memo.md), раздел 1. Для одного метода на Web и Mobile в колонке кода — оба кода через ` / `.
3. **Пример ответа с ошибкой** — по справочнику канала.
4. **Новый предметный код** — номер из свободного диапазона `ResponseErrorCode`, ключ перевода, HTTP-статус и требование добавить код в `getStatusCode()`.
5. **Web** — способ сборки ответа (`FrontendApiResponseService` или ответ в контроллере, как у соседних методов): от него зависит HTTP-статус ошибки ([request-response_web.md](./references/request-response_web.md)).

##### «Совместимость с МП»
Общие правила обратной совместимости и версионирования — `AGENTS.md` → «Правила системного анализа при разработке нового функционала», п. 4–5; ниже — их применение к Mobile API монолита.

Обязателен при доработке **существующего** метода Mobile API. Старые версии приложения продолжают вызывать изменённый метод,
а механизма ветвления по версии в монолите нет: `x-version` пишется только в лог ошибок (`Mobile\Controllers\BaseController`).
Отсечь старые версии можно только принудительным обновлением — `version_ios_required` / `version_android_required` в `AppVersionsConfig` (админка).

Каждое изменение классифицируется:

| Изменение | Тип | Что увидит старая версия |
|---|---|---|
| Новый необязательный параметр запроса | безопасное | — |
| Новое поле в ответе | безопасное* | *если приложение игнорирует неизвестные поля |
| Новый эндпоинт | безопасное | — |
| Новый обязательный параметр / параметр стал обязательным | **опасное** | Не шлёт его → ошибка валидации |
| Поле ответа удалено / переименовано | **опасное** | Падение или пустое место на экране |
| Сменился тип / формат поля | **опасное** | Ошибка разбора ответа |
| Поле ответа может стать `null` | **опасное** | Падение, если ожидается значение |
| Новое значение enum в ответе | **опасное*** | *если приложение не обрабатывает неизвестные значения |
| Сменились коды ошибок, конверт, поведение по умолчанию | **опасное** | Неверный текст ошибки или ветка экрана |

В задаче:
1. Каждое изменение — строкой таблицы блока с типом по классификатору.
2. Решение для каждого опасного изменения: сделать безопасным (новое поле рядом, старое не удалять) / новый эндпоинт / поднять обязательную версию (решение продукта) / ветвление по `x-version` (отдельная доработка — механизма нет).
3. Минимальная версия МП, поддерживающая изменение, — из задач iOS / Android в «Связях».
4. Критерий приёмки: метод проверен на последней версии приложения из стора и на новой сборке.
5. Порядок выкатки: бэк раньше приложения и работает с обеими версиями.

Пока команда МП не подтвердила, отметки `*` в классификаторе — в «Открытые вопросы» задачи:
игнорирует ли приложение неизвестные поля ответа; как обрабатывает неизвестное значение enum; кто принимает решение о поднятии обязательной версии.

##### «Тестирование»
- **Предусловия** — статус заказа, сроки (`cms_orders.end_date`), включённые настройки в админке, стенд (на dev нет обменов с RetailCRM → `end_date IS NULL`).
- **Критерии приёмки** — проверяемые: что сохраняется и где, какие ошибки на какие входы, изменения в swagger / Gate.
- Блок не пишется, если тест-документацию ведёт отдельная задача QA (связь в Трекере).

##### «Открытые вопросы»
Всё, что не подтверждено кодом, ERD, макетами или командой: неизвестный тип колонки, неподтверждённое поведение клиента, нерешённое бизнес-правило. В тексте — пометка `{red}(...)` на месте, где решение влияет на логику; в конце — сводка вопросов с адресатом, чтобы было видно, что блокирует реализацию.

#### 4. Общие правила (выведены из замечаний QA по примерам)

1. **Невалидные значения не дают 500.** Для каждого enum-поля — поведение при значении вне списка, `null` и отсутствии поля + текст ошибки (1126, доработка 1).
2. **Одно имя на один смысл.** Имена — по [словарю полей](./references/field-glossary.md); нового смысла нет — имя по конвенции словаря и строка в словарь в той же задаче. Имена в действующих эндпоинтах не меняются; синонимы (`reasonCode`, `need_bank_details`, `colorId`) в новые методы не копируются.
3. **Enum = существующие значения системы.** Сверить с чекаутом / справочниками БД (`sdek-pvz`, `5post`, `method_type: pvz`; `pickup` = самовывоз из магазина) (1239, 1240).
4. **Пример = таблица.** Пример ответа не содержит новых значений, которых нет в таблице выходных параметров; поля AS-IS — только для контекста, с пометкой «поля AS-IS без изменений сокращены».
5. **Поведение по умолчанию.** Что отдаёт метод без необязательных параметров (1240: дефолт `courier` по Москве).
6. **Зависимость от настроек и данных.** От каких настроек админки (`cms_return_method`, флаги по каналу) и полей БД (`cms_orders.end_date`) зависит результат и что отдаётся, если настройка выключена / поле пустое (1126, 1239).
7. **Куда пишется и откуда берётся** — блок «Маппинг API → БД»; передача во внешние системы — отдельная задача (в 1126 была совмещена — так больше не делаем).
8. **Проксирующий Gate прозрачен.** Если гейт только проксирует, его ответ = ответ прямого запроса в downstream при тех же query-параметрах, теле и заголовках (1241). Если в гейте выполняется логика — она описывается в задаче на гейт (раздел 2).
9. **Текст ошибки для клиента.** Согласовать с МП, из какого поля строится сообщение (`error_text` или `error_data[].message`) (1126).
10. **Старые версии МП не ломаются** — блок «Совместимость с МП».
11. **Без секретов.** Никаких токенов, cookies, `Authorization`, реальных персональных данных.
12. **Расчёт — на бэкенде.** Значение, которое клиент показывает пользователю (количество, признак, дата, сумма), бэкенд отдаёт готовым полем ответа — по `AGENTS.md` → «Принципы проектирования».

#### 5. Связь с бандлом требований

- Копия задачи хранится в `projects/<проект>/requirements/backend/US-NN/` — папка по User Story из Трекера (`US-01` = «US1. Создание возврата»; в ней все задачи этой истории). Имя файла — `<теги> <объект>_task.md`, например `[B][Mobile API] order-card-return_task.md`: канал виден из тегов, суффикс канала не нужен.
- Первая строка файла — `# ECOMDEV-NNNN: <заголовок задачи>` после заведения в Трекер.
- Трассировка к `BR` / `FR` / `US` / `UC` / `BL-RET` — в матрице трассируемости, не в тексте задачи. Новые ID-префиксы не вводятся.
- Если задача заменяет более подробный черновик — черновик можно сохранить в конце файла разделом «Приложение. Предыдущая версия (справочно)» с пометкой, что при расхождении верна задача.
- Логика из `backend/*_backend.md` и контракт из `*_openapi.yaml` / `reference/api/` не копируются — задача фиксирует только дельту для разработчика.
