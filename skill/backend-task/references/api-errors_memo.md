## 2. Форматы ответов об ошибках

Выбор структуры тела ошибки зависит от того, как клиент (frontend/mobile) будет взаимодействовать с ответом.

### Вариант А: Детальная структура (для UI-форм)

Используется в методах, где пользователь вручную вводит данные (регистрация, чекаут, профиль, форма возврата). Фронтенду необходимо знать, какое конкретно поле подсветить красным.

```json
{
  "status": "error",
  "message": "Ошибка валидации",
  "code": "40000",
  "errors": [
    {
      "code": "XXXXX",
      "message": "Поле обязательно для заполнения",
      "target": "field_name"
    }
  ]
}
```

- **`target`** — всегда **название поля** (ключа), в котором допущена ошибка, а не его значение. Если ошибка общая и не привязана к полю, передаётся пустая строка `""`.

### Вариант Б: Плоская структура (для фоновых запросов)

Используется в методах, где нет прямого пользовательского ввода (клики по кнопкам, закрытие уведомлений, фоновые обновления, получение списков). Фронтенду нужен только сам факт ошибки для вывода общего тоста/снекбара или системного логирования.

```json
{
  "status": "error",
  "message": "Некорректный запрос",
  "code": "40000"
}
```

Mobile API — те же варианты в конверте `result.error_code` / `result.error_text` / `result.error_data`.

## 3. Архитектурные паттерны и дилеммы (как выбирать статусы)

### 3.1. Ошибка валидации данных: 400 vs 422

- **`400 Bad Request`:** традиционно — синтаксическая ошибка (сломан JSON). В проекте используется как универсальный статус для ошибок валидации.
- **`422 Unprocessable Entity`:** архитектурно более правильный статус для бизнес-валидации. В коде — только у вебхуков 1С и `20279`. *Тема для обсуждения на ретро.*
- Методы сайта с ответом в контроллере отдают ошибку валидации с HTTP 200 — для них статус в задаче указывается как есть.

### 3.2. Доступ к чужим данным (безопасность): 403 vs 404

Если `User A` запрашивает заказ `User B`:

- **`403 Forbidden` (честность):** «заказ существует, но он не твой». **Минус:** можно перебирать ID и собирать базу существующих номеров заказов.
- **`404 Not Found` (маскировка):** «такого заказа в твоём профиле нет». **Плюс:** исключает перебор ID. *Рекомендуемый паттерн.*

### 3.3. Массовые обновления (bulk) и статус 200

Метод с фильтрами (например, `POST /read-all` с `type` и `order_id`) работает как `UPDATE ... WHERE`:

- чужой или несуществующий `order_id` → обновлено **0 записей**; это **не ошибка**, ответ `200 OK`;
- `400` — только при неверном формате данных (буквы вместо цифр) или сломанном теле запроса.

## 4. Шаблон блока ошибок в задаче (на примере уведомлений)

**Метод:** `POST /api/v1/notifications/read` (точечное действие)

- `401` — неавторизованный запрос (код `40001`; Mobile — `1002`).
- `400` — некорректный запрос / не передано обязательное поле `uuid` (код `40000`).
- `403` — попытка прочитать чужое уведомление (код `40003`).
- `404` — уведомление не найдено (код `40004`).

**Метод:** `POST /api/v1/notifications/read-all` (массовое действие с фильтрами)

- `401` — неавторизованный запрос (код `40001`; Mobile — `1002`).
- `400` — некорректный запрос (код `40000`): несовпадение типов (в `order_id` строка вместо числа), невалидный JSON, значение `type` вне справочника.
- `200 OK` (успех) — при пустом JSON `{}` (читаются все записи) или при фильтрах, под которые ничего не попало (обновлено 0 строк).
