### Контракт API и swagger

**Назначение.** Скилл задаёт, **каким должен быть контракт** метода (путь, метод, доступ, запрос, ответ, ошибки, имена полей) и **как его описать в swagger**, а также формат **разбора действующего API**.

**Чего здесь нет:**
- формат задачи в Трекере, логика, маппинг в БД, цепочка МП → гейт → монолит, совместимость с МП — `skill/tracker-task`; задача ссылается сюда за правилами контракта;
- спецификация логики фичи — `skill/backend-logic`;
- асинхронные контракты (очереди, события) — `skill/asyncapi-spec`.

Принципы проектирования (расчёт на бэке, обратная совместимость, версионирование, AS-IS / TO-BE) — `AGENTS.md`; здесь на них ссылаются и не пересказывают. Правила обратной совместимости по видам изменений — [references/backward-compatibility.md](./references/backward-compatibility.md).

**Статусы правил** в справочниках:
- **Согласовано** — регламент или устойчивая практика новых методов;
- **AS-IS** — так работает сейчас;
- **Предложение** — бэк не подтвердил; применять можно, вопрос — в «Открытые вопросы» задачи.

Решения по спорным правилам — `knowledge/_archive/skills_2026-11-17/Анализ_скиллов_эндпоинты.md`, часть 2, §6.1 «Проверка по коду» (17.11.2026).

#### 2. Сценарии

Сначала определить сценарий: правила **нового** метода (путь, имена по словарю, конверт по стандарту) **не применяются** к изменению существующего — там действует «имена и контракт не меняются» ([field-glossary.md](./references/field-glossary.md), правило 2).

##### 2.1. Новый метод

**Вход:** требования (SRS / US, макеты), канал, данные БД.

1. Проверить, нет ли уже метода с этими данными; для МП — цепочку МП → гейт → монолит (`tracker-task` §2).
2. Путь и HTTP-метод — по справочнику канала (`web.md` разделы 3–4, `mobile.md` разделы 2–3).
3. Доступ: закрытый / открытый; поиск ресурса по id и пользователю; капча и частота для открытых методов с SMS / перебором.
4. Запрос: каждое поле — тип, обязательность, формат, enum, nullable, предобработка; имена — по словарю.
5. Ответ: конверт канала; список — массив + `total` / `pagination`; значения для показа — готовыми (`AGENTS.md`).
6. Ошибки — по [errors.md](./references/errors.md): структура (детальная / плоская), коды, HTTP; новые предметные коды — с HTTP-статусом и `getStatusCode()`.
7. Правила раздела 3 этого файла.

**Результат:** контракт в задаче по шаблону `tracker-task/templates/new-web.md` или `new-mobile.md`; swagger — сценарий 2.3.

##### 2.2. Изменение контракта существующего метода

**Вход:** текущий контракт — по коду и swagger (при необходимости — разбор по [as-is-review.md](./references/as-is-review.md)), что нужно изменить.

1. Зафиксировать текущее поведение: поля, ошибки, поведение без параметров.
2. Новые поля — по словарю; **существующие имена, типы и конверт не меняются**, даже если нарушают стандарт канала.
3. Каждое изменение классифицировать: безопасное / опасное по [backward-compatibility.md](./references/backward-compatibility.md), раздел 2 (применение к МП — «Совместимость с МП», `tracker-task` §3; принципы — `AGENTS.md` п. 4–5). Для МП опасное — значение по умолчанию для старых версий или `v2`.
4. Поведение без новых параметров — прежнее: «Если новые параметры не переданы, метод должен работать по текущей логике без изменений, структура ответа не меняется» (ECOMDEV-1214).
5. Новые ошибки — по [errors.md](./references/errors.md); смена кодов, конверта, поведения по умолчанию — опасное изменение.

**Результат:** задача по шаблону `tracker-task/templates/change-existing.md`; swagger метода дополняется изменёнными полями по сценарию 2.4.

##### 2.3. Swagger нового метода

**Вход:** контракт из сценария 2.1.

1. Файл и правила — по [swagger.md](./references/swagger.md), раздел 0.
2. Операция, параметры, тело, ответы, ошибки — по разделу проекта (1 / 3 / 4).
3. Каждый параметр и поле — `description`, `type`, `format`, обязательность, `example`, `enum` с расшифровкой (раздел 2).
4. Пример ответа и ошибок совпадает с контрактом.

**Результат:** фрагмент swagger — разработчик добавляет его в той же задаче; аналитик прикладывает фрагмент только по запросу разработки. Критерий приёмки задачи: «swagger обновлён и проходит lint».

##### 2.4. Доописание swagger существующего метода

**Вход:** код метода, текущий swagger, переводы, данные БД.

Порядок — [swagger.md](./references/swagger.md), раздел 5:
- контракт не меняется;
- корректное не трогается;
- ничего не придумывается;
- несоответствия и неизвестное — в таблицу на согласование.

**Результат:** дополненный swagger + список на согласование (`Метод | Параметр / поле | Что в swagger | Что в коде / что неизвестно | Предложение | Кому`).

##### 2.5. Разбор действующего API

Отдельная обязанность скилла (`AGENTS.md`): разбор метода для базы знаний или AS-IS процесса — по [as-is-review.md](./references/as-is-review.md).

#### 3. Общие правила API (выведены из замечаний QA)

Уроки — задачи в `skill/tracker-task/examples/` («Что всплыло на тесте»).

1. **Невалидные значения не дают 500.** Для каждого enum-поля — поведение при значении вне списка, `null` и отсутствии поля + текст ошибки. *Урок: ECOMDEV-1126, доработка 1 — enum без поведения → 500.*
2. **Одно имя на один смысл.** Имена — по [словарю полей](./references/field-glossary.md); нового смысла нет — имя по конвенции словаря и строка в словарь в той же задаче. Имена в действующих эндпоинтах не меняются; синонимы (`reasonCode`, `need_bank_details`, `colorId`) в новые методы не копируются.
3. **Enum = существующие значения системы.** Сверить с чекаутом / справочниками БД (`sdek-pvz`, `5post`, `method_type: pvz`; `pickup` = самовывоз из магазина). *Урок: ECOMDEV-1239, 1240.*
4. **Пример = таблица.** Пример ответа не содержит новых значений, которых нет в таблице выходных параметров; поля AS-IS — только для контекста, с пометкой «поля AS-IS без изменений сокращены».
5. **Поведение по умолчанию.** Что отдаёт метод без необязательных параметров. *Урок: ECOMDEV-1240 — дефолт `courier` по Москве.*
6. **Без секретов.** Никаких токенов, cookies, `Authorization`, реальных персональных данных — ни в задаче, ни в swagger.
7. **Расчёт — на бэкенде.** Значение, которое клиент показывает пользователю (количество, признак, дата, сумма), бэкенд отдаёт готовым полем ответа — по `AGENTS.md` → «Принципы проектирования».
8. **Поля ответа описываются полностью:**
   - полные пути (`items[].available_return_quantity`, `order_delivery.pvz.id`);
   - вложенный объект — отдельной таблицей;
   - nullable — `string \| null` и когда приходит `null`;
   - enum — все значения через ` / `;
   - snake_case.
9. **Взаимоисключающие объекты** (`address` / `pvz` / `store`): когда формируется каждый объект, какой признак выбирает ветку (`<таблица>.<поле>`), проверки по порядку, что равно `null`. Признак сверяется с данными: если поле заполнено не только в нужной ветке (как `cms_delivery_tk.store_code` у служб «Отгрузка»), ветка выбирается по типу.
10. **Один метод на сайте и в МП** — поля одинаковые (колонка «Web» в [mobile.md](./references/mobile.md)), проверки одинаковые; различаются только конверт и формат ошибки.

Правила задачи — зависимость от настроек админки, «куда пишется и откуда берётся», проксирующий гейт, текст ошибки для МП, совместимость — `tracker-task` §4.

#### 4. Общие принципы OpenAPI

Из прежнего `openapi-spec` (§4.6.4, 4.6.6–4.6.8, 4.6.11). **Действуют, если проект не задаёт иное**: для сайта, Mobile API и гейта правила справочников главнее.

Справочно — где проекты расходятся с общими принципами:
- версия: в проектах 3.1.0 / Swagger 2.0 (гейт), а не 3.0.3;
- создание: в монолите 200, а не 201;
- удаление: в монолите 200 с пустыми данными, а не 204;
- пагинация: `limit` / `offset`, а не `page`;
- код ошибки: строка (`ResponseErrorCode`) на сайте, int (`error_code`) в МП.

##### 4.1. Именование

- **Пути** — kebab-case (`/user-profiles`).
- **Схемы** — PascalCase (`UserProfile`).
- **Параметры и поля** — snake_case (`user_id`).
- **Операции** — группировать по тегам логически.

##### 4.2. Обязательные элементы операции

- **tags** — группировка по функциональности;
- **summary** — краткое описание (до 50 символов);
- **description** — подробное описание;
- **parameters** — описание всех параметров (`description` и `schema` у каждого);
- **requestBody** — `content` со `schema`;
- **responses** — минимум успех и коды ошибок;
- **examples** — примеры запросов и ответов.

Структура операции:

```yaml
/users/{id}:
  get:
    tags: [users]
    summary: Получить пользователя по ID
    description: Возвращает детальную информацию о пользователе
    parameters:
      - name: id
        in: path
        required: true
        schema:
          type: integer
        description: Уникальный идентификатор пользователя
    responses:
      '200':
        description: Пользователь найден
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/User'
            example:
              id: 1
              email: "user@example.com"
              name: "John Doe"
      '404':
        description: Пользователь не найден
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/Error'
```

##### 4.3. Компоненты и переиспользование

- Схемы, общие параметры и ответы — в `components`, ссылки — через `$ref`.
- Обязательные поля — списком `required` у объекта.

```yaml
components:
  schemas:
    User:
      type: object
      required: [id, email]
      properties:
        id:
          type: integer
          description: Уникальный идентификатор
          example: 1
        email:
          type: string
          format: email
          description: Email пользователя
          example: "user@example.com"
        created_at:
          type: string
          format: date-time
          description: Дата создания
          example: "2024-01-15T10:30:00Z"
  responses:
    NotFound:
      description: Ресурс не найден
      content:
        application/json:
          schema:
            $ref: '#/components/schemas/Error'
```

##### 4.4. Коды статусов (общий принцип)

| Операция | Успех | Ошибка клиента | Ошибка сервера |
|----------|--------|----------------|----------------|
| **GET** | 200 | 404, 400 | 500 |
| **POST** | 201 | 400, 409 | 500 |
| **PUT** | 200 | 400, 404 | 500 |
| **DELETE** | 204 | 404 | 500 |

Для монолита и гейта — статусы по [web.md](./references/web.md), [mobile.md](./references/mobile.md), [errors.md](./references/errors.md).

##### 4.5. Валидация данных

Ограничения — в схеме, если они есть в коде или задаче:

```yaml
properties:
  email:
    type: string
    format: email
    maxLength: 255
  age:
    type: integer
    minimum: 0
    maximum: 150
  status:
    type: string
    enum: [active, inactive, pending]
```

##### 4.6. Описания

- `example` — для каждого поля; `description` — для всех элементов; реалистичные примеры запросов и ответов; бизнес-правила — в `description`.
- Хорошо: «Возвращает список пользователей с пагинацией», «Создаёт нового пользователя с валидацией email», «Ошибка 409 при дублировании email».
- Плохо: «Получает данные», «Создаёт объект», «Возвращает ошибку».

##### 4.7. Проверка спецификации

- **Синтаксис:** YAML / JSON валиден; `info` с `title`, `version`, `description`; `servers` с `description`.
- **Связь с моделью:** схемы данных соответствуют ERD (`projects/<проект>/requirements/diagrams/erd/`); операции покрывают сценарии Use Case / US.
- **Инструменты:**
  - Swagger Editor (https://editor.swagger.io/) — онлайн-валидатор;
  - Spectral — линтер;
  - OpenAPI Generator — генерация кода;
  - для `frontend.yml` — `redocly/cli lint` ([swagger.md](./references/swagger.md), раздел 1).

- [ ] HTTP-метод по таблице `web.md` раздел 4; одно действие — один метод

- [ ] Ошибки: 422 / `20279` с `errors[]` для полей, 400 / 401 / 404, бизнес-запреты со своим кодом
- [ ] Тексты `message` для пользователя — ru и en

**Mobile API**
