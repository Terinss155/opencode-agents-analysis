## 1. Уровни и общие соглашения

1. **Согласовано.** Правила применимы к общению МП ↔ Mobile API: гейт `/api/v1/...` (новый гейт `mobile.12stz.*`, `mobile-monorepo-go`) и монолит `/mobile/...`.
2. **Согласовано.** Дополняют правила сайта, не противореча им: snake_case, CRUD по возможности.
3. **Согласовано.** Гейт проксирует запрос в монолит без изменения параметров, тела и конверта ответа (раздел 8).

### 1.1. Что делает каждый уровень (AS-IS)

| Что | Гейт (`mobile-monorepo-go`) | Монолит (`/mobile/...`) |
|---|---|---|
| Пути | `/api/v1/...`, `/api/v2/...` | `/mobile/...`, `/mobile/v1/...`, `/mobile/v2/...` — смешаны |
| Авторизация | JWT `Authorization: Bearer` для всех методов, кроме групп `/auth` и `/errors` | Сессия `x-session-token` + ключ `x-access-token`; обязательность — правило `isAuthRequired` у метода |
| Передача запроса в монолит | `ProxyToSite`: `session_token` из JWT → `x-session-token`; `x-access-token` из конфига; пробрасывает `x-platform`, `x-version`, `Cookie`, тело. Query — **только если `isCrutch = false`** | — |
| Обязательные заголовки | `X-Platform`, `X-Version`; без них 400 `{"error": {"message": "missing X-Platform header"}}` | `x-platform`, `x-version`; язык — `X-Language` |
| Проверка запроса | В прокси — только разбор path / body; ECOMDEV-2034 убрал проверку JSON-тела для `/api/v2/cart` | `requestRules` в `beforeAction`: `isAuthRequired`, `fieldRules` (тип, длина, диапазон, своя функция), `methods`, `headers`; валидаторы через исключение |
| Успех | Прокси — ответ монолита как есть; свои методы — `{"success": true, "result": ...}` | `{"success": true, "result": ..., "total": ...}` |
| Ошибка | Прокси — ответ монолита + `"isErrorFromPHP": true` при статусе ≠ 200; свои ошибки — `{"error": {"message", "details"}}` (`dto.ErrorResponse`, и в новых методах: `reservation`, `errors/waf`); формат монолита `FailureResponse` — в основном в аннотациях swagger `@Failure` | `{"success": false, "result": {"error_code", "error_text", "error_data"}}`; HTTP — по `error_code` в `getError()` |
| Ошибки полей | — | `1015`, HTTP **400**, `error_text: "Ошибка валидации данных"`, `error_data[]` с `target` / `code` / `message`; в коде `TODO: Как будто должно возвращать 422 статус` |
| Ограничение частоты | `limiterMiddleware` создан, подключение закомментировано для v1 и v2 | Нет |
| Swagger | Swagger 2.0, генерируется из аннотаций `swag` (`docs/mobile_api/*` — сгенерированные файлы) | `docs/openapi/mobile.yml`, OpenAPI 3.1.0, правится вручную |

`getError()` монолита (AS-IS):
- HTTP по коду: 404 — `1009`, `1013`; 500 — `1016`, `1026`; 401 — `1001`, `1002`, `1007`; 405 — `1000`; 406 — `1012`, `1014`, `1018`, `1020`, `1021`; 403 — `1017`, `1023`; остальные — 400.
- Для кодов `1001`, `1002`, `1011`, `1017`, `4001`, `4002`, `1026`, `1027` текст подменяется фиксированным — текст, переданный методом, до клиента не дойдёт.
- `ApiBaseController` (новый чекаут, ECOMDEV-772 / 987) — копия `BaseController` с тем же маппингом.

## 2. Пара путей и версия

1. **Согласовано.** У метода МП всегда пара: `Gate: <МЕТОД> /api/v1/...` → `Site: <МЕТОД> /mobile/...` (`tracker-task` §2, шаг 3).
2. **Предложение.** Путь гейта повторяет ресурс монолита: `/mobile/orders/{order_id}/<подресурс>` → `/api/v1/orders/{order_id}/<подресурс>`. Одна группа маршрутов гейта — один ресурс.
3. **Предложение.** Новый метод монолита — `/mobile/<ресурс>` без версии. Ресурс — существительное во множественном числе, kebab-case; path-параметр — snake_case с суффиксом `_id`.
4. **Согласовано** (практика, §6.1 п. 5). Гейт — `/api/v1/...`. Версия `v2` появляется, только когда меняется контракт существующего метода и старые версии МП должны продолжить работать на `v1` (`PUT /api/v2/cart` → `PUT /mobile/v2/cart`). Решение — в блоке «Совместимость с МП» задачи.
5. **Согласовано.** Действие, которое не ложится на CRUD, — глагол kebab-case последним сегментом (`/subscription/check`).

## 3. HTTP-метод

| Действие | Метод | Тело | Успех |
|---|---|---|---|
| Получить список / объект | `GET` | нет, фильтры — плоские query | 200 |
| Создать | `POST` (AS-IS встречается `PUT`: `user-address`, `v2/cart`) | JSON | 200, `result` — созданный объект |
| Частично изменить | `PATCH` | JSON | 200 |
| Удалить | `DELETE` | нет | 200, `result` — `{}` (пустой объект: `answer()` / `answerCustom()` отдают `stdClass`) |
| Действие | `POST` | JSON | 200 |

Новый метод — по таблице; `PUT` для создания в новых методах не используется (**Предложение**). Метод ограничивается правилом `methods` в `requestRules` или `VerbFilter`; чужой метод → `1000` / 405.

## 4. Авторизация, доступ, заголовки

### 4.1. Авторизация и доступ

1. **AS-IS.** Гейт: все методы под JWT, кроме групп `/auth` и `/errors`. Открытый метод гейта ставится в эти группы или явно до `jwtMiddleware` — указать в задаче на гейт.
2. **AS-IS** (`ApiBaseController::getApiRequestError()`, сверено 17.11.2026). Монолит: нет или невалидна сессия → `1002` / 401 (для любого метода); закрытый метод (`isAuthRequired = true`) при сессии гостя → `1007` / 401. Повторно проверять пользователя в методе и отдавать `1015` не нужно.
3. **Согласовано.** Ресурс ищется по id **и** текущему пользователю.
4. **Предложение** (§6.1 п. 4, вопрос бэку). Ресурс не найден или чужой → `1009` / **404** — как в `GET /mobile/reservation/{id}` (2026): поиск по `id` + `user_id`, чужое и несуществующее неразличимы. Новый код не нужен: `1009` в `getError()` уже отдаёт 404. AS-IS: детали возврата — `1019` / 400.
5. Открытый метод с SMS / email / перебором — ограничение частоты. **AS-IS:** в гейте отключено — лимиты указывать в задаче и отмечать открытым вопросом.

### 4.2. Заголовки запроса

Регламентом для Mobile API не определены. Ниже — заголовки из фактических запросов МП (ECOMDEV-1240 / 1241). **В задаче — только заголовки, специфичные для метода.**

| Заголовок | Кто передаёт | Описание | В задаче |
|---|---|---|---|
| `Authorization: Bearer <JWT>` | МП → гейт | Запрос к гейту | не описывается (общий) |
| `X-Platform` (`ios` / `android`), `X-Version` | МП → гейт → монолит; обязательны | Платформа, версия приложения | не описывается (общий) |
| `x-session-token`, `x-access-token` | гейт → монолит | Токены сессии; при прямом запросе в монолит `/mobile/...` их передаёт клиент | не описывается (общий) |
| `X-Language` / `accept-language`, `Cookie`, `X-Device-Id` | МП → гейт → монолит | Язык, куки, устройство | только если метод их использует |

```json
{
  "Authorization": "Bearer <token>",
  "x-platform": "ios",
  "x-version": "1.73.0",
  "accept-language": "ru-RU;q=1.0",
  "content-type": "application/json"
}
```

Заголовки ответа для Mobile API регламентом не определены; в задаче описываются, только если метод их возвращает (`content-type: application/json`).

## 5. Запрос

1. **Согласовано.** Имена — snake_case по [словарю полей](./field-glossary.md); поле метода, который есть и на сайте, называется так же, как на сайте. Тело — JSON, поля совпадают с полями того же метода сайта.
2. **Согласовано.** Query — только плоская запись, как на сайте. Регламент описывает `limit` / `offset` / `*` как `pagination.limit` / `pagination.offset` / `filters.*` — это смысловое соответствие, в коде они читаются как отдельные параметры.

   | Ключ | Web | Описание | Ограничения (`Mobile\Controllers\BaseController`) |
   |---|---|---|---|
   | `limit` | `limit` | Размер страницы | По умолчанию `50`, максимум `1000` |
   | `offset` | `offset` | Смещение | Максимум `100000` |
   | `*` | `*` | Фильтры | — |

3. **Согласовано.** Для каждого поля тела: тип, обязательность, формат, enum (все значения), nullable и когда `null`, предобработка.
4. **Предложение.** Если метод есть на сайте — проверки полей **одинаковые**, различается только формат ошибки (раздел 9).
5. **Согласовано.** Новый обязательный параметр в существующем методе — опасное изменение: значение по умолчанию для старых версий МП (`method_return = courier`) или `v2` (раздел 2, «Совместимость с МП»).

Пример запроса:

```
GET /api/v1/delivery/{order_id}/return-method-list?country_iso=RU&city=Москва&limit=20&offset=0
```

```json
POST /api/v1/delivery/{order_id}/return-details

{
  "method_return": "sdek-pvz",
  "city_return": "Москва",
  "date_return": "2026-10-05"
}
```

## 6. Ответ

### 6.1. Параметры ответа

**Согласовано** (практика; §6.1 п. 2). Конверт одинаков для гейта и монолита — гейт его не меняет.

| Ключ | Web | Описание |
|:---|:---|:---|
| `success` | `status == "success"` | Статус ответа (`true` / `false`) |
| `result` | `data` | Объект ответа; **список — массив прямо в `result`**; пустой — `{}` |
| `result.message` | `message` | Сообщение ответа, если `result` — объект |
| `result.items` | `data.items` | Список — **только если рядом со списком в `result` есть другие поля** (`result.message` + `result.items` в `GET /v2/products/stocks`, ECOMDEV-1214) |
| `total` | `total` / `pagination.total` | Количество элементов списка — на верхнем уровне; на практике приходит и без пагинации (1240) |

Правила:
1. **Согласовано.** `{"success": true, "result": ..., "total": ...}`.
2. **Согласовано** (§6.1 п. 2). Список — массив в `result` + `total` на верхнем уровне: `answerList()`, `GET /mobile/reservation` (2026), `return-method-list`. `result.items` — только при соседних полях. Прежнее правило `mobile-endpoint` «в новом методе — `result.items`» снято 17.11.2026.
3. **Согласовано.** Поля ответа: полный путь, тип, nullable и когда `null`, все значения enum; пример = таблица.
4. **Согласовано.** Значения для показа пользователю бэк отдаёт готовыми; тексты — с учётом `X-Language`.
5. **Согласовано.** Поля одного метода на сайте и в МП — по колонке «Web» таблиц этого файла.

Пример — список:

```json
{
  "result": [
    {
      "available_dates_return": [
        "2026-10-05",
        "2026-10-06"
      ],
      "method": "courier",
      "method_type": "courier",
      "title": "Курьер"
    }
  ],
  "success": true,
  "total": 1
}
```

Пример — список рядом с другими полями:

```json
{
  "result": {
    "items": [
      {
        "subtitle": "subtitle",
        "title": "title"
      }
    ],
    "message": "Успех"
  },
  "success": true,
  "total": 100
}
```

### 6.2. Ответ с ошибкой

Коды, HTTP-статусы, таблица ошибок МП и выбор структуры — [errors.md](./errors.md).

| Ключ | Web | Описание |
|:---|:---|:---|
| `success` | `status == "success"` | Статус ответа (`true` / `false`) |
| `result` | — | Объект ошибки |
| `result.error_code` | `code` | Код верхнего уровня — int из `Mobile\Controllers\BaseController` (`1015`, `1002`, …) |
| `result.error_text` | `message` | Сообщение ошибки; МП может строить текст для пользователя из него — согласовать в задаче |
| `result.error_data` | `errors` | Массив ошибок, с согласованной структурой `Error[]` — только для детальной структуры (формы ввода) |
| `result.data` | — | Ассоциативный массив «String → String» с доп. данными |

`Error`:

| Ключ | Web | Описание |
|:---|:---|:---|
| `target` | `target` | Имя поля, к которому относится ошибка; общая ошибка — `""` |
| `code` | `code` | Предметный код из `ResponseErrorCode` — строка (`"20110"`) |
| `message` | `message` | Сообщение ошибки |

Детальная структура — форма ввода (`POST /api/v1/delivery/{order_id}/return-details`):

```json
{
  "success": false,
  "result": {
    "error_code": 1015,
    "error_text": "Некорректный запрос",
    "error_data": [
      {
        "target": "date_return",
        "code": "20110",
        "message": "Некорректная дата возврата"
      }
    ]
  }
}
```

Плоская структура — ввода нет, клиенту нужен только факт ошибки (условный пример: запрос без валидной сессии; `error_data` не передаётся):

```json
{
  "success": false,
  "result": {
    "error_code": 1002,
    "error_text": "<сообщение ошибки>"
  }
}
```

## 8. Гейт

1. **Согласовано.** Прокси прозрачен: ответ гейта = ответ прямого запроса в монолит при тех же query, теле и заголовках (урок QA ECOMDEV-1241).
2. **Предложение.** Прокси передаёт query всегда (`isCrutch = false`). Если query не нужен — указать это в задаче на гейт явно.
3. **AS-IS.** При статусе ≠ 200 гейт добавляет к ответу монолита `"isErrorFromPHP": true` — учитывать в примерах ошибок гейта.
4. **AS-IS** (§6.1 п. 10). Свои ошибки гейта (заголовки, разбор тела, обязательные поля) — `{"error": {"message", "details"}}` (`dto.ErrorResponse`) с HTTP 400 / 500; так и в новых методах (`reservation`, `errors/waf`, 09.2026). В задаче на гейт и в swagger указывать этот фактический формат.
   **Предложение** (вопрос разработчикам гейта): унифицировать — свои ошибки в формате монолита `{"success": false, "result": {"error_code", "error_text"}}` (`FailureResponse`).
5. Логика в гейте — только по решению из `tracker-task` §2 (переезд из `core`); тогда она описывается в задаче на гейт полностью.
6. В задаче на гейт: путь гейта, путь монолита, группа маршрутов, нужен ли JWT, передаются ли query, ключ пути в конфиге (`cfg.Site.<...>Path`) — по образцу ECOMDEV-1241. Шаблон — `tracker-task/templates/gate-proxy.md`.

### 9.2. Что не повторяем

| Отклонение | Где | Как в стандарте |
|---|---|---|
| Путь гейта не совпадает с ресурсом монолита (`/api/v1/delivery/{order_id}/return-details` ↔ `/mobile/orders/...`) | 6 | Раздел 2, п. 2 |
| Две группы для одного ресурса (`reservation` / `reservations`) | 5 | Один ресурс — одна группа |
| Версия в пути без причины (`/mobile/v1/products/...` рядом с `/mobile/reservation`) | 3–5 | Версия — только при изменении контракта существующего метода (раздел 2, п. 4) |
| Чужой / несуществующий ресурс → `1019` / 400 | 6 | `1009` / 404 — раздел 4.1, п. 4 (Предложение) |
| Нет авторизованного пользователя → `1015` / 400 | 6 | `isAuthRequired` → `1007` / 401 (раздел 4.1, п. 2) |
| На сайте ввод проверяется, в МП — нет (`email` в subscription/check) | 1 | Одинаковые проверки в обоих каналах (раздел 5, п. 4) |
| `isCrutch = true` — query молча не передаётся | 3, 5 | Прокси передаёт query всегда (раздел 8, п. 2) |
| В `mobile.yml` пути то с `/mobile/...`, то без при `servers` с `/mobile` | `mobile.yml` | [swagger.md](./swagger.md) |
| В swagger вместо полей — имя класса; разная `security` у соседних методов; общая схема ошибки без обёртки `success` / `result`; `limit` / `offset` типа `string` | `mobile.yml` | [swagger.md](./swagger.md) |
| Описания параметров на английском и повторяют имя (`product_id int`); ошибочный пример `Cookie: 1.16.1`; у прокси описаны только 200 и 500 | swagger гейта | [swagger.md](./swagger.md) |
| В swagger гейта у своих ошибок указан `FailureResponse`, а код отдаёт `{"error": {...}}` | `reservation` и др. | В swagger — фактический формат (раздел 8, п. 4) |

Снято 17.11.2026 (§6.1 п. 10): «три формата ошибки в гейте → свои ошибки в формате монолита» — фактический формат своих ошибок гейта записан как AS-IS, унификация — Предложение.
