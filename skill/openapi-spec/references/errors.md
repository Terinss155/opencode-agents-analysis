## 2. Структура тела ошибки

Выбор структуры зависит от того, как клиент (сайт / МП) будет взаимодействовать с ответом. Структура не зависит от способа сборки ответа сайта ([web.md](./web.md), раздел 1).

### Вариант А: детальная структура (для UI-форм)

Используется в методах, где пользователь вручную вводит данные (регистрация, чекаут, профиль, форма возврата). Клиенту нужно знать, какое конкретно поле подсветить.

```json
{
  "status": "error",
  "message": "Ошибка валидации",
  "code": "20279",
  "errors": [
    {
      "code": "XXXXX",
      "message": "Поле обязательно для заполнения",
      "target": "field_name"
    }
  ]
}
```

- **`target`** — всегда **название поля** (ключа), в котором допущена ошибка, а не его значение. Если ошибка общая и не привязана к полю, передаётся пустая строка `""`.
- В памятке в этом примере `code: "40000"` — так отвечают методы с ответом в контроллере (возврат). Новые методы через сервис ответа отдают `20279` / 422 (раздел 3.1).

### Вариант Б: плоская структура (для фоновых запросов)

Используется в методах, где нет прямого пользовательского ввода (клики по кнопкам, закрытие уведомлений, фоновые обновления, получение списков). Клиенту нужен только сам факт ошибки для общего тоста / снекбара или логирования.

```json
{
  "status": "error",
  "message": "Некорректный запрос",
  "code": "40000"
}
```

Mobile API — те же варианты в конверте `result.error_code` / `result.error_text` / `result.error_data` ([mobile.md](./mobile.md), раздел 6.2).

## 3. Как выбирать статус

### 3.1. Ошибка валидации: 400 или 422

**Согласовано** (§6.1 п. 3, практика новых методов).

| Канал | Ошибки полей (пусто, формат, enum) | Запрос не разобран | Источник |
|---|---|---|---|
| Сайт, сервис ответа | **422** / `20279` + `errors[]` | **400** / `40000` без `errors[]` | `FrontendApiBaseController` (15.07.2026): `ValidatorException` → 422; `BadRequestHttpException`, пустой обязательный параметр в notifications → 400 |
| Сайт, ответ в контроллере | HTTP **200**, ошибка в теле — указывать как есть | — | `Api2/OrdersController` |
| Mobile API | **400** / `1015` + `error_data[]` | **400** / `1015` | `ValidatorException` → `1015`; в коде `TODO: … 422` |

Переход МП на 422 не планировать: для старых версий МП это опасное изменение («Совместимость с МП»).

Справочно — позиция памятки:
- **`400 Bad Request`** традиционно означает синтаксическую ошибку (сломан JSON); в проекте исторически используется как универсальный статус валидации.
- **`422 Unprocessable Entity`** архитектурно правильнее для бизнес-валидации. На момент памятки — только у вебхуков 1С и `20279`; с 07.2026 — стандарт новых методов сайта.

### 3.2. Доступ к чужим данным: 403 или 404

Если `User A` запрашивает заказ `User B`:
- **`403 Forbidden` (честность):** «заказ существует, но он не твой». **Минус:** можно перебирать ID и собирать базу существующих номеров заказов.
- **`404 Not Found` (маскировка):** «такого заказа в твоём профиле нет». **Плюс:** исключает перебор ID. *Рекомендуемый паттерн памятки.*

**Предложение** (§6.1 п. 4, вопрос бэку). Для новых методов — 404: ресурс ищется по id **и** пользователю. Сайт — `40004`, МП — `1009`; новый код МП не нужен.

AS-IS:

| Метод | Чужой ресурс |
|---|---|
| `GET /mobile/reservation/{id}` (2026) | `1009` / 404 — образец |
| Детали возврата, сайт | 404 |
| `POST /api/v1/notifications/read` (09.2026) | 403 `40003` |
| Детали возврата, МП | `1019` / 400 |

### 3.3. Массовые обновления (bulk) и статус 200

**Согласовано.** Метод с фильтрами (например, `POST /read-all` с `type` и `order_id`) работает как `UPDATE ... WHERE`:
- чужой или несуществующий `order_id` → обновлено **0 записей**; это **не ошибка**, ответ `200 OK`;
- `400` — только при неверном формате данных (буквы вместо цифр) или сломанном теле запроса.

### 3.4. Общие правила

1. **Согласовано** (урок QA ECOMDEV-1126). Невалидное значение, `null` и отсутствие поля не приводят к 500. Для каждого enum-поля — поведение при значении вне списка, `null` и отсутствии поля + текст ошибки.
2. **Согласовано.** Если ошибок полей несколько — возвращаются все сразу, по одной записи на поле и правило.
3. **Согласовано** (урок QA ECOMDEV-1126). В задаче на МП согласовать с МП, из какого поля строится текст для пользователя — `error_text` или `error_data[].message`.
4. Недоступность бизнес-действия (возврат недоступен) ошибкой не является — это поле ответа.

### 4.4. Задача сразу на два канала (`[B]`)

**Согласовано** (решение 16.11.2026, часть 3 анализа, §4 п. 5):

- таблица ошибок — только при многих ошибках или задаче на два канала;
- для задачи на два канала колонка кода — оба кода через ` / ` (`20279 / 1015`), HTTP — тоже через ` / `.

## 5. Пример блока ошибок в задаче (уведомления)

Пример из памятки. Статусы — как реализовано (AS-IS). Для нового метода чужой ресурс — по разделу 3.2.

**Метод:** `POST /api/v1/notifications/read` (точечное действие)

- `401` — неавторизованный запрос (код `40001`; Mobile — `1002`).
- `400` — некорректный запрос / не передано обязательное поле `uuid` (код `40000`). Для нового метода — 422 / `20279` + `errors[]` (раздел 3.1).
- `403` — попытка прочитать чужое уведомление (код `40003`). AS-IS; для нового метода — 404.
- `404` — уведомление не найдено (код `40004`).

**Метод:** `POST /api/v1/notifications/read-all` (массовое действие с фильтрами)

- `401` — неавторизованный запрос (код `40001`; Mobile — `1002`).
- `400` — некорректный запрос (код `40000`): несовпадение типов (в `order_id` строка вместо числа), невалидный JSON, значение `type` вне справочника.
- `200 OK` (успех) — при пустом JSON `{}` (читаются все записи) или при фильтрах, под которые ничего не попало (обновлено 0 строк).
