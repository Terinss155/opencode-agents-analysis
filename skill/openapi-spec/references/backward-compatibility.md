# Обратная совместимость API

Справочник: что такое обратная совместимость, какие изменения API безопасны для действующих потребителей, какие требуют доработок, и как выбрать способ изменения. Применение к Mobile API монолита (проверка версии МП, блок «Совместимость с МП» в задаче) — `skill/tracker-task/SKILL.md` §3 «Совместимость с МП». Общие принципы — `AGENTS.md` → «Правила системного анализа при разработке нового функционала», п. 4–5.

## 1. Определение

Обратная совместимость — изменение существующего API, после которого все его потребители продолжают работать без доработок на своей стороне.

Если сохранить совместимость нельзя, нужна новая версия эндпоинта или отдельный эндпоинт: старые потребители остаются на прежнем, новые переходят на новый.

Для мобильного приложения это особенно важно: у клиентов одновременно установлены разные версии, и не все обновляются. Старая версия вызывает тот же эндпоинт со старым контрактом. Если контракт сломан, старая версия перестаёт работать.

## 2. Когда безопасно, когда нужны доработки

Проверяется, продолжит ли работать потребитель, который уже вызывает метод, — прежде всего старая версия МП. Каждое изменение проверяется на трёх уровнях:

1. новый сервер принимает запрос старого клиента;
2. старый клиент разбирает новый ответ, в том числе ответ с ошибкой;
3. пользователь старого клиента может завершить прежний сценарий.

Правила оценки:
- Совместимость запроса и ответа проверяется отдельно: сервер может принять старый запрос, но вернуть ответ, который старый клиент не разберёт, и наоборот.
- Новое необязательное поле само по себе совместимость не гарантирует. В запросе важно, что делает сервер, когда поле не передано; в ответе — умеет ли старый клиент пропускать неизвестные поля.
- Совпадение структуры запроса и ответа не означает, что сохранилось поведение. Ужесточённая проверка отклоняет запрос, который раньше проходил. Если клиент понятно показывает ошибку и даёт её исправить, сценарий сохраняется, но набор допустимых запросов уже другой.

Обозначения в таблицах:
- **Да** — совместимо при условии, указанном в строке;
- **Нет** — старый клиент перестаёт работать или работает неверно;
- **Зависит** — результат определяется кодом клиента или сервера. Ответ даёт команда приложения, чтение кода или проверка на версии из стора; до ответа изменение считается несовместимым. «Зависит» не запрещает изменение, а требует проверки.

### Запрос (Request)

#### 2.1. HTTP-метод и эндпоинт

| Изменение | Совместимо? | Почему / что нужно |
|---|---|---|
| Изменили HTTP-метод запроса (например, `POST` → `PUT`) | **Нет** | Старая МП продолжит отправлять `POST`, а сервер будет ждать `PUT` и отклонит запрос. Сохранить поддержку прежнего метода, пока старые версии его вызывают |
| Изменили адрес эндпоинта (например, `/orders/{id}/return` → `/returns/{id}`) | **Нет** | Старая МП обращается по прежнему адресу и получит «не найдено». Оставить прежний маршрут, он может вызывать ту же логику, что и новый |
| Добавили новый эндпоинт (например, `POST /returns` рядом с `POST /orders/{id}/return`) | **Да** | Старые клиенты новый эндпоинт не вызывают. Прежний эндпоинт должен продолжать работать с прежним контрактом |
| Удалили существующий эндпоинт (например, больше нет `POST /orders/{id}/return`) | **Нет** | Старая МП теряет возможность выполнить операцию. Не удалять, пока старые версии его вызывают: проверить по данным о вызовах (раздел 5) |
| Изменили обязательный формат тела запроса (например, вместо JSON теперь требуется `multipart/form-data`) | **Нет** | Старая МП продолжит отправлять JSON, сервер его не разберёт. Принимать прежний формат или вынести новый формат в новый эндпоинт |

#### 2.2. Path-параметры

Пример: `GET /orders/{order_id}`, где `order_id` — Path-параметр.

| Изменение | Совместимо? | Почему / что нужно |
|---|---|---|
| Добавили обязательный Path-параметр (например, `/orders/123` → `/users/55/orders/123`) | **Нет** | Для старой МП это другой адрес, которого она не знает. Сохранить прежний маршрут |
| Удалили Path-параметр (например, `/orders/123` → `/orders`) | **Нет** | Старая МП продолжит обращаться по прежнему адресу с параметром в пути. Сохранить прежний маршрут |
| Изменили тип Path-параметра (например, числовой `order_id=123` → UUID) | **Нет**, если прежние значения перестали приниматься | Старое приложение передаёт числовой идентификатор. Продолжать принимать прежний формат рядом с новым |
| Изменили допустимый формат Path-параметра (например, раньше принимался `abc-123`, теперь только цифры) | **Зависит** | Проверить, какие значения на самом деле отправляют старые версии (по логам или коду клиента). Значения, которые они используют, продолжать принимать |
| Переименовали переменную Path-параметра только в коде сервера (например, `{id}` → `{order_id}`, адрес не изменился) | **Да** | На уровне HTTP адрес прежний, клиент разницы не видит. Проверить, что фактический маршрут не изменился |
| Изменили порядок сегментов пути (например, `/users/55/orders/123` → `/orders/123/users/55`) | **Нет** | Старая МП строит адрес по прежней схеме. Сохранить прежний маршрут |

#### 2.3. Query-параметры

Пример: `GET /orders?status=completed&page=1`.

| Изменение | Совместимо? | Почему / что нужно |
|---|---|---|
| Добавили необязательный Query-параметр (например, `locale=ru`) | **Да**, если без параметра поведение прежнее | Старая МП параметр не передаёт. Сервер должен обрабатывать его отсутствие так же, как до изменения |
| Добавили обязательный Query-параметр (например, теперь требуется `city_id`) | **Нет** | Старый клиент параметр не передаёт и получит ошибку. Сделать необязательным для старых версий, различать поведение по версии или сделать новый эндпоинт |
| Сделали обязательный Query-параметр необязательным (например, `city_id` теперь можно не передавать) | **Да** | Старая МП продолжает передавать параметр, сервер принимает его по прежним правилам |
| Сделали необязательный Query-параметр обязательным (например, `page` теперь обязателен) | **Нет** | Старая МП могла отправлять запрос без него и получит ошибку. Без параметра сохранить прежнее поведение |
| Переименовали Query-параметр (например, `status` → `order_status`) | **Нет** | Сервер не узнаёт прежнее имя, и фильтр молча перестаёт работать. Принимать оба имени |
| Удалили Query-параметр (например, больше не поддерживается `status`) | **Нет**, если он влиял на результат | Старая МП продолжает его передавать и ждёт отфильтрованный результат. Даже если сервер игнорирует параметр без ошибки, результат меняется. Если параметр ни на что не влиял — да |
| Изменили тип Query-параметра (например, `page=1` → `page=first`) | **Нет**, если прежние значения перестали приниматься | Старая МП отправляет значение в прежнем формате. Продолжать его принимать |
| Изменили допустимые значения Query-параметра (например, раньше `status=new`, теперь только `status=created`) | **Нет**, если прежнее значение запрещено | Старое приложение продолжает отправлять `new`. Принимать прежние значения или сопоставлять их с новыми |
| Добавили новое значение enum во входной Query-параметр (например, `status=archived`) | **Да** | Старые клиенты отправляют прежние значения. Смысл прежних значений не должен измениться |
| Изменили значение по умолчанию у Query-параметра (например, без `limit` раньше возвращалось 20 записей, теперь 100) | **Зависит** | Старая МП не передаёт параметр и может рассчитывать на прежний объём ответа. Проверить отображение и постраничный вывод у клиента или сохранить прежнее значение по умолчанию |
| Перенесли параметр из Query в Body (например, `?city_id=55` → JSON `{ "city_id": 55 }`) | **Нет**, если прежнее место больше не поддерживается | Старая МП продолжит передавать параметр в строке запроса. Принимать оба варианта |

#### 2.4. Заголовки запроса (Request Headers)

Пример: `Authorization`, `x-platform`, `x-version`, `Content-Type`.

| Изменение | Совместимо? | Почему / что нужно |
|---|---|---|
| Добавили необязательный заголовок (например, `X-Request-ID`) | **Да** | Старая МП его не передаёт. Сервер должен работать без него так же, как раньше |
| Добавили обязательный заголовок (например, теперь требуется `X-Platform`) | **Нет**, если старые версии его не отправляют | Запрос старого клиента будет отклонён. Без заголовка сохранить прежнюю обработку или различать поведение по версии |
| Переименовали заголовок (например, `Version` → `X-App-Version`) | **Нет**, если прежнее имя перестали принимать | Старая МП отправляет прежний заголовок, сервер его не видит. Принимать оба имени |
| Изменили формат значения заголовка (например, `Version: 1.42` → `Version: 1.42.0`) | **Зависит** | Проверить, в каком формате заголовок отправляют старые версии и разбирает ли сервер оба формата |
| Добавили проверку версии приложения (например, новое правило действует с версии `X.Y.Z`) | **Зависит** | Сервер должен правильно определять платформу и версию. Старые версии, запросы без версии и с нераспознанной версией не должны попадать под новое правило (раздел 3, способ 3) |
| Изменили способ авторизации (например, прежний токен больше не принимается) | **Нет** | Старые версии перестанут авторизоваться. Принимать прежний способ, пока им пользуются, или предусмотреть переход |
| Изменили обязательный `Content-Type` (например, `application/json` → `application/xml`) | **Нет**, если прежний формат больше не принимается | Старая МП отправляет JSON. Продолжать его принимать |
| Начали отклонять запрос без заголовка (например, запрос без `x-version` теперь получает ошибку) | **Нет**, если старые клиенты могли его не передавать | Проверить по реальным запросам поддерживаемых сборок, всегда ли заголовок есть. Без заголовка — прежнее поведение |

#### 2.5. Тело запроса (Request Body)

| Изменение | Совместимо? | Почему / что нужно |
|---|---|---|
| Добавили необязательный параметр в Body (например, `is_bank_details_confirmed`) | **Да**, если без параметра поведение прежнее | Старый клиент его не передаёт. Поведение сервера без параметра должно совпадать с текущим |
| Добавили обязательный параметр в Body (например, теперь обязателен `is_bank_details_confirmed`) | **Нет** | Старый клиент его не передаёт и получит ошибку. Оставить необязательным для старых версий, различать поведение по версии или сделать новый эндпоинт |
| Сделали обязательный параметр необязательным (например, `bank_name` теперь можно не передавать) | **Да** | Старые клиенты продолжают его передавать. Сервер должен принимать значение по прежним правилам |
| Сделали необязательный параметр обязательным (например, `bank_name` теперь всегда требуется) | **Нет** | Старый клиент мог не отправлять поле и получит ошибку. Сохранить прежнюю необязательность для старых версий |
| Переименовали параметр Body (например, `bank_account` → `account_number`) | **Нет** | Старый клиент передаёт прежнее имя, сервер его не видит. Принимать оба имени |
| Удалили параметр Body (например, больше не принимается `bank_inn`) | **Зависит** | Если сервер игнорирует лишние поля и параметр ни на что не влиял — совместимо. Если сервер отклоняет неизвестные поля или клиент ждёт результата от параметра — нет. Проверить обработку лишних полей |
| Изменили тип параметра (например, `order_id: 123` → `order_id: "123"`) | **Нет**, если прежний тип перестали принимать | Старый клиент отправляет число. Сервер должен продолжать принимать прежний тип |
| Изменили формат параметра (например, дата `24.11.2026` → `2026-11-24`) | **Нет**, если прежний формат запрещён | Старое приложение отправляет дату в прежнем формате. Принимать оба формата |
| Ужесточили проверку параметра (например, номер счёта теперь строго 20 цифр) | **Нет** для значений, которые раньше проходили | Старый клиент может отправить значение, которое раньше принималось. Проверить, что клиент показывает текст ошибки и даёт исправить данные. Это сохраняет сценарий, но не отменяет изменения поведения |
| Ослабили проверку параметра (например, поле больше не обязательно заполнять) | **Да**, если прежние значения по-прежнему принимаются | Старые запросы продолжают проходить |
| Добавили новое значение enum во входной параметр (например, `payment_type=sbp`) | **Да** | Старые клиенты передают прежние значения. Их обработка должна сохраниться |
| Удалили значение enum (например, больше не принимается `payment_type=card`) | **Нет** | Старые клиенты могут продолжать его передавать. Принимать прежнее значение |
| Изменили структуру вложенного объекта (например, `bank.account` → `payment.bank.account`) | **Нет**, если прежняя структура больше не принимается | Старая МП отправляет JSON прежней структуры. Принимать прежний формат |
| Изменили формат массива (например, раньше `items: [123, 456]`, теперь массив объектов) | **Нет**, если прежний формат больше не принимается | Сервер должен принимать прежний массив, либо новый формат выносится в новую версию эндпоинта |
| Стали различать отсутствующее поле и `null` (например, раньше оба варианта означали «реквизитов нет») | **Зависит** | Старые клиенты могут отправлять любой из вариантов. Проверить фактические запросы и сохранить для них прежнюю обработку |
| Изменили значение по умолчанию для отсутствующего поля (например, раньше непереданное подтверждение считалось `null`, теперь `false`) | **Зависит** | Старое приложение поле не отправляет, а сервер начинает принимать другое решение. Проверить последствия для сохранения данных, обмена с другими системами и сценария |
| Изменили смысл существующего параметра (например, `is_confirmed` раньше означал подтверждение заказа, теперь — реквизитов) | **Нет** | Старое приложение отправляет то же значение, а сервер понимает его иначе. Для нового смысла — новый параметр |
| Перенесли параметр из Body в Query (например, `order_id` в JSON → `?order_id=123`) | **Нет**, если прежнее место больше не поддерживается | Запрос старого клиента перестанет соответствовать контракту. Принимать прежний способ передачи |

### Ответ (Response)

#### 2.6. HTTP-статус

| Изменение | Совместимо? | Почему / что нужно |
|---|---|---|
| Изменили статус успешного ответа (например, `200 OK` → `201 Created`) | **Зависит** | Старая МП может считать успехом только `200`. Проверить обработчик успешных ответов у клиента |
| Заменили ответ с телом на ответ без тела (например, `200 OK` → `204 No Content`) | **Зависит** | Старая МП может пытаться разобрать JSON и получить ошибку. Проверить клиент или сохранить прежний ответ |
| Изменили статус ошибки (например, `400 Bad Request` → `422 Unprocessable Content`) | **Зависит** | Клиент может выбирать ветку экрана по статусу. Проверить обработчик ошибок у каждой поддерживаемой версии |
| Начали возвращать успешный HTTP-статус при бизнес-ошибке (например, `400` → `200` с `success: false`) | **Зависит** | Старая МП может считать любой ответ `200` успехом и показать ложное подтверждение. Сохранить прежний способ сообщать об ошибке |
| Начали возвращать техническую ошибку вместо ошибки проверки данных (например, `400` → `500`) | **Нет** для прежней обработки ошибки | Клиент покажет общий сбой вместо ошибки поля, пользователь не поймёт, что исправить. Исправить обработку на сервере |
| Сохранили HTTP-статус ответа (например, ошибка по-прежнему `400`) | **Да**, если остальной контракт сохранён | Одного совпадения статуса недостаточно. Проверить тело ответа (таблицы 2.8 и 2.9) и логику клиента |

#### 2.7. Заголовки ответа (Response Headers)

| Изменение | Совместимо? | Почему / что нужно |
|---|---|---|
| Добавили информационный заголовок (например, `X-Request-ID`) | **Да** | Старый клиент пропускает заголовки, которых не знает |
| Удалили заголовок, который использует приложение (например, `X-Next-Page`) | **Нет** | Старая МП может перестать загружать следующие страницы. Сохранить заголовок |
| Переименовали заголовок ответа (например, `X-Next-Page` → `Next-Page`) | **Нет**, если клиент читает прежнее имя | Приложение не найдёт значение. Передавать прежний заголовок рядом с новым |
| Изменили тип содержимого ответа (например, `application/json` → `application/xml`) | **Нет** | Старая МП ждёт JSON и не разберёт ответ. Сохранить прежний формат |
| Изменили правила кэширования (например, `no-cache` → `max-age=3600`) | **Зависит** | Клиент может начать показывать устаревшие данные. Проверить, кэширует ли клиент ответы и как |
| Добавили заголовок, без которого не работает продолжение сценария (например, новый токен в `X-Flow-Token`) | **Нет**, если без него следующие запросы не проходят | Старая МП не знает о новом заголовке и не передаст его дальше. Сценарий старого клиента должен работать без него |

#### 2.8. Тело ответа (Response Body)

| Изменение | Совместимо? | Почему / что нужно |
|---|---|---|
| Добавили новое поле (например, `is_bank_data_required`) | **Да**, если клиент пропускает неизвестные поля | Проверить разбор ответа в старой МП у команды клиента. Новое поле не должно менять смысл существующих |
| Добавили новый вложенный объект (например, `return.bank_details`) | **Да**, если клиент допускает дополнительные поля | Проверить, как клиент обрабатывает неизвестные объекты |
| Удалили поле (например, больше нет `order_status`) | **Нет**, если клиент его использует | Клиент ждёт поле — ошибка разбора или пустое место на экране. Оставить поле |
| Переименовали поле (например, `order_status` → `status`) | **Нет**, если прежнее имя перестало передаваться | Клиент продолжает искать прежний ключ. Новое поле добавить рядом, прежнее оставить |
| Изменили тип поля (например, `is_returnable: true` → `"true"`) | **Нет**, если прежний тип больше не передаётся | Клиент ждёт `boolean`, получает `string` — ошибка разбора. Сохранить тип |
| Изменили структуру поля (например, объект → массив) | **Нет** | Разбор ответа в старом клиенте рассчитан на другую структуру. Новую структуру передавать в новом поле |
| Переместили поле внутри JSON (например, `order.status` → `order.details.status`) | **Нет**, если прежний путь удалён | Клиент продолжает читать прежний путь. Сохранить его |
| Поле стало приходить со значением `null` (например, `status: "new"` → `status: null`) | **Нет**, если клиент ждёт обязательное значение | Возможна ошибка разбора или неверный экран. Проверить, обрабатывает ли клиент `null` |
| Поле перестало передаваться (например, раньше всегда был `status`, теперь ключа нет) | **Нет**, если клиент требует поле | Старая МП может не обработать ответ. Оставить поле |
| Добавили новое значение enum (например, новый статус `return_status: "inspection"`) | **Зависит** | Клиент может не обработать неизвестный статус. Проверить, что клиент делает с неизвестным значением, или передавать старым версиям только прежние значения |
| Переименовали значение enum (например, `"created"` → `"new"`) | **Нет**, если прежнее значение исчезло | Старая МП ждёт `"created"`. Сохранить прежнее значение или сопоставлять значения по версии клиента |
| Изменили смысл существующего поля (например, `can_be_returned` теперь означает другое условие) | **Нет**, если нарушено ожидание клиента | Структура прежняя, но приложение неверно показывает данные. Для нового смысла — новое поле |
| Изменили единицы измерения (например, `price: 1500` раньше в рублях, теперь в копейках) | **Нет** | Клиент покажет или посчитает неверную сумму. Новые единицы передавать в новом поле или сохранить прежние |
| Изменили формат даты (например, `2026-11-24` → `24.11.2026`) | **Зависит** | Старый разбор может не распознать дату. Проверить клиент или сохранить прежний формат |
| Изменили формат чисел (например, `1500.50` → `"1 500,50"`) | **Зависит** | Клиент может ждать число, а получить строку. Передавать числа в машиночитаемом виде |
| Изменили порядок элементов массива (например, заказы теперь от старых к новым) | **Зависит** | Приложение может полагаться на порядок при показе. Сохранить сортировку или проверить логику клиента |
| Изменили состав возвращаемых записей (например, теперь исключаются отменённые заказы) | **Зависит** | Старая МП может ждать эти записи в сценарии. Проверить сценарии, которые на них опираются |
| Изменили размер страницы по умолчанию (например, 20 → 100 записей) | **Зависит** | Возможны сбои постраничного вывода, отображения и рост времени ответа. Проверить клиент или сохранить прежний размер |
| Изменили схему постраничного вывода (например, `page=2` заменили курсором `next_cursor`) | **Нет**, если прежняя схема перестала работать | Старое приложение не знает новой схемы. Сохранить прежнюю |
| Добавили обязательное действие по ответу (например, теперь нужен дополнительный запрос подтверждения) | **Нет**, если без действия сценарий не завершается | Старая МП не выполняет новый шаг. Для старых клиентов сохранить прежний сценарий |

#### 2.9. Ответ с ошибкой (Error Response)

| Изменение | Совместимо? | Почему / что нужно |
|---|---|---|
| Изменили только текст ошибки (например, «Неверный счёт» → «Номер счёта должен содержать 20 цифр») | **Да**, если приложение показывает текст сервера | Проверить, что клиент выводит текст из ответа, а не подставляет свой по коду ошибки |
| Переименовали поле ошибки (например, `error_text` → `message`) | **Нет**, если клиент читает `error_text` | Старая МП не найдёт текст ошибки. Сохранить прежний ключ |
| Удалили поле ошибки (например, больше нет `error_code`) | **Нет**, если клиент его использует | Обработка ошибки в клиенте нарушается. Сохранить поле |
| Изменили тип поля ошибки (например, `error_code: 1015` → `"1015"`) | **Зависит** | Клиент может ждать число. Проверить разбор или сохранить прежний тип |
| Добавили новое поле ошибки (например, `field: "bank_account"`) | **Да**, если клиент пропускает неизвестные поля | Прежние поля ошибки должны сохраниться |
| Добавили новый код ошибки (например, `error_code: 1020`) | **Зависит** | У старой МП может не быть обработки нового кода. Проверить, как клиент обрабатывает неизвестные коды |
| Изменили существующий код ошибки (например, ошибка реквизитов раньше `1015`, теперь `1020`) | **Зависит** | Клиент может выбирать сценарий по коду. Сохранить прежний код или проверить все обработчики |
| Перенесли конкретный текст ошибки в другое поле (например, из `error_text` в `error_data`) | **Нет**, если клиент читает только `error_text` | Приложение перестанет показывать конкретную причину. Оставить текст в прежнем поле |
| Заменили конкретный текст общим (например, «Неверный номер счёта» → «Ошибка валидации данных») | Формально **да**, по сути **нет** | Клиент покажет ошибку, но пользователь не поймёт, что исправить. Конкретный текст сохранять там, где его читает МП |
| Изменили структуру ответа с ошибкой (например, `result.error_text` → `errors[0].message`) | **Нет**, если прежний формат удалён | Старая МП не разберёт ошибку. Сохранить прежний формат |
| Убрали признак ошибки (например, `success: false` больше не передаётся) | **Нет**, если клиент его использует | МП может неверно определить результат и показать успех. Сохранить поле |
| Начали возвращать ошибку нового правила в новом формате | **Зависит** | Старая МП может не распознать именно эту ошибку. Новую ошибку возвращать в существующем формате |
| Добавили ошибку нового бизнес-правила (например, теперь отклоняется счёт из 19 цифр) | **Зависит** | Проверить, что клиент показывает отказ, не показывает ложный успех и даёт исправить данные |

### 2.10. Поведение API и бизнес-логика

Даже если запрос и ответ не изменились, совместимость может нарушиться из-за изменения поведения сервера.

| Изменение | Совместимо? | Почему / что нужно |
|---|---|---|
| Изменили бизнес-правило без изменения контракта (например, теперь нельзя вернуть изделие после определённого статуса) | **Зависит** | Старая МП может предлагать действие, которое сервер теперь запрещает. Проверить, что отказ показан понятным текстом и не выглядит как успех |
| Изменили поведение по умолчанию (например, без параметра теперь возвращаются только активные заказы, а не все) | **Зависит** | Старая МП получит другой результат на прежний запрос. Без нового параметра сохранить прежнее поведение |
| Изменили сортировку данных (например, новые заказы больше не идут первыми) | **Зависит** | Старый клиент может опираться на порядок элементов. Проверить логику клиента |
| Изменили набор возвращаемых записей (например, скрыли отменённые возвраты) | **Зависит** | Могут нарушиться сценарии, которые используют эти записи. Проверить сценарии старого клиента |
| Изменили порядок вызовов API (например, теперь нужно сначала сохранить реквизиты, затем создать возврат) | **Нет**, если прежний порядок запрещён | Старые приложения вызывают методы в прежней последовательности. Сохранить её поддержку |
| Добавили обязательный шаг процесса (например, перед оформлением возврата нужно вызвать новый метод подтверждения) | **Нет**, если старое приложение этот шаг не выполняет | Старый клиент не сможет завершить операцию. Различать поведение по версии |
| Добавили правило, которое действует с определённой версии МП (например, с версии `X.Y.Z` требуется `is_bank_details_confirmed`) | **Да** для старых версий, если реализовано способом 3 из раздела 3 | Для версий ниже пороговой прежнее поведение сохраняется. Проверить запросы без заголовков версии и с нераспознанной версией |
| Ужесточили серверную проверку (например, номер счёта должен содержать ровно 20 цифр) | **Нет** для запросов, которые раньше проходили; сценарий может сохраниться | Проверить, что клиент показывает ошибку, даёт исправить данные и отправить запрос повторно |
| Изменили обработку ошибок (например, раньше ошибка показывалась на форме, теперь сервер возвращает другой код) | **Зависит** | Старое приложение может по-другому реагировать на ошибку. Проверить обработчик ошибок клиента |
| Изменили условие доступности действия (например, `can_be_returned` теперь рассчитывается по новым правилам) | **Зависит** | Приложение может показывать или скрывать кнопку по своей логике, а не только по признаку. Проверить, как клиент использует признак |
| Добавили новый эндпоинт, не меняя прежние | **Да** | Старые клиенты его не вызывают. Существующий процесс сохраняется |
| Изменили порядок выкладки бэкенда и МП (например, бэкенд требует новое поле до публикации приложения) | **Нет**, если старые версии сразу блокируются | Бэкенд должен работать с версиями из стора и с ранее установленными поддерживаемыми сборками (раздел 3, порядок выкатки) |
| Изменили поведение при повторном запросе (например, повторное создание возврата теперь создаёт дубль) | **Нет**, если старый клиент рассчитывает на безопасный повтор | Проверить повторные запросы, таймауты и защиту от дублей |
| Увеличилось время обработки запроса (например, оформление возврата вместо 2 секунд занимает 40) | **Зависит** | Старая МП может прервать запрос по таймауту. Проверить ограничения клиента |

## 3. Как сохранить совместимость

Способы — от простого к затратному. Выбирать первый, который решает задачу.

1. **Необязательный параметр.** Новое поведение включается, только когда параметр передан. Без параметра сервер работает как раньше.
2. **Новое поле рядом со старым.** Старое поле не удаляется и не меняет смысла; новые клиенты читают новое.
3. **Разное поведение по версии клиента.** Сервер видит версию приложения в запросе и включает новое правило только с определённой версии. Запрос без версии или с нераспознанной версией обрабатывается по-старому. Пороговые версии подтверждают команды приложений.
4. **Новая версия эндпоинта или отдельный эндпоинт** — когда изменение нельзя сделать без поломки контракта (раздел 5).
5. **Принудительное обновление приложения** — отсекает старые версии полностью. Решение продукта, а не способ проектирования API.

Порядок выкатки: сервер выкатывается раньше клиента и работает с обеими версиями клиента.

### Что зафиксировать в требованиях к фиче для МП

Если поведение фичи в мобильном приложении зависит от версии (способы 3 и 5), в требованиях записываются:

1. **Минимальная версия** iOS и Android, с которой работает новое поведение. Версии подтверждают команды приложений; до подтверждения — открытый вопрос.
2. **Что видит пользователь старой версии**: функция скрыта, работает по-старому, работает частично или показана заглушка с предложением обновить приложение. Вариант выбирает продукт.
3. **Когда можно отключить поддержку старого поведения**: условие — по данным о вызовах старых версий или после принудительного обновления приложения. Условие выбирает продукт; пока оно не выбрано — открытый вопрос.

## 4. Path или query

- **Path** — часть адреса ресурса, передаётся всегда. В path — идентификатор, который однозначно указывает на ресурс.
- **Query** — не часть структуры адреса: параметры передаются в любом порядке. Query-параметр может быть и необязательным, и обязательным (например, обязательный фильтр). Обязательность сама по себе не означает, что параметр должен быть в path.
- Если параметр может со временем стать необязательным, его удобнее передавать в query: убрать его из path без смены адреса нельзя.
- Список значений — query: в path нельзя передать больше одного значения.
- Фильтры, сортировка, постраничный вывод — query.
- Новый параметр в path меняет адрес — для старых клиентов это новый эндпоинт. Новый необязательный параметр в query совместим, если без него поведение прежнее.

## 5. Новая версия эндпоинта

Если изменение нельзя внести без поломки контракта:

1. Поддерживать одновременно старую и новую версию эндпоинта, пока старой пользуются.
2. Уведомить потребителей о новой версии и списке изменений.

Новая версия требует доработки всех потребителей, которые на неё переходят:

```
GET https://bank.com/v1/order?id=5
GET https://bank.com/v2/order?id=5&type=3
```

Особенно важно, если сервис:
- доступен внешним системам за пределами экосистемы;
- имеет много потребителей;
- обслуживает мобильное приложение.

Старую версию отключают, когда ей перестали пользоваться: по данным о вызовах или после принудительного обновления приложения.

## 6. Пример: сохранить совместимость или поднять версию

Оформление кредита есть в приложении с версии 2.3.0. Приложение вызывает `POST https://bank.com/credits`:

```json
{
  "period": 24,               // integer, обязательно
  "sum": 100000,              // integer, обязательно
  "creditProductId": 2,       // integer, обязательно
  "clientId": "7dbd1150-3325-4716-a4be-f736fef3e033", // string, обязательно
  "isDocumentSigned": true    // boolean, обязательно
}
```

Новое требование: клиент выбирает диапазон срока и суммы вместо одного значения. Это доработка интерфейса приложения, API и новый релиз приложения.

Диапазон можно передать двумя парами полей (`minSum`, `maxSum`) или массивом (`sumRange: [1000, 2000]`). Ниже — массивы.

**Вариант 1. Сохраняем совместимость: дорабатываем `v1`, его вызывают и старые, и новые версии приложения.**

```json
{
  "period": 24,                  // integer, было обязательно → стало необязательно
  "sum": 100000,                 // integer, было обязательно → стало необязательно
  "sumRange": [100000, 200000],  // array[integer], необязательно
  "periodRange": [12, 24],       // array[integer], необязательно
  "creditProductId": 2,          // integer, обязательно
  "clientId": "7dbd1150-3325-4716-a4be-f736fef3e033", // string, обязательно
  "isDocumentSigned": true       // boolean, обязательно
}
```

Обязательность переходит в бизнес-правило: должна быть передана хотя бы одна пара — `sum` и `period` или `sumRange` и `periodRange`. Иначе — `422`, `"code": "SumAndPeriodRequired"`. Старые версии передают `sum` и `period` и работают без изменений.

**Вариант 2. Поднимаем версию: новый эндпоинт `POST https://bank.com/v2/credits`, его вызывает новая версия приложения.**

```json
{
  "sumRange": [1000, 2000],      // array[integer], обязательно
  "periodRange": [12, 24],       // array[integer], обязательно
  "creditProductId": 2,          // integer, обязательно
  "clientId": "7dbd1150-3325-4716-a4be-f736fef3e033", // string, обязательно
  "isDocumentSigned": true       // boolean, обязательно
}
```

Контракт `v2` проще: поля обязательны, бизнес-ошибка `422 SumAndPeriodRequired` не нужна. Цена — две версии эндпоинта, которые поддерживаются, пока старые версии приложения в ходу.

Выбор: вариант 1 — меньше эндпоинтов, но сложнее правила проверки; вариант 2 — чистый контракт, но две версии в поддержке.

## 7. Пример: правило только для новых версий приложения

Подтверждение банковских реквизитов при возврате (ECOMDEV-2649):
- новый параметр `is_bank_details_confirmed` в существующем методе создания возврата — необязательный: старые версии приложения его не передают, и возврат принимается, как раньше (способ 1);
- подтверждение обязательно только с версии приложения, в которой появился чекбокс (способ 3). Пороговые версии iOS и Android команды приложений ещё не подтвердили, поэтому в задаче вместо них стоят заглушки; пока их нет, правило не включается. Запрос без версии, с нераспознанной версией или с версией ниже пороговой может не содержать `is_bank_details_confirmed`: возврат принимается, как раньше. Явно переданный `false` отклоняется при любой версии;
- ужесточённую проверку номера счёта (ровно 20 цифр) старые версии получают сразу. По коду iOS подтверждено: начиная с версии 1.42 приложение показывает текст ошибки сервера в алерте и даёт исправить реквизиты. Для версий iOS ниже 1.42 и для Android это не проверено.
