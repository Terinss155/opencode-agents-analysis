# Обратная совместимость API

Справочник: что такое обратная совместимость, какие изменения API безопасны для действующих потребителей, какие требуют доработок, и как выбрать способ изменения. Применение к Mobile API монолита (проверка версии МП, блок «Совместимость с МП» в задаче) — `skill/tracker-task/SKILL.md` §3 «Совместимость с МП». Общие принципы — `AGENTS.md` → «Правила системного анализа при разработке нового функционала», п. 4–5.

## 1. Определение

Обратная совместимость — изменение существующего API, после которого все его потребители продолжают работать без доработок на своей стороне.

Если сохранить совместимость нельзя, нужна новая версия эндпоинта или отдельный эндпоинт: старые потребители остаются на прежнем, новые переходят на новый.

Для мобильного приложения это особенно важно: у клиентов одновременно установлены разные версии, и не все обновляются. Старая версия вызывает тот же эндпоинт со старым контрактом. Если контракт сломан, старая версия перестаёт работать.

## 2. Когда безопасно, когда нужны доработки

**Запрос**

| Изменение | Совместимо? | Почему / что нужно |
|---|---|---|
| Новый необязательный параметр | да | Старый клиент его не передаёт — сервер работает как раньше. Поведение без параметра должно совпадать с текущим |
| Обязательный параметр стал необязательным | да | Старые клиенты продолжают его передавать |
| Новое значение enum во входном параметре | да | Старые клиенты передают прежние значения |
| Новый обязательный параметр | **нет** | Старый клиент его не передаёт — получит ошибку. Сделать параметр необязательным, различать поведение по версии клиента или поднять версию эндпоинта |
| Необязательный параметр стал обязательным | **нет** | Старый клиент может его не передавать — получит ошибку. Те же способы: оставить необязательным для старых клиентов, различать поведение по версии или поднять версию эндпоинта |
| Ужесточение проверки существующего параметра (формат, длина, допустимые значения) | **нет**, нужна проверка | Старый клиент может отправить значение, которое раньше проходило. Убедиться, что клиент показывает текст ошибки и даёт исправить ввод |
| Переименование или удаление параметра | **нет** | Старый клиент передаёт прежнее имя — сервер его не видит |
| Перенос параметра между `path`, `query` и `body` | **нет** | Меняется адрес или место параметра — старый запрос не совпадёт с новым контрактом |

**Ответ**

| Изменение | Совместимо? | Почему / что нужно |
|---|---|---|
| Новое поле | да, если клиент игнорирует неизвестные поля | Проверить у команды клиента |
| Удаление или переименование поля | **нет** | Клиент ждёт поле — пустое место на экране или ошибка разбора. Добавить новое поле рядом, старое оставить |
| Смена типа или формата поля (строка → число, объект → массив) | **нет** | Ошибка разбора ответа |
| Поле может стать `null` или пропасть | **нет** | Клиент, который ждёт значение, падает или показывает пустоту |
| Новое значение enum | **нет**, если клиент не обрабатывает неизвестные значения | Проверить у команды клиента; иначе — новое поле или разное поведение по версии |
| Тот же ключ получает другой смысл | **нет** | Структура не меняется, но клиент неверно показывает или считает данные. Новый смысл — новое поле |

**Поведение и ошибки**

| Изменение | Совместимо? | Почему / что нужно |
|---|---|---|
| HTTP-статус, код ошибки, конверт ответа | **нет** | Клиент разбирает ошибку по статусу и полям — покажет не тот текст или не ту ветку экрана |
| Текст ошибки вместо конкретного — общий | формально да, по сути **нет** | Клиент покажет текст, но пользователь не поймёт, что исправить. Конкретный текст оставлять там, где клиент его читает |
| Значение по умолчанию, сортировка, размер страницы, набор возвращаемых записей | **нет** | Структура та же, результат другой. Сохранять прежнее поведение, когда новый параметр не передан |
| Новый эндпоинт | да | Старые клиенты его не вызывают |

## 3. Как сохранить совместимость

Способы — от простого к затратному. Выбирать первый, который решает задачу.

1. **Необязательный параметр.** Новое поведение включается, только когда параметр передан. Без параметра сервер работает как раньше.
2. **Новое поле рядом со старым.** Старое поле не удаляется и не меняет смысла; новые клиенты читают новое.
3. **Разное поведение по версии клиента.** Сервер видит версию приложения в запросе и включает новое правило только с определённой версии. Запрос без версии или с нераспознанной версией обрабатывается по-старому. Пороговые версии подтверждают команды приложений.
4. **Новая версия эндпоинта или отдельный эндпоинт** — когда изменение нельзя сделать без поломки контракта (раздел 5).
5. **Принудительное обновление приложения** — отсекает старые версии полностью. Решение продукта, а не способ проектирования API.

Порядок выкатки: сервер выкатывается раньше клиента и работает с обеими версиями клиента.

## 4. Path или query

- **Path** — часть адреса ресурса, передаётся всегда. В path — то, что обязательно всегда и однозначно указывает на ресурс (идентификатор).
- **Query** — не часть структуры адреса: параметры передаются в любом порядке, часть из них можно не передавать.
- Параметр обязателен всегда — path. Может быть или со временем стать необязательным — query.
- Список значений — query: в path нельзя передать больше одного значения.
- Фильтры, сортировка, постраничный вывод — query.
- Новый параметр в path меняет адрес — для старых клиентов это новый эндпоинт. Новый необязательный параметр в query совместим.

## 5. Новая версия эндпоинта

Если изменение нельзя внести без поломки контракта:

1. Поддерживать одновременно старую и новую версию эндпоинта, пока старой пользуются.
2. Уведомить потребителей о новой версии и списке изменений.

Новая версия требует доработки всех потребителей, которые на неё переходят:

```
GET https://bank.com/v1/order?id=5
GET https://bank.com/v2/order?id=5&type=3
```

Особенно важно, если сервис:
- доступен внешним системам за пределами экосистемы;
- имеет много потребителей;
- обслуживает мобильное приложение.

Старую версию отключают, когда ей перестали пользоваться: по данным о вызовах или после принудительного обновления приложения.

## 6. Пример: сохранить совместимость или поднять версию

Оформление кредита есть в приложении с версии 2.3.0. Приложение вызывает `POST https://bank.com/credits`:

```json
{
  "period": 24,               // integer, обязательно
  "sum": 100000,              // integer, обязательно
  "creditProductId": 2,       // integer, обязательно
  "clientId": "7dbd1150-3325-4716-a4be-f736fef3e033", // string, обязательно
  "isDocumentSigned": true    // boolean, обязательно
}
```

Новое требование: клиент выбирает диапазон срока и суммы вместо одного значения. Это доработка интерфейса приложения, API и новый релиз приложения.

Диапазон можно передать двумя парами полей (`minSum`, `maxSum`) или массивом (`sumRange: [1000, 2000]`). Ниже — массивы.

**Вариант 1. Сохраняем совместимость: дорабатываем `v1`, его вызывают и старые, и новые версии приложения.**

```json
{
  "period": 24,                  // integer, было обязательно → стало необязательно
  "sum": 100000,                 // integer, было обязательно → стало необязательно
  "sumRange": [100000, 200000],  // array[integer], необязательно
  "periodRange": [12, 24],       // array[integer], необязательно
  "creditProductId": 2,          // integer, обязательно
  "clientId": "7dbd1150-3325-4716-a4be-f736fef3e033", // string, обязательно
  "isDocumentSigned": true       // boolean, обязательно
}
```

Обязательность переходит в бизнес-правило: должна быть передана хотя бы одна пара — `sum` и `period` или `sumRange` и `periodRange`. Иначе — `422`, `"code": "SumAndPeriodRequired"`. Старые версии передают `sum` и `period` и работают без изменений.

**Вариант 2. Поднимаем версию: новый эндпоинт `POST https://bank.com/v2/credits`, его вызывает новая версия приложения.**

```json
{
  "sumRange": [1000, 2000],      // array[integer], обязательно
  "periodRange": [12, 24],       // array[integer], обязательно
  "creditProductId": 2,          // integer, обязательно
  "clientId": "7dbd1150-3325-4716-a4be-f736fef3e033", // string, обязательно
  "isDocumentSigned": true       // boolean, обязательно
}
```

Контракт `v2` проще: поля обязательны, бизнес-ошибка `422 SumAndPeriodRequired` не нужна. Цена — две версии эндпоинта, которые поддерживаются, пока старые версии приложения в ходу.

Выбор: вариант 1 — меньше эндпоинтов, но сложнее правила проверки; вариант 2 — чистый контракт, но две версии в поддержке.

## 7. Пример: правило только для новых версий приложения

Подтверждение банковских реквизитов при возврате (ECOMDEV-2649):
- новый параметр `is_bank_details_confirmed` в существующем методе создания возврата — необязательный: старые версии приложения его не передают, и возврат принимается, как раньше (способ 1);
- требовать подтверждение предлагается только с версии приложения, в которой появился чекбокс (способ 3). Запрос без версии или со старой версией обрабатывается по-старому;
- ужесточение проверки номера счёта (ровно 20 цифр) старые версии получают сразу. Поэтому проверено, что старое приложение показывает текст ошибки сервера и даёт исправить реквизиты.
