## 1. Способ сборки ответа

**AS-IS.** Ответ сайта собирается одним из двух способов. От способа зависят заголовки ответа и HTTP-статус ошибки.
Способ сборки не путать со структурой ошибки (детальная / плоская — [errors.md](./errors.md), раздел 2): любая структура возможна при любом способе.

| Способ | Где используется | Заголовки ответа | HTTP-статус ошибки |
|---|---|---|---|
| **Сервис ответа** — `FrontendApiResponseService` (базовый `src/Http/Controller/FrontendApiBaseController.php`, с 15.07.2026) | Новые контроллеры: `Auth`, `User`, `User/Notifications`, `Cart/CartSubscription` | Проставляются автоматически | По коду ошибки — `ResponseErrorCode::getStatusCode()`; ошибки полей (`ValidatorException`) — 422 |
| **Ответ в контроллере** — массив / `SsrResponse` | `Api2/OrdersController` (в т.ч. `return-details`, `return-method-list`), `Product`, `delivery`, `giftcards`, `/api/cart/*` | Не проставляются | **200** — ошибка видна только по телу (у `/api/cart/*` — по `getStatusCode()`, кроме кодов корзины, см. раздел 9) |

**Согласовано.** Новый метод в **существующем** контроллере делается тем же способом, что и соседние методы. Новый контроллер или раздел — через сервис ответа; стандарт разделов 3–8 — для него.

## 2. Заголовки

### Заголовок запроса

| Ключ | Описание |
|:---|:---|
| `X-Request-Id` | Подпись запроса в формате uuid |
| `X-Request-Version` | Запрашиваемая версия API в формате семантического версионирования |
| `X-Language` | Язык запроса |

**AS-IS.** Монолит эти заголовки не требует — в задаче они не описываются. Блок «Заголовки» в задаче — только для заголовков, специфичных для метода (`Authorization` у `refresh`).

```json
{
  "X-Request-Id": "6c17e0c1-8fa3-4925-9f88-56fec69fb99f",
  "X-Request-Version": "1.000.0",
  "X-Language": "ru",
  "Accept-Language": "ru-RU,ru;q=0.9,en-US;q=0.8,en;q=0.7"
}
```

### Заголовок ответа

| Ключ | Описание |
|:---|:---|
| `X-Response-Id` | Подпись ответа в формате uuid |
| `X-Response-Version` | Версия API в формате семантического версионирования |
| `X-Language` | Язык ответа |

**AS-IS.** Проставляются автоматически только сервисом ответа; при ответе в контроллере отсутствуют. В задаче не описываются.

```json
{
  "X-Response-Id": "6c17e0c1-8fa3-4925-9f88-56fec69fb99f",
  "X-Response-Version": "1.000.0",
  "X-Language": "ru"
}
```

## 3. Путь

1. **Согласовано** (практика, §6.1 п. 5). Префикс — `/api/`. Новый раздел API — `/api/v1/<раздел>` (`/api/v1/notifications` — 09.2026, `/api/v1/delivery/...`). Новый метод в существующем разделе продолжает его путь (`/api/orders/{order_id}/...`; `/cart/subscription/check` — контроллер создан 08.2026, задача ECOMDEV-1962, раздел `cart` без `/api`).
2. **Предложение.** Ресурс — существительное во множественном числе, kebab-case: `/api/v1/notifications`, `/api/v1/users/me/addresses`.
3. **Предложение.** Вложенность — по владельцу: `/api/v1/orders/{order_id}/<подресурс>`. Текущий пользователь — `users/me`, id пользователя в путь не передаётся.
4. **Предложение.** Path-параметр — snake_case с суффиксом `_id`, целое: `{order_id}`, `{address_id}`. AS-IS: в `/api/v1/delivery/*` — camelCase (`{countryIso}`, `{providerId}`, `{geoId}`).
5. **Согласовано.** Действие, которое не ложится на CRUD, — глагол kebab-case последним сегментом: `/read`, `/read-all`, `/check`. Сначала проверить, нельзя ли выразить CRUD-ом (регламент: CRUD — по возможности).

## 4. HTTP-метод

**Согласовано** (практика сервиса ответа).

| Действие | Метод | Тело | Успех |
|---|---|---|---|
| Получить список / объект | `GET` | нет, фильтры — плоские query-параметры | 200 |
| Создать | `POST` | JSON | 200, созданный объект в `data` |
| Частично изменить | `PATCH` | JSON, только изменяемые поля | 200, объект в `data` |
| Удалить | `DELETE` | нет | 200, `data` — пустой массив `[]` (так сервис ответа отдаёт пустые данные) |
| Действие (`/read`, `/check`) | `POST` | JSON | 200 |

Одно действие — один метод; чужой HTTP-метод отклоняется (`VerbFilter`). Сайт отвечает 200 и на создание: 201 в монолите не используется.

## 5. Авторизация и доступ

1. **Согласовано.** Для каждого метода указывается: закрытый (нужна авторизация) или открытый.
2. **Согласовано.** Закрытый метод без авторизации → 401 / `40001`.
3. **Предложение** (§6.1 п. 4, вопрос бэку). Ресурс пользователя ищется по id **и** текущему пользователю. Не найден или чужой → 404 / `40004` — не раскрываем существование чужих записей. AS-IS: `POST /api/v1/notifications/read` (09.2026) отдаёт чужое → 403 `PERMISSION_DENIED`, не найдено → 404; детали возврата — чужой заказ → 404.
4. **AS-IS → правило.** Открытый метод с отправкой SMS / email или перебором (вход, проверка кода) — капча и ограничение частоты: 400 капча не пройдена, 424 сервис капчи недоступен, 429 слишком частые запросы (как `/api/auth/*`). Лимиты (сколько попыток за какое время) указываются в задаче.

## 6. Запрос

1. **Согласовано.** Имена — snake_case, по [словарю полей](./field-glossary.md).
2. **Согласовано.** Query — только **плоская запись**: `?city_id=...&limit=20&offset=0`. Вложенная запись регламента `?filters[...]=...&pagination[...]=...` в монолите не используется: API-контроллеры не читают `filters` / `pagination` из запроса, `limit` / `offset` читаются плоско (например, `src/Modules/Delivery/Controller/GeoController.php`). Пагинация — `limit` / `offset` с допустимыми значениями и значениями по умолчанию.

   | Ключ | Описание |
   |:---|:---|
   | `limit` | Размер страницы — если нужна пагинация |
   | `offset` | Смещение — если нужна пагинация |
   | `*` | Фильтры — отдельными параметрами |

3. **Согласовано.** Тело — JSON, snake_case. Объекты `filters` / `pagination` в теле запроса в коде не используются — не вводить без согласования с бэком. Для каждого поля: тип, обязательность, формат (длина, регулярное правило, диапазон, enum — все значения), nullable и когда `null`.
4. **Согласовано.** Предобработка указывается явно: обрезка пробелов по краям (`email` в `cart/subscription/check`), удаление пробелов и дефисов из номеров.
5. Заголовки `X-Request-*` не описываются (раздел 2).

Пример запроса:

```
GET /api/orders/{order_id}/return-method-list?country_iso=RU&city=Москва
```

```json
POST /api/orders/{order_id}/return-details

{
  "method_return": "courier",
  "city_return": "Москва",
  "address_return": "ул. Тверская, д. 1",
  "index_return": "125009",
  "date_return": "2026-10-05"
}
```

## 7. Ответ

### Параметры ответа

**Согласовано** (сервис ответа; §6.1 п. 1 — практика 2026).

| Ключ | Описание |
|:---|:---|
| `status` | Статус ответа: `"success"` / `"error"` |
| `message` | Сообщение ответа (может быть пустой строкой) |
| `data` | Данные ответа. Объект — для одного ресурса; **пустые данные — `[]`** (значение по умолчанию сервиса ответа); **список — массив прямо в `data`**. `data.items` — только если рядом со списком в `data` есть другие поля |
| `total` | Только для списка без пагинации — количество элементов (на верхнем уровне, рядом с `data`) |
| `pagination` | Только при пагинации — `{limit, offset, total}` на верхнем уровне |

Правила:
1. **Согласовано.** Конверт успеха — `status: "success"`, `message`, `data`.
2. **Согласовано.** `message` — текст для пользователя или пустая строка. Если текст есть — ru и en в задаче; тексты — через переводы `translations/<раздел>/…+intl-icu.{ru,en}.yaml`, ключ перевода выбирает разработчик.
3. **Согласовано** (§6.1 п. 1). Список — массив в `data` + `total` или `pagination` на верхнем уровне (`GET /api/v1/notifications`, 09.2026). Ни один новый метод не отдаёт `data.items`. Прежнее правило `web-endpoint` «список — `data.items`» снято 17.11.2026.
4. **Согласовано.** Поля ответа: полный путь, тип, nullable и когда `null`, все значения enum; пример совпадает с таблицей.
5. **Согласовано** (`AGENTS.md` → «Принципы проектирования»). Значения для показа пользователю (признаки, суммы, даты, тексты) бэк отдаёт готовыми.
6. **AS-IS-отступление** (ответ в контроллере): `POST /api/orders/{order_id}/return-details` при успехе отдаёт `{"success": true, "message": "..."}` без `status` и `data`.

Пример успешного ответа — список с пагинацией:

```json
{
  "status": "success",
  "message": "",
  "pagination": {
    "limit": 100,
    "offset": 100,
    "total": 953
  },
  "data": [
    {
      "method": "courier",
      "method_type": "courier",
      "title": "Курьер",
      "available_dates_return": ["2026-10-05", "2026-10-06"]
    }
  ]
}
```

Пример — список без пагинации (структура как у `GET /api/v1/notifications`; поля элемента условные):

```json
{
  "status": "success",
  "message": "",
  "data": [
    { "<поле>": "<значение>" }
  ],
  "total": 1
}
```

## 8. Ответ с ошибкой

**Согласовано.** Коды, HTTP-статусы и выбор структуры — [errors.md](./errors.md).

| Ключ | Описание |
|:---|:---|
| `status` | Статус ответа: `"error"` |
| `message` | Сообщение ошибки |
| `code` | Код ошибки верхнего уровня — строка из `ResponseErrorCode` (`"40000"`, …) |
| `errors` | `Error[]` — только для детальной структуры (формы ввода) |

`Error`:

| Ключ | Описание |
|:---|:---|
| `target` | Имя поля, к которому относится ошибка; общая ошибка — `""` |
| `code` | Предметный код из `ResponseErrorCode` — строка (`"20110"`) |
| `message` | Сообщение ошибки |

**AS-IS-отступления** ответа в контроллере (`Api2/OrdersController`): дополнительно `"success": false`; `return-details` возвращает в `data` введённые значения и `available_dates_return`, чтобы форма перерисовалась без повторного запроса.

Детальная структура — форма ввода, клиенту нужно подсветить поле (`POST /api/orders/{order_id}/return-details`; ответ в контроллере → HTTP 200 и дополнительно `success: false`):

```json
{
  "status": "error",
  "success": false,
  "message": "Некорректный запрос",
  "code": "40000",
  "errors": [
    {
      "target": "index_return",
      "code": "20115",
      "message": "Некорректный индекс"
    }
  ]
}
```

Плоская структура — ввода нет, клиенту нужен только факт ошибки для тоста (условный пример: кнопка «Прочитать уведомление» по несуществующему `uuid`; `errors` не передаётся):

```json
{
  "status": "error",
  "message": "Не найдено",
  "code": "40004"
}
```

**Что общее и берётся в стандарт** (эндпоинты 1–3, 6):

- конверт `status` / `message` / `data`; у ошибки — `status` / `message` / `code` / `errors[]`;
- HTTP-статус ошибки соответствует коду (`ResponseErrorCode::getStatusCode()`); заголовки `X-Response-*` проставляются автоматически;
- ошибки ввода — 422 с кодом `20279` и `errors[]`, где у каждой ошибки `target` (поле) и предметный код;
- один HTTP-метод на действие, чужой метод отклоняется;
- тексты `message` — через переводы `translations/<раздел>/…+intl-icu.{ru,en}.yaml`;
- в swagger: `tags`, `summary`, `operationId`, `security`, `requestBody` со списком `required`, ответы через `$ref` на общие схемы (`BaseSuccessResponse`, `BaseErrorResponse`, `ValidationErrorResponse`), пример ошибки с кодами.

**Что не повторяем** (расхождения между эндпоинтами):

| Расхождение | Где | Как в стандарте |
|---|---|---|
| camelCase в теле | `orderId` в `read-all` | Только snake_case |
| Обязательное поле не передано → 400 без `errors[]` | `notifications/read` (`uuid`) | Поле тела → 422 / `20279` + `errors[]` с `target`; 400 / `40000` — только сломанный запрос ([errors.md](./errors.md)) |
| Чужой ресурс → 403 | `notifications/read` | 404 / `40004` — **Предложение** (раздел 5, п. 3) |
| Ошибка с HTTP 200 / тело исключения Yii | `return-details`, `change-payment-method`, ошибки корзины в `/api/cart/*` | Только сервис ответа: HTTP-статус по коду, единый конверт |
| Ответ без конверта `status` / `data` | `/api/v1/delivery/geo/*`, `pickup/*` | Конверт сервиса ответа и для методов-прокси |
| Лишнее поле `success` рядом со `status` | `return-details`, `/api/cart/*` | Только `status` |
| Нет проверки владельца ресурса | `change-payment-method` | Ресурс ищется по id и текущему пользователю |
| Path-параметр `orderId` в swagger при `order_id` в маршруте; camelCase в пути | `components/parameters/orderId`; `{countryIso}`, `{providerId}`, `{geoId}` | Имя в swagger = имя в маршруте; в новых путях — snake_case |
| `required: true` внутри `properties`, `nullable: true` при `openapi: 3.1.0` | `SaveOrderReturnDetailsRequest`, `Notification` | Список `required` у объекта; `type: [string, "null"]` ([swagger.md](./swagger.md)) |

Сняты из «не повторяем» 17.11.2026 (§6.1): «путь без `/api`» у `/cart/subscription/check` — метод продолжает путь существующего раздела `cart` (раздел 3, п. 1); «список целиком в `data`, `total` на верхнем уровне» у notifications — это и есть практика новых методов (раздел 7).

Эндпоинты 4, 5, 7, 8 остаются как есть: новый метод **в их контроллерах** делается тем же способом, что и соседние (раздел 1).
