### Формирование ADR

#### 1. Назначение

ADR фиксирует **одно значимое принятое или предлагаемое решение** и объясняет, почему в заданном
контексте выбран именно этот вариант. ADR хранит основания и компромиссы, но не заменяет BRD,
User Story, Use Case, API-контракт или другую спецификацию.

В рамках репозитория ADR применяется не только к архитектуре, но и к значимым продуктовым,
процессным и системным решениям, если важно сохранить альтернативы и последствия выбора.

##### Когда ADR нужен

- рассматривалось не менее двух реалистичных вариантов;
- решение влияет на scope, процесс, архитектуру, интеграции, данные, стоимость или сроки;
- у решения есть существенные отрицательные последствия или ограничения;
- без контекста будущая команда может повторно открыть уже закрытый спор;
- решение временное и должно быть пересмотрено при наступлении известных условий.

##### Когда ADR не нужен

- фиксируется исходное требование без выбора между вариантами — это BRD / User Story;
- описывается пошаговый сценарий — это Use Case;
- требуется протокол или дословная запись встречи — это транскрибация / резюме встречи;
- изменение тривиально, обратимо и не создаёт значимых последствий;
- вариант ещё не выбран и нет сформулированного предложения — сначала оформить открытый вопрос.

#### 2. Жизненный цикл

Допустимые статусы:

| Статус | Когда использовать |
|---|---|
| `Предложено` | Вариант сформулирован, но решение ещё не утверждено |
| `Принято` | Решение утверждено уполномоченным владельцем |
| `Отклонено` | Предложение рассмотрено и не принято |
| `Устарело` | Контекст изменился, решение больше не применяется |
| `Заменено на ADR-<ТЕМА>-<n>` | Принято новое решение; указан заменяющий ADR |

Принятый ADR не переписывается задним числом. При смене решения создаётся новый ADR, а старому
присваивается статус `Устарело` или `Заменено на ...`. Допустимы только исправления опечаток,
ссылок и фактических ошибок без изменения смысла; такое исправление отмечается в истории изменений.

#### 3. Формат ADR

```markdown
# ADR-<ТЕМА>-<номер>: <краткая формулировка решения>

| Поле | Значение |
|---|---|
| **Статус** | Предложено / Принято / Отклонено / Устарело / Заменено на ADR-... |
| **Дата решения** | ДД.ММ.ГГГГ или `Не определена` |
| **Владелец решения** | Роль / ФИО или `Не определён` |
| **Область** | Продукт / Бизнес-процесс / Архитектура / Интеграция / Данные / Инфраструктура |

## Контекст

<Проблема, ограничения, существенные факты и условия, при которых принимается решение.>

## Решение

<Один выбранный вариант. Коротко, однозначно, без перечисления альтернатив.>

## Последствия

### Положительные

- <получаемая выгода>

### Отрицательные и риски

- <цена выбора, ограничение или новый риск>

## Рассмотренные альтернативы

### <Название альтернативы>

- **Результат:** отклонена / отложена.
- **Причина:** <почему вариант не выбран в текущем контексте>.

## Условия пересмотра

- <проверяемое событие или изменение контекста, при котором решение нужно пересмотреть>.

## Источники

- [<название первичного материала>](<относительный путь>)
- <если первичный материал отсутствует — явно указать это без фиктивной ссылки>

## Связанные артефакты

- `<ID>` — [<артефакт>](<относительный путь>)

## История изменений

| Дата | Изменение |
|---|---|
| ДД.ММ.ГГГГ | ADR создан |
```

#### 4. Правила написания

- Один ADR содержит одно решение. Независимые решения оформляются отдельными ADR.
- Заголовок формулирует выбранный вариант, а не вопрос: `Запрет редактирования заявки в MVP`,
  а не `Как редактировать заявку?`.
- Контекст содержит только подтверждённые факты, ограничения и проблему; неизвестное отмечается
  как `Не определено`.
- Раздел «Решение» должен быть понятен без чтения альтернатив и содержать один вариант.
- Последствия описываются с двух сторон. ADR без отрицательных последствий считается неполным.
- Альтернатива не удаляется из записи только потому, что она отклонена. Указывается конкретная
  причина отклонения в текущем контексте.
- Условия пересмотра должны быть наблюдаемыми: изменение фазы проекта, появление API партнёра,
  превышение метрики, изменение законодательства. Формулировка `при необходимости` запрещена.
- Дата принятия не подменяется датой создания файла. Если дата решения неизвестна — указать
  `Не определена`.
- Владелец решения — лицо или роль с полномочиями утвердить выбор, а не автор ADR.
- Транскрибация является первичным источником и не редактируется по смыслу. ADR содержит вывод,
  но не выдаёт предположение автора за решение участников встречи.
- Если источник отсутствует в репозитории, это отмечается явно. Нельзя создавать несуществующую
  ссылку или додумывать состав участников.
- Связанные требования и технические артефакты указываются стабильными ID и ссылками. Их
  содержание в ADR не копируется.

#### 5. Трассируемость и размещение

- Файл: `requirements/adr/ADR-<ТЕМА>-<номер>-<slug>.md`.
- Номер ADR стабилен и не переиспользуется после удаления или отклонения записи.
- Первичные транскрибации: `requirements/drafts/transcriptions/`.
- Обработанные резюме встреч могут оставаться в `requirements/drafts/` и ссылаться на первичный
  материал, если он доступен.
- Место ADR в цепочке трассировки требований — `AGENTS.md` → «Иерархия артефактов требований».
  Связи с требованиями и техническими артефактами фиксируются в разделе «Связанные артефакты»
  самого ADR, по стабильным ID.

#### 6. Пример

```markdown
# ADR-RET-001: Запрет редактирования созданной заявки на возврат в MVP

| Поле | Значение |
|---|---|
| **Статус** | Принято |
| **Дата решения** | 10.09.2026 |
| **Владелец решения** | Не определён |
| **Область** | Продукт / Интеграция |

## Контекст

Клиент может ошибиться при выборе точки передачи, даты приезда курьера или других данных заявки.
Редактирование после создания требует синхронизации изменений с транспортными компаниями и
создаёт риск расхождения данных и дублирования накладных.

## Решение

В MVP созданная заявка не редактируется. Для изменения данных клиент отменяет текущую заявку и
создаёт новую, если действующие ограничения позволяют повторное оформление.

## Последствия

### Положительные

- Упрощается логика MVP и интеграция с транспортными компаниями.
- Снижается риск рассинхронизации и дублирования накладных.

### Отрицательные и риски

- Клиент выполняет дополнительные действия для исправления ошибки.
- Может вырасти количество обращений в поддержку и отмен заявок.

## Рассмотренные альтернативы

### Редактирование точки передачи или даты внутри заявки

- **Результат:** отклонена для MVP.
- **Причина:** требует синхронизации изменений и отмены ранее созданных операций на стороне ТК.

## Условия пересмотра

- Переход к проработке Post-MVP редактирования заявки.
- Подтверждение транспортными компаниями безопасного изменения заявки без создания дубликатов.
```

#### 7. Чек-лист качества

- [ ] ADR фиксирует одно решение, а не протокол всей встречи.
- [ ] Заголовок содержит стабильный ID и формулировку выбранного варианта.
- [ ] Статус соответствует жизненному циклу решения.
- [ ] Дата решения отделена от даты создания файла.
- [ ] Указан владелец решения либо честная пометка `Не определён`.
- [ ] Контекст содержит проблему, ограничения и подтверждённые факты.
- [ ] Решение сформулировано коротко и однозначно.
- [ ] Указаны положительные последствия.
- [ ] Указаны отрицательные последствия и риски.
- [ ] Рассмотренные альтернативы сохранены с причинами отклонения.
- [ ] Условия пересмотра наблюдаемы и проверяемы.
- [ ] Есть ссылки на доступные первичные источники; отсутствующие источники обозначены явно.
- [ ] Связанные требования и технические артефакты указаны по стабильным ID.
- [ ] ADR не дублирует содержание BRD, User Story, Use Case или технической спецификации.
- [ ] При замене решения создан новый ADR, а старый не удалён и ссылается на новый.
