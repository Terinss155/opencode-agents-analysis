### Ревью макетов по требованиям

#### 1. Назначение и границы

Проверяется только то, что клиент видит и делает на экране сайта или мобильного приложения: блоки, поля, тексты, действия и экраны, которые должны быть нарисованы. Сверка идёт в обе стороны: от требований к макету и от макета к требованиям.

**Вне рамок ревью — не записывается ни в расхождения, ни в «Не проверено»:**
- то, что происходит за кадром: логика бэкенда, интеграции, обработка на складе, автоматические переходы статусов, сроки и правила процесса, если они не выводятся текстом на экран;
- источник данных для поля (какая таблица, какое поле, какой эндпоинт) и формат хранения;
- расхождения между самими требованиями и ADR, которые не меняют того, что нарисовано на экране (устаревшие ссылки на ADR, разные формулировки шагов процесса в Use Case и User Story) — это зона gap-анализа и ревью качества бандла. Если требования различаются по тексту или элементу, который клиент видит на этом экране, — это предмет ревью (тип «Не определено», раздел 4);
- шаг Use Case или User Story, который противоречит действующему ADR: сверка идёт по ADR; если по нему элемент на экране в этом этапе не показывается, пункт не записывается;
- модель статусов: какие статусы существуют, как называются, когда наступают (см. правило «Статусы» в разделе 6);
- визуальный стиль: отступы, цвета, шрифты, иконки, соответствие дизайн-системе, анимации.

Критерий: расхождение записывается, только если по нему нужно что-то дорисовать или поменять на макете, либо в требованиях не описан элемент, который на макете есть. Если ответ на расхождение ничего не меняет на экране — это не предмет ревью.

Отчёт: `projects/<проект>/reviews/ui/[ГГГГ-ММ-ДД] <экран>_ui-review.md`.

#### 2. Подготовка

1. Составить список макетов для проверки: файлы PNG из `projects/<проект>/sources/mockups/`.
2. Определить этап ревью (MVP или полный объём) по задаче и по папке макетов.
3. Для каждого макета найти требования: спецификацию экрана (`SCR-…`), User Story с критериями приёмки, Use Case. Соответствие записывается в раздел отчёта «Что сверялось».
4. Если требование ссылается на ADR, сверка идёт с действующей версией решения: заменённый ADR (`Статус: Решение изменено`) не используется. Устаревшая ссылка сама по себе расхождением не считается.
5. Открыть каждый макет и выписать всё, что на нём видно: блоки, заголовки, поля, подписи, кнопки, сообщения. Тексты выписываются дословно.
6. Длинный макет инструмент чтения показывает уменьшенным. Если мелкий текст из-за этого не читается, элемент попадает в «Не проверено» с пометкой «нужна нарезка макета по высоте»; при наличии нарезанных фрагментов текст читается с них, а в отчёте ссылка даётся на исходный макет.

#### 3. Что сверять

**От требований к макету**
- [ ] Каждый блок из «Состава экрана» есть на макете и стоит в описанном порядке
- [ ] Каждое поле из «Параметров экрана», которое показывается клиенту, есть на макете
- [ ] Каждое действие из «Действий на экране» есть на макете с той же подписью
- [ ] Для каждого технического состояния экрана из требований есть макет: загрузка, пусто, ошибка, не найдено
- [ ] Для каждого варианта из «Правил отображения», который меняет состав экрана, есть макет: по каналу, способу, типу доставки

**От макета к требованиям**
- [ ] У каждого элемента макета есть описание в требованиях
- [ ] У каждого элемента, который показывается не всегда, в требованиях есть условие видимости
- [ ] У каждой кнопки и ссылки в требованиях описано, что происходит при нажатии

**Тексты**
- [ ] Заголовки, подписи кнопок, сообщения об ошибках и подсказки совпадают с требованиями дословно — там, где требования задают текст

**Сценарии**
- [ ] Каждый сценарий из критериев приёмки, где клиент действует на этом экране или видит результат, можно пройти по макетам: для `Given` есть исходный экран, для `When` — элемент действия, для `Then` — экран, диалог или сообщение с результатом
- [ ] Для каждого шага и расширения Use Case, где клиент видит экран или сообщение, есть макет

**Каналы**
- [ ] Если требование относится к сайту и мобильному приложению, есть макеты обоих каналов и их содержание совпадает там, где требования не различают каналы

#### 4. Расхождения

| Тип | Когда |
|---|---|
| Нет на макете | Элемент, экран, диалог или вариант описан в требованиях, на макете отсутствует |
| Нет в требованиях | Элемент есть на макете, в требованиях не описан |
| Противоречие | Есть и там, и там, но различается: текст, состав, условие видимости |
| Не определено | Из требований нельзя понять, что должно быть на экране: элемент описан неоднозначно или требования (спецификация, User Story, Use Case) задают для одного видимого элемента разный текст или состав. Приводятся все варианты, даже если макет совпадает с одним из них |

| Уровень | Когда |
|---|---|
| Высокий | Сценарий клиента нельзя пройти по макетам; нет обязательного элемента, диалога или экрана ошибки |
| Средний | Сценарий проходится, но на экране отличается состав данных, условие показа или действие |
| Низкий | Отличается формулировка текста или порядок блоков |

В колонке «Что исправить» указывается сторона: макет, требование (с ID) или вопрос автору бандла. При противоречии приводятся оба варианта. Какой вариант верен, ревью не решает.

#### 5. Шаблон отчёта

```markdown
# Ревью макетов: <экран или сценарий>

Дата: ДД.ММ.ГГГГ · Этап: <MVP | полный объём>

## Что сверялось
| Макет | Требования |
|---|---|
| `sources/mockups/<файл>.png` | <ID спецификации экрана, User Story, Use Case> |

## Итог
<Два-три предложения: общий вывод, число расхождений по уровням, что мешает передаче в разработку.>

## Расхождения
| № | Макет | Требование | Тип | На макете | В требовании | Уровень | Что исправить |
|---|---|---|---|---|---|---|---|
| 1 | `<файл>.png` | <ID и раздел> | Противоречие | «<текст с макета>» | «<текст требования>» | Низкий | Вопрос: какой текст верный |

## Покрытие вариантов и состояний
| Вариант или состояние | Описано в требованиях | Есть макет |
|---|---|---|
| Пустой список | <ID и раздел> | Нет → № 2 |

## Не проверено
- <что относится к экрану, но не проверено и почему: текст не читается, нужна нарезка макета, поведение не видно на статичном макете>
```

#### 6. Правила

- Текст с макета цитируется дословно в кавычках. Текст, который не читается, не восстанавливается по смыслу: элемент попадает в «Не проверено».
- Требование указывается по ID и разделу, макет — по имени файла.
- Одно расхождение — одна строка. Одинаковое расхождение на нескольких макетах записывается один раз с перечнем файлов.
- Расхождением считается только то, что видно на макете или записано в требованиях как видимое клиенту. Предположения о замысле дизайнера не пишутся.
- Отсутствующий вариант или состояние записывается в «Расхождения» один раз с типом «Нет на макете». В «Покрытии вариантов и состояний» для него ставится «Нет → № <номер>»; описание и уровень там не повторяются.
- **Статусы.** Модель статусов (состав, названия, переходы) не проверяется. Если для статуса в требованиях описан отдельный вид экрана (свой набор блоков или действий), отсутствие макетов по всем таким статусам записывается **одной** строкой «Нет макетов для статусов: …» с перечнем. Если состав статусов не утверждён (открыт вопрос), отсутствие макетов расхождением не считается — одна строка в «Не проверено» со ссылкой на открытый вопрос. Название статуса на макете сверяется, только если требования задают его текст для экрана.
- **Этап.** Элемент, помеченный в требованиях как Post-MVP, на MVP-макетах не ожидается и при MVP-ревью не упоминается. Post-MVP-элемент на MVP-макете — расхождение типа «Противоречие». Элемент или состояние, этап которого в требованиях не определён, — одна строка в «Не проверено» с пометкой «этап не определён».
- **Текст, который задаёт бизнес.** Если требования говорят, что текст задаётся бизнесом или берётся из справочника, дословно он не сверяется: проверяется наличие элемента. Но текст на макете записывается в «Расхождения» (тип «Противоречие», уровень «Средний», сторона — макет), если он видимо не подходит к варианту экрана (текст про другой способ, канал или статус) или обещает клиенту то, что противоречит действующему ADR (срок, условие, сумма). Одинаковый текст на макетах разных вариантов, для которых требования задают разный текст, — то же расхождение одной строкой с перечнем макетов.
- **Демо-данные.** Конкретные значения на макете (суммы, итоги, даты, номера, имена, адреса) — пример и не сверяются, в том числе арифметика сумм. Сверяется только согласованность количества внутри макета (счётчик и число показанных элементов); несогласованность — «Низкий», сторона — макет.
- **Каналы.** Если нет макетов целого канала (сайта или приложения), это одна строка на весь экран, а не по каждому блоку.
- **Соседние экраны.** Экраны, на которые ведёт или с которых приходит проверяемый экран, но которые не входят в набор макетов, не проверяются. Упоминаются одной строкой в «Не проверено», только если на проверяемом экране есть элемент перехода на них.
- Макеты и требования не изменяются.

#### 7. Чек-лист качества

- [ ] В «Что сверялось» перечислены все проверенные макеты с их требованиями, указан этап ревью
- [ ] Каждое расхождение меняет то, что видно на экране, или касается элемента макета без описания; нет пунктов о логике за кадром, источниках данных, модели статусов, ссылках на ADR
- [ ] Отсутствующие макеты по статусам и по каналу сведены каждый в одну строку
- [ ] Текст, который задаёт бизнес, проверен на соответствие варианту экрана и действующим ADR
- [ ] Сверка выполнена в обе стороны
- [ ] У каждого расхождения есть тип, уровень и сторона исправления
- [ ] Отсутствующие варианты не продублированы: в «Покрытии» стоит ссылка на номер расхождения
- [ ] Тексты с макета приведены дословно
- [ ] В отчёте нет оценок визуального стиля
