### Матрица трассируемости требований (RTM)

#### 1. Назначение

RTM — вкладка 03 бандла `requirements/`. Прослеживает требование на всю глубину:

```
BO → PP → BR → US → UC → бэк-логика → модель данных → API → sequence → экран → NFR → тест
```

Показывает, что каждое требование обосновано сверху (есть цель) и раскрыто снизу (есть
история, при необходимости Use Case, и реализация). **На уровне Use Case не
останавливаемся** — трассировка идёт до технических артефактов. Ведётся бизнес-аналитиком /
PO весь проект.

RTM не пересказывает содержание вкладок — только связывает их идентификаторы и показывает статус.

#### 2. Легенда идентификаторов

Обязательный первый раздел матрицы — глоссарий кодов бандла, чтобы читатель понимал
аббревиатуры, не открывая каждую вкладку. Эталонный список префиксов (`BO-`, `PP-`, `BR-`,
`US-`, `UC-`, `BL-`, `TASK-`, `ERD-`, `API-`, `SEQ-`, `SCR-`, `NFR-`, `TC-`, `ADR-`) и их значения —
`AGENTS.md` → «Легенда ID-префиксов».

В матрицу выписываются строки **только под реально существующие в этом бандле артефакты**;
выдуманные префиксы не добавляются. `<ТЕМА>` — код процесса (например `RET` для возврата).
ADR при наличии указывается только в легенде: он обосновывает выбор, но не является отдельным
уровнем цепочки и не добавляется в таблицы реализации.

#### 3. Формат — три таблицы

**Проблема, которую решают три таблицы:** одна задача бэкенда обслуживает несколько US/UC.
Если вести реализацию по строкам-UC и класть в ячейку путь + описание задачи, эта задача
дублируется в десятке строк. Решение: в таблице реализации стоят только **короткие ID**, а
сам артефакт (файл, тип, статус) описан **один раз** в реестре.

##### Таблица 1. Обоснование

`Бизнес-цель | Болевая точка | Бизнес-требование | User Story | Use Case | Статус`

```markdown
| Бизнес-цель | Болевая точка | Бизнес-требование | User Story | Use Case | Статус |
|---|---|---|---|---|---|
| BO-1 | PP-1 | BR-1 | US-RET-100 | UC-RET-01 … UC-RET-07 | В разработке |
| BO-1 | PP-2 | BR-3 | US-RET-106 | — (простая US) | Согласовано |
```

##### Таблица 2. Реализация (трассировка вниз)

Строки по `US → UC`, дальше столбцы вниз по цепочке реализации. Ячейки — **короткие ID**
артефактов из таблицы 3 через запятую, либо `—`.

`User Story | Use Case | Бэк-логика | Модель данных | API-контракт | Sequence | Экран / фронт | NFR | Тест-кейс`

```markdown
| User Story | Use Case | Бэк-логика | Модель данных | API-контракт | Sequence | Экран / фронт | NFR | Тест-кейс |
|---|---|---|---|---|---|---|---|---|
| US-RET-102 | UC-RET-01, UC-RET-02 | BL-RET-QTY-01 | — | API-RET-GETPOS | — | — | — | — |
| US-RET-105 | UC-RET-05 | TASK-RET-DATA | TASK-RET-DATA | — | SEQ-RET-MOB, SEQ-RET-1C | — | — | — |
| US-RET-106 | — | TASK-RET-DATA | TASK-RET-DATA | — | — | SCR-RET-01 | — | — |
```

- Первые два столбца — `US` и `UC`. Одна строка на Use Case; простая US без UC — тоже строка, в столбце UC `—`.
- Порядок столбцов = порядок цепочки: сначала бэк-логика, от неё — модель данных, контракт API, последовательность взаимодействия, затем экран, NFR, тест.
- Нет артефакта данного типа для этой строки — `—`.

##### Таблица 3. Реестр технических артефактов

Строка на артефакт, **без дублирования** — даже если артефакт покрывает много US/UC.

`ID | Тип | Файл | Скилл | Статус`

```markdown
| ID | Тип | Файл | Скилл | Статус |
|---|---|---|---|---|
| BL-RET-QTY-01 | Бэк-логика | `./backend/available-return-quantity_backend.md` | backend-logic | DRAFT |
| TASK-RET-DATA | Модель данных / задача БД | `./backend/return-entity_data-model_task.md` | backend-logic, erd-model | DRAFT |
| SEQ-RET-MOB | Sequence | `./as-is/sequence/mobile_sequence.plantuml` | sequence-diagram | — |
| SCR-RET-01 | Экран | `./screen-spec/screen-spec.md` (SCR-RET-01) | screen-spec | DRAFT |
```

- `Тип`: Бэк-логика · Модель данных · Экран · API-контракт · Sequence · ERD · NFR · Тест-кейс.
- `Файл` — путь (не пересказ). Пути относительны файлу матрицы: `./backend/…`, `./as-is/sequence/…`, `../reference/api/web/…`.
- Тип, которого в бандле нет (ERD, OpenAPI-yaml, NFR, тест-кейсы) — **строк нет**; под таблицей примечание «Артефакты типов … отсутствуют».
- AS-IS sequence — строка `SEQ-<ТЕМА>-ASIS`, тип «Sequence (AS-IS, базовая линия)».

#### 4. Правила

- **Полная трассировка:** цепочка `BO → PP → BR → US → UC → бэк-логика → … → тест` не обрывается на Use Case.
- **Сверху вниз:** у каждой бизнес-цели ≥ 1 бизнес-требование; у каждого BR ≥ 1 US; у каждого UC (и каждой простой US) — строка в таблице 2.
- **Снизу вверх:** каждая US трассируется до BR и BO; каждый UC — до своей US. Сирота снизу → лишний scope; сирота сверху → уровень не декомпозирован.
- **Артефакт — один раз.** В таблице 2 на технику ссылаются только по короткому ID; определение (файл, тип, статус) — единственная строка в таблице 3. Так задача бэкенда, покрывающая несколько историй, не дублируется.
- **Нет артефакта — прочерк.** В таблице 2 ячейка `—`, в таблице 3 строки нет; отсутствие фиксируется примечанием, а не пустой ячейкой и не выдуманным файлом. Файл ради заполнения матрицы не создаётся.
- **Acceptance Criteria в матрицу не выносятся** — они живут в файле User Story рядом со своей историей. Полнота «у каждой US есть AC» проверяется по чек-листу `skill/user-story`, а не здесь.
- ID сквозные и стабильные; освободившиеся номера не переиспользуются.
- Матрица обновляется синхронно с версией бандла. Содержание вкладок не дублируется — только ID и статус.

```markdown
## Легенда идентификаторов
| Префикс | Расшифровка | Где определяется |

| UC-RET-<n> | Use Case | use-case/use-case.md |
| TASK-RET-DATA | Модель данных | backend/return-entity_data-model_task.md |
| SEQ-RET-* | Sequence | as-is/sequence/*.plantuml |

## Таблица 1. Обоснование
| Бизнес-цель | Болевая точка | Бизнес-требование | User Story | Use Case | Статус |

| BO-1 Срок возврата денег | PP-2 Клиент не видит статус | BR-8 Отдельная заявка со статусной моделью | US-105 | UC-RET-05 | В разработке |

## Таблица 2. Реализация
| User Story | Use Case | Бэк-логика | Модель данных | API-контракт | Sequence | Экран / фронт | NFR | Тест-кейс |

| US-105 | UC-RET-05 | TASK-RET-DATA | TASK-RET-DATA | — | SEQ-RET-MOB, SEQ-RET-1C | — | — | — |
| US-106 | — | TASK-RET-DATA | TASK-RET-DATA | — | — | SCR-RET-01 | — | — |

## Таблица 3. Реестр технических артефактов
| ID | Тип | Файл | Скилл | Статус |
|---|---|---|---|---|
| TASK-RET-DATA | Модель данных / задача БД | ./backend/return-entity_data-model_task.md | backend-logic, erd-model | DRAFT |

```

Одна строка `TASK-RET-DATA` в таблице 3 обслуживает и US-105, и US-106 — но описана один раз.

#### 6. Чек-лист качества

- [ ] Заполнена легенда идентификаторов (включая технические префиксы)
- [ ] Нет бизнес-цели без бизнес-требования; нет BR без US
- [ ] Каждый Use Case (и каждая простая US) имеет строку в таблице 2
- [ ] В таблице 2 техника указана только короткими ID
- [ ] Ни один артефакт не описан в таблице 3 дважды
- [ ] Все ID из таблицы 2 существуют в таблице 3; все US/UC — в таблицах 1 и 2
- [ ] Отсутствующие типы артефактов (ERD / OpenAPI / NFR / тест) помечены примечанием, а не выдуманы
- [ ] Acceptance Criteria в матрицу не скопированы
- [ ] Статусы актуальны; матрица соответствует текущей версии бандла
