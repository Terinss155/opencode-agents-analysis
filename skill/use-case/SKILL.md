### Формирование Use Case

#### 0. Когда Use Case НЕ подходит

Use Case описывает **целенаправленное взаимодействие, в котором система создаёт или изменяет состояние**. Если этого нет — выбери другой артефакт (см. `AGENTS.md` → «Выбор артефакта»):

- **Просмотр / восприятие экрана** (карточка, список, дашборд): система ничего не меняет, основной сценарий выходит в 1–2 шага, «гарантия успеха» = «информация отображена» → пиши **спецификацию экрана** (`skill/screen-spec`), а не Use Case.
- **Мелкая самоочевидная стори**: всё покрывается «вижу X, Y, Z» → достаточно **US + критериев приёмки Gherkin** (`skill/user-story`).

Признак, что ты натягиваешь просмотр на Use Case: основной сценарий короткий и пустой, а всё содержательное уезжает в «Бизнес-правила отображения» и «Параметры экрана».

#### 1. Формат Use Case

```markdown
## UC-<тема>-<порядковый номер>. <Название варианта использования>

| Поле | Содержание |
|---|---|
| **Область действия** | <система / приложение / модуль / процесс> |
| **Цель** | Цель пользователя |
| **Основное действующее лицо** | <актор, который инициирует сценарий> |
| **Участники** | <другие роли / системы / сервисы или "Отсутствуют"> |
| **Предусловие** | <что должно быть выполнено до начала сценария> |
| **Гарантии успеха / Результат** | <наблюдаемый результат успешного завершения> |
| **Триггер** | <событие или действие, запускающее сценарий> |

### Описание

1. Пользователь <выполняет действие, указанное как триггер>.
2. Система <выполняет действие / проверку / получает данные>.
3. Система <отображает результат>.
4. Пользователь <выполняет следующее действие>.
5. Система <сохраняет / создаёт / изменяет данные или состояние>.
6. Система <отображает итоговый результат>.

### Расширения

**<номер шага>.1. <Альтернативный или ошибочный сценарий>**

<номер>.1.1. Система <действие>.
<номер>.1.2. Пользователь <действие>.
<номер>.1.3. Система <результат / возврат к шагу / завершение сценария>.

### Открытые вопросы

- <вопрос, без ответа на который сценарий нельзя описать однозначно, или «Отсутствуют»>
```

#### 2. Правила написания Use Case

- **Название** описывает цель пользователя: `Оформить возврат`, `Добавить товар в корзину`.
- Каждый Use Case в документе оформляется отдельным заголовком по шаблону `## UC-<тема>-<порядковый номер>. <Название>`. Номер раздела и отдельная строка с названием не заменяют этот заголовок.
- Для декомпозиции допускается иерархический порядковый номер, например `UC-RET-04.1`, если связь с родительским Use Case явно описана.
- **Цель** описывает ценность или результат, который актор хочет получить.
- **Предусловие** описывает состояние до начала сценария.
- **Триггер** — событие или действие, которое запускает сценарий.
- **Гарантии успеха / Результат** должны быть наблюдаемыми и проверяемыми.
- Основной сценарий должен начинаться с триггера и приводить к указанному результату.
- Действия пользователя и системы описываются отдельными шагами.
- Один шаг — одно законченное действие одного участника.
- Если система выполняет значимую проверку, получение, сохранение или изменение данных — это действие описывается явно.
- Не пропускать шаг, в котором система фактически создаёт или изменяет сущность / состояние.
- Не описывать внутреннюю техническую реализацию, если она не влияет на пользовательский сценарий.
- Не фиксировать способ хранения состояния (`Frontend`, клиентское состояние, БД, кеш), если он не подтверждён входными данными и не влияет на наблюдаемый сценарий.
- Не придумывать бизнес-правила, статусы, проверки или ограничения, которых нет во входных данных.
- Если информации недостаточно — зафиксировать открытый вопрос, а не дополнять сценарий предположением.

#### 3. API и endpoints в Use Case

API можно указывать в шагах, где система:

- получает данные;
- проверяет данные;
- создаёт сущность;
- сохраняет изменения;
- изменяет состояние;
- удаляет данные;
- инициирует действие через API.

Endpoint указывается **после описания действия системы**.

Корректно:

```text
3. Система получает список доступных причин возврата.
   GET /api/orders/v2/return-reasons
```

```text
8. Система создаёт заявку на возврат.
   POST /api/orders/{order_id}/return
```

Некорректно:

```text
3. GET /api/orders/v2/return-reasons
```

API-вызов не должен заменять описание действия системы: из шага должно быть понятно, **что делает система и зачем выполняется вызов**.

Если endpoint неизвестен — не придумывать его.

```text
3. Система получает список доступных способов возврата.
   API: уточняется.
```

Полные request / response можно фиксировать отдельно в API-контракте или техническом разделе, если формат проекта не требует включать их непосредственно в Use Case.

#### 4. Альтернативные и ошибочные сценарии

Для каждого значимого шага основного сценария проверить:

> **А что если этот шаг не может быть выполнен так, как описано?**

Если возможен другой путь — добавить расширение.

Расширение привязывается к шагу основного сценария:

```text
3. Система проверяет наличие выбранного количества товара.

3.1. Выбранного количества недостаточно.
3.1.1. Система сообщает максимально доступное количество.
3.1.2. Пользователь изменяет количество.
3.1.3. Сценарий продолжается с шага 3.
```

Расширения располагаются по возрастанию номеров шагов основного сценария. Каждое расширение должно явно завершать сценарий либо указывать шаг, с которого он продолжается.

В расширения выносить:

- отрицательный результат проверки;
- отсутствие данных;
- недоступность функции или интеграции;
- невалидные данные;
- отказ или отмену со стороны пользователя;
- альтернативный выбор;
- ошибку сохранения или изменения состояния;
- невозможность достичь гарантии успеха.

Если расширений нет, раздел не удалять:

```text
Расширения: отсутствуют.
```

#### 5. Обязательные элементы Use Case

1. Название варианта использования.
2. Область действия.
3. Цель.
4. Основное действующее лицо.
5. Участники или отметка `Отсутствуют`.
6. Предусловие.
7. Триггер.
8. Гарантии успеха / Результат.
9. Основной сценарий.
10. Расширения или явная отметка, что они отсутствуют.
12. API endpoint в тех системных шагах, где он известен и нужен для понимания реализации.
13. Открытые вопросы или явная отметка `Отсутствуют`.

#### 6. Удачный пример

```markdown
## UC-CART-01. Положить товар в корзину

| Поле | Содержание |
|---|---|
| **Область действия** | Мобильное приложение интернет-магазина |
| **Цель** | Добавить выбранный товар в корзину для последующего оформления заказа |
| **Основное действующее лицо** | Пользователь мобильного приложения |
| **Участники** | Система управления остатками |
| **Предусловие** | Пользователь находится на детальной странице товара и выбрал необходимое количество |
| **Гарантии успеха / Результат** | Выбранное количество товара добавлено в корзину и отображается пользователю |
| **Триггер** | Пользователь нажимает «Добавить в корзину» |

### Описание

1. Пользователь нажимает «Добавить в корзину».
2. Система получает актуальную информацию о доступном количестве товара.
   GET /api/products/{product_id}/availability
3. Система определяет, что выбранное количество доступно.
4. Система добавляет выбранное количество товара в корзину пользователя.
   POST /api/cart/items
5. Система подтверждает успешное добавление товара.
6. Система отображает добавленный товар и выбранное количество в корзине.

### Расширения

**3.1. Недостаточно товара в наличии**

3.1.1. Система определяет, что выбранное количество превышает доступный остаток.
3.1.2. Система сообщает пользователю максимально доступное количество.
3.1.3. Пользователь изменяет количество товара.
3.1.4. Сценарий продолжается с шага 2.

**4.1. Не удалось добавить товар в корзину**

4.1.1. Система сообщает пользователю, что товар не был добавлен.
4.1.2. Система предоставляет возможность повторить действие.

### Открытые вопросы

Отсутствуют.
```

Почему соответствует требованиям:

- триггер запускает сценарий;
- действия пользователя и системы разделены;
- система действительно изменяет состояние корзины;
- результат сценария совпадает с гарантией успеха;
- API указан рядом с конкретным системным действием;
- альтернативные сценарии привязаны к шагам основного сценария.

#### 7. Пример, который не соответствует требованиям

```markdown
## UC-CART-01. Положить товар в корзину

| Поле | Содержание |
|---|---|
| **Область действия** | Мобильное приложение интернет-магазина |
| **Основное действующее лицо** | Пользователь мобильного приложения |
| **Участники** | Отсутствуют |
| **Предусловие** | Пользователь находится на странице товара |
| **Гарантии успеха / Результат** | Товар добавлен в корзину |
| **Триггер** | Пользователь находится на странице товара |

### Описание

1. Пользователь выбирает количество товара.
2. Система проверяет наличие товара.
3. GET /api/products/{product_id}/availability

### Расширения

Отсутствуют.
```

Почему не соответствует требованиям:

- триггер описывает состояние, а не событие;
- сценарий не содержит действия пользователя по добавлению товара;
- система не выполняет действие, которое изменяет состояние корзины;
- основной сценарий не приводит к заявленной гарантии успеха;
- API-вызов заменяет описание действия системы;
- не указана цель пользователя;
- не рассмотрены значимые альтернативы: недостаток товара и ошибка добавления.

#### 8. Второй пример, который не соответствует требованиям

```markdown
## UC-ORD-01. Оформить заказ

| Поле | Содержание |
|---|---|
| **Область действия** | Интернет-магазин |
| **Основное действующее лицо** | Пользователь |
| **Участники** | Backend, БД, Redis, платёжный сервис |
| **Предусловие** | В корзине есть товары |
| **Гарантии успеха / Результат** | Заказ создан |
| **Триггер** | Пользователь нажимает «Оформить заказ» |

### Описание

1. Пользователь нажимает «Оформить заказ».
2. Frontend отправляет POST /api/orders, Backend валидирует DTO, выполняет SELECT в БД, проверяет остатки, создаёт транзакцию и записывает заказ.
3. Backend сохраняет данные заказа в PostgreSQL и кладёт идентификатор заказа в Redis.
4. Система вызывает платёжный сервис, получает payment_url и возвращает HTTP 200.
5. Frontend парсит JSON и открывает экран подтверждения заказа.
6. Пользователь видит созданный заказ.

### Расширения

2.1. При ошибке SQL система делает rollback.
2.2. При timeout Redis Backend повторяет запрос.
```

Почему не соответствует требованиям:

- Use Case смешивает **пользовательский сценарий и внутреннюю техническую реализацию**;
- в участники вынесены технические компоненты (`Backend`, `БД`, `Redis`), хотя на этом уровне важнее роли и внешние системы, влияющие на сценарий;
- один шаг содержит сразу несколько действий: отправку запроса, валидацию, чтение из БД, проверку остатков и создание заказа;
- детали `SELECT`, `DTO`, `PostgreSQL`, `Redis`, `rollback`, `HTTP 200` относятся скорее к Sequence Diagram, API-спецификации или техническому дизайну;
- расширения описывают внутренние инфраструктурные ошибки, но не показывают, **что в этих случаях происходит с пользовательским сценарием и что видит пользователь**;
- шаги сформулированы на разных уровнях абстракции: рядом стоят пользовательские действия, HTTP-вызовы и операции с БД.

Корректнее описывать так:

```text
1. Пользователь нажимает «Оформить заказ».
2. Система проверяет возможность оформления заказа с выбранными товарами.
3. Система создаёт заказ.
   POST /api/orders
4. Система получает данные для продолжения оплаты.
5. Система отображает пользователю созданный заказ и доступное действие для оплаты.
```

А техническую последовательность `Frontend → Backend → БД → Redis → платёжный сервис` вынести в Sequence Diagram.

#### 9. Чек-лист качества

- [ ] Название Use Case описывает цель пользователя.
- [ ] Заголовок каждого Use Case соответствует формату `## UC-<тема>-<номер>. <Название>`.
- [ ] Цель пользователя сформулирована явно.
- [ ] Указаны основной актор и остальные участники.
- [ ] Указан уровень Use Case.
- [ ] Предусловие описывает состояние до начала сценария.
- [ ] Триггер является событием или действием.
- [ ] Гарантия успеха наблюдаема и тестируема.
- [ ] Основной сценарий начинается с триггера.
- [ ] Основной сценарий приводит к гарантии успеха.
- [ ] Действия пользователя и системы разделены.
- [ ] Один шаг содержит одно законченное действие.
- [ ] Не пропущено действие системы, которое создаёт или изменяет данные / состояние.
- [ ] Для значимых шагов проверены альтернативные и ошибочные сценарии.
- [ ] Расширения привязаны к конкретным шагам основного сценария.
- [ ] Расширения расположены по порядку шагов и содержат точку продолжения либо завершения сценария.
- [ ] API endpoint указан после описания действия системы, а не вместо него.
- [ ] Неизвестные endpoint и бизнес-правила не придуманы.
- [ ] Открытые вопросы зафиксированы, если данных недостаточно.
- [ ] Use Case можно использовать как основу для разработки и тестирования.
