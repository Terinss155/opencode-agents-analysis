### Формирование спецификации экрана

Спецификация экрана описывает **экран восприятия**: пользователь открывает экран, система показывает состояние, состояние при этом **не меняется**. Линейного сценария «шаг за шагом» тут почти нет — ценность в том, *что, откуда и при каких условиях* отображается.

Когда писать спецификацию экрана, а когда Use Case или только US + AC — `AGENTS.md` → «Выбор артефакта: Use Case / Спецификация экрана / US + Gherkin».

#### 1. Формат

```markdown
## SCR-<тема>-<номер>. <Название экрана>

| Поле | Содержание |
|---|---|
| **Область действия** | <сайт / мобильное приложение / оба; модуль> |
| **Назначение** | Что пользователь должен понять или сделать, глядя на этот экран |
| **Роль** | <кто видит экран> |
| **Точки входа** | Откуда пользователь попадает (из списка, по кнопке, автопереход после UC-…) |
| **Источник данных** | Эндпоинт(ы) чтения; при отсутствии — «уточняется» |
| **Связанные Use Case** | UC, результатом которых является этот экран; UC, которые запускаются действиями с экрана |
| **Макеты** | Пути к файлам макетов |

### Состав экрана

Список блоков в порядке отображения. По каждому блоку: что показывается, из какого поля, при каком условии.

### Правила отображения

Условная логика: матрицы «по каналу», «по статусу», видимость элементов, форматирование.

### Состояния экрана

Загрузка, пусто, ошибка загрузки, доступ запрещён / объект не найден, частичные данные.

### Действия на экране

Каждое действие: подпись, условие доступности, что происходит (ссылка на Use Case или US). Экран сам действие не реализует — только показывает и запускает.

### Параметры экрана

Таблица: `поле экрана` | `источник (таблица.поле / вычисляется / эндпоинт)` | `условие видимости / примечание` | `AS-IS`.

### Открытые вопросы

- <вопрос> или «Отсутствуют».
```

#### 2. Правила написания

- **Название** — имя экрана, не действие: «Карточка возврата», «Список возвратов», не «Посмотреть возврат».
- Заголовок — `## SCR-<тема>-<номер>. <Название>`.
- **Не описывать линейный сценарий шагами.** Если тянет писать «1. Пользователь… 2. Система…» больше чем на 2–3 строки — это Use Case, а не экран.
- Каждый элемент экрана привязать к источнику данных (`таблица.поле`, `вычисляется`, эндпоинт). Неизвестный источник — «уточняется», не придумывать.
- Условие видимости указывать явно для всего, что показывается не всегда.
- Все состояния (загрузка/пусто/ошибка/не найдено) описать — это и есть «расширения» для экрана.
- Действия описывать как ссылки на Use Case / US, а не расписывать их логику здесь.
- AS-IS до TO-BE: для каждого поля отметить, отдаётся ли оно сейчас и откуда.
- Не выдумывать бизнес-правила и статусы, которых нет во входных данных.

#### 3. Обязательные элементы

1. Название и идентификатор `SCR-<тема>-<номер>`.
2. Назначение, роль, точки входа.
3. Источник данных (эндпоинт или «уточняется»).
4. Связанные Use Case.
5. Состав экрана по блокам.
6. Правила отображения (или «Условной логики нет»).
7. Состояния экрана.
8. Действия на экране (или «Действий нет, экран только для просмотра»).
9. Параметры экрана — таблица «поле → источник».
10. Открытые вопросы или «Отсутствуют».

#### 4. Чек-лист качества

- [ ] Название — имя экрана, не действие.
- [ ] Нет натянутого пошагового сценария.
- [ ] Каждый элемент экрана привязан к источнику данных.
- [ ] Условия видимости указаны явно.
- [ ] Описаны состояния: загрузка, пусто, ошибка, не найдено.
- [ ] Действия вынесены в ссылки на Use Case / US, а не расписаны здесь.
- [ ] Для каждого поля отмечен AS-IS (отдаётся / не отдаётся, откуда).
- [ ] Связанные Use Case перечислены (что приводит на экран, что запускается с него).
- [ ] Неизвестные эндпоинты и правила не выдуманы.
- [ ] Открытые вопросы зафиксированы.
