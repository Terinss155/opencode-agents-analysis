# AGENTS.md

Репозиторий — проект аналитики требований процесса «Возвраты 2.0» (E-commerce) вместе с библиотекой OpenCode агентов и скиллов для аналитики требований. Это НЕ приложение: нет кода, сборки, тестов, линтеров. Не запускай build/test/lint.

Этот файл — **единственный источник общей методологии**: иерархия артефактов, «золотое правило», выбор артефакта, структура бандла требований, легенда ID-префиксов, конвенция имён файлов, рабочий процесс. Агенты и скиллы на эти разделы ссылаются, но не копируют их.

## Структура
- `.opencode/agents/*.md` — определения агентов (frontmatter).
  - `mode: primary`: `business-analyst`, `system-analyst`, `product-owner`, `repository-researcher` (permission: редактирование `ask`, bash `ask`).
  - `mode: subagent`: `security-reviewer` (edit: deny — пишет только в `reports/`).
- `skill/*/SKILL.md` — скиллы OpenCode; подгружаются по frontmatter `description` через `skills.paths` в `opencode.json`. Каждый скилл описывает **только свой артефакт** (назначение → формат → правила → пример → чек-лист). Зови скилл при запросе соответствующего артефакта.
- `opencode.json` — конфиг: `default_agent: system-analyst`, `edit`/`bash` = ask, `skills.paths: ["./skill"]`, скиллы — только из allow-списка (`*` = deny).

## Запрет на изменение `12storeez-master/`
- **Категорически запрещено изменять, создавать, удалять или переименовывать любые файлы и папки внутри `12storeez-master/`.** Это внешний репозиторий (Yii2-монолит 12Storeez), доступен **только для чтения** при анализе.
- Запрещено также добавлять `12storeez-master/` в git (правило в `.gitignore`).
- Любые правки, которые «кажутся» нужными в коде монолита, оформляются как артефакты аналитики в `requirements/`, а не вносятся в сам код.

## Запрет на изменение `requirements/drafts/`
- **Категорически запрещено изменять, дополнять, переформулировать, удалять или переименовывать файлы внутри `requirements/drafts/`** (включая `transcriptions/`). Это первоисточник — транскрибации встреч, резюме, присланные бизнесом/продуктом ТЗ и описания процессов. Доступен **только для чтения** при анализе.
- Правки орфографии, форматирования, «уточнения» и объединение нескольких черновиков в один документ также запрещены — это исказит первоисточник.
- Новый файл в `requirements/drafts/` добавляется только тогда, когда бизнес/продукт прислал новый исходный материал, а не как результат анализа.
- Результат обработки, переосмысления или структурирования черновика оформляется как отдельный артефакт аналитики в `requirements/` (BRD, User Story, ADR и т.д.) со ссылкой на исходный файл — а не правкой самого черновика.
- В `requirements/drafts/` лежат только материалы, полученные от бизнеса и других команд. Собственные рабочие черновики аналитика (ранние описания процессов, на основе которых собран бандл) первоисточником не являются и хранятся в `requirements/arhive/` (решение автора бандла от 01.10.2026).

## Архив `requirements/arhive/`
- Ранние рабочие материалы аналитика, по которым собраны действующие артефакты. Не первоисточник и не действующий артефакт: актуальны BRD, User Story, ADR и т.д.
- Действующие артефакты на файлы архива и их внутренние ID (`BR-COM-*`, `COM-OQ-*`, `CDEK-*`, `5POST-*`, `CUR-*`) не ссылаются. Нужное правило или вопрос переносится в BRD (`RULE`/`FR`/`OQ` и т.д.); закрытые вопросы не переносятся.

## Разделение контекстов
- **Бизнес-контекст (код):** `12storeez-master/` — внешний репозиторий (Yii2-монолит 12Storeez). Только для чтения при анализе; **запрещено изменять** (см. раздел «Запрет на изменение `12storeez-master/`») и **запрещено добавлять в git**.
- **Артефакты аналитики (описывают работу):** `requirements/` — **бандл требований** процесса «Возвраты 2.0» (в репозитории один процесс, поэтому бандл разложен прямо в корне `requirements/`): все документы требований, диаграммы, черновики, справочники. Создавать и сохранять артефакты только здесь. Файлы разных уровней не сваливаются в одну папку — см. «Бандл требований».
  - `requirements/reference/` — сквозные справочники, не привязанные к одному бандлу процесса: `architecture/` (AS-IS архитектура монолита целиком — backend, БД, API, фронтенд, инфраструктура, интеграции, подводные камни; ведёт `repository-researcher`), `{репозиторий}_структура.md` (карта репозитория; ведёт `repository-researcher`) и `api/{web,mobile}/` (AS-IS API-контракты по каналу — маппинг эндпоинта на код и БД; ведёт `system-analyst`, см. `skill/openapi-spec`). Не путать с `requirements/*_структура.md` ниже — это разбор кода одного конкретного процесса, а не всей базы.
  - `requirements/drafts/` — исходные бизнес-материалы (транскрибации встреч, резюме, ТЗ и бизнес-процессы от бизнеса/продукта, присланные файлы). **Первоисточник, доступен только для чтения — менять, дополнять или переписывать запрещено** (см. «Запрет на изменение `requirements/drafts/`»). Обработка и переосмысление этих материалов оформляется как новый артефакт аналитики в `requirements/`, а не правкой файла-источника.
  - `requirements/*_структура.md` — точечные справочники по коду одного процесса (например `order-view_структура.md`; пути, строки, ключевые факты; ведёт `repository-researcher`).
- **Отчёты:** `reports/` — ревью и отчёты о качестве по бандлу требований (создать, если нет). Не версионируются в git (см. `.gitignore`) — это локальные рабочие артефакты, а не часть бандла требований.

## Бандл требований

`requirements/` = один логический документ для бизнеса (процесс «Возвраты 2.0»), вкладки которого раскладываются по подпапкам по типу артефакта.

```
requirements/
├── index.md          ← точка входа: вкладки, порядок чтения, версия и статус бандла
├── brd.md            ← вкладка 00. BRD (skill/brd)
├── traceability.md   ← вкладка 03. Матрица трассируемости (skill/traceability-matrix)
├── gap-analysis.md   ← Gap-анализ: сверка с исходным BRD, реестр вне зоны BA/SA (skill/gap-analysis)
├── user-story/     ← вкладка 01: user-story*.md + Acceptance Criteria (skill/user-story)
├── use-case/       ← вкладка 02: use-case*.md, только сложные/ветвящиеся US (skill/use-case)
├── screen-spec/    ← screen-spec*.md, экраны восприятия (skill/screen-spec)
├── mockups/        ← исходные макеты (png/фигма-экспорт), на которые ссылаются screen-spec/use-case
├── adr/            ← [ГГГГ-ММ-ДД ЧЧ-ММ] ADR-<ТЕМА>-<NNN>-<решение>-vN.md, значимые решения и компромиссы с версиями (skill/adr)
├── as-is/          ← пошаговый AS-IS + as-is.bpmn.md (skill/business-process-bpmn)
├── to-be/          ← to-be.bpmn.md, если есть
├── backend/        ← задачи для бэка (SIS)
├── diagrams/       ← все диаграммы: diagrams/<тип>/<as-is|to-be>/<объект>_<тип>.<ext>
│   ├── sequence/   ← sequence-диаграммы (skill/sequence-diagram)
│   ├── erd/        ← модели данных / ERD (skill/erd-model)
│   └── state/      ← диаграммы состояний (жизненный цикл сущности)
├── nfr/            ← nfr.md, если есть
├── info/           ← вспомогательный анализ кодовой базы
├── drafts/         ← первоисточник (read-only, см. запрет выше)
├── arhive/         ← ранние рабочие черновики аналитика (не первоисточник, ссылки на них не ставятся)
└── reference/      ← сквозные справочники (см. «Разделение контекстов»)
```

- **Правило размещения:** тип артефакта, у которого может быть больше одного файла (user story, use case, спецификация экрана, задачи для бэка, диаграммы, AS-IS-шаги), всегда лежит в своей подпапке — даже если сейчас файл один. В корне `requirements/` — только `index.md`, `brd.md`, `traceability.md`, `gap-analysis.md` и, если ведутся, продуктовые `business-case.md` / `backlog-priority.md`.
- **Диаграммы:** все диаграммы (sequence, ERD, состояния) лежат в `requirements/diagrams/<тип>/<as-is|to-be>/`. Тип виден по подпапке, состояние процесса — по второй подпапке, объект — по началу имени файла (`return-entity_erd.md`, `return-status_state.md`). BPMN процесса остаётся в `as-is/` / `to-be/` (артефакт BA). На диаграмму без своего ID-префикса ссылаются по пути файла.
- **ADR:** хранится в `requirements/adr/` и объясняет причину значимого выбора, альтернативы и последствия. ADR не является новым уровнем требований и не добавляется отдельным звеном в цепочку трассировки.
- **Первичные транскрибации:** неизменённые исходные записи встреч хранятся в `requirements/drafts/transcriptions/`. Обработанное резюме и ADR не заменяют первичную транскрибацию.
- Связь между вкладками — только по стабильным ID (см. «Легенда ID-префиксов») и markdown-ссылкам. Содержимое между вкладками не копируется.

Формат `index.md`:

```markdown
# Требования: Возвраты 2.0

Версия бандла: N · Дата: ДД.ММ.ГГГГ · Статус: На согласовании

| Вкладка | Расположение | Назначение | Статус |
|---|---|---|---|
| 00. BRD | [brd.md](./brd.md) | Цели, scope, AS-IS, целевое состояние, бизнес-требования | ... |
| 01. User Stories | [user-story/](./user-story/) | Пользовательские требования + критерии приёмки | ... |
| 02. Use Cases | [use-case/](./use-case/) | Детализация сложных сценариев | ... |
| Спецификации экранов | [screen-spec/](./screen-spec/) | Экраны восприятия | ... |
| ADR | [adr/](./adr/) | Обоснование значимых решений, альтернативы и последствия | ... |
| 03. Трассируемость | [traceability.md](./traceability.md) | BO → BR → US → UC → тех. артефакты | ... |
| Gap-анализ | [gap-analysis.md](./gap-analysis.md) | Сверка с исходным BRD, реестр требований вне зоны BA/SA | ... |

Порядок чтения: 00 → 01 → (02 по ссылкам из историй).
```

## Иерархия артефактов требований

Каждый уровень отвечает на свой вопрос; содержание не дублируется между уровнями.

| Уровень | Вопрос | Что содержит | Артефакт / скилл |
|---|---|---|---|
| **BRD** | Что должно измениться в бизнес-процессе и зачем? | Бизнес-контекст, цели, scope, AS-IS (ссылка), целевое состояние как состав возможностей, бизнес-требования. Без пошагового сценария. | `skill/brd` |
| **User Story + Acceptance Criteria** | Какую законченную ценность получает пользователь? | Канонический источник пользовательской потребности и сценария (через AC в Gherkin). | `skill/user-story` |
| **Use Case (0..N на одну US)** | Как проходит сложный / ветвящийся участок сценария этой US? | Пошаговое раскрытие только сложных участков. Число UC — от сложности сценария, не от числа US. | `skill/use-case` |
| **SIS/SRS, ERD, Sequence, OpenAPI, NFR** | Как это реализуют системы? | Техническая реализация. | скиллы `system-analyst` |

**Золотое правило:** пользовательский сценарий не пересказывается на нескольких уровнях. BRD хранит бизнес-контекст и целевое состояние; User Story + AC — канон сценария; Use Case — детализация сложного участка User Story.

**ADR — вспомогательный артефакт обоснования решения:** он отвечает на вопрос «почему выбран этот вариант», ссылается на требования и технические артефакты по стабильным ID, но не копирует их содержание. Один ADR фиксирует одно решение.

**Версионирование ADR** (подробности и шаблон — `skill/adr`):
- Каждое изменение ранее принятого решения — новый ADR-файл. Старый ADR не переписывается, содержимое внутри него не заменяется.
- Имя файла: `[YYYY-MM-DD HH-MM] ADR-RET-XXX-<decision-name>-vN.md`, например `[2026-09-11 11-29] ADR-RET-011-return-point-selection-v1.md` → `[2026-09-25 15-40] ADR-RET-027-return-point-selection-v2.md`.
- Все версии одного решения имеют одинаковое смысловое название `<decision-name>`; первая фиксация — `v1`, каждое изменение — `+1`.
- Дата и время в имени берутся из имени транскрибации, на которой принято решение или его изменение (`[bandicam 2026-09-11 11-29-22-750] ...` → `[2026-09-11 11-29]`).
- Новая версия получает новый уникальный ADR-ID (следующий свободный номер) и в шапке указывает `Предыдущая версия: <полное имя файла>` и `Заменяет: ADR-RET-XXX`.
- В старой версии меняются только метаданные: `Статус: Решение изменено` и `Заменён: <полное имя файла новой версии>`, плюс строка в «Истории изменений».
- Ссылки на транскрибации — только полным фактическим именем исходного файла, без сокращений и альтернативных названий.
- После новой версии актуальные ссылки в документации переводятся на неё; исторические ссылки (журналы изменений, описание состояния на момент старого решения) не переписываются без необходимости.

**Трассировка сквозная и полная:** матрица трассируемости (`skill/traceability-matrix`) прослеживает цепочку `BO → PP → BR → US → UC → бэк-логика → модель данных → API → sequence → экран → NFR → тест` — до технических артефактов включительно, не останавливаясь на Use Case. Технический артефакт, обслуживающий несколько историй, описывается в матрице один раз (реестр), в строках US/UC — только его короткий ID. Нет артефакта данного типа — прочерк, файл ради заполнения не создаётся.

## Выбор артефакта: Use Case / Спецификация экрана / US + Gherkin

Одна User Story → **0..N Use Case** (число определяется сложностью сценария, а не тем, что «на каждую историю нужен UC»); часть историй ложится на спецификацию экрана; часть — только на критерии приёмки. Как выбрать:

| Что описывает стори | Признак | Артефакт |
|---|---|---|
| **Действие / транзакция со сложным сценарием** | Триггер → шаги с решениями → система **создаёт / изменяет** состояние → наблюдаемый результат; есть ветвления | **Use Case** (`skill/use-case`) — один или несколько |
| **Просмотр / восприятие** (карточка, список, дашборд) | 1 действие пользователя (открыл); система ничего не меняет; «сценарий» = «открыл → показано»; ценность — в том, *что и когда показано* | **US + AC + спецификация экрана** (`skill/screen-spec`), без Use Case |
| **Мелкое / самоочевидное** | Нечего расписывать сверх «вижу X, Y, Z» | Только **US + критерии приёмки Gherkin** (`skill/user-story`) |

Триггер к переключению с Use Case: основной сценарий вышел в 1–2 шага, «гарантия успеха» = «информация отображена», нет шага, где система создаёт/меняет сущность → это спецификация экрана, а не Use Case. Не натягивать просмотровый экран на пошаговый формат.

## Легенда ID-префиксов

Единый глоссарий кодов бандла. Матрица трассируемости повторяет этот список первым разделом; в остальных вкладках коды используются без расшифровки.

| Префикс | Расшифровка | Где определяется |
|---|---|---|
| `BO-<n>` | Business Objective — бизнес-цель | вкладка 00 (BRD), «Бизнес-цели» |
| `PP-<n>` | Pain Point — болевая точка AS-IS | вкладка 00 (BRD), «Предпосылки и контекст (AS-IS)» |
| `BR-NN` | Business Requirement — бизнес-требование | вкладка 00 (BRD), §7.1 «Бизнес-требования» |
| `RULE-NN` | Business Rule — бизнес-правило | вкладка 00 (BRD), §7.2 «Бизнес-правила» |
| `FR-NN` | Functional Requirement — функциональное требование | вкладка 00 (BRD), §7.3 «Функциональные требования» |
| `NFR-NN` | Non-functional Requirement — нефункциональное требование раздела BRD | вкладка 00 (BRD), §7.4 «Нефункциональные требования» |
| `INT-NN` | Integration / Technical Requirement — интеграционное требование | вкладка 00 (BRD), §7.5 «Интеграционные / технические требования» |
| `US-CR-NN`, `US-VW-NN`, `US-LC-NN`, `US-CH-NN` | User Story — пользовательское требование по теме: CR — оформление, VW — просмотр, LC — жизненный цикл, CH — каналы (в репозитории один процесс, код `<ТЕМА>` в US опущен) | вкладка 01 (User Stories) |
| `UC-<ТЕМА>-<n>` | Use Case — сценарий / ветка внутри User Story | вкладка 02 (Use Cases) |
| `BL-<ТЕМА>-<...>` | backend-логика | `backend/*.md` (`skill/backend-logic`) |
| `TASK-<ТЕМА>-<...>` | задача проектирования БД / модели данных | `backend/*.md` (`skill/backend-logic`, `skill/erd-model`) |
| `ERD-<ТЕМА>` | модель данных / ERD | `diagrams/erd/<as-is|to-be>/*_erd.*` + `*_sql.sql` (`skill/erd-model`) |
| `API-<...>` | API-контракт / метод | `*_openapi.yaml` или `requirements/reference/api/{web,mobile}/` (AS-IS-разбор эндпоинта по каналу, сквозной — не привязан к одному бандлу; `skill/openapi-spec`) |
| `SEQ-<ТЕМА>-<...>` | sequence-диаграмма | `diagrams/sequence/as-is/*.plantuml` для AS-IS, `diagrams/sequence/to-be/*.plantuml` для TO-BE (`skill/sequence-diagram`) |
| `SCR-<ТЕМА>-<n>` | спецификация экрана восприятия | `screen-spec/` (`skill/screen-spec`) |
| `NFR-<КАТ>-<n>` | нефункциональное требование отдельного NFR-артефакта (не путать с `NFR-NN` раздела 7.4 BRD) | `nfr/nfr.md` (`skill/nfr-requirements`) |
| `TC-<...>` | тест-кейс QA (если ведётся отдельным артефактом) | QA |
| `ADR-<ТЕМА>-<n>` | запись о значимом продуктовом, процессном или архитектурном решении | `adr/[ГГГГ-ММ-ДД ЧЧ-ММ] ADR-<ТЕМА>-<NNN>-<решение>-vN.md` (`skill/adr`) |

`<ТЕМА>` — код процесса (например `RET` для возврата). Префикс добавляется, только когда в бандле появляется артефакт соответствующего типа; выдуманные префиксы не вводятся.

## Рабочий процесс
- PO → ценность и приоритеты (RICE/WSJF/MoSCoW), User Story. BA → процессы AS-IS/TO-BE, BRD, Use Case, матрица трассируемости, Gap-анализ (сверка с исходным BRD и реестр требований вне зоны BA/SA — `skill/gap-analysis`); передаёт SA.
- SA → технические артефакты: backend-логика, ERD, Sequence, OpenAPI, AsyncAPI, NFR; обеспечивает совместимость с User Story/Use Case.
- Значимые решения фиксируются через `skill/adr`: PO — продуктовые, BA — процессные и бизнес-правила, SA — архитектурные, интеграционные и системные.
- `repository-researcher` → разбор кодовой базы `12storeez-master`, карта интеграций, справочники `requirements/*_структура.md`; к нему обращаются BA/SA, когда нужно понять, где и как работает логика в монолите.
- `security-reviewer` — ревью ИБ требований (ISO 27001, NIST, OWASP, PCI DSS, 152-ФЗ; STRIDE/PASTA/DREAD).
- Перед фиксацией требований BA/PO синхронизируются по приоритетам; технические детали — только через SA.

## Язык и стиль
- Все артефакты и общение — на русском.
- Требования атомарные, измеримые, проверяемые; запрещены общие формулировки («быстро», «удобно»).
- Acceptance Criteria — в формате Gherkin (Given/When/Then); User Story — по INVEST.
- Порядок: AS-IS до TO-BE; трассируемость от бизнес-цели до User Story и технического артефакта.
- Факты не выдумывать: при нехватке вводных запросить уточнение, не додумывать.
- Каждый артефакт — отдельный файл в своей подпапке `requirements/` (см. «Бандл требований»).
