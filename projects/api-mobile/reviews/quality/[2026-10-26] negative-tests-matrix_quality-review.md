## Итог

Покрытие по модулям хорошее: пустые и невалидные поля, запросы без авторизации и несуществующие ID есть почти везде. Требуется поправить ожидаемые коды ответа в части тестов и добавить проверки, которых нет в матрице: заголовки запроса, неверный HTTP-метод, доступ к чужим данным, бизнес-ошибки заказа и корзины.

## Как Mobile API отвечает на ошибки

Ответ с ошибкой: `success: false`, код ошибки — в `result.error_code`, текст — в `result.error_text`.

| HTTP | `error_code` | Когда |
|---|---|---|
| 400 | 1003, 1004, 1005, 1006, 1008, 1011, 1015, 1019, 1027 и прочие | Обязательное поле, неверный тип или значение, нет заголовка, неверный пароль, некорректный запрос, дубль заказа |
| 401 | 1001, 1002 | Нет `x-session-token`, сессия невалидна или истекла |
| 401 | 1007 | Сессия валидна, но пользователь не вошёл, а метод требует входа |
| 403 | 1017 | Неверный или пустой `x-access-token` — в любом методе |
| 403 | 1023 | Действие запрещено (например, пользователь заблокирован на создание заказов) |
| 404 | 1009 | Объект не найден у пользователя / товар недоступен в нужном количестве |
| 405 | 1000 | Неверный HTTP-метод |
| 406 | 1012, 1018, 1020, 1021, 1014 | Ошибки позиций корзины, корзина пуста, товары закончились, ошибка подписки |
| 500 | 1016, 1026 | Ошибка БД, непредвиденная ошибка |

Порядок проверок в каждом запросе: `x-access-token` → HTTP-метод → сессия → заголовки `x-platform`, `x-version` → вход пользователя → поля → `limit` / `offset`. Первая сработавшая проверка определяет ответ.

422 Mobile API не отдаёт ни в одном методе.

## 2. Общие тесты для всех модулей

Достаточно одного параметризованного теста на модуль.

| № | Проверка | Пример | Ожидание |
|---|---|---|---|
| 2.1 | Неверный или пустой `x-access-token` | Любой метод модуля с `x-access-token: invalid` | 403, `error_code` 1017 |
| 2.2 | Нет заголовка `x-platform` или `x-version` (сессия валидная) | Любой метод модуля без `x-platform` | 400, `error_code` 1008 |
| 2.3 | Неверный HTTP-метод | `GET /mobile/orders/cancel` | 405, `error_code` 1000 |
| 2.4 | Сессия и вход пользователя — два разных теста | а) нет `x-session-token` или он битый; б) валидная гостевая сессия в методе, где нужен вход | а) 401, 1002; б) 401, 1007 |
| 2.5 | Превышение пагинации в списках: заказы, адреса, подписки, товары, уведомления | `limit=1001`; `offset=100001` | 400, `error_code` 1015 |
| 2.6 | Сломанный JSON в теле — хотя бы для пары POST/PUT | `--data-raw '{"barcode": '` | Ожидание зафиксировать по первому прогону |

## 5. Рекомендации к проверкам

- Проверять не только HTTP-статус, но и `result.error_code`: одним HTTP 400 отвечают разные ошибки, и по статусу тест не отличит «нет поля» от «неверного значения».
- В тестах, где запрос может пройти (создание адреса, заказа, подписки), удалять созданные данные после теста.

## Ограничения сверки

Проверены базовый контроллер Mobile API v1 и методы заказов, адресов пользователя и корзины. Методы `/mobile/v2/...` (модуль `modules/mobilev2`) отдельно не сверялись: коды ответов там могут отличаться, их подтверждает первый прогон тестов.
