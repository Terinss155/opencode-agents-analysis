**Екатерина Лемешева** · 19.11.2026, 17:02

> Маша, хочу предложить ещё один вариант логики, если рассматривать оба признака вместе, а не пытаться определить весь сценарий возврата по одному is_bank_details_confirmed.
>
> is_refund_to_original_payment_method определяет, возвращаем ли деньги на исходный способ оплаты.
>
> Если true — банковские реквизиты не запрашиваем, подтверждать нечего.
>
> Если false — переходим к сценарию возврата по реквизитам, если по бизнес-правилам они требуются.
>
> Если реквизиты нужны, клиент обязан их подтвердить. В новой версии сайта и МП без подтверждения возврат не создаётся. В старой версии МП возврат может создаваться без зафиксированного подтверждения.
>
> Как это будет выглядеть
>
> Для уже оформленного возврата, если false второго признака действительно означает необходимость реквизитов:
>
> Возврат на исходный способ (is_refund_to_original_payment_method)    Подтверждение реквизитов (is_bank_details_confirmed)    Смысл
> true    null    Реквизиты не нужны, подтверждение неприменимо
> false    true    Реквизиты предоставлены и подтверждены
> false    null    Реквизиты предоставлены, но подтверждение неизвестно (старая МП или исторические данные)
> false    false    Для нового процесса недопустимо: возврат без обязательного подтверждения не создаётся
> В этом варианте is_bank_details_confirmed отвечает исключительно за факт подтверждения:
>
> true — подтверждение зафиксировано;
>
> null — подтверждение неизвестно либо неприменимо;
>
> false — явное отсутствие подтверждения, но в нашем процессе такой возврат не создаётся.
>
> Получается, что понять причину null можно по второму признаку и фактическому наличию реквизитов.
>
> Как тебе такой вариант? Мне кажется, он точнее разделяет назначение двух признаков и не смешивает отсутствие подтверждения с ситуацией, когда мы не знаем, было ли оно.
