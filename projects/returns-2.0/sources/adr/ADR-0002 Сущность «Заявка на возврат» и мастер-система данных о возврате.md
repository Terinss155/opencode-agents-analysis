# 🟢 ADR-0002 Сущность «Заявка на возврат» и мастер-система данных о возврате

Ссылка Яндекс Вики: https://wiki.yandex.ru/teams/web-development/arxitektura/adr/adr-0002-sushhnost-zajavka-na-vozvrat-i-master-sis/

### Контекст и постановка проблемы

---

Проект «Возвраты 2.0», шаг 1 — отказ от бумажного заявления на возврат интернет-заказов (MVP до 15.12.2026). Клиент оформляет возврат в ЛК сайта / МП (или через «Дружбу» в RetailCRM), электронное заявление формируется из данных заявки, при возврате в розничный магазин клиент предъявляет QR, сотрудник сканирует его в АРМ «Возврат онлайн-заказов» (1С: КА).

**Как возврат учитывается сегодня.** Отдельной сущности «возврат» нет ни в одной системе:

* &[в **RetailCRM** возврат — это статус изделия в заказе («Возврат, если был отгружен») \+ статус заказа «Полный / Частичный возврат» \+ причина; заявка из ЛК приходит как «Возврат из ЛК»; номера возврата нет;](1092057)

* в **1С: КА** документ «Возврат товаров от покупателя» и приходный ордер &[появляются только по факту приёмки](1092060) (склад Бетта Про или магазин); до этого возврат в 1С не существует;

* &[на **сайте / в МП** заявка на возврат есть как форма, но без собственного номера и без хранения реквизитов;](1092059)

* **основанием** возврата для бухгалтерии служит бумажное заявление (скан, прикреплённый к заказу); в спорных кейсах де-факто мастер-системой считается RetailCRM (комментарий товародвижения к БТ).

Шаг 1 требует: один номер возврата, на который могут ссылаться клиент, «Дружба», магазин, склад и бухгалтерия; данные заявления (состав, причины, способ возврата ДС, реквизиты, комментарий «Дружбы») как структурированные поля, а не скан; возможность в любой момент сформировать PDF-заявление по номеру; версионирование при изменениях через «Дружбу»; статусы создан / завершён / отменён, видимые во всех трёх системах.

**Что нужно решить:**

1. Вводим ли отдельную сущность «Заявка на возврат» уже на шаге 1 (а не статусами заказа) и в каких системах она существует.

2. Какая система является **мастером** данных о заявке — источником истины при расхождениях, владельцем номера и жизненного цикла.

3. &[Как присваивается номер заявкам, которые рождаются **не на сайте**: оформленные «Дружбой» в RCRM и созданные магазином в 1С для клиента без QR ( ](1092062) Q-25 ; сценарий запланирован на январь 2027).

**Что уже решено заказчиком (01.10, 05.10) и принимается как вход:** заявка хранится как набор реквизитов, PDF формируется по запросу и не хранится; статусов три; автоотмены нет; одна заявка зеркалится в трёх системах; «Дружба» оформляет заявку в RCRM, магазин проводит возврат без заявки, 1С создаёт заявку и передаёт на сайт/МП/RCRM (январь).

**Границы ADR.** Не рассматриваются: интеграции с ТК, полная статусная модель, автоматизация возврата ДС (шаг 2); механизм и топология обменов ( ADR-0003 ); хранение банковских реквизитов ( ADR-0004 ); содержимое QR ( ADR-0005 ).

### Драйверы решения (Decision Drivers)

---

*Предзаполнено, скорректировать на обсуждении.*

* Срок MVP до 15.12 и критический путь (бэкенд сайта \+ МП); 1С и RCRM не должны стать блокером.

* Минимизация доработок на стороне вендора RetailCRM — главный внешний риск проекта (слот вендора, сроки, ограниченность кастомизации).

* Единственный источник истины при расхождениях между системами (отмена клиентом ↔ правка оператором ↔ приёмка в магазине).

* Доступность для клиентского сценария 24/7 (создание, отмена, QR, PDF из ЛК) — 1С имеет регламентные окна и не рассчитана на клиентский трафик.

* Юридическая роль: заявка — основание возврата; аудит «кто/что/когда», версии заявления ( NFR-5 , FR-2 .4).

* Персональные данные и банковские реквизиты (152-ФЗ): чем меньше систем хранят реквизиты, тем лучше ( NFR-4 ).

* Расширяемость на шаг 2: статусы от ТК, экспертиза, автовозврат ДС, возвраты по розничным чекам — сущность не должна переделываться.

* Сквозная уникальность номера по всем каналам и источникам (сайт, RCRM, 1С).

* Совместимость с действующими процессами «Дружбы» и логистов (реестры из RCRM дважды в день — без изменений).

* Объём доработок в 1С КА (команда 1С не на критическом пути только при небольшом объёме).

* Отчётность для бухгалтерии: откуда берутся данные для возврата ДС по магазинному и ТК-каналам.

### Рассматриваемые варианты

---

#### Вариант A — Сайт/МП — мастер заявки; заявка зеркалится в RCRM и 1С

Отдельная сущность «Заявка на возврат» создаётся в базе сайта: номер, клиент, заказ, позиции с причинами, канал, способ возврата ДС, реквизиты (шифрованно), версия, статус, аудит-лог. Сайт — единственный источник номера и владелец жизненного цикла (создан → завершён / отменён). В RCRM заявка отражается расширением карточки «Возврат из ЛК» (доп. поля: номер, способ возврата ДС, реквизиты с ролевым доступом, ссылка на заявление). В 1С КА — новый объект «Заявка на возврат» (только для магазинного канала в шаге 1), на который ссылается документ «Возврат товаров от покупателя». Заявки, рождённые в RCRM («Дружба») и в 1С (магазин без QR), создаются через API сайта и получают номер от сайта.

#### Вариант B — 1С КА — мастер заявки; сайт и RCRM — фронты

Объект «Заявка на возврат» создаётся в 1С КА при получении заявки с сайта или из RCRM; 1С выдаёт номер, ведёт статусы, хранит реквизиты и формирует отчёт для бухгалтерии. Сайт и RCRM хранят копию с номером 1С. Соответствует первоначальной редакции BRD (17.09): «сущность "Возврат" в 1С», «последнее действие в 1С — мастер» ( FR-6 .4).

|Документ «Возврат товаров от покупателя», приходный ордер и факт возврата ДС живут рядом с заявкой — единый отчёт без внешних источников|По ред. 3 оценки в шаге 1 1С по ТК-каналам **не дорабатывается** — заявки курьер/СДЭК/5POST/Почта до 1С не доходят, т.е. мастер не видит большую часть заявок|

#### Вариант C — RetailCRM — мастер заявки

Заявка = расширенный «Возврат из ЛК» в RetailCRM с собственным номером; «Дружба» и логисты работают там же; сайт и 1С получают данные из RCRM. Закрепляет де-факто текущую роль RCRM как мастера спорных кейсов.


|✅ Плюсы|⚠️ Минусы|
|:---|:---|
|Минимальные изменения в процессе «Дружбы» и логистов — всё уже в RCRM|Зависимость от вендора на критическом пути: объект, номер, версии, аудит, ролевой доступ к реквизитам — всё в чужом продукте с ограниченной кастомизацией|
|Заявки «Дружбы» рождаются в мастере — нет обратного вызова|Магазинный канал в RCRM сегодня **не ведётся** («ничего не оформляем, магазин проводит сам») — потребуется завести его в RCRM, иначе мастер не покрывает канал|
|Источник данных для отчёта бухгалтерии по ТК-каналам (решение 05.10) совпадает с мастером|Хранение банковских реквизитов у вендора — вопрос 152-ФЗ и договора|
||QR, PDF-заявление и отмена клиентом требуют вызовов RCRM из ЛК с клиентской нагрузкой — против рекомендаций вендора и против направления ADR-0001 (изоляция RCRM шлюзом)|
||Противоречит решениям заказчика 01.10|

#### Вариант D — Не вводить сущность; расширить статусы заказа полями заявления

Оставить модель «возврат = статус заказа», добавить поля способа возврата ДС / реквизитов / ссылки на заявление в заказ (RCRM и 1С).

### Вопросы для обсуждения на арх. комитете

---

**Закрыто (решения заказчика 01.10 и 05.10, фиксируются как вход):**

* Нужна ли отдельная сущность уже на шаге 1? — **Да**, «Заявка на возврат» как новый объект в 1С, на сайте/МП и в RCRM; статус заказа в RCRM сохраняется для совместимости.

* Хранить ли PDF-заявление? — **Нет**, хранятся данные заявки, PDF формируется по запросу ( Q-27 снят).

* Статусная модель шага 1 — **создан / завершён / отменён** ( Q-9 закрыт); автоотмены **нет** ( Q-4 снят).

* Мастер и источник номера — предварительно **сайт/МП** (решение заказчика 01.10, требует подтверждения комитетом).

* **Отсылка к клиентским заказам:** Корректно ли брать за эталон текущий процесс работы с заказами клиентов? **На процесс работы с заказами клиентов не смотрим. Фиксируем, что мастер-система по возвратам - 1С КА.**

* **Работа с ТК**: можно ли использовать существующий механизм работы с ТК по аналогии с заказами? **Работа с ТК будет согласовываться в рамках отдельной ADR.**

* **Правило разрешения коллизий.** BRD 17.09 ( FR-6 .4) закрепляет «последнее по времени действие в 1С — мастер», что противоречит мастеру-сайту. Предлагается: мастер — сайт; изменения из RCRM/1С применяются через API сайта как новая версия; при конфликте «клиент отменил ↔ оператор изменил» побеждает отмена (возврат нельзя «воскресить»), конфликт логируется и уходит «Дружбе». Подтвердить. **Правило будет разработано на этапе ТЗ и согласовано между системами.**

* Номер для заявки, созданной в 1С или RCRM. Варианты: (а) синхронный вызов API сайта, номер возвращается в ответе — один источник, но нужна доступность сайта; (б) предвыделенные диапазоны/префиксы по источнику (S-, C-, R-) с последующей регистрацией на сайте — работает офлайн, но номер «непрозрачный» и нужен контроль дублей. Предлагается (а) с резервом: при недоступности сайта магазин оформляет по бумажному сценарию (допустимый остаток ≤ 15%). У каждой системы есть внутренний номер, а ключ присваивает мастер-система и возвращает его остальным системам.

*  Момент попадания заявки ТК-каналов в 1С. Бухгалтерия по ТК-каналам работает из RCRM (решение 05.10). Подтвердить, что 1С-объект «Заявка на возврат» в шаге 1 создаётся только по магазинному каналу, и зафиксировать это как сознательное ограничение до шага 2.

* **Что означает «мастер» для спорных кейсов.** Сегодня товародвижение и бухгалтерия сверяются с RCRM. Нужно закрепить: истина по заявке (состав, реквизиты, способ возврата ДС, версии) — истина по возврату — 1С. 

* **Доступ уполномоченных сотрудников к заявке на сайте** ( FR-2 .3: сформировать PDF по номеру, посмотреть аудит): через админку сайта, через RCRM в отдельной сущности - заказ с видом Возврат.

* **Срок хранения данных заявки для формирования клиентом** — для юристов/ИБ ориентир 5 лет как основание возврата;

### Последствия (Consequences)

> *Заполняется после решения. Ниже — предварительная оценка инициатора для варианта A, чтобы комитет видел цену решения.*

* **Что становится проще:** один номер и один источник истины по заявке; клиентский сценарий не зависит от 1С/RCRM; 1С вне критического пути.

* **Что становится сложнее / какие компромиссы приняты:** правила разрешения коллизий ложатся на плечи 1С; роль RCRM как «мастера спорных кейсов» меняется — нужна коммуникация бухгалтерии и товародвижению.

* **Технический долг или риски, которые сознательно принимаем:** в шаге 1 заявки ТК-каналов не существуют в 1С — отчёт бухгалтерии собирается из двух источников (1С \+ RCRM).
