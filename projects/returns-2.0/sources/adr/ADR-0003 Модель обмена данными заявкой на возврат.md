# 🟢 ADR-0003 Модель обмена данными заявкой на возврат

Ссылка Яндекс Вики: https://wiki.yandex.ru/teams/web-development/arxitektura/adr/adr-0002-sushhnost-zajavka-na-vozvrat-i-master-sis/

### Контекст и постановка проблемы

---

В шаге 1 «Заявка на возврат» (ADR-0002) существует в трёх системах и должна оставаться согласованной. Сегодня между системами ходят **заказы и статусы заказов**: ↔ RetailCRM ; сайт → 1С КА — существующий обмен по заказам, статусам и комментариям *(механизм уточняется: HTTP-сервисы 1С / коннектор / пакетный)*; прямого обмена RetailCRM ↔ 1С нет *(уточнить)*. Данные возврата, как отдельной сущности, (состав к возврату, причины, способ возврата ДС, реквизиты, комментарий «Дружбы») между системами не передаются.

Требования NFR-2: гарантированная доставка без потерь, идемпотентность, повторные попытки, очередь ошибок с алертом; FR-6.4: повторная передача не создаёт дубль, коллизии логируются; NFR-4: ПДн и реквизиты — только по защищённым системным каналам; NFR-8: при недоступности интеграции магазин оформляет возврат по резервному сценарию.

**Что нужно решить:**

1. **Топология** — через какую систему идут данные: звезда с сайтом-хабом, цепочка сайт → RCRM → 1С (как в BRD 17.09, FR-6.3), или прямые связи «каждый с каждым».

2. **Механизм** — синхронный REST point-to-point (\+ webhooks/polling), событийная шина с брокером, или расширение существующих обменов 1С.

3. **Гарантии** — где живут идемпотентность, ретраи; как разрешаются коллизии версий.

4. **Контракт** — contract-first (OpenAPI), владелец контрактов, версионирование.

**Границы ADR.** Не рассматриваются: интеграции с ТК и Бетта Про (шаг 2 / отдельно), состав полей (ТЗ), выбор мастер-системы (ADR-0002 —  принимается здесь).

### Драйверы решения (Decision Drivers)

---

*Предзаполнено, скорректировать на обсуждении.*

* Срок MVP до 15.12: обмены должны быть реализуемы силами бэкенда сайта (2 разраб.) и 1С (1–2 разраб.) параллельно с фронтами; МП и веб стартуют с моков по контрактам.

* Минимум доработок у вендора RetailCRM; использование штатных возможностей API RetailCRM (кастомные поля, история изменений, триггеры).

* Гарантированная доставка и идемпотентность (NFR-2, FR-6.4) при пиковых 50–80 заявках в день — объёмы малые, важна надёжность, а не пропускная способность.

* Наблюдаемость: по каждому номеру заявки видно, куда и когда ушло, что не доставлено; алерты.

* Разрешение коллизий: отмена клиентом ↔ правка оператором ↔ приёмка в магазине; версии заявления.

* Безопасность ПДн/реквизитов: TLS, аутентификация систем (OAuth \+ white list, как в ADR-0001), ролевой доступ, отсутствие реквизитов в логах.

* Независимость клиентского контура от доступности 1С и RCRM; резервный сценарий для кассы (NFR-8).

* Расширяемость на шаг 2: добавление ТК, Бетта Про, статусов, уведомлений без переделки обменов.

* Соответствие архитектурным принципам (ACL/изоляция внешних систем, contract-first) и прецеденту ADR-0001.

* Объём доработок в смежных командах (1С КА, RCRM-интегратор, инфраструктура) и стоимость эксплуатации.

### Рассматриваемые варианты

---

#### Вариант A — Звезда: сайт — хаб; синхронные REST-контракты point-to-point \+ transactional outbox на сайте

Сайт владеет заявкой и является единственным узлом обмена. Исходящие потоки (сайт → RCRM, сайт → 1С) реализуются через таблицу outbox в БД сайта с фоновой доставкой, ретраями и DLQ; доставка в RCRM — через API RetailCRM (кастомные поля заказа / «Возврата из ЛК»), в 1С — через HTTP-сервис 1С КА. Входящие потоки (RCRM → сайт, 1С → сайт) — через API сайта: для 1С — прямой вызов HTTP-API сайта (создание/статус заявки); для RCRM — либо триггер RetailCRM с HTTP-вызовом нашего эндпоинта, либо polling истории изменений (`/api/v5/orders/history`) с сайта *(что доступно у вендора — уточнить)*. Внешний вызов в сайт из RCRM идёт через шлюз по образцу ADR-0001 (OAuth \+ white list). Контракты — OpenAPI, contract-first, владелец — аналитика проекта \+ бэкенд сайта.


|✅ Плюсы|⚠️ Минусы|
|:---|:---|
|Нет новой инфраструктуры — реализуемо в сроки MVP силами бэкенда сайта|Входящий поток RCRM → сайт зависит от возможностей вендора (webhook-триггеры vs polling); polling — задержка и лишний трафик|
|Outbox \+ идемпотентность по (номер заявки, версия) закрываются без брокера|Point-to-point: каждый новый потребитель — новый адаптер в сайте|
|Один узел наблюдаемости: по номеру заявки виден весь жизненный цикл обменов|Бэкенд сайта — критический путь, объём растёт (outbox, DLQ, админка ошибок)|
|Для RCRM — только штатный API и доп. поля; для 1С — один HTTP-сервис и один исходящий вызов|Синхронные вызовы 1С из сайта требуют доступности HTTP-сервисов 1С вне регламентных окон (ретраи сглаживают, но статус «завершён» может задерживаться)|
|Контракты OpenAPI дают моки для МП/веба с первого дня||
|Переиспользуется прецедент ADR-0001 (шлюз, OAuth \+ white list) для входящих вызовов от вендора||

#### Вариант B — Веер RCRM ← Сайт → 1С: сайт — единственный инициатор всех обменов (push \+ pull)

Та же звезда с сайтом в центре, но **все вызовы исходят только от сайта**; входящего API на сайте нет, RCRM и 1С напрямую не связаны. Исходящие данные (заявка, отмена, версия) сайт **push**-ит через outbox: в RCRM — API RetailCRM (доп. поля «Возврата из ЛК»), в 1С — HTTP-сервис 1С КА. Обратные данные сайт **pull**-ит по расписанию: из RCRM — история изменений заказов (`/api/v5/orders/history`, курсор по `sinceId`) — правки оператора, заявки «Дружбы», статусы; из 1С — HTTP-сервис «изменения по заявкам с версии N» (журнал изменений на стороне 1С) — статусы «завершён/отменён», с января — заявки, созданные магазином. Номер заявке, рождённой в RCRM или 1С, присваивает сайт при pull (до этого в системе-источнике — временный идентификатор источника).


|✅ Плюсы|⚠️ Минусы|
|:---|:---|
|Нет входящих эндпоинтов на сайте: не нужны OAuth \+ white list, шлюз по образцу ADR-0001 и защита публичного API — минимальные требования ИБ и меньше объём бэкенда|Задержка обратных потоков равна интервалу polling: правка оператора, статус «завершён», заявка «Дружбы» доезжают до сайта и клиента через минуты, а не секунды; каждый новый поток — ещё одно расписание|
|Не зависит от возможностей вендора по webhook-триггерам: история изменений — штатный, документированный метод API RetailCRM|Заявка, созданная в RCRM или 1С, получает номер **не синхронно** — в источнике живёт временный идентификатор до первого pull; усложняет Q-25, QR для таких заявок и сверку «одна заявка в трёх системах»|
|1С не делает исходящих HTTP-вызовов — только HTTP-сервисы на приём и отдачу; проще для команды 1С, нет зависимости от сетевого доступа 1С наружу|1С должна вести журнал изменений заявок с версиями для отдачи «с версии N» — доработка больше, чем один исходящий вызов; при сбое журнала изменения теряются незаметно|
|Сайт полностью владеет расписанием, ретраями и порядком обработки — одна точка конфигурации и наблюдаемости; недоступность RCRM/1С не создаёт «потерянных» входящих вызовов, pull просто повторится|Polling создаёт постоянный фоновый трафик и нагрузку на API RetailCRM (лимиты запросов вендора) и на 1С даже при нулевых изменениях; нужно соблюдать rate limit|
|RCRM и 1С развязаны полностью: сбой или регламентное окно одной системы не влияет на другую|Окно гонки push/pull: сайт может вытянуть из RCRM собственную только что отправленную версию как «изменение» — нужна дедупликация по версии/источнику изменения|
|Проще тестирование и моки: все взаимодействия — исходящие с сайта, воспроизводимы в интеграционных тестах|«Завершён» клиенту и бухгалтерии — с задержкой до интервала pull \+ обработка; для подтверждения заявки из магазина (январь) клиент ждёт push-уведомления дольше|
|Легко наращивать в шаге 2 ещё одним pull-адаптером (Бетта Про, ТК), не открывая сайт новым внешним системам||

#### Вариант C — Событийная шина: сайт публикует события заявки, 1С и RCRM — подписчики через адаптеры

Сайт пишет события `ReturnRequestCreated / Updated / Cancelled / Completed` в брокер (через outbox); подписчики — адаптер 1С (читает очередь, вызывает HTTP-сервис 1С) и адаптер RCRM (читает очередь, вызывает API RetailCRM). Обратные события от 1С и RCRM публикуют те же адаптеры. *(Наличие и владелец брокера в инфраструктуре — уточнить.)*


|✅ Плюсы|⚠️ Минусы|
|:---|:---|
|Гарантированная доставка, ретраи и DLQ — штатные свойства брокера; NFR-2 закрывается инфраструктурой|Ни RCRM (вендор), ни 1С напрямую с брокером не работают — нужны два адаптера плюс эксплуатация брокера: новая инфраструктура и владелец, не укладывается в MVP 15.12 при текущем составе команд|
|Развязка по времени: недоступность 1С/RCRM не блокирует сайт и наоборот|Асинхронность не нужна там, где нужен синхронный ответ (получение номера для заявки из 1С/RCRM, проверка QR на кассе) — всё равно остаются REST-вызовы|
|Шаг 2 (ТК, Бетта Про, уведомления, BI) — добавление подписчиков без изменения сайта|Объёмы (≤ 80 заявок/день) не оправдывают брокер сами по себе|
|Единая событийная история заявки для аудита и аналитики|Сложнее отладка и наблюдаемость для команды без опыта событийных интеграций|
||Увеличивает объём доработок в смежных командах (инфраструктура, 1С, интегратор)|

#### Вариант A\+ (гибрид, предлагается к обсуждению) — Вариант A в шаге 1 с заделом на C

Реализовать вариант A, но оформить outbox сайта как **событийный журнал заявки** (append-only, типизированные события с версией), а адаптеры к RCRM и 1С — как отдельные воркеры-подписчики внутри сайта. В шаге 2 журнал можно вынести в брокер, не меняя контрактов 1С и RCRM.


|✅ Плюсы|⚠️ Минусы|
|:---|:---|
|Все плюсы A в сроки MVP; путь к C без переделки контрактов|Чуть больше проектирования на старте (схема событий, версионирование)|
|Событийная модель заявки появляется сразу — удобно для аудита и статусной модели шага 2|Риск «недоделанного брокера» внутри монолита, если не ограничить объём|

### Вопросы для обсуждения на арх. комитете

---

**Закрыто (фиксируется как вход):**

* В шаге 1 нет интеграции с ТК; 1С дорабатывается только по магазинному каналу (ред. 3).

* Бухгалтерия по ТК-каналам получает данные из RCRM , по магазину — из 1С .

* **Необходим endpoint для повторной отправки данных по возврату с сайта в 1С**

* **Нужно ли зеркалить магазинную заявку в RCRM** в шаге 1 («одна заявка в трёх системах», 01.10), если «Дружба» магазинный канал не ведёт? Предложение: в MVP — только сайт ↔ 1С; отражение в RCRM — read-only поле/ссылка, если вендор успевает; иначе — январь. Заявка на возврат по заказу будет прилетать в RCRM, по чекам - остаётся как есть.

* **Контракт сайт ↔ 1С.** HTTP-сервис 1С КА для приёма заявки и отмены; исходящий вызов 1С → API сайта для статуса и (январь) создания заявки. Синхронный ответ с номером при создании из 1С ( Q-25 , ADR-0002). Кто владелец контракта и схемы — 1С;  версионирование по пути.

* **Идемпотентность.** Ключ — номер заявки \+ монотонная версия; получатель отбрасывает версию ≤ сохранённой; повтор создания с тем же ключом возвращает существующую заявку. Где хранится ключ в 1С и в RCRM (кастомное поле «version»)? **Договорённость** **о формате сообщения идемпотентности.**

* **Outbox, ретраи, DLQ.** Экспоненциальные ретраи, максимум N попыток, затем DLQ с алертом в канал команды; админ-экран повторной отправки — в **MVP**. Где именно живёт outbox - **сайт**.

* **Задержка статуса «завершён».** Статус зависит от факта возврата ДС (ручная операция в 1С); допустимая задержка доставки на сайт — **часы**.

* **Нагрузка и SLA.** ≤ 80 заявок/день, пики после выходных; синхронные вызовы — единицы RPS. Требования к latency только для проверки QR на кассе.

### Последствия (Consequences)

> *Заполняется после решения. Ниже — предварительная оценка инициатора для варианта A / A\+.*

* **Что становится проще:** один узел обменов и наблюдаемости; никаких новых инфраструктурных компонентов; для вендора RCRM — только поля и штатный API; МП и веб стартуют с моков по OpenAPI.

* **Что становится сложнее / какие компромиссы приняты:** реализация админ-экрана повторной отправки на сайте и метода для повторной отправки данных по возврату с сайта в 1С..

* **Влияние на дорожную карту / сроки:** укладывается в план MVP ; отражение магазинной заявки в RCRM и заявка из 1С.

* **Технический долг или риски, которые сознательно принимаем:**  обмен RCRM → 1С по заявкам не создаётся — данные бухгалтерии по ТК-каналам живут вне 1С до шага 2.
