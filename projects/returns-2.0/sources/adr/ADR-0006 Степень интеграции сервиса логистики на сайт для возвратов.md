# 🟢 ADR-0006 Степень интеграции сервиса логистики на сайт для возвратов

Ссылка Яндекс Вики: https://wiki.yandex.ru/teams/web-development/arxitektura/adr/adr-0006-stepen-integracii-servisa-logistiki-na-sa/

**Статус:** Принято · **Инициатор:** Елена Васильева · **Домен:** интеграции · **Команда:** Returns 2.0 (бэкенд сайта / веб, сервис логистики) · **Связанные ADR:** ADR-0002 (сущность «Заявка на возврат»)

### Контекст и постановка проблемы

---

Проект «Возвраты 2.0», шаг 1 — отказ от бумажного заявления (MVP до 15.12.2026). Клиент оформляет возврат в ЛК сайта / МП и на шаге выбора способа возврата должен видеть **только фактически доступные способы** (BRD, п. 5.1): пункты выдачи (ПВЗ), курьер, розничный магазин. BRD шага 1 фиксирует, что это не «интеграция с ТК» (статусы, трекинг, создание отправлений — вне объёма), а **актуальное отображение способов возврата по регионам**.

**Как устроено сегодня (прямой поток, заказы).**

* Данные о доставке частично живут в **сервисе логистики**, частично — на **сайте**. Логистика отдаёт на сайт пункты выдачи и интервалы для доставки "курьером"; логика по определению способов доставки на стороне сайта.
* Для курьера логистика отдаёт даты и интервалы доставки по коду типа доставки (`delivery_type_code`), с учётом таймзоны и типа заказа. Код типа доставки существует только для городов, ФИАС которых заранее залиты в соответствующий тип доставки на сайте.
* Для курьерских интервалов в прямом потоке действует переключатель в сервисе Логистики (тогл): интервалы от транспортной компании (пока только для СДЭК) либо ручные интервалы из логистики.

**Что отличается для возвратного потока.** Возврат — отдельная сущность ([ ADR-0002 ]()). Не каждый ПВЗ принимает возвраты; курьер не доставляет, а **забирает** (в запросе интервалов вместо адреса доставки `delivery_address` нужен адрес отправки `sending_address`); набор ФИАС и количество типов доставки для забора отличаются от прямого потока (у СДЭК для прямого потока четыре типа доставки, на возврат — один).

**Спорная территория между сайтом и сервисом логистики** — получение способов возврата в разрезе населённого пункта. На встречах 01.10 и 20.10 зафиксированы два сценария:

1. **Сценарий «копируем логику доставок»** — для возвратов повторяется существующая схема прямого потока без новой архитектуры.
2. **Сценарий «переезд в логистику»** — часть логики (способы возврата по населённому пункту, магазины) переносится в сервис логистики.

**Что нужно решить:** итоговый вариант реализации и степень интеграции сервиса логистики для возвратного потока по проекту «Возвраты 2.0» — какие данные и в каком объёме сайт получает из логистики, а какие остаются на стороне сайта.

**Границы ADR.** Не рассматриваются:

* интеграция логистики для прямого потока (заказов);
* получение филиалов Почты России из логистики. Справочно: по решению 14.10 для Почты России выводится только ссылка на карту с филиалами; канал работает только для Калининградской области, полная интеграция нецелесообразна;
* интеграция с ТК по статусам, трекингу и созданию отправлений (вне объёма шага 1, BRD);
* курьерская служба «Дали» — вынесена за MVP (логисты подтвердили, что «Дали» для возвратов под вопросом).

### Драйверы решения (Decision Drivers)

---

*Предзаполнено, скорректировать на обсуждении.*

* **Срок MVP до 15.12.** Релиз-фриз перед сейлом в середине декабря: выкладка всех доработок должна быть завершена к началу декабря. Разработка по сайту стартует со следующего спринта.
* **Трудозатраты (анализ \+ разработка \+ тестирование)** на стороне сайта и логистики; критический путь проекта — бэкенд сайта.
* **Корректность данных**: клиент не должен видеть ПВЗ, не принимающие возвраты, и интервалы, недоступные для забора.
* **Единый источник данных о способах доставки/возврата** — целевое архитектурное направление (вынос части логики с сайта в логистику).
* **Отказоустойчивость**: поведение сайта при недоступности логистики, пустом ответе и некорректном адресе.
* **Консистентность с прямым потоком**: переиспользование методов, тогла интервалов, обработки таймзон.
* **Объём тестирования**: новый процесс увеличивает тест-планы смежных команд.
* **Объём ручной подготовки данных**: заливка ФИАС для курьера в новый тип доставки.

### Рассматриваемые варианты

---

#### Вариант 1 — Минимальная интеграция: логистика отдаёт ПВЗ на возврат и интервалы для курьера; остальное — на стороне сайта

Сайт повторяет логику прямого потока. Из сервиса логистики **получаются**:

* **ПВЗ на возврат** — те же методы, что для доставок, плюс фильтр по признаку возврата (`is_return_available`); логистика отдаёт пункты; сайт определяет, в каких населённых пунктах есть пункты приёма возвратов;
* **интервалы забора курьером** — на вход подаётся код типа доставки (для возвратов — отдельный тип, создан ранее), адрес отправки `sending_address` вместо `delivery_address` и **всегда** таймзона (из ответа гео-сервиса при детализации города, при его отсутствии — из кэша).

**Остаётся на стороне сайта:** определение набора способов возврата в населённом пункте (по наличию ПВЗ на возврат и заливке ФИАС для курьера), справочник магазинов, принимающих возвраты, ссылка на карту Почты России. ФИАС для курьера заливаются в новый тип доставки (по возврату), информацию предоставляет команда сервиса логистики.


|✅ Плюсы|⚠️ Минусы|
|:---|:---|
|Выполнимо к 15.12: повторяется существующая схема (Ctrl\+C / Ctrl\+V с небольшими доработками), новых методов в логистике почти нет|Логика определения способов возврата по населённому пункту остаётся на сайте и дублирует часть логики логистики|
|Затраты минимальны: вариант 2 оценивается как минимум вдвое дороже|Для курьера требуется заливка ФИАС в новый тип доставки: ручная подготовка данных|
|Доработки логистики не блокируют сайт: дорабатываемый фрагмент независим|Возможна «двойная работа»: при последующем переезде логики в логистику часть реализации на сайте придётся переделывать|
|Переиспользуются тогл интервалов, обработка таймзон и сценарии ошибок прямого потока|«Способы возврата по городу» — дублирование логики между сайтом и логистикой|
|Минимальный объём тестирования смежных команд|Риск, что к варианту 2 «никогда не дойдём» (опасение участников встречи 14.10)|
|Не зависит от оценки и приоритета задач в логистике по варианту 2||

#### Вариант 2 — Расширенная интеграция: логистика отдаёт способы возврата по населённому пункту, ПВЗ, интервалы курьера и магазины

Сервис логистики становится владельцем данных о способах возврата. Из логистики **получаются**:

* **способы возврата в рамках населённого пункта** (ПВЗ, курьер, магазин) — единый ответ по городу/ФИАС;
* **ПВЗ на возврат** (с фильтром по признаку возврата);
* **интервалы забора курьером** (с `sending_address` и таймзоной);
* **магазины**, принимающие возвраты (с учётом правила «магазины без собственных касс возвраты не принимают» и списка исключений, например «Цветной»).

На сайте не остаётся справочников способов возврата — только отображение полученных данных. Для этого в логистике создаются новые методы и правила доступности, а перенос затрагивает также объём заливки данных и контракт с клиентскими приложениями.


|✅ Плюсы|⚠️ Минусы|
|:---|:---|
|Единый источник данных о способах доставки и возврата; логика доступности в одном месте|Трудозатраты в сервисе Логистики не менее чем в 2 раза выше варианта 1 (анализ \+ разработка \+ тестирование)|
|Соответствует целевому направлению архитектуры (вынос части логики с сайта)|Не укладывается в срок 15.12 при текущих ресурсах: новый функционал и новые методы в логистике, оценка со стороны сайта отсутствует|
|Нет дублирования логики между сайтом и логистикой|Новый процесс: увеличивается объём тестирования, риск «увязнуть» в тестах (оценка 14.10)|
|Способы возврата управляются централизованно|Доработки логистики выходят на критический путь проекта; задержка в логистике блокирует сайт и МП|
||Требуется согласовать новый контракт между сайтом, МП и логистикой до начала разработки|

### Вопросы для обсуждения на арх. комитете

---

**Закрыто (решения встреч 01.10 и 14.10, фиксируются как вход):**

* По итогам встречи 14.10 выбран сценарий 1 («копируем логику доставок для возвратов, без новой архитектуры»). Решение предварительное, требует подтверждения комитетом. Сценарий 2 занял бы минимум в 2 раза больше времени (оценка команды сайта).
* Для ПВЗ используются те же методы, что для прямого потока, плюс фильтр по признаку возврата.
* Для курьера (СДЭК) задача по интервалам на сайте потенциально копируется с прямого потока; передаётся `sending_address` вместо `delivery_address`. Для сервиса логисткии требуются доработки по получению дат на возврат от ТК
* Допускается создание возврата без выбранного интервала, если сервис логистика не отвечает
* ФИАС для курьера заливаются отдельно в новый тип доставки (создан ранее). Вариант «признак возврата в существующем типе» не принят: у СДЭК четыре типа доставки на прямом потоке и один на возврат, гео и логика типов различаются.
* Таймзона всегда передаётся в метод получения интервалов: из ответа гео-сервиса при детализации города, при отсутствии — из кэша. При ручных интервалах требуется явная передача таймзоны в Логистику.
* Тогл переключения интервалов (ТК / ручные из логистики) уже существует для прямого потока и применяется для возвратов.
* Интервалы СДЭК — только в пределах РФ.
* «Дали» — вынесена за MVP. Почта России — только ссылка на карту.
* Взаимодействие на сайте: корнер-кейсы (недоступность, пустой ответ, некорректный адрес) проектируются по аналогии с прямым потоком.
* Дедлайн — середина декабря (до старта сейла); разработка стартует со следующего спринта.
* Что показываем клиенту, если по введённому адресу забор не выполняется — формулировка сообщения и действие (обращение в «Дружбу»)
* Хранение способов возврата — вариант «на стороне сайта» подтверждён.
* Заливка ФИАС — Владелец, срок и способ заливки ФИАС в новый тип доставки: уточняют BTS, заливка в БД сайта - WEB
* Фиксируется ли в дорожной карте задача на переезд логики в логистику и с какого срока. Полная интеграция логистики на сайт — горизонт не ранее 2027 года

### Решение (Decision Outcome)

---

> *Заполняется по итогам арх. комитета.*

#### **Выбранный вариант**

**Вариант 1 — Минимальная интеграция: логистика отдаёт ПВЗ на возврат и интервалы для курьера; остальное — на стороне сайта**

#### **Обоснование**

Сроки и встраивание в существующую архитектуру.

Оба варианта реализуемы, но первый быстрее; сайт всё равно будет переделываться, смысла тратить больше времени сейчас нет. Полная интеграция логистики на сайт — горизонт не ранее 2027 года

### Последствия (Consequences)

---

> *Заполняется после решения. Ниже — предварительная оценка инициатора для варианта 1, чтобы комитет видел цену решения.*

* **Что становится проще:**

  * возвратный поток повторяет известную схему прямого потока (методы получения ПВЗ, интервалы, тогл источника получения интервалов, обработка таймзон и ошибок);
  * новых компонентов и новой архитектуры нет;
  * доработка логистики (фильтр по признаку возврата, адрес отправки, новый тип доставки) не блокирует разработку сайта.

* **Что становится сложнее / какие компромиссы приняты:**

  * логика «какие способы возврата доступны в населённом пункте» остаётся на стороне сайта и частично дублирует логику логистики;
  * для курьера требуется отдельная заливка ФИАС в новый тип доставки и её поддержание в актуальном состоянии;
  * сайт обращается к сервису логистики, нужны обработка недоступности, пустого ответа и некорректного адреса.

* **Влияние на дорожную карту / сроки:**

  * укладывается в план MVP; все доработки должны быть выложены до начала декабря (релиз-фриз перед сейлом), срок запуска — середина декабря (15.12);
  * вариант 2 оценивается минимум вдвое дороже и в срок MVP не укладывается.

* **Технический долг или риски, которые сознательно принимаем:**

  * частичное дублирование логики способов возврата между сайтом и логистикой до отдельного решения о переезде;
  * риск двойной работы, если логистика позже реализует методы по варианту 2: смягчается согласованием контракта до начала доработок;
  * риск, что вариант 2 не будет запланирован: полная интеграция логистики на сайт — горизонт не ранее 2027 года;
  * «Дали» и Почта России (интеграция) вне MVP.
