# ПАЙПЛАЙН SRS — P2. Создать только проверяющий скрипт (ПОСЛЕ ОДОБРЕНИЯ P1)

**Отправлять исключительно после просмотра и утверждения карты P1.** Данное задание само по себе не утверждает новые решения: реализуй **только согласованную спецификацию P1**. Если спецификация из предыдущего разговора тебе недоступна или отличается от входных материалов, остановись и запроси её, не угадывай.

## Разрешённая область записи

По умолчанию **только один файл** в аналитическом репозитории: `skill/srs/check_srs.py`. Если карта P1 предусматривает дополнительные файлы для реализации, сначала перечисли их и получи отдельное разрешение на каждый; само это задание не разрешает их создавать.

**Абсолютно запрещено изменять:** `projects/*/requirements/**`, все SRS сайта и МП, Wiki-копии, BRD, User Stories, критерии приёмки, ADR, вопросы, `projects/*/sources/**`, `AGENTS.md`, `CLAUDE.md`, `skill/srs/SKILL.md`, `skill/srs/template.md`, `skill/srs/template-wiki.md`, другие скиллы, Mermaid, `.claude/agents/`, `.opencode/agents/`, `srs-check-pipeline.md`, существующие репозитории рабочего кода `12stz/`, БД, Git history и рабочие ручные правки.

## Перед записью

1. Перечитай действующие `AGENTS.md`, `CLAUDE.md`, актуальный `skill/srs/SKILL.md` и согласованную карту P1.
2. Проверь `git status` и `git diff` **для всех потенциально затрагиваемых файлов**, зафиксируй в ответе наличие уже существовавших изменений. Если `skill/srs/check_srs.py` существует, прочитай его и не перезаписывай без согласования конфликта.
3. Убедись, что реализация не требует новых разрешений. При несогласованном архитектурном выборе остановись и предложи вариант.

## Обязательные свойства результата

- Python с локальной стандартной библиотекой в приоритете. Работает на Windows в проектном окружении без внешних API, отправки данных в облако и доступа к рабочей БД.
- **Только читает** SRS/Markdown/Wiki и Git-diff, выдаёт компактные замечания в stdout, ошибки чтения — в stderr. Никаких изменений файлов, `--fix`, `--apply`, автоудаления вопросов, форматирования SRS, генерации baseline, сохранения отчётов, временных файлов и кэшей.
- Сопоставляет US сайта/МП, но **номера шагов, число шагов, URI и маршруты вызовов независимы**. Точно идентичное действие — одинаковая русская формулировка с разрешёнными платформенными отличиями; ненадёжное сопоставление — `NEEDS_REVIEW`.
- Сохраняет существование временного рабочего блока `Открытые вопросы` в начале SRS МП для проекта `returns-2.0`. Никогда не трактует сам вопрос или частичный ответ как утверждённую реализацию и не требует копии в SRS сайта.
- Принимает допустимость общей серверной логики в SRS МП и ссылки из сайта, без двойного копирования расчётов. Не требует идентичных sequence-диаграмм; их полная фактическая цепочка остаётся в документах.
- Разделяет **ERROR** (только детерминированно доказанное формальное нарушение), **WARNING** (эвристический сигнал), **NEEDS_REVIEW** (нужна смысловая сверка), **INFO** (сведения). Никакие предупреждения не становятся правкой или заключением о готовности к разработке.
- Сообщения короткие: `тип / код / файл / US / раздел или шаг / краткая причина`; агрегированный итог; ограничение многократных повторов; при запросе — подробный JSON или отдельные подробности. Не печатает полное содержание исходных файлов или персональные данные.
- При ошибке чтения или неизвестной разметке честно сообщает «не удалось надёжно проверить», вместо фиктивного результата «всё корректно». Не склеивает неполный парсинг с успешной проверкой.
- Никаких вызовов ИИ/LLM внутри скрипта, никаких сетевых запросов, автоматического commit/push, запуска субагентов.

## Порядок реализации

1. Реализуй **только MVP-проверки и интерфейс**, одобренные в P1. Не добавляй непрошеные проверки, генераторы и автоматические исправления.
2. Покажи CLI `--help` и одну примерную команду для SRS сайта/МП, например:
   `python -B skill/srs/check_srs.py --web projects/returns-2.0/requirements/srs/srs-web-mvp.md --mobile projects/returns-2.0/requirements/srs/srs-mobile-mvp.md`
   Пути и опции уточни по реально созданному скрипту, не выдумывай работающие ключи.
3. Если действующие запреты `AGENTS.md` допускают запуск **только самой read-only проверки** как утилиты аналитики, разрешён один явный пробный запуск против указанных входных файлов через `python -B`. Если это противоречит запрету на тесты/линтеры или безопасности, **не запускай**, честно объясни ограничение и предоставь команду для дальнейшего отдельного согласования. Никаких `pytest`, `unittest`, build/lint, `update_srs_files.py` или сторонних тестовых систем.
4. Проверка до/после `git status`/`git diff --name-only`: новые или изменённые файлы **в рамках P2** должны быть только внутри разрешённой области. Существовавшие ручные изменения вне её должны остаться прежними. Если обнаружен неожиданный побочный файл, остановись, сообщи и не удаляй его автоматически.

**После P2 остановись.** Не подключай скрипт автоматически к другим скиллам, хукам или пайплайну; не создавай новые агенты и конфигурации. Интеграция в рабочий процесс, регулярный запуск и любые правки SRS — только отдельными будущими задачами с разрешением пользователя.
