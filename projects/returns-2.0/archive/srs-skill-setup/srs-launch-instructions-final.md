# Безопасный запуск обновления SRS-скилла в Claude Code

## Какой комплект использовать

**Актуальные материалы для работы сейчас:**

1. `srs-rules-and-automation-v5.md` — **проект исправленных правил**; источник для анализа, не команда на изменение проекта.
2. `claude-srs-stage-1-audit-v3.md` — **первое** задание для Claude Code: только чтение.
3. `claude-srs-stage-2-skill-v3.md` — задание на изменение только SRS-скилла **после одобрения карты этапа 1**.
4. `claude-srs-stage-3-dry-run-v3.md` — проверка результатов **после одобрения этапа 2**, без изменений файлов.

**Источники для сравнения, не для внедрения:** `srs-rules-and-automation.md`, `srs-rules-and-automation(1).md`, `srs-check-pipeline.md` (будущий проект конвейера), `AGENTS.md`, `CLAUDE.md`, текущие `skill/srs/SKILL.md`, `template.md`, `template-wiki.md`.

Не передавать в качестве команды на исполнение старые стадии `claude-srs-stage-*-only.md`, версии v2/v3/v4 правил или `claude-code-srs-skill-update-request*.md`: их заменяет этот комплект.

## Шаг 0 — подготовка и контроль риска

- Открой Claude Code в **аналитическом репозитории**, в котором есть `AGENTS.md` и `skill/srs/`. Не работай в рабочем кодовом репозитории `12stz`.
- Убедись, что нужные исходные проекты правил и конвейера доступны Claude Code в репозитории или приложены отдельно как материалы для чтения. **Новые файлы v5 и задания можно приложить к чату Claude Code; не нужно добавлять их в папки действующих SRS.**
- Для контроля полезно самостоятельно сохранить текущее состояние (например, Git-коммит, сделанный **самостоятельно**, или отдельная резервная копия). **Не поручай Claude делать коммит:** по `AGENTS.md` это возможно только по отдельной явной просьбе, а в трёх стадиях запрет установлен дополнительно.
- Если в репозитории есть незакоммиченные ручные изменения, они должны оставаться неприкосновенными. Этап 1 только их обнаруживает через `git status` / `git diff`.

## Шаг 1 — первый запрос Claude Code (ТОЛЬКО ЧТЕНИЕ)

Отправь **ровно** `claude-srs-stage-1-audit-v3.md` и `srs-rules-and-automation-v5.md`.

При необходимости приложи исходные `srs-check-pipeline.md` и `srs-rules-and-automation(1).md`, если их нет в репозитории Claude Code. Они нужны **только как материал для сравнения**.

Ожидаемый результат: в ответе чата карта `файл/пункт → текущее правило → замена → причина`, список противоречий и отделение «исправляем скилл сейчас» от «проектируем пайплайн потом».

**Критерий безопасности:** `git status` после этапа 1 не должен показывать новых изменений. Ни один документ SRS, Wiki, US, ADR, исходник или скилл не должен измениться.

**Остановись здесь и оцени карту.** Если карта спорная — отправь её на уточнение, а не переходи к следующему шагу.

## Шаг 2 — отдельное одобрение изменения скилла

После проверки карты напиши Claude Code отдельным сообщением:

> Утверждаю согласованную карту изменений этапа 1 **только в части трёх файлов SRS-скилла**. Выполни задание `claude-srs-stage-2-skill-v3.md`. Менять разрешено исключительно `skill/srs/SKILL.md`, `skill/srs/template.md`, `skill/srs/template-wiki.md`. Действующие SRS, их Wiki-копии, User Stories, вопросы, `AGENTS.md`, `CLAUDE.md`, скрипты, конфигурации и проект пайплайна оставь без изменений. По завершении покажи diff и остановись.

Приложи **только** `claude-srs-stage-2-skill-v3.md`. Если Claude выявил существенное новое противоречие, он должен остановиться до твоего решения.

Сверь список изменённых файлов и diff; **разрешено максимум три файла и только из указанного списка**. Не соглашайся на пакетную правку SRS или на создание скрипта автоматической проверки под видом «необходимой подготовки».

## Шаг 3 — отдельная пробная проверка (ТОЛЬКО ЧТЕНИЕ)

После одобрения diff из этапа 2 отправь **только** `claude-srs-stage-3-dry-run-v3.md`. Claude анализирует существующие US 1.3, 1.4, 1.5, US 2–3 и показывает «было → стало бы» в сообщении.

Проверь, что он:

- не выделяет каждый расчёт/проверку бэкенда отдельным шагом;
- сохраняет все условия, поля, ограничения, сроки и существующие договорённости;
- синхронизирует **одинаковые тексты одинаковых действий** сайта/МП при разных API и маршрутах;
- сохраняет **полную цепочку** внутри sequence-диаграмм, но не дублирует её в таблице шагов;
- показывает ошибки отдельно от успешного результата;
- сохраняет блок **«Открытые вопросы» в начале SRS МП**, включая частичные ответы, а содержательные особенности — в «Правилах и особенностях сценария»;
- не меняет действующие документы: это только демонстрация в чате.

**На этом работа по внедрению правил завершается.** Если примеры вызывают вопросы, корректируется **только скилл** отдельной согласованной задачей.

## Что делать с `srs-check-pipeline.md`

Это **отдельный следующий проект**, а не часть этапов 1–3. Когда новый скилл будет проверен и одобрен, открыть самостоятельный аудит конвейера:

1. Согласовать **точку одобрения до любых записей** в реальные документы.
2. Исправить ложные механические проверки равенства номеров, поля и числа условий сайта/МП, запрет на слова «если» и порог 20 слов.
3. Сохранить актуальное решение (§14 проекта конвейера) о полной sequence-цепочке и компактной таблице сценария.
4. Сначала разработать режим **только чтение → отчёт** и проверить ложные срабатывания.
5. Отдельно разрешать каждый набор точечных изменений с картой влияния, защитой ручных правок и проверкой diff.

Ни этот файл, ни правила v5 **не разрешают** сейчас внедрять пайплайн или редактировать существующие SRS.

## Если Claude предлагает сделать больше разрешённого

Ответь: «Остановись. Сейчас разрешён только этап N. Все дополнительные изменения оформи предложением в ответе. Действующие SRS, Wiki, требования и проект пайплайна не трогать».
