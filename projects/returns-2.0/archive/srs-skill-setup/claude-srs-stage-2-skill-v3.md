## Что исправить

- Граница шага: один логически завершённый этап, без обязательного отдельного шага на каждый расчёт/проверку бэкенда; промежуточные данные указывать только по смыслу.
- Состояния одной операции (вызов запроса + загрузка + блокировка повторного клика) описывать вместе; успех и ошибка — с однозначными разными результатами.
- Дословно синхронизировать формулировки идентичных действий сайта/МП, с сохранением разных API, отдельных цепочек проксирования, платформенных элементов и независимой нумерации.
- В шагах вызова API — назначение/необходимый смысл данных, **без списка всех параметров и полей**. Подробность допустима только если критична для понимания следующего действия.
- «Опционально»: жирный заголовок + нумерованные условия даже для одного условия. Простые независимые действия допускаются в нём, сложные — как отдельные последовательности в пределах согласованной US.
- Согласованную командой декомпозицию US 3 (QR-код) / US 3.1 (скачивание заявления и чека двумя таблицами) сохранить.
- Название раздела для нового формата — «Правила и особенности сценария», с группировкой по темам. **Действующие SRS и их заголовки на этом этапе не переименовывать.**
- Для проекта `returns-2.0`: временный «Открытые вопросы» после «Полезных материалов» **только в SRS МП**, по номерам US, с частичными ответами и ссылками; раздел виден в рабочем варианте Яндекс Вики. Это проектная особенность. Если есть непреодолимое противоречие с `AGENTS.md`, изложи его и не реализуй спорный пункт до решения пользователя. `AGENTS.md` не меняй.
- Удалить из шаблонов навязывание отдельного шага «Бэкенд» между каждым API-вызовом и ответом. Не навязывать обе платформенные диаграммы каждой отдельной SRS.
- Для возвратов допускается единственный источник общего описания серверной логики в SRS МП, а для сайта — свой метод и ссылка. Не превращать это в универсальное правило для любого проекта.
- **Сохранить полную sequence-диаграмму взаимодействия компонентов** для своего канала, включая внутренние и внешние сервисы в подтверждённой цепочке. Позиция §14 `srs-check-pipeline.md` является актуальным проектным решением; не выполнять раннее предложение из §9 сократить sequence до App → API. Однако **шаги таблиц** не должны копировать внутренние вызовы. Mermaid `box` можно предложить отдельно, не делать обязательным.
- Не переносить в скилл в качестве действующих правил автоматическое редактирование, нормирование «20 слов», жёсткое равенство номеров/веток сайта и МП, итоговую оценку готовности по проценту и автоматический запуск агентов из проекта конвейера.
- Сохранять прямые короткие русские формулировки; значимые отрицательные условия оставлять, чтобы не искажать смысл.
- Добавить в смысловую самопроверку: ясный триггер, отсутствие искусственного дробления, полноту подтверждённых требований, одинаковость текста совпадающих действий и таблицу только реальных платформенных различий в отчёте о сверке.
