# ID Migration

Временный рабочий файл миграции. Не BRD, не RTM, не спецификация. Удаляется после завершения этапа 2.
Этап 1 — 22–23.09.2026; решения владельца по разделу 4 (единая редакция) внесены 23.09.2026.
Active-файлы на этапе 1 не изменялись.

Основа: `requirements/brd.md` v12 (рабочая копия) и четыре канонических файла историй:
`user-story-creation.md`, `user-story-view.md`, `user-story-lifecycle.md`, `user-story-channels.md`.
Use Case не считается более актуальным источником, чем BRD и US.

**Утверждённая схема финальных ID** (одноразовая миграция до baseline):

- `BR-01…08`, `RULE-01…44`, `FR-01…40`, `NFR-01…07`, `INT-01…09` — сквозная нумерация внутри
  типа в фактическом порядке строк подразделов 7.1–7.5 текущего `brd.md`, без выведенного
  из оборота дубля `FR-7-A`; пропуски старых `BR-1…BR-41` не сохраняются.
- После миграции ID стабильны: существующие требования не перенумеровываются, освободившиеся
  финальные номера не переиспользуются.
- Старые и промежуточные ID остаются только в этом файле. Historical/source-материалы
  (`drafts/**`, audit-файлы, `reports/**`, строки «История изменений») не переписываются.

**Риск миграции:** новые `BR-03…BR-08` и `FR-NN` не совпадают по смыслу со старыми `BR-3…BR-8`
и промежуточными `FR-n-X`. Каждую ссылку заменять по её смыслу и таблице раздела 1 (правила ниже), в каждом файле
за один проход.

**Правила безопасной миграции (этап 2, обязательны):**

1. Никаких глобальных замен по старому `BR-*`, промежуточному `RULE/FR/NFR/INT-*-X` или старому
   `US-*`. Каждое вхождение заменяется отдельно.
2. Для split / reclassified требований final ID выбирается по приоритету: (1) фактический смысл
   конкретной ссылки; (2) точный mapping раздела 1; (3) канонический объект текущего BRD /
   соответствующей User Story; (4) только после этого — краткая подсказка раздела 7.
3. Раздел 7 — только inventory мест со stale references, а не таблица механических замен. Запись
   вида `BR-12` → `RULE-11` означает `RULE-11` только для ссылок о сроке передачи изделия
   (бывш. `RULE-12-B`), а не для всех вхождений `BR-12`.
4. Если соответствие неоднозначно — ссылку не менять и не угадывать; зафиксировать для владельца.
5. Текст требований BRD защищён. В `brd.md` разрешено только: присвоить final ID; заменить stale
   Requirement ID в cross-reference; восстановить однозначно подтверждённую связь после split /
   reclassification; удалить утверждённый дубль `FR-7-A`; выполнить изменения metadata / links,
   явно перечисленные в разделе 4. Запрещено переформулировать, сокращать, расширять, стилистически
   улучшать нормативный текст, менять бизнес-смысл, переносить логику между требованиями.
6. Внутри существующих формулировок (включая «оставить в …») меняется только мигрируемый
   Requirement ID. Ссылки на неперенумеровываемые типы (`OQ-*`, `C-*`, `A-*`, `BO-*`, `PP-*`,
   `ADR-RET-*`, `UC-RET-*`, `SCR-RET-*`) остаются как есть. Связи не теряются.
7. `requirements/business-case.md` исключён из миграции (раздел 7): legacy ID в нём не считаются
   ошибкой итогового stale-ID поиска; файл не используется для построения и проверки RTM.

**Проверка карты (23.09.2026):** фактический состав раздела 7 `brd.md` — 109 строк
(BR 8 · RULE 44 · FR 41 · NFR 7 · INT 9), повторяющихся ID нет; совпадает с исходным подсчётом.
