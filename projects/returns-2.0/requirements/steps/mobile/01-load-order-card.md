# Шаг 01 (mobile, TO-BE). Открытие карточки заказа и доступность возврата

**Канал:** Мобильное приложение
**Статус:** DRAFT · **Дата:** 29.09.2026
**AS-IS:** [as-is/mobile/01-load-order-card.md](../../../as-is/mobile/01-load-order-card.md)
**Результат шага:** приложение получило карточку заказа с позициями, признаками возможности возврата, остатком штук к возврату, дедлайном возврата и действием «Оформить возврат». В базе ничего не меняется.

> Параметры в угловых скобках (`<...>`) — рабочие наименования, не утверждённые окончательно (новые поля, таблицы, параметры и внутренние переменные).
> Изменения относятся только к мобильному каналу. Веб-канал описывается отдельно.

## 1. Идентификация и первичная проверка заказа

1.1. Система получает id выбранного заказа (`GET /mobile/orders/{id}`) и выполняет запрос на получение карточки заказа.

1.2. Идентификация и проверка прав доступа:
- **Условие:** система ищет запись, где `cms_orders.id = {id} AND cms_orders.user_id = {authorized_user_id} AND cms_orders.lamoda_id IS NULL`.
- **Результат:** если запись не найдена, система прерывает выполнение и возвращает ошибку с кодом 1009 («Заказ {id} не найден у пользователя»).

1.3. Проверка типа заказа (исключение брони):
- **Условие:** `cms_orders.type != 'reservation'`.
- **Результат:** если `cms_orders.type = 'reservation'`, система возвращает ошибку с кодом 1009 («Заказ {id} не найден у пользователя»).

1.4. Проверка доступности возврата по статусу заказа:
- **Условие:** `cms_orders.status` входит в набор статусов, у которых `cms_order_statuses.group = 'complete'` или `cms_order_statuses.is_returned = 1`. Набор на дату выгрузки справочника (28.07.2026): {17, 31, 33, 56, 84}.
- **Результат:** если статус заказа не входит в набор, расчёт срока и остатков не выполняется. Позиции возвращаются в `items[]` с `items[].can_be_returned = false`.

## 2. Определение категории пользователя и расчёт срока возврата

2.1. Определение допустимого периода возврата (`<days_limit>`):
- **Условие:** признак `cms_users_user.is_vic` берётся на момент запроса.
  - если `cms_users_user.is_vic = 1` (категория Friends & Family / VIC) → `<days_limit>` = `<cms_parameters.days_can_be_returned_ff>` (значение параметра, на дату — 30);
  - иначе (`cms_users_user.is_vic = 0`, обычный клиент) → `<days_limit>` = `cms_parameters.days_can_be_returned` (значение параметра, на дату — 14).

2.2. Расчёт дедлайна возврата (`<return_until_date>`):
- **Условие (вариант уточняется у бизнеса, см. открытый вопрос 2):**
  - **Вариант А — точное время (как AS-IS):** `<return_until_date>` = `cms_orders.end_date` + `<days_limit>` дней, с точностью до секунды.
    Пример: `end_date = 2026-09-28 15:42:10` → `<return_until_date> = 2026-10-12T15:42:10+03:00`.
  - **Вариант Б — до конца дня:** `<return_until_date>` = дата(`cms_orders.end_date`) + `<days_limit>` дней, время 23:59:59 по Москве.
    Пример: `end_date = 2026-09-28 15:42:10` → `<return_until_date> = 2026-10-12T23:59:59+03:00`.
- **Результат:** формируемое поле JSON `result.<return_until_date>` — строка в формате ISO 8601 или `null` (если `cms_orders.end_date IS NULL`, см. открытый вопрос 1).

2.3. Проверка актуальности срока возврата:
- **Условие:** `cms_orders.end_date IS NULL OR <return_until_date> > CURRENT_TIMESTAMP()`.
- **Результат:** если дата выполнения заказа равна `NULL` или вычисленный дедлайн строго больше текущего времени — `true`, иначе — `false`.

## 3. Первичная проверка позиций заказа

3.1. **Условие:** `cms_order_positions.status = 1 AND cms_order_positions.is_present = 0`.
- `cms_order_positions.status` хранит `internal_id` из справочника `cms_order_position_statuses`; `1` — «Добавлен» (`code = new`).
- Статус позиции заказа при создании, изменении и отмене заявки на возврат **не меняется**.
- Проверка отсекает позиции, которые не были выкуплены (отказ, отмена, нет в наличии), и позиции-подарки.

3.2. **Результат:**
- `true` — позиция участвует в расчёте остатка (п. 4);
- `false` — система сразу устанавливает в ответе `items[].can_be_returned = false`, расчёт по позиции не выполняется.

## 4. Динамический расчёт доступного количества для возврата

**ВАЖНО:** `cms_order_positions.quantity` не изменяется логикой возвратов. Расчёт выполняется в момент запроса и отдаётся только в JSON-ответе карточки заказа.

Модель данных:
- в `cms_order_positions` одна строка соответствует одному товару (`barcode`), а количество купленных штук хранится в `quantity` (может быть больше 1);
- в `<cms_return_positions>` одна строка соответствует одной возвращаемой штуке со своей причиной возврата (`quantity = 1`). Несколько штук одного товара — это несколько строк с одинаковым `barcode`.

Для каждой позиции, прошедшей п. 3, система выполняет поиск ранее созданных заявок на возврат по текущему `cms_orders.id`.

4.1. Подсчёт количества товара в ранее созданных заявках (`<already_returned_count>`):
- **Условие:** система суммирует `<cms_return_positions>.quantity` по всем строкам возврата, для которых одновременно выполняется:
  1. `<cms_returns>.order_id = cms_orders.id`
  2. `AND <cms_return_positions>.barcode = cms_order_positions.barcode`
  3. `AND <cms_returns>.status NOT IN ('cancelled')`

  Примечание: суммируются товары из заявок во всех статусах, кроме «Отмена»: «Создан», «В пути», «Принят», «Выполнен», «Отклонён» и др. Заявки со статусом «Отмена» исключаются из подсчёта: по ним клиент может оформить возврат заново. По отклонённой заявке повторно вернуть товар нельзя.
- **Результат:** полученная сумма записывается во внутреннюю переменную `<already_returned_count>`. Если строк не найдено, `<already_returned_count> = 0`.

4.2. Вычисление доступного остатка (`<return_available_count>`):
- **Условие:** `<return_available_count> = max(0, cms_order_positions.quantity − <already_returned_count>)`.
- **Результат:**
  - если `<already_returned_count> = 0` (заявок нет или все в статусе «Отмена»), то `<return_available_count> = cms_order_positions.quantity`;
  - если `<already_returned_count> > 0`, то `<return_available_count> = cms_order_positions.quantity − <already_returned_count>`;
  - если разность меньше 0 (рассинхрон данных), то `<return_available_count> = 0`.

  Пример: `barcode 111`, `quantity = 3`; строки возврата в заявках «Создан» (1), «Выполнен» (1), «Отмена» (1). Тогда `<already_returned_count> = 2`, `<return_available_count> = 1`.

4.3. Формируемые поля JSON:
- **Условие:** для каждой позиции заказа в ответе.
- **Результат:**
  - `items[].count` = `cms_order_positions.quantity` (AS-IS: купленное количество, берётся из БД);
  - `items[].<return_available_count>` = `<return_available_count>` (TO-BE: новое динамическое поле с остатком штук).

4.4. Использование расчёта:
- **Условие:** `<return_available_count>` в карточке служит только для отображения и ограничения выбора на экране изделий.
- **Результат:** новый метод создания заявки на возврат повторно проверяет `<return_available_count>` в момент создания.

## 5. Определение флага доступности по позиции и по заказу

5.1. Флаг позиции (`items[].can_be_returned`) = `true`, если одновременно:
1. позиция прошла п. 3 (`cms_order_positions.status = 1 AND cms_order_positions.is_present = 0`);
2. `AND` статус заказа входит в набор из п. 1.4;
3. `AND (cms_orders.end_date IS NULL OR <return_until_date> > CURRENT_TIMESTAMP())` — срок возврата ещё не истёк или нет `end_date` (п. 2.3);
4. `AND <return_available_count> > 0` (п. 4.2).

Если хотя бы одно условие не выполнено, `items[].can_be_returned = false`.

5.2. Флаг по заказу (`result.messages[]`):
- **Условие:** хотя бы у одной позиции `items[].can_be_returned = true`.
- **Результат:** если условие выполняется, в `result.messages[]` добавляется элемент:
  - `status = "can_be_returned"`;
  - `message` = «Вы можете вернуть вещи до {return_until_date}» (дата в формате ДД.ММ.ГГГГ). Текст при `<return_until_date> = null` — см. открытый вопрос 3;
  - `button` = «Оформить возврат».

  Позиция элемента в массиве не фиксирована: раньше него могут стоять элементы `can_be_cancelled` и `can_be_payed`.
- Если условие не выполняется, элемент со `status = "can_be_returned"` не добавляется.

## 6. Определение необходимости банковских реквизитов (AS-IS, без изменений)

- **Условие:** если `cms_orders.payment_method ∈ {3, 5}`, то `return.is_bank_data_required = true`, иначе `false`.
- Признак рассчитывается независимо от доступности возврата.

## 7. Формирование ответа мобильному приложению

Новые поля (TO-BE):
- `result.<return_until_date>` — дедлайн возврата (п. 2.2);
- `items[].<return_available_count>` — остаток штук к возврату (п. 4.2).

Поля AS-IS без изменений состава (логика расчёта `can_be_returned` и текст `message` — по пп. 5.1–5.2):
- `result.messages[]` — элемент со `status = can_be_returned`;
- `items[].can_be_returned` — какие позиции можно выбрать;
- `items[].barcode` — идентификатор позиции для создания заявки;
- `items[].count` — купленное количество;
- `return.is_bank_data_required` — необходимость банковских реквизитов.

Мобильное приложение отображает карточку заказа. Если в `messages[]` есть элемент `can_be_returned`, отображается кнопка «Оформить возврат». На экране выбора изделий количество к возврату по позиции ограничено `items[].<return_available_count>`.

## Ограничения

- Статус позиции (`cms_order_positions.status`) по-прежнему изменяют 1С (обновление заказа из 1С, `OrderUpdateService::updatePositions`) и RetailCRM (импорт заказа, `OrderPosition::fillByRetailCrmPosition`) — для строки целиком, через сопоставление по `cms_order_position_statuses.code`. Если позиция уйдёт из статуса 1 (например, в «ВОЗВРАТ (если был отгружен)», `internal_id = 9`), она станет недоступна к возврату целиком, независимо от `<return_available_count>`.
- `cms_order_positions.quantity` может перезаписать RetailCRM при импорте заказа. В этом случае `<return_available_count>` считается от нового значения `quantity`.
- Расчёт остатка (п. 4) выполняется только в карточке заказа. В остальных ответах мобильного API, отдающих позиции (список заказов, главный экран, брони, сертификаты), `items[].can_be_returned` считается по правилам AS-IS, без учёта заявок.
