## Контекст

- RetailCRM передаёт сайту заказы и заявки на возврат сама — по триггеру с вебхуком; для возвратов схема та же ([разбор встречи 16.11.2026](<../../meetings/[2026-11-16 15-06] Weekly 12storeez & Intaro_summary.md>), тема 1).
- В вебхуке RetailCRM передаёт `externalId` — ID записи на сайте. У заказа это `cms_orders.id` ([retailcrm-exchange_questions.md](../questions/retailcrm-exchange_questions.md), вопрос 4).
- Заявка на возврат — отдельная сущность сайта со своим счётчиком ID (ECOMDEV-2587). ID заказа и ID заявки могут совпасть; тогда по `externalId` не определить, пришёл заказ или заявка.
- Сквозной номер `R…` от 1С (`ADR-RET-098`) — номер, а не ID записи в базе сайта, поэтому по нему заказ от заявки в вебхуке не отличить.
- В теле вебхука заказов RetailCRM уже передаёт тип заказа `orderType`. Заявка на возврат в RetailCRM — заказ с `orderType = return`; других значений типа у возвратов нет.
- В выпущенном коде сайт `orderType` не читает: заявка Дружбы с типом `return` создастся на сайте обычным заказом ([retailcrm-exchange_questions.md](../questions/retailcrm-exchange_questions.md), п. 4 раздела «Как сейчас работает обмен»). Доработка чтения `orderType` готова, но не выкачена.
- Повторный запрос с тем же номером RetailCRM в течение 2 секунд сайт сейчас отбрасывает как дубль (там же, п. 5).

## Решение

Заявки на возврат RetailCRM передаёт в тот же вебхук, что и заказы. Отдельный параметр типа в вебхук не добавляется. Сайт определяет, к заказу или к заявке на возврат относится `externalId`, по полю `orderType` в теле вебхука: `return` — заявка на возврат, остальные значения — заказ.

## Последствия

### Положительные

- Совпадение ID заказа и ID заявки на сайте не приводит к записи изменений не в ту сущность.
- Формат вебхука RetailCRM не меняется: признак типа уже есть в теле, доработка триггера под параметр не нужна.
- Чтение `orderType` на сайте уже доработано.

### Отрицательные и риски

- Тип записи на сайте определяется данными заказа RetailCRM: заявка, оформленная в RetailCRM с другим типом заказа, придёт на сайт как заказ.
- Пока доработка чтения `orderType` не выпущена, заявка Дружбы с типом `return` создастся на сайте обычным заказом.
- Заявки идут в тот же приёмник, что и заказы: проверку дублей по номеру RetailCRM за 2 секунды нужно учесть в доработке приёма, чтобы не отбросить запрос по заявке.
- Обратное направление — сайт передаёт изменения в RetailCRM по `externalId` — этим решением не закрыто (открытый вопрос 1).

## Рассмотренные альтернативы

### Параметр `type` в вебхуке (`order` / `return`)

- **Результат:** отклонена.
- **Причина:** дублирует `orderType`, который уже есть в теле вебхука; требует доработки триггеров RetailCRM без новой информации для сайта.

### Различать заявку по номеру с префиксом `R`

- **Результат:** отклонена.
- **Причина:** номер `R…` — не ID записи в базе сайта, а в вебхуке передаётся ID.

### Отдельный вебхук для возвратов

- **Результат:** не выбрана.
- **Причина:** тип записи определяется по `orderType` в существующем вебхуке.

## Условия пересмотра

- ID заказа и заявки на возврат на сайте перестают пересекаться (общий счётчик или префикс в `externalId`).
- У заявок на возврат в RetailCRM появляется тип заказа, отличный от `return`.
- RetailCRM переходит на отдельный вебхук для заявок на возврат.
