## Контекст

В v1 для статусов позиции заказа «Заявка на возврат», «Частичный возврат» и «Полный возврат»
заводились новые коды, а коды 5 и 9 в новом процессе не использовались. Основная причина: код 9 сразу
делает позицию возвращённой — в суммах заказа, обмене с 1С и блокировке оплаты наличными, — а в
текущем процессе он ставится при подаче заявки из ЛК.

В новом процессе «Возврат» ставится, когда приняты все изделия позиции (переход O4 схемы статусов
версии 4), а не при подаче заявки. В этот момент позиция действительно возвращена, и логика кода 9
(исключение из суммы заказа, передача в 1С как возврата) соответствует состоянию позиции.

Код 9 — `lost` «ВОЗВРАТ (если был отгружен)»: активен, для него настроены статусы Mindbox, по нему
возвращаются баллы; в RetailCRM он уже заведён. Код 5 — `returned`: выключен, статусов Mindbox для
него нет, по такой позиции баллы не вернутся.

RetailCRM предложил коды `return-requested` («Заявка на возврат») и `return-partial` («Частичный
возврат»). Сайт принимает статус позиции из RetailCRM по символьному коду из своего справочника;
незнакомый код ломает обработку всего изменения заказа. Нужен ли статус «Частичный возврат», зависит
от решения по делению строки позиции заказа — не определено.

## Решение

1. Статус позиции заказа «Возврат» — действующий код `lost` (`internal_id = 9`). Новый код для него
   не заводится.
2. Статусы «Заявка на возврат» и «Частичный возврат» получают новые коды; RetailCRM предложил
   `return-requested` и `return-partial`.
3. Код `returned` (`internal_id = 5`) в новом процессе не используется.
4. RetailCRM начинает ставить новые коды в заказах только после того, как сайт заведёт их в
   справочнике статусов позиций.

## Последствия

### Положительные

- Обмен с Mindbox и RetailCRM для статуса «Возврат» не дорабатывается: баллы возвращаются по
  настроенному маппингу.
- Логика монолита, завязанная на код 9, срабатывает в момент, когда позиция действительно возвращена.

### Отрицательные и риски

- Позиции «Возврат» старых и новых заказов имеют один код: в отчётах их различают по наличию заявки на
  возврат.
- Логику, завязанную на код 9 при подаче заявки из ЛК (текущий процесс), нужно отключить для нового
  процесса, иначе позиция станет «Возврат» при подаче заявки.
- Для новых кодов нужны строки `cms_mb_statuses_map`, иначе в Mindbox уходит статус по умолчанию.

## Рассмотренные альтернативы

### Новый код для «Возврат», например `return-done`

- **Результат:** отклонена.
- **Причина:** потребует настройки статусов Mindbox и доработки обмена с 1С и Mindbox; `lost` уже
  заведён в RetailCRM и Mindbox.

### Код `returned`

- **Результат:** отклонена.
- **Причина:** статус выключен, статусов Mindbox для него нет — по позиции не вернутся баллы.

### Новые коды для всех трёх статусов (v1)

- **Результат:** отклонена.
- **Причина:** довод v1 против кода 9 — срабатывание при подаче заявки — в новом процессе не
  действует: «Возврат» ставится после приёмки всех изделий позиции.

## Условия пересмотра

- Отчётам или Mindbox потребуется отличать возвраты нового процесса от старых по коду статуса позиции.
- 1С или Mindbox начнут обрабатывать код `lost` иначе, чем полный возврат позиции.
