# ADR-RET-102: Параметр `type` в вебхуке RetailCRM отделяет заявку на возврат от заказа

## Контекст

- RetailCRM передаёт сайту заказы и заявки на возврат сама — по триггеру с вебхуком; для возвратов схема та же ([разбор встречи 16.11.2026](<../../../meetings/[2026-11-16 15-06] Weekly 12storeez & Intaro_summary.md>), тема 1).
- В вебхуке RetailCRM передаёт `externalId` — ID записи на сайте. У заказа это `cms_orders.id` ([retailcrm-exchange_questions.md](../../questions/retailcrm-exchange_questions.md), вопрос 4).
- Заявка на возврат — отдельная сущность сайта со своим счётчиком ID (ECOMDEV-2587). ID заказа и ID заявки могут совпасть; тогда по одному вебхуку не определить, пришёл заказ или заявка.
- Сквозной номер `R…` от 1С (`ADR-RET-098`) — номер, а не ID записи в базе сайта, поэтому по нему заказ от заявки в вебхуке не отличить.
- Сейчас сайт тип заказа RetailCRM не читает: заявка Дружбы с типом `return` создастся на сайте обычным заказом (код монолита; [retailcrm-exchange_questions.md](../../questions/retailcrm-exchange_questions.md), п. 4 раздела «Как сейчас работает обмен»).
- Повторный запрос с тем же номером RetailCRM в течение 2 секунд сайт сейчас отбрасывает как дубль (код монолита; там же, п. 5).

## Решение

Заявки на возврат RetailCRM передаёт в тот же вебхук, что и заказы. В вебхук добавляется параметр `type`: `order` — заказ, `return` — заявка на возврат. RetailCRM дорабатывает триггер, сайт — метод, который принимает вебхук: по `type` сайт определяет, к заказу или к заявке на возврат относится `externalId`.

## Последствия

### Положительные

- Совпадение ID заказа и ID заявки на сайте не приводит к записи изменений не в ту сущность.

### Отрицательные и риски

- Доработка на двух сторонах: триггер RetailCRM и метод приёма сайта. Пока обе не выпущены, заявка Дружбы с типом `return` создастся на сайте обычным заказом.
- Заявки идут в тот же приёмник, что и заказы: проверку дублей по номеру RetailCRM за 2 секунды нужно учесть в доработке приёма, чтобы не отбросить запрос по заявке.
- Обратное направление — сайт передаёт изменения в RetailCRM по `externalId` — этим решением не закрыто (открытый вопрос 1).

## Рассмотренные альтернативы

### Различать заявку по номеру с префиксом `R`

- **Результат:** отклонена.
- **Причина:** номер `R…` — не ID записи в базе сайта, а в вебхуке передаётся ID.

### Отдельный вебхук для возвратов

- **Результат:** не выбрана.
- **Причина:** выбран параметр `type` в существующем вебхуке.

## Открытые вопросы

1. Не перепутает ли RetailCRM заказ и заявку с одинаковым `externalId`, когда сайт передаёт изменения в RetailCRM? ([retailcrm-exchange_questions.md](../../questions/retailcrm-exchange_questions.md), вопрос 4)
2. Как сайт обрабатывает вебхук без параметра `type` — как заказ?
3. Какой тип заказа у «Возврата из ЛК» в RetailCRM? ([retailcrm-exchange_questions.md](../../questions/retailcrm-exchange_questions.md), вопрос 2)

## Условия пересмотра

- ID заказа и заявки на возврат на сайте перестают пересекаться (общий счётчик или префикс в `externalId`).
- RetailCRM переходит на отдельный вебхук для заявок на возврат.
