# ADR-RET-109: Реквизиты, которые клиент сообщил Дружбе по телефону, считаются подтверждёнными клиентом

## Контекст

На этапе 0 сайт и МП передают в 1С признак `is_bank_details_confirmed` — клиент подтвердил банковские реквизиты галочкой в форме (ECOMDEV-2649, ECOMDEV-2651). Реквизиты может внести и Дружба в RetailCRM со слов клиента по телефону. Галочки подтверждения в RetailCRM нет.

## Решение

Если клиент сам сообщил реквизиты Дружбе по телефону, это считается его согласием. Для таких реквизитов сайт ставит признак подтверждения, как будто клиент подтвердил их сам, и передаёт его в 1С.

Уточнение по переписке 19–20.11.2026: если возврат создаётся через RetailCRM и для него нужны банковские реквизиты, бэкенд сайта передаёт в 1С `is_bank_details_confirmed = true`; оформление возврата через RetailCRM считается альтернативным способом подтверждения. Согласие Backend Developer (Оля Свистунова) и Project Manager (Катя Тихомирова) — 20.11.2026.

Уточнения 20.11.2026:
- Дружба получает реквизиты от клиента при каждом возврате; ранее предоставленные реквизиты повторно не используются.
- Отдельное согласование с юристами не требуется: Дружба и сейчас принимает реквизиты от клиента в чат или на почту и возвращает деньги по ним.
- Возврат, оформленный в RetailCRM, сайт определяет по полю заявки `channel = support` (ECOMDEV-2587); `rcrm_id` для этого не используется — он есть и у заявок с сайта и из МП после передачи в RetailCRM.

## Последствия

### Положительные

- Возврат по реквизитам, внесённым Дружбой, не отличается для 1С и бухгалтерии от возврата по реквизитам из формы.
- В RetailCRM не нужна отдельная галочка подтверждения.

### Отрицательные и риски

- Подтверждение по телефону нигде не фиксируется самим клиентом: признак ставит система.
- Сайту нужно отличать возврат, созданный через RetailCRM (`true`), от возврата из старой версии МП без подтверждения: для него по итоговому контракту передаётся `null` (переписка 19–20.11.2026, ECOMDEV-2651).
- Сайт может поставить `true` только по реквизитам, которые к нему пришли. Обмен с RetailCRM сейчас реквизиты в заказ не записывает: их пишут только возвраты сайта и МП. Предложение Backend Developer: RetailCRM присылает реквизиты вместе с возвратом, сайт сохраняет их и ставит `true`. Если RetailCRM реквизиты прислать не сможет, для таких возвратов остаётся `null`, и решение пересматривается.
- Сейчас реквизиты из RetailCRM на сайт не попадают: в вебхуке их нет, а в старом обработчике, где сайт сам запрашивает заказ из RetailCRM, реквизиты из ответа не сохраняются. Добавление реквизитов в обмен есть в ТЗ команды RetailCRM.
- Дружба получает реквизиты после оформления возврата — клиент присылает их в чат или на почту — и прикрепляет к заказу файлом. В полях RetailCRM реквизитов может не быть, поэтому признак можно поставить только тогда, когда реквизиты пришли на сайт, а не в момент создания возврата.
- Дружба реквизиты в поля заказа RetailCRM не вносит: прикрепляет файл или пишет их в комментарии. Поля реквизитов в заказе RetailCRM есть («Получатель денег (ФИО)», «БИК Банка», «ИНН Банка», «Название Банка», «Номер лицевого счета», «Номер банковской карты физлица»), но передавать сайту из них нечего.
- Сайт при каждой отправке заказа в RetailCRM передаёт поля реквизитов из своего заказа: пустые строки, если реквизитов нет, а в поле ФИО получателя — ФИО покупателя. Реквизиты, вписанные Дружбой в RetailCRM, следующая отправка заказа с сайта сотрёт.

## Рассмотренные альтернативы

### Отдельная галочка подтверждения в RetailCRM

- **Результат:** не рассматривалась на встрече.
- **Причина:** галочки в RetailCRM нет; звонок клиента с реквизитами признан согласием.

## Условия пересмотра

- Бухгалтерия или ИБ требуют подтверждения реквизитов самим клиентом, а не Дружбой.
- RetailCRM не может передавать сайту реквизиты возврата.
- Сотрудники Дружбы оформляют возврат по реквизитам, которые клиент не сообщал и не подтверждал при обращении.

## Открытые вопросы

1. Какими ключами и при каком событии RetailCRM будет передавать сайту банковские реквизиты: в вебхуке изменения заказа (этап 0.1) и вместе с заявкой на возврат («Возвраты 2.0»)? Кому: команда RetailCRM (Intaro), Алёна Господинова.
2. Пробовала ли Дружба вписывать реквизиты в поля заказа RetailCRM? Пропадали ли они потом из заказа? Кому: Дружба (Ольга Соколова).
3. Можно ли сделать так, чтобы сайт не перезаписывал в RetailCRM заполненные реквизиты пустыми или сначала принимал их из вебхука? Кому: Backend Developer (Оля Свистунова).
4. Будут ли сотрудники Дружбы вносить реквизиты в поля заказа RetailCRM вместо файла и комментария, в том числе реквизиты, которые клиент прислал после оформления возврата или исправил? Кому: Дружба (Ольга Соколова), Project Manager (Катя Тихомирова).
5. Как на этапе 0.1, где возврат хранится в заказе и заявки нет, сайт поймёт, что реквизиты внесла Дружба? Признак `channel = support` есть только у заявки «Возвратов 2.0» (ECOMDEV-2587). Кому: Backend Developer (Оля Свистунова).
