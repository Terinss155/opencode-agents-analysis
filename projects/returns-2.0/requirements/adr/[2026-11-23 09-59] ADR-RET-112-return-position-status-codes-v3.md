## Контекст

В v2 статус позиции заказа «Возврат» получил действующий код `lost` (`internal_id = 9`), а статусы
«Заявка на возврат» и «Частичный возврат» — новые коды; RetailCRM предложил `return-requested` и
`return-partial`. Нужен ли «Частичный возврат», зависело от решения по делению строки позиции заказа.

Решено делить строку: возвращаемые изделия отделяются от оставшихся новой строкой позиции заказа, и
каждая строка хранит свой статус. Пример: в позиции 3 изделия, клиент возвращает одно. Строка с
двумя изделиями остаётся в прежнем статусе, изделия у клиента. Отделённая строка с одним изделием
получает «Заявка на возврат», после приёмки — «Возврат». «Частичный возврат» не подходит ни одной из
строк: оставшиеся изделия не возвращались, а отделённая строка возвращена полностью.

Статус заказа при возврате не меняется (`ADR-RET-039`), поэтому частичный возврат заказа виден только
по строкам позиции. 1С статус «Частичный возврат» технически не нужен. Клиенту статус позиции заказа
не показывается: в ЛК сайта по позиции приходит только признак «возвращена», в позициях заказа в МП
статуса нет; по макетам «Возвратов 2.0» клиент видит статусы заявки на возврат, а не позиции.

## Решение

1. Статус позиции заказа «Возврат» — действующий код `lost` (`internal_id = 9`). Новый код для него
   не заводится.
2. Новый код получает только статус «Заявка на возврат»; RetailCRM предложил `return-requested`.
3. Статуса позиции заказа «Частичный возврат» нет. Строка позиции, все изделия которой приняты,
   получает «Возврат», даже если у позиции остаются невозвращённые изделия в другой строке.
4. Код `returned` (`internal_id = 5`) в новом процессе не используется.
5. RetailCRM начинает ставить новый код в заказах только после того, как сайт заведёт его в
   справочнике статусов позиций.

## Последствия

### Положительные

- Сайт, RetailCRM и 1С не заводят и не обрабатывают статус и код `return-partial`; для Mindbox не
  нужна строка маппинга `cms_mb_statuses_map` под «Частичный возврат».
- Статус строки не зависит от других строк позиции: строка переходит в «Возврат», когда приняты её
  изделия, без пересчёта статусов остальных строк.
- Обмен с Mindbox и RetailCRM для статуса «Возврат» не дорабатывается: строка уходит в Mindbox
  по действующему маппингу `lost` → `401`; запускает ли код `401` возврат баллов, не подтверждено Mindbox
  ([mindbox-exchange_questions.md](../questions/mindbox-exchange_questions.md), вопрос 5).

### Отрицательные и риски

- Частичный возврат позиции не виден по одному статусу: его определяют по наличию у позиции строки
  «Возврат» и строки с прежним статусом. Отчётам, которые смотрят статус одной строки, нужно учитывать
  все строки позиции.
- Решение опирается на деление строки позиции заказа. Как хранятся и объединяются строки, не
  определено. По решению RetailCRM строка позиции в RetailCRM не делится, статусы изделий ведутся в свойствах одной позиции; решение требует проверки на тесте ([order-position-split_questions.md](../questions/order-position-split_questions.md), решение 11).
- Позиции «Возврат» старых и новых заказов имеют один код: в отчётах их различают по наличию заявки на
  возврат.
- Логику, завязанную на код 9 при подаче заявки из ЛК (текущий процесс), нужно отключить для нового
  процесса, иначе позиция станет «Возврат» при подаче заявки.
- Для кода «Заявка на возврат» нужны строки `cms_mb_statuses_map`, иначе в Mindbox уходит статус по
  умолчанию.

## Рассмотренные альтернативы

### Статус «Частичный возврат» с кодом `return-partial` (v2)

- **Результат:** отклонена.
- **Причина:** при делении строки позиции статус не подходит ни одной строке; технически он не нужен
  1С, клиенту статус позиции не показывается.

### Новый код для «Возврат», например `return-done`

- **Результат:** отклонена.
- **Причина:** потребует настройки статусов Mindbox и доработки обмена с 1С и Mindbox; `lost` уже
  заведён в RetailCRM и Mindbox.

### Код `returned`

- **Результат:** отклонена.
- **Причина:** статус выключен, статусов Mindbox для него нет — по позиции не вернутся баллы.

## Условия пересмотра

- Решение о делении строки позиции заказа изменится: позиция снова будет храниться одной строкой с
  изделиями в разных статусах.
- Отчётам, RetailCRM или Mindbox потребуется отличать частично возвращённую позицию по статусу одной
  строки.
- Отчётам или Mindbox потребуется отличать возвраты нового процесса от старых по коду статуса позиции.
- 1С или Mindbox начнут обрабатывать код `lost` иначе, чем полный возврат позиции.
