## Контекст

Бумажное заявление на возврат заменяется электронным: клиент оформляет заявку в ЛК сайта или МП, заявление формируется из данных заявки по утверждённому шаблону, подпись клиента не требуется. Мастер-система по заявкам на возврат — 1С КА; номер заявки присваивает 1С.

Нужно было выбрать, где формируется печатная форма заявления и где хранится PDF. Рассматривались три варианта: 1С, выделенный микросервис, бэкенд сайта; во всех вариантах файл хранится в S3.

Факторы выбора:

- данные заявления совпадают с данными мастер-системы;
- один шаблон для клиента, сотрудника и магазина;
- заявление открывается по ссылке независимо от доступности 1С, после того как сформировано;
- генерация PDF не нагружает 1С и монолит сайта;
- сервис можно переиспользовать для других печатных форм — у BTS уже есть сервис печатных форм в разработке.

Формирование заявления в любом варианте зависит от 1С: PDF формируется, когда заявку приняла 1С и присвоила номер.

## Решение

1. Печатную форму клиентского заявления на возврат формирует выделенный сервис печатных форм. Владелец — команда BTS (ADR-0011).
2. 1С передаёт в сервис данные заявки, а не готовую форму. Шаблон печатной формы и способ генерации PDF — на стороне сервиса.
3. Сервис кладёт PDF в S3. Ссылка на документ возвращается в 1С, 1С передаёт её на сайт и в RetailCRM.
4. Бэкенд сайта получает ссылку на заявление от 1С и отдаёт её сайту и МП. Клиент видит и скачивает заявление в карточке возврата в ЛК сайта и в МП.
5. PDF хранится. Клиент и сотрудник открывают заявление по ссылке; повторно заявление не формируется.
6. Доступ к файлам (ADR-0011): приватный бакет S3; клиенту и сотруднику сайт выдаёт ссылку с коротким сроком действия после проверки прав; скачивания журналируются (кто, когда). В карточке возврата — не прямая ссылка на объект S3.
7. Версий заявления нет: в системах всегда ссылка на актуальный PDF. При изменении данных 1С передаёт их в сервис, сервис формирует новый PDF, 1С передаёт новую ссылку.
8. При аннулировании заявки PDF удаляется из S3 вместе со ссылкой; открыть и распечатать заявление нельзя.
9. Номер банковской карты в шаблон заявления не выводится и в нём не хранится; на заявлении указывается номер счёта.
10. Сотрудник открывает заявление в документе «Заявка на возврат» в 1С и в карточке заявки в RetailCRM (`ADR-RET-096`).
11. Защиту сервиса от массовой генерации файлов прорабатывает владелец сервиса.

## Последствия

### Положительные

- Содержимое заявления соответствует данным мастер-системы: инициатор формирования — 1С.
- Один шаблон для всех точек печати; шаблон меняется в одном месте.
- Генерация PDF вынесена из 1С и монолита сайта и не влияет на их производительность.
- Сервис переиспользуется для других печатных форм.
- Сформированное заявление доступно клиенту по ссылке, даже когда 1С в регламентном окне.
- Сайт не хранит банковские реквизиты для формирования заявления.
- Клиент получает заявление в ЛК сайта и МП без обращения в Дружбу.

### Отрицательные и риски

- Новый сервис в цепочке: 1С → сервис → S3 → 1С → сайт. Больше точек отказа и задержка, пока ссылка дойдёт до сайта.
- Пока 1С не приняла заявку или находится в регламентном окне, заявление не формируется — клиент не видит его в карточке возврата.
- Срок готовности сервиса печатных форм к MVP возвратов зависит от команды BTS.
- В S3 хранятся персональные данные и номер счёта клиента; сайт выдаёт ссылки с проверкой прав и журналирует скачивания — доработка сайта.
- Обмен 1С → сайт и 1С → RetailCRM дорабатывается: передаётся ссылка на документ. Сайт и МП дорабатываются: в карточке возврата — просмотр и скачивание заявления.
- Данные заявления берутся из 1С: сайт передаёт данные заявки в 1С, 1С — в сервис. По `ADR-RET-024` сайт хранил поля, которые клиент вводит в ЛК, для формирования заявления по запросу; для заявления это больше не нужно.
- `INT-01` (заявление как файл между системами не передаётся) и `NFR-01` (воспроизведение заявления из исходных данных) расходятся с решением — нужна правка BRD.

## Рассмотренные альтернативы

### Формирование PDF в 1С

- **Результат:** отклонена.
- **Причина:** на архкомитете выбран вариант B, открытые вопросы варианта A не обсуждали. По сравнительной таблице ADR-0011 у варианта A хуже переиспользование для других печатных форм и нагрузка на сервер 1С.

### Формирование PDF на сайте

- **Результат:** отклонена.
- **Причина:** на архкомитете выбран вариант B. По обсуждению: PDF формировался бы из копии данных, а не из мастер-системы, возможны коллизии; правки шаблона в двух местах; генерация внутри монолита может повлиять на его производительность; сайту пришлось бы хранить банковские реквизиты.

### Не хранить PDF, формировать по запросу (`ADR-RET-024`)

- **Результат:** отклонена.
- **Причина:** заявление формируется один раз, дальше к нему только обращаются по ссылке; версии заявления не нужны.

## Условия пересмотра

- Сервис печатных форм BTS не готов к сроку MVP возвратов.
- Регулятор, юристы или бухгалтерия требуют электронную подпись заявления или хранение всех его версий.
- В заявление добавляется полный номер карты.

## Открытые вопросы

1. Сколько хранить PDF заявления: 1 год или 5 лет?
2. Нужен ли ГОСТ-шифрование для номера карты в 1С?
3. Как 1С аутентифицируется в сервисе печатных форм?
4. В каком поле обмена и в какой момент жизненного цикла заявки 1С передаёт на сайт и в RetailCRM ссылку на PDF?
5. Удаляется ли предыдущий PDF, когда сервис формирует новый по изменённым данным?
6. Печатает ли магазин заявление по тому же шаблону сервиса? В ADR-0011 — «переделываем на единый шаблон», на архкомитете прозвучало, что розница — отдельно.
7. Нужна ли ссылка на PDF заявления в админке сайта? На архкомитете ссылку в админке допустили, по `ADR-RET-096` в админке сайта доступ к заявлению не нужен.
