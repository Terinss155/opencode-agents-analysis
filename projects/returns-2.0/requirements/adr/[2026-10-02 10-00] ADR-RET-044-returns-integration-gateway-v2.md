## Контекст

В v1 (`ADR-RET-030`, 25.09.2026) Team Lead BSA предложил вести обмены по возвратам через новый шлюз
(gateway). Head of PMO поставила условие: если переделку не успеть в этом квартале — текущая схема.

Сейчас обмен заказами идёт по цепочке RetailCRM — сайт — 1С в обе стороны. Прямой интеграции
RetailCRM ↔ 1С нет.

## Решение

Обмен возвратами идёт через сайт: сайт — центральная система между RetailCRM и 1С. Прямой
интеграции RetailCRM ↔ 1С по возвратам не будет.

Возврат — новый тип заказа и новый объект в каждой системе. Обмен новый, но на тех же механизмах,
что обмен заказами. Сайт:
- дорабатывает модель хранения под новый тип заказа и новые свойства;
- создаёт в 1С документ возврата по возвратному заказу.

Требования к обмену RetailCRM ↔ сайт готовят совместно: каждая сторона составляет свой список полей
по своим потребностям, затем стороны синхронизируются.

## Последствия

### Положительные

- Используются отработанные механизмы обмена заказами.
- Проект не зависит от решения архитектурного комитета по шлюзу.

### Отрицательные и риски

- Сохраняется архитектурно слабая схема, которую команда разработки считает требующей переписывания.
- Растёт объём работ сайта: новый тип заказа, свойства, создание документа в 1С.
- Отказ от шлюза для этого проекта на встрече не проговаривался явно. Решение выведено из того, что
  сайт назван центральной системой.

## Рассмотренные альтернативы

### Обмены по возвратам через новый шлюз (решение v1)

- **Результат:** не используется в этом проекте.
- **Причина:** на встрече 02.10.2026 согласована схема через сайт.

### Прямая интеграция RetailCRM ↔ 1С

- **Результат:** отклонена.
- **Причина:** такой интеграции нет, обмен идёт через сайт.

## Условия пересмотра

- Архитектурный комитет утверждает шлюз для обменов по возвратам до начала разработки.
