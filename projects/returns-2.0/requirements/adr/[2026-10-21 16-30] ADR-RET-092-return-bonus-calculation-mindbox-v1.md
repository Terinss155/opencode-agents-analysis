# ADR-RET-092: Баллы к возврату считаются калькуляцией заказа Mindbox с разделением позиции на строки, возврат фиксируется обновлением заказа

| Поле | Значение |
|---|---|
| **Статус** | Предложено |
| **Дата решения** | Не определена |
| **Владелец решения** | Не определён |
| **Область** | Интеграция |
| **Версия** | v1 |

## Контекст

На экране оформления возврата показывается «Баллы к возврату» за выбранные изделия. Баллы к
возврату считает Mindbox, монолит передаёт ему выбранные изделия
([refund-bonus_questions.md](../questions/refund-bonus_questions.md), решение 7). Баллы
возвращаются при «Возврат принят» и только за принятые изделия (`ADR-RET-091`).

Ограничения:

- Одинаковые изделия хранятся в заказе одной позицией с количеством. Списанные баллы известны на
  всю позицию; отдельного идентификатора изделия нет.
- По одному заказу возможно несколько заявок на возврат, в том числе по одной позиции
  (`ADR-RET-073`).
- Отдельной операции возврата в Mindbox сайт не вызывает. Операция `ReturnOrder` относится к
  устаревшей интеграции.

Описание методов в ТЗ программы лояльности:

| Операция | Что описано | Чего в ТЗ нет |
|---|---|---|
| `Website.CalculateAuthorizedCart` — предварительный расчёт заказа | Строки заказа: `lineId`, `lineNumber`, `quantity`, статус строки, сумма баллов к списанию `bonusPoints[].amount`. Mindbox может разделить строку на несколько с одинаковым `lineId`; клиент присваивает каждой новой строке свой идентификатор для последующих запросов | ID существующего заказа в запросе; поля ответа `bonusPointsChanges.spentAmount`, `bonusPointsChanges.earnedAmount`, `lines[].appliedPromotions.spentBonusPointsAmount` |
| `Website.UpdateOrderv2` — обновление статуса заказа | ID заказа в Mindbox и на сайте; строки: товар, количество, статус строки, `positionStatus` | Сумма баллов `bonusPoints.amount`; `lineId` и `lineNumber` строк |
| `BeginAuthorizedOrderTransaction` — создание чека авторизованного клиента | Создание заказа со строками `lineNumber`, `lineId` | Применение к возврату |

AS-IS монолита: калькуляция корзины и обновление заказа идут через сервис-прослойку. В
калькуляцию монолит передаёт ID пользователя, баллы и позиции с `line_id`, без ID заказа. В
обновление заказа — ID заказа, позиции с `line_id`, статусом и количеством и сумму баллов
`bonuses`. Какие операции Mindbox вызывает прослойка — не определено.

## Решение

Предварительный расчёт баллов к возврату и фиксация возврата выполняются стандартными операциями
заказа Mindbox, без отдельной операции возврата.

1. **Расчёт.** Перед экраном с суммами монолит вызывает калькуляцию заказа
   `Website.CalculateAuthorizedCart` по существующему заказу. Передаёт ID заказа, актуальный состав
   заказа, количество и статусы строк, текущую сумму списанных баллов. Позиция, из которой
   возвращается часть одинаковых изделий, делится на две строки: остающиеся изделия с исходным
   статусом и возвращаемые изделия со статусом возврата.
2. **Показ.** В «Баллы к возврату» выводится `bonusPointsChanges.spentAmount`.
3. **Фиксация.** При «Возврат принят» монолит вызывает операцию обновления заказа с составом и
   статусами строк, как в расчёте, по принятым изделиям. В сумму баллов передаётся остаток
   списанных баллов за изделия, которые клиент оставляет: сумма
   `lines[].appliedPromotions.spentBonusPointsAmount` по этим строкам.
4. **Повторный возврат.** Следующий расчёт по заказу ведётся от актуального состояния заказа в
   Mindbox и оставшейся суммы списанных баллов.

## Последствия

### Положительные

- Один расчёт для экрана и для фактического возврата баллов: «Баллы к возврату» совпадают с
  начислением.
- Деление баллов на одинаковые изделия и учёт прошлых возвратов выполняет Mindbox; монолит баллы
  не делит.
- Используются действующие операции Mindbox и действующие вызовы монолита; новая операция в
  Mindbox не нужна.

### Отрицательные и риски

- Калькуляция в прослойке сейчас не принимает ID заказа: нужна доработка прослойки и монолита.
- Передача суммы баллов и номеров строк в `Website.UpdateOrderv2` в ТЗ не описана; подтверждено
  только перепиской с Mindbox.
- Монолит хранит соответствие строк Mindbox изделиям после разделения позиции: Mindbox может
  вернуть несколько строк с одинаковым `lineId`.
- При делении остаётся остаток: в примере Mindbox на 3 изделия со 100 баллами приходится 33 + 66.
- Код статуса Mindbox для строки возврата не определён; сейчас статус для Mindbox один на всю
  позицию.
- По описанию в ТЗ калькуляция применяет промоакции, активные в момент расчёта. Если по
  существующему заказу применяются текущие акции, а не действовавшие при покупке, баллы к возврату
  посчитаются неверно.
- Расчёт зависит от доступности Mindbox в момент открытия экрана.

## Рассмотренные альтернативы

### Отдельная операция возврата в Mindbox

- **Результат:** отклонена.
- **Причина:** `ReturnOrder` относится к устаревшей интеграции; Mindbox рекомендует стандартную
  калькуляцию заказа.

### Расчёт баллов к возврату в монолите

- **Результат:** отклонена.
- **Причина:** баллы списывает и возвращает Mindbox; собственный расчёт монолита может разойтись с
  фактическим возвратом (решение 7 в
  [refund-bonus_questions.md](../questions/refund-bonus_questions.md)).

### Передача позиции целиком с уменьшенным количеством, без разделения на строки

- **Результат:** отклонена.
- **Причина:** статус передаётся на всю строку; возврат части одинаковых изделий через статус
  позиции не передать.

## Условия пересмотра

- Прослойка или Mindbox не поддерживают расчёт по ID существующего заказа.
- `Website.UpdateOrderv2` не принимает сумму баллов или номера строк.
- Mindbox вводит отдельную операцию расчёта или фиксации возврата.
