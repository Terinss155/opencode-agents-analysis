# ADR-RET-065: Одинаковые единицы в одной строке заказа — повторная заявка на оставшиеся единицы в MVP через Дружбу

## Контекст

В заказе одинаковые единицы (одна модель, цвет, размер, баркод) хранятся одной строкой с количеством
больше одного. В заявке на возврат каждая единица — отдельная запись со своей причиной (`ADR-RET-012`).

При подаче заявки меняется статус позиции исходного заказа (`ADR-RET-039`). Статус хранится на
строке, поэтому он меняется сразу у всех единиц строки. При следующем оформлении сайт определяет
доступные для возврата единицы по статусу позиции и исключает позиции с действующей заявкой. Остальные
единицы этой строки клиенту больше не показываются.

Разбиение одинаковых позиций на отдельные строки в RetailCRM включается глобальной настройкой. Ранее
RetailCRM оценил это как крупную доработку; в MVP разбиение не делается (`ADR-RET-028`).

## Решение

1. В MVP статус позиции исходного заказа меняется у всей строки, как сейчас.
2. Если по строке с количеством больше одного уже есть действующая заявка, оставшиеся единицы этой
   строки клиент повторно в ЛК и МП не оформляет. Их возврат проводит Дружба вручную.
3. Несколько действующих заявок на разные позиции одного заказа допускаются.
4. Возврат одинаковых единиц разными заявками, с разными причинами и статусами — в следующей
   реализации, после разбиения позиций по строкам.

## Последствия

### Положительные

- Не нужно менять модель строк заказа и настройку RetailCRM в MVP.
- Нельзя оформить вторую заявку на уже заявленную единицу.

### Отрицательные и риски

- Клиент не может сам вернуть оставшиеся единицы строки: нагрузка на Дружбу.
- Клиенту нужно объяснить, почему оставшиеся единицы недоступны. Текст не определён.

## Рассмотренные альтернативы

### Признак «есть заявка на возврат» вместо смены статуса позиции

- **Результат:** отклонена.
- **Причина:** Дружбе и клиенту нужен статус позиции в исходном заказе (`ADR-RET-039`; подтверждено
  12.10.2026).

### Всегда разбивать одинаковые позиции по строкам чека в RetailCRM

- **Результат:** отложена.
- **Причина:** предложение Team Lead BSA; настройка глобальная, событийно её переключать, вероятно,
  нельзя. Нужно отдельное обсуждение с RetailCRM.

### Показывать клиенту на фронте отдельные строки без смены модели заказа

- **Результат:** отклонена.
- **Причина:** статус всё равно меняется у всей строки, поэтому расчёт оставшихся единиц неверен.

## Условия пересмотра

- RetailCRM подтвердит разбиение одинаковых позиций по строкам для заказов с возвратом.
- Доля обращений в Дружбу по повторному возврату одинаковых единиц станет заметной для отдела.
