# ADR-RET-093: В запросе дат и интервалов курьера полный адрес передаётся по частям — для доставки и для возврата; код города не передаётся

## Контекст

Адрес клиента для возврата передаётся в логистику как адрес отправки, а не адрес доставки
(`ADR-RET-060`). Для дат СДЭК нужен полный адрес с улицей и домом; код города не подходит. В v1
полный адрес передавался одной строкой. Командам сайта и мобильного приложения, которые дорабатывают
прямой поток, собирать адрес в одну строку на разных клиентах проблематично. По их просьбе
логистика принимает адрес по частям: доработка метода `Intervals` — задача TNT-2876. Возвратный
поток делается по аналогии с прямым: признак возврата и адрес отправки — задача TNT-2837.

Адрес в данных сайта и приложения:

- в детализации адреса из геосервиса дом с корпусом и строением приходит и одним полем
  (`house.title`, например «д. 23А, стр 1»), и раздельно (`building` — дом и литера, `block` —
  строение и корпус);
- в сохранённых адресах сайта и приложения корпус и строение хранятся в номере дома; отдельных
  полей для корпуса и квартиры нет;
- Mobile API Gateway сейчас не передаёт в логистику ни адрес доставки, ни адрес отправки, ни
  признак возврата, поэтому смена типа поля ничего не ломает.

## Решение

1. В запросе дат и интервалов курьера передаётся полный адрес — и для прямого потока, и для
   возврата. Код города (ФИАС) не передаётся.
2. Адрес передаётся объектом по частям, без сборки строки на стороне сайта, приложения или
   монолита: страна (ISO-код, по умолчанию RU), регион, город, улица, дом.
3. Корпус и строение передаются в том же поле, что и номер дома. Квартира не передаётся.
4. Для доставки адрес передаётся как адрес доставки, для возврата — как адрес отправки вместе с
   признаком возврата. Правило одно для сайта и мобильного приложения.

## Последствия

### Положительные

- Сайту, приложению и монолиту не нужно собирать строку адреса и согласовывать её формат.
- Адрес из детализации геосервиса и сохранённый адрес передаются одинаково — по полям.
- Структура адреса подходит для новых ТК, которым нужен адрес по полям (условие пересмотра v1).

### Отрицательные и риски

- Задачи на прямой поток, написанные под строку, переписываются: шлюз МП и монолит (ECOMDEV-2559).
- В поле дома адреса из заказа встречается квартира («210 кв 85»): лишние данные могут помешать
  получить даты СДЭК.
- Отдельное поле для корпуса и строения не заводится; если ТК потребует их раздельно, контракт
  придётся расширять.

## Рассмотренные альтернативы

### Полный адрес одной строкой (v1)

- **Результат:** отклонена.
- **Причина:** сборка строки на разных клиентах проблематична; команды прямого потока попросили
  передавать адрес по частям.

### Части адреса вместе с полной строкой, собранной на стороне клиента

- **Результат:** отклонена.
- **Причина:** сборка строки на клиенте — то, от чего уходит решение; логистике достаточно частей.

### Корпус и строение отдельным полем

- **Результат:** отклонена.
- **Причина:** сайт и приложение хранят корпус и строение в номере дома; отдельное поле потребовало
  бы разбора номера дома на клиенте.

## Условия пересмотра

- СДЭК или новая ТК не возвращает даты при корпусе и строении в поле дома.
- Сайт или приложение начинают хранить корпус и строение отдельно от номера дома.
- СДЭК начнёт отдавать конкретные интервалы для возврата — проверить, что адреса по частям
  достаточно.
