# ADR-RET-113: Сайт не подтверждает реквизиты возвратов, оформленных через Дружбу в RetailCRM, и передаёт в 1С `null`

## Контекст

На этапе 0 сайт и МП передают в 1С признак `is_bank_details_confirmed`: клиент подтвердил банковские
реквизиты галочкой в форме (ECOMDEV-2649, ECOMDEV-2651). В v1 решили, что реквизиты, которые клиент
сообщил Дружбе, тоже считаются подтверждёнными, и для возвратов, оформленных через RetailCRM, сайт
ставит `true`.

Поставить `true` сайт может только по реквизитам, которые к нему пришли. Реквизиты возвратов,
оформленных через Дружбу, на сайт не попадают:

- в вебхуке RetailCRM реквизитов нет;
- сотрудники Дружбы не вносят и никогда не вносили реквизиты в поля заказа RetailCRM: клиент
  присылает реквизиты в чат или на почту, оператор прикладывает их к заказу файлом или пишет в
  комментарии, проверяет их сотрудник по возвратам. По мнению Head of Customer Service, переписывать
  реквизиты в поля — ручная работа с риском ошибки, за которую оператор отвечать не должен.

Сайт не может определить, что клиент сообщил и подтвердил реквизиты по возврату, оформленному через
Дружбу. Сработало условие пересмотра v1: RetailCRM не передаёт сайту реквизиты возврата.

Для «Возвратов 2.0» RetailCRM заложил в своё ТЗ передачу реквизитов заявки сайту: заявки, созданные в
RetailCRM, сайт передаёт в 1С. Возьмёт ли Дружба на себя ответственность за подтверждение реквизитов
клиентом и будет ли она заполнять поля реквизитов в RetailCRM, не определено: это выясняют Product
Manager и Project Manager.

## Решение

1. На этапе 0 признак подтверждения ставят только сайт и МП — по галочке клиента в форме реквизитов.
2. Для возврата, оформленного через Дружбу в RetailCRM, сайт подтверждение не ставит и передаёт в 1С
   `is_bank_details_confirmed = null` — подтверждение неизвестно.
3. В «Возвратах 2.0» для заявок, созданных Дружбой в RetailCRM, сайт тоже передаёт `null` — пока
   Product Manager и Project Manager не утвердят другое и Дружба не начнёт заполнять поля реквизитов
   в RetailCRM.

## Последствия

### Положительные

- Сайт не подтверждает за клиента реквизиты, которых не получал: признак `true` означает только
  подтверждение клиентом в форме.
- Дружбе не нужно менять процесс и переписывать реквизиты в поля заказа RetailCRM.
- Для этапа 0 не нужны доработки обмена с RetailCRM: приём реквизитов из вебхука, защита реквизитов
  в RetailCRM от перезаписи сайтом.

### Отрицательные и риски

- Для возвратов через Дружбу 1С и бухгалтерия получают `null` — как для старой версии МП и
  исторических данных. Подтверждение таких реквизитов сайт не фиксирует; проверка реквизитов остаётся
  за сотрудником по возвратам.
- Если в «Возвратах 2.0» решат подтверждать реквизиты заявок Дружбы, приём реквизитов из RetailCRM
  заработает только после того, как Дружба начнёт заполнять поля реквизитов.

## Рассмотренные альтернативы

### Возврат через RetailCRM считается подтверждением, сайт ставит `true` (v1)

- **Результат:** отклонена.
- **Причина:** реквизиты возвратов через Дружбу на сайт не приходят, поэтому сайту не по чему
  ставить `true`.

### Дружба вносит реквизиты в поля заказа RetailCRM, RetailCRM передаёт их сайту

- **Результат:** отклонена для этапа 0.
- **Причина:** Дружба поля реквизитов не заполняет; для этапа 0 потребовались бы доработки
  вебхука RetailCRM и обмена на сайте.

## Условия пересмотра

- Product Manager и Project Manager утвердят, что Дружба отвечает за подтверждение реквизитов клиентом,
  и Дружба начнёт заполнять поля реквизитов в заказе RetailCRM.
- Бухгалтерия или ИБ потребуют, чтобы у возвратов через Дружбу подтверждение фиксировалось в 1С.
