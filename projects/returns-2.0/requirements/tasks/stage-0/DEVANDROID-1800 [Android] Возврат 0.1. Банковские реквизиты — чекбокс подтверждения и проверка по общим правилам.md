# DEVANDROID-1800: [Android] Возврат 0.1. Банковские реквизиты: чекбокс подтверждения и проверка по общим правилам

## Цель

Добавить на экран реквизитов чекбокс подтверждения и проверку полей по общим правилам и передавать подтверждение в запросе оформления возврата, чтобы в возврат попадали проверенные клиентом реквизиты.

## Описание реализации

Бэкенд: ECOMDEV-2526 (правило «нужны реквизиты», формат реквизитов), ECOMDEV-2649 (параметр `is_bank_details_confirmed` в `POST /mobile/orders/{order_id}/return`). Задача iOS с тем же поведением — DEVIOS-2709. Ниже — целевое поведение экрана; если текущая реализация Android уже ему соответствует, доработка этой части не нужна.

### 1. Показ блока реквизитов

Нужны ли реквизиты, решает бэкенд: признак `return.is_bank_data_required` в данных заказа (`GET /api/orders/{order_id}` через ESB). Своей логики по способу оплаты в приложении нет и не добавляется.

1. Экран «Способ возврата», блок «Банковские реквизиты» — показывается только при `is_bank_data_required = true`. Если признак не пришёл в данных заказа, блок показывается, как сейчас.
2. Кнопка оформления возврата на экране «Способ возврата» — при `is_bank_data_required = true` и незаполненных, неверных или неподтверждённых реквизитах подсвечивает блок реквизитов и прокручивает экран к нему.

Правило признака меняется на бэкенде (ECOMDEV-2526): блок начнёт показываться и для заказов с подарочным сертификатом.

### 2. Экран «Банковские реквизиты»

Макет экрана: [Figma — «Банковские реквизиты»](https://www.figma.com/design/u5Fe5N4lypCdqgZn6533F2/%F0%9F%93%B1-06.-Profile--Redesign-?node-id=7243-47024)

1. Поле «ИНН банка» удалено.
2. Поле «Номер банковской карты» показывается, только если номер лицевого счёта начинается с {red}(`30232810`) (кредитный счёт).
3. Поля проверяются по правилам из таблицы ниже, ошибка показывается под полем.
4. Под полями — чекбокс подтверждения реквизитов.
5. Кнопка «Готово» доступна, только если все видимые поля прошли проверку и чекбокс отмечен.

**Правила проверки полей**

| Поле | Правило | Текст ошибки |
|---|---|---|
| Фамилия получателя | обязательно, до 255 символов | «Заполните это поле» |
| Имя получателя | обязательно, до 255 символов | «Заполните это поле» |
| Отчество получателя | обязательно, до 255 символов | «Заполните это поле» |
| Название банка | обязательно, до 255 символов | «Заполните это поле» |
| БИК банка | обязательно, ровно 9 цифр | «Неверный формат БИК» |
| Номер лицевого счёта | обязательно, ровно 20 цифр | «Неверный формат номера счета» |
| Номер банковской карты | только при кредитном счёте: обязательно, ровно 16 цифр | «Неверный формат карты» |

- Пустое обязательное поле — «Заполните это поле». Тексты совпадают с сайтом.
- Маски ввода и цифровая клавиатура для БИК, счёта и карты не меняются.
- Ссылки и теги в ФИО и названии банка проверяет только бэкенд, его ошибка показывается по разделу 4.
- При выходе из поля с неверным значением под полем показывается ошибка; при вводе ошибка скрывается, как только значение начинает проходить правило. Отображение ошибки — по макету экрана. {red}(Нужны ли тексты ошибок под полями на этапе 0 — открытый вопрос 3.)

**Кредитный счёт и поле «Номер банковской карты»**

- Кредитный счёт — номер лицевого счёта, первые 8 цифр которого `30232810` {red}(подтверждение бухгалтерии — открытый вопрос 2). Символы маски не учитываются, сравниваются только цифры.
- Поле «Номер банковской карты» по умолчанию скрыто и показывается, как только первые 8 цифр введённого номера счёта — `30232810`. Пример: `30232810…` → поле показывается; `40817810…` → поле скрыто.
- Если клиент изменил начало счёта и счёт перестал быть кредитным, поле карты скрывается, введённый номер карты не проверяется и не отправляется.

**Чекбокс подтверждения**

- Чекбокс — новый элемент экрана, внешний вид — по макету.
- Текст: «Подтверждаю корректность указанных мной банковских реквизитов» — как на сайте.
- По умолчанию не отмечен. Отметка — действие клиента, предзаполнять её нельзя.
- Отметка сохраняется вместе с реквизитами: при повторном открытии экрана чекбокс отмечен.
- Изменение любого поля снимает отметку: клиент подтверждает реквизиты в том виде, в котором они уйдут в возврат.

### 3. Оформление возврата

При оформлении возврата в `POST /api/orders/{order_id}/return` (через ESB → `POST /mobile/orders/{order_id}/return`) передавать:

- при `is_bank_data_required = true` — реквизиты и новый параметр `is_bank_details_confirmed = true` (будет добавлен в рамках задачи ECOMDEV-2649); `bank_inn` не передаётся; `user_card_number` — только при кредитном счёте;
- при `is_bank_data_required = false` — без реквизитов и без `is_bank_details_confirmed`, как сейчас;
- передача остальных параметров и заголовков платформы и версии приложения аналогична текущей реализации.

| Параметр | Место | Тип данных | Значение |
|---|---|---|---|
| `is_bank_details_confirmed` | `body` | `boolean` | `true` — чекбокс отмечен |

Начиная с версии Android {red}(`*.**.*`) подтверждение реквизитов обязательно: при `is_bank_data_required = true` бэкенд отклоняет возврат без `is_bank_details_confirmed = true` {red}(версия — открытый вопрос 1).

### 4. Ошибки от бэкенда

При ошибке оформления возврата приложение показывает пользователю текст ошибки из ответа, как сейчас; формат ответа с ошибкой бэкенд не меняет. Новые тексты от бэкенда:

- «Подтвердите банковские реквизиты» — реквизиты нужны, а подтверждение не передано;
- ошибки формата реквизитов по правилам ECOMDEV-2526, в том числе по ссылкам и тегам в ФИО и названии банка.

Выпускать версию приложения после релиза бэкенда ECOMDEV-2526 и ECOMDEV-2649: текущий бэкенд требует ИНН и номер карты при любом счёте и отклонит возврат без них. Номер версии с чекбоксом сообщить в ECOMDEV-2649: от него зависит, сможет ли бэкенд требовать подтверждение начиная с этой версии.

## Тестирование

{% cut "Критерии приёмки" %}

**Показ блока реквизитов**

1. `is_bank_data_required = true` → блок «Банковские реквизиты» показывается; возврат нельзя оформить, пока реквизиты не заполнены, не прошли проверку и не подтверждены: блок подсвечивается, экран прокручивается к нему.
2. `is_bank_data_required = false` → блок не показывается, возврат оформляется без реквизитов, как раньше.

**Экран реквизитов**

3. Поля «ИНН банка» нет; подписи, маски и клавиатуры остальных полей не изменились.
4. Неверное значение любого поля из таблицы раздела 2 даёт ошибку под полем с текстом из таблицы при выходе из поля; ошибка скрывается, как только значение исправлено. Счёт короче 20 цифр даёт ошибку.
5. Поле «Номер банковской карты» скрыто, пока номер счёта не начинается с `30232810`; при таком счёте поле показывается и обязательно. Если счёт изменён на некредитный, поле скрывается и не мешает «Готово».
6. Чекбокс по умолчанию не отмечен; «Готово» недоступна, пока хотя бы одно видимое поле не проходит проверку или чекбокс не отмечен.
7. При повторном открытии экрана отметка сохраняется; изменение любого поля снимает отметку.

**Оформление возврата**

8. `is_bank_data_required = true` → в запросе переданы реквизиты и `is_bank_details_confirmed = true`; `bank_inn` не передан; `user_card_number` передан только при кредитном счёте.
9. Реквизиты, которые принимает экран, не получают от бэкенда ошибок формата (кроме ссылок и тегов в ФИО и названии банка).
10. Бэкенд отклонил возврат → пользователю показан текст ошибки из ответа.
