# ECOMDEV-2649: [B] Возврат 0.1. Реквизиты и подтверждение клиента в запросе создания возврата

## Цель

Сохранять в заказе реквизиты и подтверждение клиента из запроса создания возврата на сайте и в МП и рассчитывать признак возврата на исходный способ оплаты.

## Описание реализации

**Endpoint**

- Web:
  - `POST /orders/refund/save-reason`
- Mobile API — метод Site дорабатывается в этой задаче; Gate `core.12stz.*` (ESB) передаёт тело запроса и заголовки `x-platform`, `version` (как `x-version`) без изменений, код гейта не дорабатывается {red}(обновление swagger гейта — открытый вопрос 4):
  - Gate `POST /api/orders/{order_id}/return` → Site `POST /mobile/orders/{order_id}/return`

{red}(Версии МП с чекбоксом подтверждения реквизитов: iOS с `*.**.*`, Android с `*.**.*`. Начиная с них подтверждение обязательно — раздел 3, шаг 3. Версии не определены — открытый вопрос 1, заполнить до выкатки.)

### Контекст

1. Сайт сохраняет реквизиты отдельным запросом `POST /user/cabinet/return-item/ajax/check-bank-details` в `cms_users_refund`, а возврат создаёт без реквизитов в запросе: бэкенд копирует в `cms_orders.user_refund` последнюю запись пользователя из `cms_users_refund`, если заказ оплачен не онлайн. Поэтому к возврату могут попасть устаревшие реквизиты, а в BNPL-заказ — реквизиты из прошлых возвратов клиента.
2. Запрос `POST /orders/refund/save-reason` принимает только `positions`, остальные поля отбрасываются.
3. МП передаёт реквизиты в теле запроса и сохраняет их в заказ, если заказ оплачен не онлайн. Подтверждения реквизитов клиентом нет ни на сайте, ни в МП.

Ограничения, текущие методы не позволяют:

1. принять реквизиты и подтверждение клиента в запросе создания возврата на сайте;
2. принять подтверждение реквизитов в запросе МП;
3. сохранить реквизиты в заказ с онлайн-оплатой, если при оплате использован подарочный сертификат;
4. сохранить признак того, что деньги возвращаются на исходный способ оплаты.

### Необходимо

1. Добавить поле `is_refund_to_original_payment_method` в `cms_orders` и `cms_orders_history` — раздел 1.
2. Добавить параметры запроса: реквизиты и `is_bank_details_confirmed` в `POST /orders/refund/save-reason`, `is_bank_details_confirmed` в `POST /mobile/orders/{order_id}/return` — раздел 2.
3. Изменить проверку и сохранение реквизитов при создании возврата — раздел 3.
4. Рассчитывать `is_refund_to_original_payment_method` при каждом создании возврата — раздел 4.

После выкатки сайт не вызывает `POST /user/cabinet/return-item/ajax/check-bank-details` в сценарии возврата (ECOMDEV-2532): реквизиты приходят в `POST /orders/refund/save-reason`. Метод `check-bank-details` не меняется и не удаляется; других вызовов на сайте у него нет.

Вне этой задачи: общая проверка «нужны реквизиты» и общая проверка формата реквизитов — ECOMDEV-2526; передача признаков в 1С — ECOMDEV-2651; форма сайта — ECOMDEV-2532; экраны приложения — DEVIOS-2709, DEVANDROID-1800.

Значения признаков для 1С — ECOMDEV-2651.

#### 1. Новые данные БД

| Поле | Тип | Обяз-ть | Описание |
|---|---|---|---|
| `cms_orders.is_refund_to_original_payment_method` | `boolean` | `NOT NULL`, по умолчанию `false` | Деньги по возврату возвращаются на исходный способ оплаты. Заполняет бэкенд при создании возврата — раздел 4 |
| `cms_orders_history.is_refund_to_original_payment_method` | `boolean` | `NOT NULL`, по умолчанию `false` | Значение поля заказа в истории изменений |

Каждое изменение `cms_orders.is_refund_to_original_payment_method` записывается в `cms_orders_history`. Значение по умолчанию — `false`, так как триггер истории не замечает переход «пусто → значение».

Способ реализации, согласованный с разработкой: поле создаётся в двух таблицах с `NOT NULL` и `DEFAULT false` по аналогии с `is_rcrm_modified_before_payment`; триггеры истории пересоздаются по аналогии с добавлением полей `status_yandex_pay` и `yandex_pay_url`.

{red}(Существующие заказы при добавлении поля получат `false`, в том числе заказы с возвратом, оформленным до внедрения признака. Как их обрабатывать — открытый вопрос 2 (1С-12), согласовать до выкатки.)

#### 2. Параметры

**`POST /orders/refund/save-reason`** — новые параметры в теле запроса. Параметр `positions` не меняется.

| Параметр | Место | Тип данных | Обязательность | Описание |
|---|---|---|---|---|
| `surname` | `body` | `string` | да* | Фамилия держателя счёта |
| `name` | `body` | `string` | да* | Имя держателя счёта |
| `patronymic` | `body` | `string` | да* | Отчество держателя счёта |
| `bank_name` | `body` | `string` | да* | Название банка |
| `bank_bic` | `body` | `string` | да* | БИК банка |
| `user_account` | `body` | `string` | да* | Номер лицевого счёта |
| `user_card_number` | `body` | `string` | да** | Номер банковской карты |
| `is_bank_details_confirmed` | `body` | `boolean` | да* | Клиент подтвердил реквизиты. Допустимо только `true` |

\* Если реквизиты нужны по общей проверке ECOMDEV-2526.

\*\* Если реквизиты нужны и `user_account` начинается с любого префикса из параметра CMS `refund_credit_account_prefixes` (кредитный счёт; список и значение по умолчанию `30232810` — ECOMDEV-2526).

Новые параметры объявляются в форме запроса: без этого они не дойдут ни до проверки, ни до заказа.

ИНН банка сайт не передаёт: поле убрано из формы. При сохранении реквизитов с сайта ключ `bank_inn` в `cms_orders.user_refund` записывается пустой строкой `""`, чтобы в 1С и RetailCRM `bank_inn` по-прежнему уходил пустым.

#### 3. Проверка и сохранение реквизитов

Шаги выполняются при создании возврата на сайте и в МП последовательно. Если на шаге 2 или 3 возвращается ошибка, возврат не создаётся, `cms_orders.user_refund` и `cms_orders.is_refund_to_original_payment_method` не меняются.

1. Определить по заказу, нужны ли реквизиты, общей проверкой ECOMDEV-2526.
2. Сайт: если реквизиты нужны — проверить их общей проверкой формата ECOMDEV-2526; если поле не прошло проверку, вернуть ошибку валидации по этому полю в текущем формате ответа (`success = false`). В МП эта проверка применяется в рамках ECOMDEV-2526.
3. Если реквизиты нужны — проверить `is_bank_details_confirmed`:
   - сайт: параметр не передан или не равен `true` → вернуть ошибку валидации по полю `is_bank_details_confirmed` с текстом «Подтвердите банковские реквизиты»;
   - МП — по значению параметра:
     - `true` (новые версии приложения, клиент отметил чекбокс) → продолжить;
     - `false` → вернуть ошибку в текущем формате с текстом «Подтвердите банковские реквизиты»;
     - параметр не передан — по версии приложения:
       - версия не ниже пороговой: iOS {red}(`*.**.*`), Android {red}(`*.**.*`) — версии с чекбоксом → вернуть ошибку в текущем формате с текстом «Подтвердите банковские реквизиты»;
       - версия ниже пороговой (старые версии без чекбокса), заголовки версии не переданы или версия не распознана → продолжить, в заказ сохранить `null`; ошибки сервера нет.

   Версия определяется существующей проверкой версии МП по заголовкам `x-platform` и `x-version` — той же, что скрывает Яндекс Pay и Яндекс СБП в старых версиях. {red}(Пороговые версии — открытый вопрос 1.)

   Ограничение: возврат без подтверждения оформляется из старых версий без чекбокса, а также при отсутствующей или нераспознанной версии.
4. Если реквизиты нужны — сохранить в JSON `cms_orders.user_refund` реквизиты из запроса и ключ `is_bank_details_confirmed`; прежнее значение `cms_orders.user_refund` перезаписывается целиком:
   - `is_bank_details_confirmed`: сайт — `true`; МП — переданное `true` или `null`, если параметр не передан;
   - номер карты — только если `user_account` начинается с любого префикса из параметра `refund_credit_account_prefixes` (список читает тот же сервис, что и проверка ECOMDEV-2526); при другом счёте номер карты из запроса отбросить;
   - сайт: запись пользователя в `cms_users_refund` не читать и не изменять.
5. Если реквизиты не нужны:
   - сайт — реквизиты и `is_bank_details_confirmed` не проверять и в `cms_orders.user_refund` не записывать, даже если они переданы; реквизиты из `cms_users_refund` в заказ не подставлять, в том числе в BNPL-заказ;
   - МП — как сейчас.

   {red}(Что делать с реквизитами, которые остались в `cms_orders.user_refund` от предыдущего возврата по этому заказу, — открытый вопрос 3.)
6. Рассчитать `is_refund_to_original_payment_method` по разделу 4 и сохранить вместе с созданием возврата — при любом результате шага 1.
7. Далее — существующая логика создания возврата, не меняется.

#### 4. Расчёт `is_refund_to_original_payment_method`

Признак рассчитывается по заказу:

- `true` — заказ оплачен одним из способов из таблицы ниже и при оплате не использован подарочный сертификат (условие использования сертификата — из общей проверки ECOMDEV-2526);
- `false` — во всех остальных случаях.

| Способ оплаты | Код |
|---|---|
| Онлайн на сайте | 1 |
| СБП | 16 |
| Яндекс Pay | 19 |
| Яндекс СБП | 20 |
| Яндекс цифровой рубль | 21 |
| Долями | 13 |
| Подели | 14 |
| Сплит | 17 |

Повторный возврат по заказу пересчитывает и перезаписывает признак.

> Ограничение: у возвратов, оформленных в RetailCRM или 1С, признак остаётся `false` — сайт пока не принимает такие возвраты.

### Обратная совместимость

- Ответы `POST /orders/refund/save-reason` и `POST /mobile/orders/{order_id}/return` при успехе не меняются; формат ответа с ошибкой прежний.
- Сайт: если реквизиты не нужны, запрос с одним `positions` обрабатывается как сейчас. Если реквизиты нужны, поведение меняется намеренно — по разделу 3.
- Для текущих версий МП изменения обратно совместимы: для версий ниже пороговой новый параметр запроса необязателен. Обязательным он становится только для версий не ниже пороговых — в них появляется чекбокс.

Выкатывать одним релизом с ECOMDEV-2526 и ECOMDEV-2532: без общей проверки ECOMDEV-2526 нет правила «нужны реквизиты» для шагов 1–2, а без ECOMDEV-2532 сайт не передаёт реквизиты и подтверждение и не сможет создать возврат, для которого они нужны. Версии МП с чекбоксом выходят после этого релиза.

## Тестирование

{% cut "Критерии приёмки" %}

**Предусловия:** заказы, для которых реквизиты нужны (оплата курьеру; онлайн-способ с подарочным сертификатом), и заказы, для которых не нужны (онлайн-способы без сертификата и BNPL); у пользователя есть запись в `cms_users_refund` с реквизитами, отличными от переданных в запросе; номера счёта, которые начинаются и не начинаются с префикса из списка `refund_credit_account_prefixes` (по умолчанию `30232810`); запросы МП без заголовков версии, с версией ниже и не ниже пороговой.

**Сайт, реквизиты нужны**

1. Корректные реквизиты и `is_bank_details_confirmed = true` → возврат создан; в `cms_orders.user_refund` — реквизиты из запроса, `bank_inn: ""` и `is_bank_details_confirmed: true`; запись `cms_users_refund` не изменилась.
2. Реквизит не прошёл проверку формата (например, БИК не из 9 цифр) → возврат не создан, ошибка по этому полю, `success = false`.
3. `is_bank_details_confirmed` не передан или `false` → возврат не создан, ошибка по полю `is_bank_details_confirmed` с текстом «Подтвердите банковские реквизиты»; `cms_orders.user_refund` и `is_refund_to_original_payment_method` в заказе не изменились.
4. Передан только `positions` при наличии записи в `cms_users_refund` → возврат не создан, ошибки по полям реквизитов.

**Сайт, реквизиты не нужны**

5. Передан только `positions` или переданы реквизиты с подтверждением → возврат создан, `cms_orders.user_refund` не изменился.
6. BNPL-заказ при наличии записи в `cms_users_refund` → возврат создан, реквизиты из `cms_users_refund` в заказ не попали.

**МП, реквизиты нужны**

7. `is_bank_details_confirmed = true` → возврат создан, в `cms_orders.user_refund` — реквизиты и `true`.
8. `is_bank_details_confirmed = false` → возврат не создан, ошибка с текстом «Подтвердите банковские реквизиты».
9. Параметр не передан, версия iOS или Android ниже пороговой, заголовков версии нет или версия не распознана → возврат создан, в `cms_orders.user_refund` — реквизиты и `is_bank_details_confirmed: null`.
10. Параметр не передан, версия iOS или Android не ниже пороговой → возврат не создан, ошибка с текстом «Подтвердите банковские реквизиты».
11. Заказ с онлайн-оплатой и сертификатом → реквизиты из запроса записаны в `cms_orders.user_refund`.

**МП, реквизиты не нужны**

12. Возврат создаётся как сейчас; `is_bank_details_confirmed` не проверяется.

**Номер карты**

13. Счёт начинается с префикса из списка `refund_credit_account_prefixes` (по умолчанию `30232810`), номер карты из 16 цифр → номер карты записан в `cms_orders.user_refund` на сайте и в МП. Счёт не начинается ни с одного префикса из списка, номер карты передан → возврат создан, номера карты в `cms_orders.user_refund` нет.

**Признак `is_refund_to_original_payment_method`**

14. В `cms_orders` и `cms_orders_history` есть поле `is_refund_to_original_payment_method`, `NOT NULL`, по умолчанию `false`.
15. Возврат на сайте и в МП по заказу, оплаченному способом 1, 16, 19, 20, 21, 13, 14 или 17 без сертификата, → признак `true`; по заказу с сертификатом или с оплатой курьеру → `false`.
16. Изменение признака записано в `cms_orders_history`; повторный возврат по заказу пересчитывает признак, а `cms_orders.user_refund` перезаписывается целиком реквизитами нового запроса, если они нужны.

**Совместимость**

17. Ответы обоих методов при успешном создании возврата не изменились; возврат через МП проверен на последней версии приложения из стора и на новой сборке.
18. Swagger монолита дополнен новыми параметрами `POST /orders/refund/save-reason` и параметром `is_bank_details_confirmed` `POST /mobile/orders/{order_id}/return`.
