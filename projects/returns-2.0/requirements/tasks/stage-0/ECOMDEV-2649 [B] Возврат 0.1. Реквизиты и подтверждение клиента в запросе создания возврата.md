# ECOMDEV-2649: [B] Возврат 0.1. Реквизиты и подтверждение клиента в запросе создания возврата

## Цель

Сейчас сайт создаёт возврат без реквизитов в запросе: бэкенд берёт последнюю сохранённую запись пользователя, поэтому к возврату могут попасть устаревшие реквизиты. Подтверждения реквизитов клиентом нет ни на сайте, ни в приложении.

Нужно сохранять в заказе реквизиты, которые клиент указал и подтвердил при оформлении возврата, вместе с признаком подтверждения, и рассчитывать признак возврата на исходный способ оплаты.

**Web:** `POST /orders/refund/save-reason`

**Mobile API:** Site `POST /mobile/orders/{order_id}/return` ← Gate `POST /api/orders/{order_id}/return` (`core.12stz.*`, ESB). Гейт передаёт тело запроса без изменений, его код не дорабатывается — только swagger.

Вне задачи: правило «нужны реквизиты» и формат полей — ECOMDEV-2526; передача признаков в 1С — ECOMDEV-2651; форма сайта и экран iOS — задачи фронта и iOS.

## Описание реализации

### 1. Новое поле в БД

| Таблица | Поле | Тип | Nullable | Default |
|---|---|---|---|---|
| `cms_orders` | `is_refund_to_original_payment_method` | `boolean` | нет | `false` |
| `cms_orders_history` | `is_refund_to_original_payment_method` | `boolean` | нет | `false` |

По аналогии с полем `is_rcrm_modified_before_payment`: поле в обеих таблицах, триггеры истории пересоздаются. Значение по умолчанию — `false`, так как триггер истории не замечает переход «пусто → значение».

### 2. Новые параметры запроса

**`POST /orders/refund/save-reason`** — параметры в теле запроса:

| Параметр | Тип | Обязательность | Описание |
|---|---|---|---|
| `surname` | `string` | да* | Фамилия держателя счёта |
| `name` | `string` | да* | Имя держателя счёта |
| `patronymic` | `string` | да* | Отчество держателя счёта |
| `bank_name` | `string` | да* | Название банка |
| `bank_bic` | `string` | да* | БИК банка |
| `bank_inn` | `string` | нет | ИНН банка |
| `user_account` | `string` | да* | Номер лицевого счёта |
| `user_card_number` | `string` | да** | Номер банковской карты |
| `is_bank_details_confirmed` | `boolean` | да* | Клиент подтвердил реквизиты. Допустимо только `true` |

\* Если реквизиты нужны по ECOMDEV-2526 §1. Формат полей — по ECOMDEV-2526 §2. Параметр `positions` не меняется.

\*\* Только если реквизиты нужны и номер лицевого счёта начинается с {red}(`30232810`) (кредитный счёт), по ECOMDEV-2526 §2. Для других счетов не передаётся; если передан — не сохраняется.

Пример тела запроса, когда реквизиты нужны:

```json
{
  "positions": [
    { "id": 123456, "reasonCode": "300" },
    { "id": 123457, "reasonCode": "305" }
  ],
  "surname": "Иванова",
  "name": "Анна",
  "patronymic": "Сергеевна",
  "bank_name": "ПАО Сбербанк",
  "bank_bic": "044525225",
  "bank_inn": "7707083893",
  "user_account": "40817810099910004312",
  "is_bank_details_confirmed": true
}
```

Когда реквизиты не нужны, тело запроса прежнее — только `positions`.

> Форма запроса сейчас принимает только `positions` и молча отбрасывает остальные поля. Новые параметры нужно объявить в форме с правилами проверки, иначе они не дойдут ни до проверки, ни до заказа.

**`POST /mobile/orders/{order_id}/return`** — новый необязательный параметр `is_bank_details_confirmed` (`boolean`). Старые версии приложения его не передают.

Ответы обоих методов не меняются.

### 3. Логика создания возврата

Нужны ли реквизиты, определяется по заказу по правилу ECOMDEV-2526 §1.

| | Сайт | МП |
|---|---|---|
| **Реквизиты не нужны** | Реквизиты и признак не проверяются и в заказ не записываются | Как сейчас |
| **Реквизиты нужны: проверка** | Поля проверяются по ECOMDEV-2526 §2. `is_bank_details_confirmed` обязателен и равен `true`. Таблица `cms_users_refund` не читается и не записывается | Реквизиты проверяются как сейчас. `false` → возврат не создаётся; параметр не передан → возврат создаётся |
| **Реквизиты нужны: сохранение** | В `cms_orders.user_refund` — реквизиты из запроса и `is_bank_details_confirmed: true` | В `cms_orders.user_refund` — реквизиты и переданное `true` или `null`, если параметр не передан |
| **Номер карты** | Сохраняется только при кредитном счёте (ECOMDEV-2526 §2) | То же: при некредитном счёте номер карты из запроса отбрасывается |

Реквизиты и признак хранятся в JSON `cms_orders.user_refund` одноимёнными ключами. Повторный возврат по заказу перезаписывает их целиком, как сейчас. Остальная логика создания возврата не меняется.

**Признак `is_refund_to_original_payment_method`** — рассчитывается по заказу при создании возврата на сайте и в МП и сохраняется в `cms_orders`:

- `true` — заказ оплачен одним из способов ниже и при оплате не использован подарочный сертификат (условие — как в ECOMDEV-2526 §1);
- `false` — все остальные случаи.

| Способ оплаты | Код |
|---|---|
| Онлайн на сайте | 1 |
| СБП | 16 |
| Яндекс Pay | 19 |
| Яндекс СБП | 20 |
| Яндекс цифровой рубль | 21 |
| Долями | 13 |
| Подели | 14 |
| Сплит | 17 |

Повторный возврат по заказу пересчитывает и перезаписывает признак. У возвратов, оформленных в RetailCRM или 1С, признак остаётся `false`.

На сайте реквизиты больше не попадают в BNPL-заказы: сейчас туда подставляются реквизиты из прошлых возвратов клиента. 1С возвращает деньги по BNPL в личном кабинете BNPL-сервиса по идентификатору платежа, реквизиты при этом не используются.

### Ошибки

| Метод | Когда | Ответ |
|---|---|---|
| `POST /orders/refund/save-reason` | Поле реквизитов не прошло проверку | Ошибка валидации по полю, как сейчас (`success = false`), тексты — ECOMDEV-2526 §2 |
| `POST /orders/refund/save-reason` | Подтверждение не передано или не `true` | То же, поле `is_bank_details_confirmed`: «Подтвердите банковские реквизиты» |
| `POST /mobile/orders/{order_id}/return` | `is_bank_details_confirmed = false` | Текст первой ошибки, как сейчас: «Подтвердите банковские реквизиты» |

### Совместимость с МП

Новый параметр необязательный: старые версии приложения продолжают оформлять возврат, признак сохраняется как `null`. Бэкенд выкатывается раньше приложения.

## Тестирование

**Предусловия:** заказ, для которого реквизиты нужны, и заказ, для которого не нужны; у пользователя есть сохранённая запись в `cms_users_refund`.

**Критерии приёмки**

1. Сайт: возврат с корректными реквизитами и `is_bank_details_confirmed = true` создаётся; в `cms_orders.user_refund` — реквизиты из запроса и `true`.
2. Сайт: без реквизитов, без подтверждения или с `false` возврат не создаётся, ошибка — по полю. Наличие записи в `cms_users_refund` на результат не влияет, сама запись не меняется.
3. МП: `true` → в заказе `true`; параметр не передан → возврат создаётся, в заказе `null`; `false` → возврат не создаётся.
4. Реквизиты не нужны: возврат создаётся без реквизитов на обеих платформах; сайт не записывает реквизиты в заказ.
5. Счёт не начинается с `30232810`: на сайте возврат без `user_card_number` создаётся; в МП номер карты из запроса в заказ не записывается. Счёт начинается с `30232810`: номер карты записывается в заказ.
6. В `cms_orders` и `cms_orders_history` есть поле `is_refund_to_original_payment_method`, по умолчанию `false`.
7. После возврата на сайте и в МП `is_refund_to_original_payment_method = true` для заказов, оплаченных способом из таблицы раздела 3 без сертификата, и `false` для остальных; значение попадает в `cms_orders_history`.
8. Возврат через МП проверен на последней версии приложения из стора.
9. Swagger монолита и гейта дополнен параметром `is_bank_details_confirmed`.
