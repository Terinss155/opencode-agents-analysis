# ECOMDEV-2526: [B] Возврат 0.1: единые правила запроса и проверки банковских реквизитов для сайта и МП

## Цель

Определять необходимость банковских реквизитов и проверять их формат одной общей логикой бэкенда для сайта и МП.

## Описание реализации

**Endpoint**

- Web:
  - `GET /orders/refund/get-positions?id={order_id}`
  - `POST /user/cabinet/return-item/ajax/get-reasons-list`
- Mobile API — методы Site дорабатываются в этой задаче; Gate `core.12stz.*` (ESB) передаёт запросы без изменений, код гейта не дорабатывается:
  - Gate `GET /api/orders` → Site `GET /mobile/orders`
  - Gate `GET /api/orders/{order_id}` → Site `GET /mobile/orders/{order_id}`
  - Gate `POST /api/orders/{order_id}/return` → Site `POST /mobile/orders/{order_id}/return`

### Контекст

1. Необходимость реквизитов сейчас определяется в каждом методе по-своему: сайт требует их для всех способов оплаты, кроме онлайн, включая BNPL; МП — только для оплаты курьеру. Подарочный сертификат нигде не учитывается.
2. Формат реквизитов на сайте и в МП проверяется разными правилами: в МП ИНН банка обязателен, номер карты обязателен при любом счёте.

Ограничения, текущие методы не позволяют:

1. получить одинаковый признак «нужны реквизиты» для одного заказа на сайте и в МП;
2. проверить реквизиты одинаково на всех эндпоинтах, которые их принимают.

### Необходимо

1. Создать общую проверку «нужны реквизиты» и использовать её в эндпоинтах из раздела 1.
2. Создать общую проверку формата реквизитов и использовать её в `POST /mobile/orders/{order_id}/return` — раздел 2.

Вне этой задачи: применение обеих проверок в `POST /orders/refund/save-reason` и сохранение реквизитов в заказ на сайте и в МП — ECOMDEV-2649.

#### 1. Правило «нужны реквизиты»

Реквизиты нужны, если выполнено хотя бы одно условие:

- заказ оплачен курьеру (наличными или картой);
- при оплате заказа использован подарочный сертификат на любую сумму, включая полную оплату сертификатом {red}(Р-1: считается ли сертификат использованным, если его списание отменено, — открытый вопрос 1).

В остальных случаях реквизиты не нужны, в том числе для BNPL (Долями, Подели, Сплит): 1С возвращает деньги по BNPL в личном кабинете BNPL-сервиса. Оплатить BNPL-заказ с сертификатом нельзя: при оплате сертификатом способы BNPL не предлагаются.

Признак определяется одной общей проверкой по заказу. Её используют все эндпоинты ниже и ECOMDEV-2649.

| № | Эндпоинт | Поле | Было | Стало |
|---|---|---|---|---|
| 1 | `GET /orders/refund/get-positions?id={order_id}` | `data.need_bank_details` | `true` для всех способов, кроме онлайн-оплаты; BNPL — `true` | по общей проверке |
| 2 | `POST /user/cabinet/return-item/ajax/get-reasons-list` | `data.need_bank_details` | `true` для всех способов, кроме онлайн-оплаты сайта и СБП | по общей проверке |
| 3 | `GET /mobile/orders`, `GET /mobile/orders/{order_id}` | `return.is_bank_data_required` | `true` только для оплаты курьеру | по общей проверке |
| 4 | `POST /mobile/orders/{order_id}/return` | проверка наличия реквизитов | реквизиты требуются только для оплаты курьеру | реквизиты требуются, если нужны по общей проверке; проверка формата — раздел 2 |

- Эндпоинт 4 определяет необходимость реквизитов заново по заказу и не опирается на признак, полученный приложением.
- Общую проверку «оплата курьеру» не менять: на ней построены доставка «Dalli с примеркой» и признак примерки в Mindbox. Условие о сертификате добавляется только в правило «нужны реквизиты».
- Возврат выкупленной брони (оплата при выкупе брони, код 18) в задачу не входит: в ЛК сайта он запрещается отдельной задачей, в МП на экране брони кнопки возврата нет. `GET /mobile/reservation/{id}` не дорабатывается.

#### 2. Проверка формата реквизитов

Общая проверка применяется, когда реквизиты нужны по разделу 1. Если реквизиты не нужны, формат не проверяется. Перед проверкой из номерных полей убираются пробелы и дефисы.

| Поле запроса | Правило |
|---|---|
| `surname` | обязательно, до 255 символов, без ссылок и тегов |
| `name` | обязательно, до 255 символов, без ссылок и тегов |
| `patronymic` | обязательно, до 255 символов, без ссылок и тегов |
| `bank_name` | обязательно, до 255 символов, без ссылок и тегов |
| `bank_bic` | обязательно, ровно 9 цифр |
| `bank_inn` | необязательно; если заполнено — ровно 10 цифр |
| `user_account` | обязательно, ровно 20 цифр |
| `user_card_number` | обязательно и ровно 16 цифр, если `user_account` начинается с {red}(`30232810`) (кредитный счёт); для других счетов поле не проверяется |

- Тексты ошибок — текущие тексты проверки реквизитов на сервере, одинаковые на обоих эндпоинтах; для новых правил (20 цифр счёта, 16 цифр карты) — в том же стиле.
- Формат ответа с ошибкой на каждом эндпоинте прежний.
- Поле ИНН убирается из форм сайта и новых версий МП; старые версии МП продолжают передавать ИНН из 10 цифр.
- Номер карты при некредитном счёте запрос не отклоняет. Сохраняется ли он в заказ — ECOMDEV-2649.

### Обратная совместимость

- Сайт: меняются только значения `need_bank_details`, структура ответов прежняя.
- Все изменения обратно совместимы для текущих версий МП: структура запросов и ответов не меняется; `bank_inn` и `user_card_number` при некредитном счёте становятся необязательными, старые версии передают их и проходят проверку.
- Для заказов с сертификатом, оплаченных онлайн, старые версии МП начнут показывать блок реквизитов и передавать их, бэкенд их принимает.

Выкатывать одним релизом с ECOMDEV-2649 и ECOMDEV-2532: правило раздела 1 меняет показ формы на сайте, а сохранение реквизитов по этому правилу появляется только в ECOMDEV-2649.

## Тестирование

{% cut "Критерии приёмки" %}

**Предусловия:** заказы с оплатой курьеру наличными и картой; с онлайн-оплатой, СБП, Яндекс Pay, Яндекс СБП, Яндекс цифровым рублём — с сертификатом и без; с полной оплатой сертификатом; BNPL (Долями, Подели, Сплит).

**Признак «нужны реквизиты»**

1. Оплата курьеру, полная оплата сертификатом, частичная оплата сертификатом с любым онлайн-способом → `need_bank_details = true` на эндпоинтах 1–2 и `is_bank_data_required = true` на эндпоинте 3.
2. Онлайн-оплата, СБП, Яндекс Pay, Яндекс СБП, Яндекс цифровой рубль без сертификата, BNPL → признак `false` на эндпоинтах 1–3.
3. Для одного заказа признак на сайте и в МП совпадает.
4. Для заказа с сертификатом доставка «Dalli с примеркой» и признак примерки в Mindbox не изменились.

**`POST /mobile/orders/{order_id}/return`**

5. Реквизиты нужны, реквизиты не переданы → возврат не создан, ошибка в текущем формате.
6. Реквизиты не нужны → возврат создаётся без реквизитов.
7. Отклоняются с ошибкой по полю: пустое обязательное поле; БИК не из 9 цифр; заполненный ИНН не из 10 цифр; счёт не из 20 цифр; счёт начинается с `30232810`, карта пустая или не из 16 цифр. Ссылка или тег в ФИО или названии банка → ошибка по полю.
8. Номера с пробелами и дефисами проходят, если после их удаления остаётся нужное количество цифр.
9. ИНН не передан → возврат создаётся. Счёт не начинается с `30232810`, номер карты не передан или передан → возврат создаётся.
10. Возврат через МП проверен на последней версии приложения из стора.
