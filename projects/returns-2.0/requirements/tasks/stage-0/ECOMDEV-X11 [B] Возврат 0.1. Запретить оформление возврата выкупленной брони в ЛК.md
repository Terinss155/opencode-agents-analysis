# ECOMDEV-X11: [B] Возврат 0.1. Запретить оформление возврата выкупленной брони в ЛК

## Цель

Бронь оформляется только в МП, но после выкупа видна в ЛК сайта как обычный заказ, и клиент может оформить по ней возврат. Брони возвращают в магазине; в МП возврат брони из ЛК уже недоступен. Нужно запретить оформление возврата брони в ЛК сайта и не давать создать его запросом на бэкенд ни на сайте, ни в МП.

**Web:** `GET /profile/orders`, `GET /profile/online-orders-json`, `GET /profile/view/{id}`, `GET /orders/refund/get-positions?id={order_id}`, `POST /orders/refund/save-reason`

**Mobile API:** Site `POST /mobile/orders/{order_id}/return` ← Gate `POST /api/orders/{order_id}/return` (`core.12stz.*`, ESB). Гейт не дорабатывается.

Бронь — заказ с `cms_orders.type = reservation`, независимо от способа оплаты: онлайн-оплата брони процессом не предусмотрена.

---

## Описание реализации

Что требуется изменить:

1. Список заказов и страница заказа на сайте: для брони не показывать кнопку возврата (`show_refund_button = false`). Бронь в списке и на странице показывается, как сейчас.
2. Форма возврата на сайте: для брони не отдавать позиции к возврату.
3. Создание возврата на сайте и в МП: для брони отклонять запрос.

### 1. Список заказов и страница заказа

|Метод|Параметр|Было|Стало|
|:---|:---|:---|:---|
|`GET /profile/orders` (страница списка заказов), `GET /profile/online-orders-json` (подгрузка списка)|`show_refund_button` в каждом заказе списка|`true`, если заказ в статусе «Заказ выполнен» или возвращён и срок возврата не истёк|`false` для брони; для остальных заказов — как сейчас|
|`GET /profile/view/{id}`|`status.show_refund_button`|то же|`false` для брони; для остальных заказов — как сейчас|

Признак в списке и на странице заказа считается одинаково.

Проверки выполняются последовательно — от первого пункта к последнему:

1. Если `cms_orders.type = reservation` → `show_refund_button = false`, дальше не проверяется.
2. Иначе:

> **AS-IS:** далее применяется существующая логика расчёта доступности возврата. Она не изменяется в рамках данной задачи и должна соответствовать текущей реализации. Приведённые в задаче условия могут быть описаны укрупнённо; если фактическая AS-IS-логика отличается, необходимо сохранить текущую реализацию при условии, что она не противоречит новой логике.

- заказ в статусе «Заказ выполнен» или возвращён;
- `cms_orders.end_date` + `days_can_be_returned` дней больше текущего времени;
- хотя бы одна позиция может быть возвращена.

Входные параметры не меняются.

### 2. Форма возврата — `GET /orders/refund/get-positions?id={order_id}`

Если `cms_orders.type = reservation` → ответ с ошибкой, позиции не отдаются. Для остальных заказов логика не меняется.

### 3. Создание возврата — `POST /orders/refund/save-reason`, `POST /mobile/orders/{order_id}/return`

Проверка выполняется первой, до проверки причин и реквизитов: если `cms_orders.type = reservation` → возврат не создаётся, статусы заказа и позиций не меняются, в заказ ничего не записывается. Для остальных заказов логика не меняется.

### Ошибки

|Метод|Когда|Ответ|
|:---|:---|:---|
|`GET /orders/refund/get-positions`|Заказ — бронь|`success = false`, `message`: «Возврат брони оформляется в магазине» {red}(текст — по макету дизайна)|
|`POST /orders/refund/save-reason`|Заказ — бронь|`success = false`, `message`: «Возврат брони оформляется в магазине» {red}(текст — по макету дизайна)|
|`POST /mobile/orders/{order_id}/return`|Заказ — бронь|Текст первой ошибки, как сейчас: «Возврат брони оформляется в магазине» {red}(текст — по макету дизайна)|

Формат ответа с ошибкой на каждом методе — как у текущих ошибок этого метода.

### Совместимость с МП

|Изменение|Тип|Что увидит старая версия|
|:---|:---|:---|
|`POST /mobile/orders/{order_id}/return` отклоняет возврат брони|безопасное|Брони нет в списке заказов МП, кнопки возврата на экране брони нет — запрос из приложения не приходит; при прямом запросе — текст ошибки в алерте|

## Тестирование

**Предусловия:** бронь (`cms_orders.type = reservation`) в статусе «Заказ выполнен», `end_date` в пределах срока возврата; обычный заказ в тех же условиях.

**Критерии приёмки**

1. Страница брони на сайте: `status.show_refund_button = false`, кнопки «Оформить возврат» нет.
2. Список заказов на сайте (`GET /profile/orders`, `GET /profile/online-orders-json`): у брони `show_refund_button = false`, кнопки «Оформить возврат» в карточке нет; бронь в списке показывается.
3. Обычный заказ: `show_refund_button` в списке и на странице заказа — как до доработки.
4. `GET /orders/refund/get-positions` для брони возвращает ошибку, позиции не отдаются.
5. `POST /orders/refund/save-reason` и `POST /mobile/orders/{order_id}/return` для брони возвращают ошибку; статусы заказа и позиций не меняются, `cms_orders.user_refund` не меняется.
6. Возврат обычного заказа на сайте и в МП оформляется как до доработки.
