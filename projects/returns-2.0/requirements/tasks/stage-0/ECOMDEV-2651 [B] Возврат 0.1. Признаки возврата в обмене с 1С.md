# ECOMDEV-2651: [B] Возврат 0.1. Признаки возврата в обмене с 1С

## Цель

Передавать в 1С вместе с заказом два признака возврата:

- `is_bank_details_confirmed` — клиент подтвердил банковские реквизиты. Признак уже сохраняется в заказе по задаче ECOMDEV-2649, здесь — только передача в 1С.
- `is_refund_to_original_payment_method` — деньги возвращаются на исходный способ оплаты. Нужен, чтобы пустые реквизиты в документе 1С не выглядели ошибкой. Признак новый: его нужно рассчитать и сохранить.

**Где:** `POST /orders/refund/save-reason` (сайт), `POST /mobile/orders/{order_id}/return` (МП), выгрузка заказа в 1С (SOAP `loadOrder`). Запросы и ответы методов не меняются.

Разделы 1, 2 и 4 можно делать сразу. Раздел 3 — после ответа 1С на вопрос 1С-1.

## Описание реализации

### 1. Новое поле в БД

| Таблица | Поле | Тип | Nullable | Default |
|---|---|---|---|---|
| `cms_orders` | `is_refund_to_original_payment_method` | `boolean` | нет | `false` |
| `cms_orders_history` | `is_refund_to_original_payment_method` | `boolean` | нет | `false` |

По аналогии с миграцией `is_rcrm_modified_before_payment`: поле в обеих таблицах, триггеры истории пересоздаются. Значение по умолчанию — `false`, а не `null`: триггер истории не замечает переход «пусто → значение».

### 2. Расчёт признака при создании возврата

При создании возврата на сайте и в МП признак рассчитывается по заказу и сохраняется вместе с возвратом:

- `true` — заказ оплачен одним из способов ниже **и** в нём не использован подарочный сертификат;
- `false` — во всех остальных случаях: оплата курьеру, использован сертификат (полностью или частично), оплата при выкупе брони (18), Click & Collect Light (12), устаревшие способы, способ не задан.

| Группа | Способ оплаты | Код |
|---|---|---|
| Прямая онлайн-оплата | Онлайн на сайте | 1 |
| Прямая онлайн-оплата | СБП | 16 |
| Прямая онлайн-оплата | Яндекс Pay | 19 |
| Прямая онлайн-оплата | Яндекс СБП | 20 |
| Прямая онлайн-оплата | Яндекс цифровой рубль | 21 |
| BNPL | Долями | 13 |
| BNPL | Подели | 14 |
| BNPL | Сплит | 17 |

Условие «использован сертификат» — то же, что в правиле «нужны реквизиты» (ECOMDEV-2526 §1).

Повторный возврат по заказу пересчитывает и перезаписывает признак. Остальная логика создания возврата не меняется.

> Ограничения: признак ставится только при возврате на сайте и в МП — у возвратов, оформленных сотрудником в RetailCRM или 1С, остаётся `false`. Признак хранится на уровне заказа и относится к последнему возврату; прежние значения — в `cms_orders_history`.

### 3. Передача признаков в 1С

Оба поля добавляются в блок `customer`, рядом с банковскими реквизитами, в каждую выгрузку заказа: в тело запроса `loadOrder` и в копию тела для журнала обмена (`cms_orders_exchange_log`, `category = 3`), чтобы журнал совпадал с отправленным. Поля есть в каждом заказе, в том числе без возврата; пустое значение — JSON `null`, не пустая строка.

| Поле | Блок | Значение | Когда |
|---|---|---|---|
| `is_bank_details_confirmed` | `customer` | `null` | возврат не оформлен (`"return": false`) или в заказе нет реквизитов |
| | | `true` | реквизиты есть, в `cms_orders.user_refund` ключ `is_bank_details_confirmed` = `true` |
| | | `false` {red}(ждёт 1С-1) | реквизиты есть, подтверждения нет: возврат из старой версии МП (ключ `null`) или возврат, оформленный до выкатки (ключа нет) |
| `is_refund_to_original_payment_method` | `customer` {red}(ждёт 1С-1) | `null` | возврат не оформлен (`"return": false`) |
| | | `true` / `false` | возврат оформлен — значение `cms_orders.is_refund_to_original_payment_method` |

- Наличие реквизитов определяется по данным заказа (`cms_orders.user_refund`), а не по правилу «нужны реквизиты» ECOMDEV-2526.
- `false` в `is_bank_details_confirmed` означает «подтверждение не зафиксировано», а не отказ клиента: новые версии сайта и МП без подтверждения возврат с реквизитами не создают (ECOMDEV-2649).
- `bank_inn` передаётся как сейчас: пустой строкой, если ИНН не заполнен.
- `return.money` и остальные поля блока `return` не меняются.

### 4. `full_name` при возврате на исходный способ оплаты

`full_name` 1С использует только для возврата на расчётный счёт. Правило формирования не меняется: ФИО из реквизитов, если они есть, иначе — ФИО покупателя из профиля; при возврате из МП по BNPL — пустая строка.

## Тестирование

**Предусловия:** заказы в статусе «Заказ выполнен» в пределах срока возврата — с каждым способом оплаты из таблицы раздела 2, с оплатой курьеру, с частичной и полной оплатой сертификатом. Для разделов 3 и 4 — стенд с обменом с 1С или журнал `cms_orders_exchange_log`.

**Критерии приёмки**

1. В `cms_orders` и `cms_orders_history` есть поле `is_refund_to_original_payment_method`, по умолчанию `false`; триггеры истории пересозданы.
2. После возврата на сайте и в МП признак `true` для заказов из таблицы раздела 2 без сертификата и `false` для всех остальных; значение попадает в `cms_orders_history`.
3. Ответы `POST /orders/refund/save-reason` и `POST /mobile/orders/{order_id}/return` не изменились; возврат через МП проверен на версии приложения из стора.
4. В выгрузке в 1С и в журнале обмена оба признака есть в блоке `customer` у каждого заказа. Заказ без возврата — оба `null`. После возврата: `is_bank_details_confirmed` = `true` при подтверждённых реквизитах, `false` — при реквизитах из старой версии МП, `null` — без реквизитов; `is_refund_to_original_payment_method` — значение из `cms_orders`. Блок `return` не изменился. {red}(после 1С-1)
5. `full_name` в выгрузке — по правилу раздела 4, без изменений относительно текущей выгрузки.
