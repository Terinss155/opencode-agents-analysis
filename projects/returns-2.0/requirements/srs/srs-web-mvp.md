## Основные принципы

1. Инструкции по способам возврата:
   - для каждого способа клиент видит два текста: описание на панели «Оформление возврата» и инструкцию «Что дальше» на странице созданного возврата;
   - оба текста заводятся в админке отдельно для каждого способа, содержание определяет бизнес. Тексты на макетах — пример.
2. Возврат части позиции:
   - одинаковые изделия хранятся в заказе одной позицией, и при создании заявки статус меняется у всей позиции;
   - если по позиции есть активная заявка, оставшиеся изделия видны в блоке «Ваш заказ», но в MVP выбрать их к возврату на сайте не получится: статус меняется у всей позиции. Их возврат оформляет Отдел дружбы с клиентами по обращению клиента. *Если появится способ возвращать остаток позиции на сайте, ограничение можно снять*;
   - при отмене заявки статус позиции возвращается, и её снова можно вернуть до последнего дня оформления заявки.
3. Форма возврата (выбор изделий, причины, оформление возврата, банковские реквизиты, выбор города и точки) открывается боковой панелью поверх страницы заказа. Если пользователь нажал за пределами панели, сайт отображает модальное окно «Закрыть форму возврата?» с предупреждением, что введённые данные не сохранятся, и кнопками «Продолжить оформление» и «Закрыть». «Продолжить оформление» закрывает модальное окно, введённые данные сохраняются; «Закрыть» закрывает форму без сохранения данных, пользователь остаётся на странице заказа.
4. Номер возврата:
   - номер, который видит клиент, присваивает сайт для любой заявки: созданной клиентом, Отделом дружбы с клиентами или магазином;
   - формат — номер заказа и порядковый номер возврата по заказу: `598591-01`, …, `598591-10`. Отменённые заявки тоже учитываются в нумерации;
   - для обмена с 1С используется отдельный внутренний номер, клиенту он не показывается.
5. Права, статус и сроки проверяет бэкенд при каждом запросе. Сайт скрывает недоступные действия только для удобства пользователя.
6. При технической ошибке метода сайт показывает стандартное сообщение об ошибке, как в остальных разделах. Введённые пользователем данные не сбрасываются.

## Функциональные требования

### Админка

Для сценариев сайта в админке нужны доработки, которых нет в текущих экранах.

1. Пользователь админки должен иметь возможность управлять внутренними (техническими) и клиентскими статусами возврата. Нескольким внутренним статусам можно задать одно клиентское название: клиент видит такие статусы как один статус.
2. Пользователь админки должен иметь возможность объединять внутренние статусы возврата в группы по этапам процесса (например, «Новые», «В работе», «Завершённые»). Группа видна только в админке.
3. Пользователь админки должен иметь возможность управлять данными способа возврата: название, описание на панели «Оформление возврата», инструкция для блока «Что дальше» страницы созданного возврата, включение на сайте и в МП.
4. Пользователь админки должен иметь возможность задавать порядок способов возврата: по нему формируется список способов и выбирается способ по умолчанию, если способ доставки заказа недоступен для возврата.
5. Пользователь админки должен иметь возможность включать и отключать способы возврата для города: по этой настройке метод получения способов возврата для города отдаёт только включённые для города способы.

**Примечание**

*Способы возврата*

1. Способ возврата отображается, если его возвратная служба работает в городе возврата. Возвратные службы ведутся отдельно от служб доставки, со своим списком городов, и он может не совпадать с городами доставки. «Почта России» определяется по тому же правилу: её возвратная служба работает только в Калининграде и Калининградской области, поэтому в других городах этого способа нет. Например, курьер СДЭК есть только в населённых пунктах с офисом СДЭК.
2. Если способа, совпадающего со способом доставки заказа, нет, то предвыбирается первый способ по приоритету. Так бывает, если способ доставки заказа недоступен для возврата или город возврата отличается от города заказа.
3. Дата «Вернуть до» на панели «Оформление возврата» предварительная: она считается при открытии панели и не меняется, пока пользователь на ней. Окончательная дата — дата создания заявки + 10 календарных дней. Если пользователь начал оформление до полуночи, а подтвердил после, окончательная дата будет на день позже предварительной.

*Курьер: адрес забора*

4. Адрес из заказа не считается введённым вручную, даже если клиент вводил его вручную при оформлении заказа: адрес заказа уже проверил Отдел дружбы с клиентами, и по нему заказ доставлен. Даты и интервалы курьера для адреса из заказа запрашиваются как обычно.
5. Подсказка с введённым текстом — отдельная строка в раскрывающемся списке подсказок, в которой повторяется текст, введённый в поле. Это не само поле ввода: на эту подсказку нужно нажать, как на найденный адрес. Адрес принимается, только когда пользователь нажал на подсказку в списке — найденный адрес или подсказку с введённым текстом. Подсказка с введённым текстом приходит в ответе метода `GET /получить подсказки адреса` последней строкой списка подсказок дома. Исключение — геосервис недоступен: тогда списка нет, и улица и дом вводятся как обычный текст. Даты и интервалы курьера запрашиваются:
   - адрес найден в подсказках — после нажатия на найденный дом в списке подсказок;
   - адреса нет в подсказках — после нажатия на подсказку с введённым текстом в списке подсказок дома;
   - геосервис недоступен — когда пользователь ушёл из поля «Дом, корпус», а улица и дом заполнены;
   - адрес подставлен из заказа — сразу после подстановки;
   - пользователь изменил улицу или дом — дата, интервал и индекс сбрасываются, запрос повторяется по тем же правилам.

*Курьер: даты и интервалы*

6. Часовой пояс города `timezone` всегда передаётся в запрос дат и интервалов курьера. По нему логистика считает ручные интервалы; без него интервалы считаются по московскому времени (UTC+03:00). Часовой пояс приходит только в ответе метода `GET /получить данные города`. Поэтому данные города запрашиваются и тогда, когда город подставлен из заказа.
7. В MVP даты и интервалы курьера для возврата приходят только от СДЭК и только по населённым пунктам РФ.
8. Для курьера СДЭК на каждую дату приходит один интервал — 9:00–18:00 по местному времени.
9. Число дат задаёт логистика. Сайт его не меняет, в том числе для клиентов F&F.

### Логика бэкенда

**`GET /получить способы возврата для города` (`GET /api/orders/{order_id}/return-method-list`) — доработка метода**

* отбирать и отдавать способы возврата по новой логике — общей с новым методом способов возврата мобильного приложения ([SRS МП, US 1.3](./srs-mobile-mvp.md)): возвратные службы, работающие в городе возврата, порядок приоритета, признак способа заказа, служба и код типа доставки возвратной службы (`delivery_type_code`), дата «Вернуть до» для СДЭК, 5Post, Магазина 12 STOREEZ и Почты России — текущая дата + 10 календарных дней. Расчёт один для обоих каналов, отличается только набор способов, включённых для канала
* текущий расчёт списка способов используется и этим методом, и методом выпущенных версий мобильного приложения. Его не менять: метод сайта переводится на новую логику, метод выпущенных версий приложения работает по-прежнему
* входные параметры не меняются: страны, региона и города возврата достаточно. В ответ добавляются признак способа заказа, служба, `delivery_type_code` и дата «Вернуть до»
* поддержать новые способы «Магазин 12 STOREEZ» и «Почта России»

**`GET /получить магазины, принимающие возвраты` (`GET /content/showrooms/showrooms-return?city_fias={city_fias}`) — новый метод**

* отдавать магазины, которые принимают возвраты в выбранном городе, — тот же отбор и набор данных, что в методе мобильного приложения

**`GET /получить пункты выдачи` (`GET /api/v1/delivery/pickup/provider/{provider}/points`) — доработка метода**

* передавать через `monolith_bfb_ms` в сервис логистики возвратную службу выбранного способа (`provider`) и фильтр `is_return_available = true`, чтобы получить только пункты, принимающие возвраты
* для служб доставки заказов метод работает как сейчас (оформление заказа)

**`GET /получить данные пункта выдачи` (`GET /api/v1/delivery/pickup/provider/{provider}/points/{point}`) — доработка метода**

* отдавать признак `is_return_available` из ответа логистики

**`GET /получить даты и интервалы курьера` (`GET /delivery/delivery/intervals`) — доработка метода**

* Необходимо добавить новые параметры в запрос к Логистике (через `monolith_bfb_ms`):
  * `sending_address` (TBD) — полный адрес забора изделий для возврата. Передаётся одной строкой (требование Логистики).
  * `is_return` (TBD) — признак возврата, по которому Логистика определяет, что необходимо проверить доступные даты и интервалы для возвратного потока.
* код типа доставки возвратной курьерской службы (`delivery_type_code`) и часовой пояс города (`timezone`) передаются, как сейчас; часовой пояс — всегда
* код города не передаётся. Состав строки `sending_address`:
  * адрес из подсказок — `data.house.fullTitle` из ответа `GET /получить данные адреса` (`GET /api/v1/delivery/geo/countries/{countryIso}/addresses/details?geo_id={geo_id}`);
  * адрес из заказа — поля адреса заказа: страна, регион, населённый пункт, улица, дом, квартира, индекс;
  * адрес, введённый вручную, — на уточнении.
* для возврата интервалы не зависят от корзины: тип заказа из корзины не определяется
* без адреса забора метод работает как сейчас (оформление заказа)

### Просмотреть детальную информацию по заявке на возврат US 3

Как клиент, оформивший возврат, я хочу иметь полный доступ к информации и материалам по своей заявке, чтобы легко контролировать статус возврата на каждом этапе и оперативно получать нужные данные без обращения в поддержку

### Дизайн

Макеты: [web/v1 После создания возврата (просмотр и раздел возвратов)](<../../sources/mockups/web/v1 После создания возврата (просмотр и раздел возвратов)/>), макеты 1–7

### Сценарий

#### Предусловие

1. Заявка на возврат создана

#### Основная последовательность "Просмотреть детальную информацию по заявке на возврат"

| Шаг | Исполнитель | Описание |
|---|---|---|
| 1 | Пользователь | Открывает страницу возврата |
| 2 | Сайт | Вызвать метод `GET /получить детальную информацию по заявке на возврат` (TBD) |
| 3 | Сайт | Отобразить страницу возврата по макету<br><br>**Опционально**<br>1. Если для способа возврата не задан текст «Что дальше», то блок не отображать<br>2. Если способ возврата — СДЭК, 5Post или Магазин 12 STOREEZ, то отобразить кнопку «Смотреть на карте»<br>3. Если способ возврата — Магазин 12 STOREEZ, то отобразить кнопку «Показать QR-код» |
| 4 | Сайт | Обработать действие пользователя на странице<br><br>**Опционально**<br>1. Если пользователь нажал «Копировать» рядом с номером возврата, то скопировать номер в буфер обмена и показать уведомление «Номер возврата скопирован»<br>2. Если пользователь нажал «Смотреть на карте», то открыть карту с точкой передачи из заявки. Изменить точку нельзя<br>3. Если пользователь нажал «Показать QR-код», то отобразить модальное окно с QR-кодом заявки |

**Примечание**

1. Дата и интервал курьера на странице — выбранные при оформлении. Если их согласовал или перенёс Отдел дружбы с клиентами, показываются новые. Если клиент сам договорился с курьером о переносе, на странице остаются прежние.
2. Дата «Вернуть до» — срок передачи изделий в точку сдачи, сохранённый при создании заявки.
3. Если дата «Вернуть до» прошла, заявка не отменяется автоматически (автоотмена — Post-MVP). Если через 30 дней после создания изделия не поступили на склад или в магазин, заявка переходит в статус «Подтверждение возврата» и её обрабатывает Отдел дружбы с клиентами.
4. Срок возврата денег клиенту сообщается в тексте «Что дальше» из админки. Компания отправляет деньги в течение 3 дней: при возврате в магазин — от приёмки в магазине, для остальных способов — от поступления на склад. Клиенту сообщается только срок отправки, одной формулировкой для всех способов оплаты: срок зачисления зависит от банка. Поэтому текст для магазина отличается от текста для остальных способов.
5. Изменить заявку (способ возврата, точку, дату и интервал курьера) клиент на сайте не может. Изменения вносит Отдел дружбы с клиентами по обращению клиента.
6. Статус возврата показывается под клиентским названием, которое задаётся в админке. Если у нескольких внутренних статусов одно клиентское название, клиент видит их как один статус.
7. QR-код можно показать с экрана, без печати и без интернета.
8. Если клиент не может показать QR-код, сотрудник магазина находит заявку по ФИО, номеру телефона или номеру заказа.
