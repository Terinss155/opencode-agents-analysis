## 0. Уточнения понимания требований

1. Подтверждение относится к реквизитам, а не к способу возврата в любом сценарии. Мезинова связывает галочку только с реквизитами: «я отвечаю за эти реквизиты, с реквизитами согласен» (00:00:59). Нажатие «Оформить возврат» подтверждением не считается.
2. Признак возврата на исходный способ оплаты — не выбор клиента. Его определяет система, чтобы пустые реквизиты в 1С не выглядели ошибкой (00:01:55–00:02:38).
3. Сайт не подставляет ранее сохранённые реквизиты в форму: форма открывается пустой, клиент вводит реквизиты каждый раз (`as-is/web/07-fill-bank-details.md`). Бэкенд берёт реквизиты для возврата из записи пользователя в `cms_users_refund`, а не из запроса на создание возврата (раздел 1).
4. Задачи этапа 0 для сайта ссылаются на устаревшие эндпоинты (раздел 7).
5. «Реквизиты не нужны» и «возврат на исходный способ оплаты» — не одно и то же (раздел 2).

## 2. BNPL и правило второго признака

### 2.1. Возврат денег по BNPL (Сплит, Подели, Долями)

Подтверждено кодом:
- Сайт сам не запускает возврат денег по BNPL. Возврат для Сплит, Яндекс Pay и СБП (`pushRefundPayment`) и для Подели (`refundPayment`) нигде не вызывается. Для Долями есть только ручная кнопка в админке (`OrdersBackendController.php:1121`). Провайдеры возвращают сумму по заказу, банковские реквизиты при этом не используются.
- Записи для чеков возврата по Долями, Подели, Сплит и YooKassa (`cms_order_position_require_refund_receipts`) код сайта не создаёт, триггеров на них нет — записи приходят извне.
- Реквизиты попадают в BNPL-заказ только из-за условия кода `DIRECT_ONLINE`. Форма реквизитов для BNPL клиенту не показывается. При возврате на сайте в заказ подставляются ранее сохранённые реквизиты пользователя — подтверждено на production (раздел 2.1.1). При возврате в МП в заказ пишутся пустые реквизиты (код и staging: 17 BNPL-заказов; на production не проверялось).
- Мезинова: при «онлайн, сплит» в 1С приходят «пустые строчки» (00:01:55).
- Деловое правило: возврат по BNPL — через сервис оплаты частями (`RULE-36`).

Со слов пользователя (06.11.2026): деньги возвращают сотрудники вручную через сторонние платёжные сервисы, автоматической интеграции на возврат нет. По официальным инструкциям Сплит, Подели и Долями поддерживают возврат через кабинеты партнёров; провайдер может пересчитать оставшиеся платежи клиента, а не вернуть сразу всю сумму. Общий механизм провайдеров не доказывает фактический процесс 12 STOREEZ.

Не установлено: оформляет ли Дружба возвраты BNPL через кабинеты провайдеров и используются ли при этом реквизиты из заказа (вопрос 1С-5). Если не используются — согласовать с 1С исключение их передачи и использование признака `is_refund_to_original_payment_method`.

Риски:
- Если реквизиты оставить, Дружба может отправить деньги по старым реквизитам из другого заказа.
- Если убрать, а 1С их где-то ожидает, у 1С может сломаться обработка.

Реквизиты заказа читают выгрузка в 1С (`OneCExchangeTransformer.php:460–493`) и выгрузка в RetailCRM (`RcrmOrderTransformer.php:208–247`: поля `fiom`, `bik`, `innb`, `nameb`, `nls`, `nbc`), а также карточка заказа в админке (только просмотр). ## 3. Названия

Соглашение в коде, БД и обмене с 1С — префикс `is_*`: `is_vic`, `is_click_and_collect`, `is_payment_changed`, `is_bank_data_required`. Для реквизитов в коде используются `bank_details` / `bank_data`, а `refund_details` / `POST /api/orders/{order_id}/return-details` на сайте означают адрес и способ передачи изделий.

| Признак | Название | Почему |
|---|---|---|
| Подтверждение реквизитов клиентом | `is_bank_details_confirmed` (предварительно) | `refund_details` легко спутать с `POST /api/orders/{order_id}/return-details` (адрес, дата курьера). `bank_details` — то же слово, что в `need_bank_details`. «Confirmed» — подтверждено клиентом, а не «verified» (проверено системой). В описании API: «клиент подтвердил реквизиты, указанные для этого возврата». |
| Возврат на исходный способ оплаты | `is_refund_to_original_payment_method` | «Original» соответствует термину проекта «исходный способ оплаты» (`RULE-38`). Вариант `is_refund_to_payment_method` читается как «на какой-то способ оплаты». Для BNPL исходный способ оплаты — сам сервис оплаты частями. |

Одно имя для API, БД и нашего обмена допустимо, соглашения совпадают. Имя в обмене — наше предложение для 1С: как назвать поле у себя, команда 1С решит сама (00:05:52).

## 4. Хранение реквизитов и подтверждения

Подтверждено кодом и данными staging:
- При оформлении возврата реквизиты копируются в заказ (`Order::setUserRefund`, `OrderRefundService.php:241`). Последующее изменение `cms_users_refund` заказ не меняет.
- Заказ, оплаченный при получении, требует реквизиты при каждом возврате: МП присылает их в теле каждого запроса, на сайте форма открывается пустой.
- Повторный возврат по тому же заказу с реквизитами Б перезаписывает `cms_orders.user_refund`.
- `cms_orders_history` — полная копия строки заказа при каждом изменении, включая `user_refund`, с `history_time`. На staging — 38 992 строки, последняя 06.11.2026. У двух заказов в истории две разные версии реквизитов: прежние реквизиты А сохраняются.
- Новая колонка в `cms_orders` обязательно добавляется и в `cms_orders_history` — это проверяет `check-migrate-trigger.sh`.
- В админке реквизиты только отображаются (`orders-backend/_form.php:700`, `DetailView`). RetailCRM и 1С `user_refund` не меняют.

Не установлено:
- Хранит ли 1С реквизиты А в документе первого возврата после получения заказа с реквизитами Б (вопрос 1С-6).

Связь записи истории с конкретным возвратом. Идентификатора возврата на этапе 0 нет: возврат — это изменение заказа и его позиций. Возврат восстанавливается по времени: в одну и ту же секунду в `cms_orders_history` появляется строка с новыми `user_refund`, `status = 31`, `last_change_source = user`, а в `cms_order_positions_history` — строки позиций со `status = 9` и причиной возврата. Пример на staging, заказ 500127100:

| Время | `cms_orders_history` | `cms_order_positions_history` |
|---|---|---|
| 2026-08-05 21:41:19 | реквизиты `fea8…`, статус 31, `user` | позиция 2420475 → статус 9, причина 300 |
| 2026-08-05 23:10:39 | реквизиты `4cbf…`, статус 31, `user` | позиция 2420475 → статус 9, причина 700 |

Ограничения:
- Связь косвенная, по совпадению времени, явной ссылки «возврат → реквизиты» нет.
- В истории позиций источник изменения — `cms`, а не `user`, поэтому возврат клиента отличается от изменения сотрудником только по истории заказа.
- Строки истории пишутся и при других изменениях заказа (повторная отправка, обмен с 1С), поэтому для разбора спора нужен ручной поиск по времени.

Вывод: по истории можно установить, какие реквизиты действовали при каждом возврате, но только ручным сопоставлением по времени. Для разбора спорных ситуаций Дружба опирается на документ возврата в 1С (вопрос 1С-6). Явная связь «возврат → подтверждённые реквизиты» появляется в «Возвратах 2.0», где реквизиты хранятся в заявке.

`is_bank_details_confirmed` хранится внутри `cms_orders.user_refund` вместе с реквизитами, которые подтверждает. Пара «реквизиты + признак» всегда меняется целиком, прежние пары сохраняются в `cms_orders_history`. Новые таблицы не нужны.

## 5. Где формировать, проверять и хранить признаки

| | `is_bank_details_confirmed` | `is_refund_to_original_payment_method` |
|---|---|---|
| Формирует | Клиент: галочка в форме реквизитов, по умолчанию снята | Бэкенд при создании возврата: `true` для прямой онлайн-оплаты и BNPL без сертификата |
| Проверяет | Бэкенд в `POST /orders/refund/save-reason` и `POST /mobile/orders/{id}/return`: если реквизиты нужны, без `true` возврат не создаётся | Не проверяется, клиент его не передаёт |
| Хранит | `cms_orders.user_refund` (JSON) вместе с реквизитами. В `cms_users_refund` — никогда | Новая колонка в `cms_orders`. Свойство возврата, а не реквизитов; должно быть видно и при пустых реквизитах. Сохраняется в момент создания: способ оплаты заказа может смениться (`is_payment_changed`). Значение по умолчанию 0 |
| Передаёт в 1С | Новое поле: блок `customer` или `return` — согласовать с 1С | Новое поле, логично в блоке `return` рядом с `money` — согласовать |

Сайт — строгий вариант: в `POST /orders/refund/save-reason` передаются реквизиты и признак подтверждения. Бэкенд проверяет формат, требует признак `true` и записывает в заказ ровно то, что пришло. `cms_users_refund` больше не источник для возврата. ## 11. Подарочные сертификаты

### 11.1. Фактически реализовано (AS-IS)

Оплата сертификатом в заказе:
- Использование сертификата записывается в `cms_giftcard_use` (`order_id`, `guid`, `amount`, `is_locked`, `is_purchased`) и передаётся в 1С в каждой выгрузке заказа: `giftcard_payments: [{guid, charge_amount}]` (`GiftcardUseRepository.php:92`, `OneCClient.php:160–168`). Записи берутся без фильтра по `is_locked` / `is_purchased`.
- При оформлении на сайте сертификат сочетается только с прямой онлайн-оплатой (`PaymentMethodEnum::CERTIFICATE_PAYMENT_METHODS`, `GiftcardPaymentIdValidator.php:18`).
- `payment_method = 15` («Сертификат») код сайта при оформлении не присваивает. Он приходит из RetailCRM: способ оплаты заказа перезаписывается типом последнего платежа RetailCRM через справочник типов оплаты (`RcrmOrderService.php:214–216`, `modules/orders/services/OrderService.php:974–976`, `PaymentType::getRetailStatus`). На staging у 55 заказов с кодом 15 последний источник изменения — `retailcrm` (43), `1c` (10), прочие (2).
- По `payment_method` полную оплату сертификатом отличить нельзя: заказ, полностью оплаченный сертификатом, сохраняет онлайн-код, выбранный при оформлении. По `total_sum` тоже нельзя: после возврата сумма заказа пересчитывается (у полностью возвращённого заказа — 0).
- Признак доли сертификата:
  - полностью сертификатом — в `cms_orders_payments` нет успешных платежей (`status = 1`) других типов, кроме сертификата (`type = 15`), и `0 < paid_sum ≤` сумма `cms_giftcard_use.amount`;

- Ни сайт (`POST /orders/refund/save-reason` → `OrderRefundService::refundPositions` → `validateReasons`), ни МП (`Mobile/OrdersController::actionReturnPositions`) не вызывают `OrderHelper::canBeReturned` (`OrderHelper.php:587`). Срок и статус заказа проверяются только при показе кнопки возврата.

Покупка самого сертификата — отдельный сценарий: заказ с `is_certificate_order = 1`, основной статус на staging — 79. Это не возврат изделий, оплаченных сертификатом; задачи этапа 0 его не затрагивают.
