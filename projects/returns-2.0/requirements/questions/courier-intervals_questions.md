### Ответ по коду: страница «Проверка доставки» в админке сайта

Как работает сейчас:

1. Сотрудник выбирает город. Страница показывает способы доставки города. У курьерских способов есть кнопки «Показать» и «Показать для CNC».
2. Кнопка вызывает `GET /cms/delivery/check/get-intervals?id=<id способа доставки>&order_type=<тип заказа>`. Монолит отправляет в BFB (`POST {BFB_MS_HOST}/delivery/intervals`) три параметра: код типа доставки, тип заказа и пустой часовой пояс. Адрес и город в запрос не передаются, поэтому интервалы одинаковы для любого адреса. Часовой пояс пустой, а сайт для возврата передаёт его всегда (`ADR-RET-062`).
3. Как монолит обрабатывает ответ:

| Ответ | Что видит сотрудник |
|---|---|
| Даты и интервалы есть | Окно со списком дат и интервалов |
| BFB вернул код, отличный от `200` | Ошибка пишется в лог. Сотрудник видит пустое окно без пояснения |
| `200`, в ответе нет массива `data.delivery_type.delivery_dates` или он пуст | Пустое окно без пояснения |
| Исключение при запросе (например, сеть) | Сервер возвращает текст ошибки вместо списка. Скрипт страницы на нём падает: окно не открывается, кнопка остаётся в состоянии «Загрузка» до перезагрузки страницы |
| Сетевой сбой самого запроса к админке | Сообщение «Ошибка загрузки интервалов» |

Вывод: для возврата страница в текущем виде не подходит. Сотрудник не может проверить даты по адресу клиента и не может отличить «дат нет» от сбоя.

Источник — код монолита: `modules/delivery/controllers/CheckBackendController.php` (`actionGetIntervals`, строки 79–116), `modules/delivery/views/check-backend/_table.php` (строки 25–71), `modules/common/client/MonolithBfbMsClient.php` (`getDeliveryIntervals`, строки 33–70), `modules/delivery/dto/DeliveryIntervalRequestDto.php`. Что BFB передаёт запрос дальше в gRPC `Logistics.WinnerService.Intervals`, известно со слов System Analyst BTS; в монолите видно только обращение к BFB.

## Открытые вопросы

#### 1. Дорабатываем ли страницу «Проверка доставки» для возврата в MVP?

**Кому:** Product Manager — Катя Филатова

На встрече 20.10 Product Manager сказала, что админку нужно дорабатывать, иначе Дружба не увидит даты СДЭК на возврат. Сейчас страница запрашивает интервалы без адреса и часового пояса, а пустой ответ и ошибку не различает (см. «Ответ по коду»).

- **а) Рекомендуемый вариант:** дорабатываем в MVP. Сотрудник вводит адрес забора и выбирает тип доставки возврата. Страница передаёт адрес и часовой пояс города, как сайт и приложение. Пустой ответ и ошибку показывает разными сообщениями.
- **б)** Не дорабатываем. Дату Дружба узнаёт у логистов (вопрос 3).

Если выбран вариант а — какие сообщения видит сотрудник, когда дат нет и когда произошёл сбой?

#### 2. Что делает Дружба с возвратом курьером без даты, если дат нет и в админке? Есть ли у Дружбы такой порядок действий или нужна новая инструкция?

**Кому:** Head of Customer Service — Ольга Соколова

Дружба видит заявку в отдельном статусе в RetailCRM, связывается с клиентом, согласует дату и интервал и вносит их в возврат. Если и админка не показала даты, порядок пока такой: запросить дату у логистов; не получилось — сменить способ возврата. Порядок действий на каждом шаге не согласован.

#### 3. Кто в логистике даёт Дружбе дату курьера, если админка её не показала, и как быстро?

**Кому:** Acting Head of Transport Logistics — Артём Лисин; Product Manager — Катя Филатова

Нужны: к кому обращается Дружба, по какому каналу и в какой срок отвечает логистика. Интервал для СДЭК один — 9:00–18:00 (`ADR-RET-076`), поэтому нужна только дата.

#### 4. Запрашиваем ли даты курьера для адреса, введённого вручную?

**Кому:** Product Manager — Катя Филатова; команда ecom (сайт и МП)

Сейчас для ручного адреса даты не запрашиваются, заявка сразу уходит Дружбе (`ADR-RET-074`). System Analyst BTS предлагает отправлять ручной адрес в логистику: у СДЭК свой геосервис, и в прямом потоке по 3 адресам из 5 даты пришли (таблица «Что уже решено», строка 7). Проверка была для прямого потока; для возврата адрес идёт в другой метод СДЭК. От выбора зависит объём доработок сайта и МП.

- **а)** Оставляем как есть: для ручного адреса даты не запрашиваем, заявка уходит Дружбе. Доработок нет.
- **б)** Запрашиваем даты и для ручного адреса. Если даты пришли — клиент выбирает дату, как для адреса из подсказок. Если не пришли — заявка уходит Дружбе, как при пустом ответе (`ADR-RET-075`). Признак ручного адреса и причина «проверить адрес» для Дружбы сохраняются.

Если выбран вариант б — проверить на возвратном методе СДЭК, отдаёт ли он даты для таких адресов.

#### 5. Что сайт и приложение передают в запросе дат курьерского возврата: полный адрес, `city_fias` или и то и другое?

**Кому:** System Analyst BTS — Елена Васильева

СДЭК ответил, что нужен полный адрес: населённый пункт, улица и дом. Его метод при этом принимает и код города. System Analyst BTS уточняет у СДЭК, можно ли передавать только код города.

Что уже известно по контракту и доработке для заказов (ECOMDEV-588, [справочник](../../../../knowledge/esb-protobufs/api/logistics-intervals.md)):
- для заказа адрес доставки — одна строка `delivery_address`; отдельного поля для `city_fias` нет;
- для адреса из подсказок источник строки — детализация адреса (одно поле, разное написание в JSON):
  - сайт: `GET /api/v1/delivery/geo/countries/{countryIso}/addresses/details?geo_id={geo_id}`, поле `data.house.fullTitle`;
  - МП: `GET /api/v1/geo/countries/{country_iso_code}/addresses/{geo_id}/details` (Mobile API Gateway), поле `house.full_title`;
- без адреса логистика для СДЭК возвращает ошибку;
- для возврата адрес клиента передаётся отдельным параметром — как адрес отправки, а не адрес доставки (`ADR-RET-060`); в контракте логистики этого параметра пока нет.

Нужно подтвердить для возврата:
- имя и формат параметра адреса отправки: одна строка, как `delivery_address`?
- для адреса из заказа и ручного адреса — строка, собранная из полей адреса (регион, населённый пункт, улица, дом, квартира, индекс)?
