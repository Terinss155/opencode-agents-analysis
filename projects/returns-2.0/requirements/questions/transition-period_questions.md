# Переход со старых возвратов на новые

Возвраты 2.0 · 24.11.2026

## Коротко

Новые возвраты заменяют старую схему, в которой возврат оформлялся через сам заказ. Обе схемы реагируют на изменения заказа по-разному, поэтому одновременно работать они не могут: при запуске старую схему нужно выключить. При этом часть процессов, например обмены через Отдел дружбы, должна продолжать работать по-старому. В документе собрано, что уже решено о запуске и переходном периоде и какие вопросы остались к архитектору, разработке и проекту.

## Что уже решено

| № | Тема | Решение | Источник |
|---|---|---|---|
| 1 | Старые возвраты | Возвраты, оформленные по старой схеме до запуска, доводятся до финала по старой схеме; новые возвраты после запуска создаются только как отдельная сущность. В момент запуска в RetailCRM блокируется ручной перевод заказов в статусы заявки на возврат | `ADR-RET-067` |
| 2 | Включение | Новый процесс на сайте и в МП включается переключателем; до включения он доступен только для проверки | `ADR-RET-069` |
| 3 | Обмены в MVP | Процесс обмена не меняется: Дружба оформляет его вручную. Изделие, которое клиент возвращает при обмене, оформляется возвратным заказом | `ADR-RET-070`; `ADR-RET-110`, решение 22 |
| 4 | Статус заказа | В новом процессе статус заказа при возврате не меняется; возврат виден по статусам позиций и заявки | `ADR-RET-039` |

## Открытые вопросы

#### 1. Как сохранить обмены через RetailCRM и Дружбу по старой схеме, если при запуске новых возвратов старую реализацию нужно выключить?

**Кому:** System Architect (Леша Осипенко), Backend Developer (Оля Свистунова), Project Manager (Катя Тихомирова)

**Решено:**
- Обмены в MVP идут по ручной схеме через Дружбу (`ADR-RET-070`; `ADR-RET-110`, решение 22).
- При запуске в RetailCRM блокируется ручной перевод заказов в статусы заявки на возврат (`ADR-RET-067`, решение 1).

**Открыто:**
- По оценке разработки, старая и новая реализации не могут работать одновременно. В старом процессе возврат меняет статус заказа, и на эти статусы завязаны триггеры; в новом процессе статус заказа не меняется, триггеры срабатывают на статусы позиций и заявки. Триггеры одного процесса перебивают другой, поэтому старую реализацию придётся выключить при запуске ([разбор стендапа 23.11.2026](<../../meetings/[2026-11-23 09-59] Стэндап, есть часть про возвраты_summary.md>), тема 2).
- Project Manager против: обмены планировали оставить на старой схеме, Дружба должна иметь возможность оформить их по-старому (там же).
- Р-1.1. Какие возвратные статусы заказа и какие триггеры на них нужны ручному обмену через RetailCRM после переключения? Кому: System Architect, Backend Developer.
- Р-1.2. Можно ли оставить эти статусы и триггеры только для обменов и не задеть ими новые возвраты? Кому: System Architect.
- Р-1.3. Если сохранить старую схему для обменов нельзя, как Дружба оформляет обмен в MVP? Кому: Project Manager.

Возвратные статусы заказа и завязанные на них признаки и маппинг Mindbox — [справочник статусов](../../../../knowledge/12storeez-master-web/database/order-status-dictionaries.md), разделы 3 и 5.

**Дальнейшее действие:** после ответов зафиксировать решение новой версией `ADR-RET-067` или `ADR-RET-070` и учесть в задаче на переключатель (`ADR-RET-069`).
