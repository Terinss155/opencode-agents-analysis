## 2. Правила

Одно правило — один способ записи. Проверка — перед записью каждого шага, примечания, ветки и блока бэкенда.

### Р1. Шаг вызова метода

1. Формат: «Вызвать метод `<название по-русски>` (`<HTTP-метод> <путь>`[, TBD]) [по <входные данные смыслом>]».
2. Входные данные — русскими словами, не больше трёх, и только если без них непонятно, что вернёт метод: «по городу возврата», «по службе выбранного способа и городу возврата», «с данными, заполненными на экране «Оформление возврата»».
3. Не пишутся: имена параметров запроса, тела и заголовков; список «Передать: …»; что передаётся «как сейчас».
4. Имя поля ответа пишется, только если по нему клиент выбирает ветку или показывает значение (`can_be_cancelled = true`, `is_return_available = true`); у нового поля — TBD.
5. TBD — у нового метода, нового пути и нового поля. У существующих — нет, даже если параметр впервые используется для возврата. Признак — есть ли он в текущем контракте (`knowledge/<репозиторий>/api/` или код).

### Р2. Где пишутся параметры

1. Только в разделе бэкенда, подраздел «Доработка существующих методов».
2. Только новые или изменённые параметры: имя (TBD, если не утверждено), назначение, требование к значению, если оно есть.
3. Существующие параметры не перечисляются. Исключение — меняются их смысл, обязательность или значение по умолчанию.

### Р3. Ветки ошибок

1. Ветка ошибки пишется, только если известно условие ошибки и у неё своё поведение для пользователя: свой текст, экран или переход.
2. «Другая ошибка», «Ошибка сервера», «Не удалось» без своего поведения не пишутся ни в шагах, ни на диаграммах.
3. Техническая ошибка любого метода — один пункт в «Основных принципах» SRS.

### Р4. Примечание

1. Тест: «Если удалить этот пункт, разработчик или тестировщик сделает иначе?» Нет — пункт не пишется.
2. Не пишется то, что уже сказано в шаге, следует из исполнителя шага или из «Основных принципов».
3. Пишется: правило расчёта, которого нет в шагах; ограничение, которое меняет реализацию; поведение, которое иначе додумают.
4. Пункт — одно-два предложения. «Почему» — только если без него правило выглядит ошибкой.

### Р5. Общая логика сайта и МП

1. Логика общего метода описывается один раз — в SRS МП.
2. В SRS сайта по общему методу: метод, «новый» или «доработка», «логика — SRS МП, US N» и только отличия сайта.
3. Отличие сайта — то, что на сайте работает иначе и подтверждено: свой эндпоинт, свой контейнер интерфейса, свой источник данных.
4. Новое правило общего метода вносится в SRS МП; в SRS сайта текст не копируется.
5. Одно поле, одно значение — одно название в обеих SRS.

### Р6. Шаги на сайте и в МП

1. Одинаковое поведение — одинаковые шаги: тот же номер (если шаги идут попорядку, исключение, если у сайта или МП есть еще шаг отличающийся от другой платформы), тот же текст. Различаются только исполнитель и контейнер (панель / экран, модальное окно / шторка, страница / экран).
2. Свой шаг платформы (например, вызов метода, когда другая платформа берёт данные из уже полученного ответа) добавляется только там; номера после него сдвигаются.
3. Несколько независимых действий на одном экране — один шаг «Обработать действие пользователя» с вариантом в «Опционально» на каждое действие.
4. Действие, которое запускает последовательность, — шаг пользователя и затем шаги системы по порядку.

### Р7. Описание нового параметра или поведения

1. Формат: `имя` (TBD) — что это и для чего [, требование источника].
2. Противопоставление прежнему поведению или прямому потоку не пишется, если оно не нужно для совместимости.

### Р8. Вопросы

1. Все открытые вопросы — только в разделе «Открытые вопросы» SRS МП, по блокам US. В SRS сайта вопросов нет.
2. Перед записью вопроса — проверка по коду. Если код отвечает полностью, вопрос не пишется: ответ становится требованием.
3. Вопрос только о внутренней реализации другой команды не пишется.

### Р9. Раздел бэкенда

1. Подразделы в постоянном порядке: «Новые методы» → «Доработка существующих методов» → «Логика».
2. «Новые методы» — метод и одна строка назначения; почему новый, а не доработка, — одной строкой, если причина есть (выпущенные версии МП).
3. «Доработка существующих методов» — по компонентам: Монолит, Mobile API Gateway, Логистика, `monolith_bfb_ms`.
4. «Логика» — что метод делает: проверки, отбор, расчёт, ответ.
5. Открытых вопросов в разделе нет — они в «Открытых вопросах» SRS МП (Р8).
6. «Ход метода» — таблица `№ | Кто | Действие | Если не получилось`, только если метод обращается к двум и более сервисам или от порядка действий зависит результат.

### Р10. Ссылки в шагах сценария

1. Запрещены ссылки на другие документы: ADR, BRD, User Story как документ, `FR-*`, `RULE-*`, `OQ-*`, транскрибации, разборы встреч, `sources/`, другие SRS, ссылки на файлы.
2. Разрешены ссылки на шаги процесса: «(US 1.1)», «как на шаге 2 US 1.1», «шаги 8–10 повторяются».
3. Разрешены ссылки на таблицы этой же SRS.
4. Сравнение с другим разделом продукта («как на экране магазина при бронировании товара») допускается, если без него поведение придётся описывать заново.

### Р11. Общий расчёт при разных методах

1. Если на сайте и в МП разные методы, но расчёт один (одно правило — один расчёт для всех каналов), расчёт описывается один раз — в SRS МП: таблица значений, пример, при необходимости диаграмма.
2. В SRS сайта у такого метода — доработка, поля ответа сайта и «расчёт — SRS МП, US N».
3. Диаграмма «Логика метода» — только в SRS МП и только если доработка меняет порядок или ветвление проверок (`skill/srs` п. 6.2, п. 5).
4. Формат блока бэкенда одинаковый на обоих каналах — по `skill/srs` п. 6.2: нумерованный список, таблица `Поле | Что означает | Как считается | Где используется`, пример отдельной таблицей.

### Р12. Диаграмма — вместе с шагом

1. После правки шага в диаграммах того же раздела ищутся номер шага и ключевое условие (`is_return_available`, «Индекс»). Диаграмма правится в том же заходе.
2. При разбиении или перестановке шагов порядок узлов на flowchart и стрелок на sequence меняется в том же заходе.
3. Каждый ромб flowchart — ветка в шагах, и наоборот.

### Р13. Удаление фрагмента

1. Перед удалением ищутся ссылки на фрагмент: вопросы, примечания, «Логика бэкенда», диаграммы, вторая SRS, вики-копии, задачи.
2. Удалённое перечисляется в ответе списком «Удалено: где, что».

### Р14. Замена пометок о новизне

1. «(новый метод)» → «(TBD)», «(путь, новый метод)» → «(путь, TBD)», «доработка метода» в шаге — убрать.
2. TBD при правках не удаляется. Снимается только после релиза метода и сверки с контрактом.

### Р15. Правка парой

1. Шаг, ветка, примечание, вопрос, диаграмма меняются в SRS сайта и SRS МП за один заход.
2. Правка только одной платформы — с причиной; причина попадает в «Допустимые различия».
3. Вики-копии переносятся после принятия блока правок и сверяются с основным файлом.

### Р16. Sequence «Взаимодействие компонентов»

1. Диаграмма показывает всю цепочку, включая внутренние сервисы: шлюз, `monolith_bfb_ms`, `mindbox-srv-go`, внешние системы (решение пользователя 23.10.2026).
2. Внутренняя часть цепочки обводится блоком `box` «Бэкенд» — по решению Р-7.
3. Шаги сценария остаются пользовательским уровнем: шаг `Бэкенд` называет результат («Вернуть сумму и баллы к возврату»), а не цепочку вызовов.
