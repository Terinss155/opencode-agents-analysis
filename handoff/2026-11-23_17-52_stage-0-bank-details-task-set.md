# Завершение постановок этапа 0 — банковские реквизиты

## 1. Целевая логика этапа 0

### Определение необходимости реквизитов

Бэкенд определяет, нужны ли банковские реквизиты при оформлении возврата.

По согласованному правилу ECOMDEV-2526 реквизиты нужны, если заказ оплачен курьеру (наличными или картой) либо при оплате использован подарочный сертификат на любую сумму.

Для остальных случаев реквизиты не нужны.

Сайт, iOS и Android получают соответствующий признак от бэкенда и не рассчитывают его самостоятельно.

### Сайт

Клиент вводит банковские реквизиты, проверяет их и подтверждает чекбоксом.

**Основное изменение — реквизиты передаются непосредственно в метод создания возврата.**

AS-IS:

Ввод реквизитов → отдельный запрос сохранения → создание возврата → бэкенд читает ранее сохранённые реквизиты из БД.

TO-BE:

Ввод реквизитов → проверка полей → подтверждение чекбоксом → `POST /orders/refund/save-reason` с позициями, реквизитами и подтверждением → серверная проверка и сохранение данных при создании возврата.

Необходимо:

- добавить чекбокс подтверждения реквизитов;
- обеспечить правильную обязательность и проверку полей;
- передавать реквизиты и `is_bank_details_confirmed` в `POST /orders/refund/save-reason`;
- прекратить отдельное сохранение реквизитов перед созданием возврата;
- правильно обрабатывать ошибки и не показывать успешное оформление при отказе бэкенда.

`POST /user/cabinet/return-item/ajax/check-bank-details` больше не вызывается **в сценарии оформления возврата**.

Проверь, где ещё используется этот метод. Не удаляй и не изменяй его для других сценариев без необходимости. Его дальнейшая судьба не должна блокировать этап 0.

### iOS и Android

Для каждого приложения нужно понятно описать:

1. Откуда приложение получает признак необходимости реквизитов.
2. Когда показывается блок реквизитов.
3. Какие поля вводит клиент и какие ограничения действуют.
4. Когда и как показываются ошибки валидации.
5. Как работает чекбокс подтверждения.
6. Что происходит при изменении уже подтверждённых реквизитов.
7. Какие данные отправляются при создании возврата.
8. Как обрабатываются ошибки бэкенда.

Оба приложения должны реализовывать согласованные бизнес-правила.

При этом проверь фактические различия их текущей реализации. Не копируй AS-IS iOS в Android без проверки.

### Бэкенд

Нужно обеспечить:

- единое правило необходимости реквизитов с учётом подарочного сертификата;
- единую серверную проверку банковских реквизитов;
- получение реквизитов сайта непосредственно в запросе создания возврата;
- сохранение реквизитов из запроса вместо использования старой записи пользователя;
- приём и сохранение `is_bank_details_confirmed`;
- расчёт `is_refund_to_original_payment_method`;
- сохранение обратной совместимости со старыми версиями МП.

`is_bank_details_confirmed` хранится как ключ JSON `cms_orders.user_refund`.

`is_refund_to_original_payment_method` рассчитывается бэкендом по способу оплаты и использованию подарочного сертификата. Поле сохраняется в `cms_orders`, изменение отражается в `cms_orders_history`.

**Признак возврата на исходный способ оплаты рассчитывается при успешном создании возврата независимо от того, нужны ли банковские реквизиты.**

При ошибке создания возврата значения признаков не должны изменяться.

### Обмен с 1С

Не дублируй там логику их расчёта.

Не добавляй прямой синхронный вызов 1С из клиентского запроса создания возврата, если существующий процесс использует выгрузку заказа.

Найди и установи:

1. Как бэкенд определяет платформу и версию приложения: заголовки, параметры запроса, middleware, настройки или другой существующий механизм.
2. Где эта проверка уже используется в проекте.
3. Доступна ли достоверная информация о версии в цепочке МП → Gate / ESB → Monolith для `POST /mobile/orders/{order_id}/return`.
4. Можно ли на существующем механизме реализовать разное требование к `is_bank_details_confirmed` для старых и новых версий iOS и Android.
5. Что происходит, когда версия отсутствует, не распознана или передана некорректно.

Проверь два варианта.

**Вариант А — обязательность с учётом версии приложения**

Если существующий механизм позволяет надёжно определить версию:

- для версий, в которых появился чекбокс, подтверждение обязательно, когда реквизиты нужны;
- `true` — возврат разрешён при выполнении остальных проверок;
- `false` или отсутствие параметра — возврат отклоняется;
- для старых версий, в которых чекбокса ещё нет, отсутствие параметра разрешено, в заказе сохраняется `null`.

Не придумывай пороговые версии: их нужно подтвердить по реальным версиям релизов iOS и Android.

**Вариант Б — необязательный параметр Mobile API**

Если надёжного существующего механизма проверки версий нет:

- `true` — возврат разрешён;
- `false` — возврат отклоняется, когда реквизиты нужны;
- параметр отсутствует — возврат разрешён, в заказе сохраняется `null`.

На новых экранах iOS и Android чекбокс обязателен независимо от технической необязательности API-параметра.

Сравни варианты по сложности, обратной совместимости, возможности реализации в текущих задачах и рискам.

**Не добавляй новый механизм определения версий и не выбирай неподтверждённые пороги самостоятельно.**

Если проверка версий уже есть и подходит, предложи использовать её. Если нет — сохрани согласованную обратную совместимость и явно укажи ограничение.

## 5. Требования к качеству постановок

## 7. Итоговая проверка комплекта

Проверь весь процесс:

1. Бэкенд определяет необходимость реквизитов.
2. Сайт, iOS или Android получает признак и показывает необходимые поля.
3. Клиент вводит данные и подтверждает их.
4. Клиент отправляет запрос на создание возврата.
5. Бэкенд проверяет и сохраняет необходимые данные.
6. Бэкенд рассчитывает признак возврата на исходный способ оплаты.
7. Существующий обмен передаёт данные и оба признака в 1С.

Для каждого этапа должно быть понятно, какая задача отвечает за его реализацию.

Проверь:
- сохранение всех требований из исходников;
- согласованность сайта, iOS, Android и бэкенда;
- соответствие API-контрактов;
- отсутствие дублирования логики;
- сохранение старых сценариев МП;
- правильную последовательность выкатки;
- отсутствие противоречий между описанием, примерами и критериями приёмки.

Особенно внимательно проверь сценарии с подарочным сертификатом, BNPL, отсутствием реквизитов и старыми версиями приложений.
